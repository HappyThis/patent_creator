# 隐藏参考方案

## 技术问题

交互式 agent 会话通常以用户在线等待为前提，而外部系统提交任务时更关注快速确认、可靠重试、状态查询和后续控制。若外部调用方提交后必须等待模型推理完成，容易超过调用方超时窗口；若调用方超时后重试，系统又可能重复写入用户输入或重复执行同一任务。与此同时，agent 运行环境可能休眠、重启或在执行中断开，系统需要判断任务处于“已接收但未执行”“输入已写入但未完成”或“已完成但状态未更新”等不同阶段。

因此，需要一种程序化对话任务提交机制，在不割裂既有 agent 会话执行语义的前提下，实现快速接收、幂等重试、后台执行、状态查询、取消清理和恢复一致性。

## 核心技术构思

方案建立“持久任务记录、接收确认边界、幂等身份、后台领取执行、会话输入应用边界和条件终态更新”组成的可靠提交机制。外部请求到达时，系统先持久化提交意图并返回接收结果；后台执行器之后领取待执行任务，只有在领取成功后才将输入应用到会话并启动 agent 推理。任务记录保存输入是否已经应用、执行状态、终态和错误诊断，使系统在重试、取消和恢复时可以做出一致判断。

## 必要技术特征

1. 持久接收边界：外部请求进入后先创建任务记录，记录待处理输入、调用方标识、创建时间和初始状态，并快速返回已接收或已存在结果。
2. 幂等身份：同一调用方重复提交时，通过稳定幂等键或提交标识定位已有任务，返回已有状态而不是创建新任务。
3. 生命周期状态：任务至少区分待执行、执行中、已完成、已取消、已跳过和失败等状态，并记录关键时间点。
4. 条件领取：后台执行器以事务或条件更新方式领取待执行任务，防止多个执行者同时处理同一任务。
5. 输入应用边界：任务输入写入会话前后必须有持久标记，用于区分“尚未污染会话”和“已经进入会话上下文”。
6. 复用会话执行：真正执行时回到既有 agent 会话推理、流式输出、取消和恢复机制，不另建一套不一致的推理通道。
7. 取消和清理：取消请求根据当前状态决定是否直接终止、请求执行链路中止或只标记后续不再更新；清理任务不应误删已进入会话的历史内容。
8. 条件终态更新：完成、失败、取消、恢复修正等终态写入必须防止迟到结果覆盖已经取消或清理的状态。
9. 恢复判定：系统重启或唤醒后扫描未终结任务，根据输入是否应用、是否存在执行证据和任务年龄，决定重新排队、继续等待或标记失败。

## 关键流程

提交流程中，系统校验输入可持久化，按幂等身份查找任务；已有任务直接返回其标识和状态，新任务则写入待执行状态并唤醒后台执行。执行流程中，后台执行器条件领取任务，标记执行中，将输入应用到会话并记录应用边界，然后复用 agent 会话执行链路。完成流程中，执行结果以条件终态方式写入任务记录。恢复流程中，未应用输入的执行中任务可回到待执行；已应用输入但缺少安全恢复证据的任务应进入失败或人工可诊断状态，避免重复写入。

## 技术效果

该方案使外部系统能够快速获得接收确认，同时在重试、取消、重启和执行中断场景下维持一致性。幂等身份避免重复任务；输入应用边界避免重复写入会话；条件领取和条件终态更新避免并发执行和迟到结果覆盖；恢复判定减少任务丢失、重复执行和状态不明。

## 高质量深度标尺

高分方案应明确任务记录与会话消息之间的边界，说明幂等重试如何返回已有任务，后台执行如何防并发领取，输入何时写入会话，取消和清理如何不破坏会话历史，恢复时如何区分写入前崩溃和写入后崩溃。只说“放入异步队列后台执行”或“返回 task id 后查询状态”的方案深度不足。

## 常见弱方案

- 只使用内存队列，缺少持久任务记录。
- 收到外部请求时立即写入会话，导致重试时重复输入。
- 有任务状态但没有输入应用边界，无法安全恢复。
- 后台执行没有条件领取，可能并发处理同一任务。
- 取消或迟到完成事件可以覆盖已终结状态。

## 等价机制说明

本参考方案不限定字段名称或状态名称。只要被评估方案能以持久边界、幂等身份、输入应用 checkpoint、条件状态更新和恢复判定解决外部提交可靠性问题，即可视为等价深度方案。
