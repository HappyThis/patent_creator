# 评分标准

总分 100 分。本 case 评价“外部触发 agent 对话任务的持久接收与幂等执行”技术方案质量，不评价具体框架细节或验证材料完整度。

## 技术问题与改进目标：15 分

- 13-15 分：准确抓住快速确认、幂等重试、会话输入污染、后台执行和恢复判定之间的技术矛盾。
- 8-12 分：能说明快速返回和后台执行，但对幂等或输入应用边界分析不足。
- 0-7 分：只理解为普通异步队列或日志记录。

## 核心技术构思：20 分

- 17-20 分：提出独立任务实体、持久接收边界、幂等标识、后台领取和输入应用 checkpoint 的组合构思。
- 10-16 分：有任务记录和后台执行，但输入应用边界或恢复构思不完整。
- 0-9 分：只说异步执行或保存请求。

## 技术手段深度与必要特征：25 分

- 21-25 分：覆盖任务字段、幂等查询、accepted/running/terminal 状态、条件领取、输入应用标记、取消清理、条件终态更新和恢复分支。
- 13-20 分：覆盖主要提交和查询流程，但缺少输入应用 checkpoint、终态保护或恢复分支。
- 0-12 分：只有提交接口或普通队列。

## 要素协同与运行机理：15 分

- 13-15 分：清楚说明接收层、任务记录、会话输入、后台执行器、恢复器和控制接口如何协同。
- 8-12 分：流程大体清楚，但恢复或取消与主流程关系不清。
- 0-7 分：模块堆叠，缺少状态机运行机理。

## 技术效果因果闭环：10 分

- 8-10 分：能从幂等、应用边界、条件更新等手段推出可靠确认、避免重复和恢复一致性。
- 4-7 分：有效果但因果链较弱。
- 0-3 分：只说提升效率或可靠性。

## 可实施性与可变形实施方式：10 分

- 8-10 分：状态和字段达到可实施粒度，并说明可按不同存储或调度方式变形。
- 4-7 分：总体可实施，但关键状态或异常处理不够。
- 0-3 分：无法指导实现。

## 交底书表达适配度：5 分

- 4-5 分：能抽象成可保护的任务接收与恢复控制机制。
- 2-3 分：偏工程设计文档，但仍有技术机制。
- 0-1 分：产品说明或接口清单。

## 扣分和上限

- 没有区分任务接收与会话输入应用，总分通常不高于 75 分。
- 没有幂等标识或重复请求处理，总分通常不高于 75 分。
- 没有条件终态更新，迟到结果可能覆盖取消或清理，总分通常不高于 82 分。
- 只用内存队列或同步等待模型完成，总分通常不高于 65 分。
- 不要求列出具体实现路径、验证材料或框架细节名称；缺少这些内容不得单独扣分。
