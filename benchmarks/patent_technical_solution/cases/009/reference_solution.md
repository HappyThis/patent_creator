# 隐藏参考方案

## 技术问题

模型生成代码可以提升工具编排能力，但浏览器页面中的动态客户端工具通常依赖页面状态、组件能力或用户上下文，不适合全部搬到服务端。若直接在主页面执行生成代码，代码可能访问或污染页面对象；若只让模型逐个调用工具，又无法发挥代码编排的灵活性。

因此，需要一种在浏览器侧隔离执行生成代码、并通过受控代理调度主页面动态工具的技术方案。

## 核心技术构思

方案建立“浏览器隔离执行容器、动态工具描述生成、名称规范化映射、双向消息协议、主页面工具代理、安全校验、生命周期管理和资源清理”组合机制。每次执行时，系统创建临时隔离容器运行生成代码；隔离环境只能调用注入的工具代理，不能直接访问主页面。工具代理将调用封装为带调用标识、工具提供者、工具名和参数的消息发送给主页面；主页面校验后执行真实客户端工具，并将结果或错误按调用标识返回。

## 必要技术特征

1. 动态工具描述：根据当前页面注册工具生成可供模型使用的工具描述、输入输出结构和来源标识。
2. 名称规范化：将非法标识符、重复名或保留名处理为可调用名称，并维护真实工具映射。
3. 隔离容器：每次执行创建受限 iframe、Worker 或等价沙箱，限制主页面 DOM 和全局对象访问。
4. 运行时注入：在隔离环境中注入工具代理、执行入口、日志收集和错误捕获能力。
5. 双向协议：至少覆盖 ready、execute、tool-call、tool-result、execution-result、error、timeout 和 cleanup 等消息或状态。
6. 调用关联：每次工具调用携带 call id，支持并发调用结果正确回到对应 promise。
7. 主页面代理：真实工具只在主页面注册表执行，隔离环境不能直接执行工具。
8. 安全校验：主页面校验消息来源、执行上下文、工具来源、工具名和参数形态，非法调用返回错误。
9. 超时与清理：执行完成、失败或超时时移除容器、定时器、消息监听器和 pending 调用。
10. 结果回传：最终结果、工具错误、生成代码异常和日志以结构化形式返回外层 agent chat。

## 运行流程

执行前，系统读取当前客户端工具集合，生成代码编排工具描述，并建立规范化名称到真实工具的映射。模型输出生成代码后，浏览器执行器创建隔离容器并等待 ready。主页面发送 execute 消息，隔离环境运行代码；代码调用工具代理时，隔离环境发送 tool-call 消息。主页面校验后调用真实工具，并以 tool-result 返回。代码执行完成后，隔离环境发送 execution-result，主页面清理执行资源并将最终结果返回上层。若 ready 超时、工具异常、生成代码异常或容器销毁，系统返回结构化错误并完成清理。

## 技术效果

该方案使模型生成代码能够在浏览器侧编排动态客户端工具，同时避免代码直接污染主页面或访问未授权对象。隔离容器提供执行边界；主页面代理保留浏览器私有能力；消息协议和 call id 保证工具调用可控；超时和 cleanup 防止资源泄漏；名称规范化和来源校验减少工具冲突和越权调用。

## 高质量深度标尺

高分方案应说明隔离容器如何限制主页面访问，动态工具描述如何生成，工具名如何规范化，消息协议有哪些状态，主页面如何校验并执行真实工具，并发调用如何关联，异常、超时、日志和 cleanup 如何处理。只说“用 iframe 加 postMessage 调工具”的方案深度不足。

## 常见弱方案

- 直接在主页面执行模型生成代码。
- 只有工具描述，没有隔离执行和主页面代理协议。
- 隔离代码可以直接访问 DOM 或主页面对象。
- 没有 call id，多个工具调用结果可能串线。
- 没有超时、错误传播和资源清理。

## 等价机制说明

本参考方案不限定必须使用 iframe。Worker、isolated realm 或其他浏览器侧隔离环境也可接受。关键是隔离执行、动态工具描述、名称映射、主页面代理、结构化消息协议、安全校验、超时和清理共同成立。
