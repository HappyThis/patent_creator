## 技术方案

### 总体构思与状态划分

本方案在浏览器端流式接收 agent 响应的体系中，将“客户端本地清理”与“服务端 agent turn 取消”拆分为两个相互独立但可协同的控制面。客户端连接、React 组件、ReadableStream reader 以及页面生命周期只负责本地资源释放和观察关系维护；服务端是否终止当前 agent turn，则仅由显式取消意图、应用配置策略或服务端自身的安全策略决定。由此，刷新页面、组件卸载、路由切换、reader 被动取消或短时网络抖动不再天然等价于取消服务端任务，避免长时间工具调用或模型生成因观察端变化而被误中止。

服务端为每个 agent turn 建立以请求标识为键的运行记录，运行记录至少包括请求标识、流标识、当前状态、关联的取消控制器、最近一次请求上下文、流式分片缓存以及观察连接集合。运行状态可划分为运行中、可恢复等待、显式取消中、已完成、错误结束和孤儿流收敛等状态。浏览器连接断开时，服务端只从观察连接集合中移除该连接，并将流维持在运行中或可恢复等待状态；只有收到具有取消语义的控制帧或策略判定需要取消时，才触发对应请求标识的取消控制器。

### 客户端侧断开分类与本地清理

客户端在发起或恢复流式对话时，为本地 reader、消息监听器、关闭监听器和组件生命周期建立本地清理控制器。本地清理控制器的职责是关闭当前 ReadableStream、移除事件监听、释放活跃请求标识的本地占用、停止向当前组件继续投递分片，并向上层返回本地结束或本地中断状态。该控制器默认不向服务端发送取消帧，因此其触发不改变服务端 agent turn 的运行状态。

客户端对中断来源进行分类处理：由用户点击“停止”、应用业务逻辑调用主动取消、父级任务取消或明确的 abortSignal 触发的事件，标记为显式取消；由页面刷新、组件卸载、标签页关闭、路由切换、浏览器连接关闭、reader.cancel() 被框架清理触发或短暂网络断开导致的事件，标记为观察端脱离；由超时、握手失败或服务端返回错误导致的事件，标记为传输异常。只有显式取消会进入服务端取消通道，观察端脱离仅执行本地清理并保留后续恢复能力，传输异常则根据可恢复性进入重连或错误呈现。

| 中断来源 | 本地处理 | 服务端处理 |
| --- | --- | --- |
| 用户停止或应用主动取消 | 关闭当前 reader，并发送取消控制帧 | 按请求标识触发取消控制器，终止对应 turn |
| 刷新、卸载、切页或短时断网 | 移除监听器、释放本地观察状态 | 保留运行记录和可恢复流，等待恢复探测 |
| 恢复握手失败或服务端不可达 | 向界面呈现可重试或离线状态 | 不因单次失败立即取消，按策略计时处理 |
| 断开即取消策略命中 | 本地清理并携带原因码 | 在策略判定后触发取消或宽限期取消 |

### 显式取消通道与服务端执行控制

显式取消通道采用与普通流式响应分离的控制消息表达取消意图。客户端在用户点击停止或应用主动取消时，将当前 agent turn 的请求标识与取消类型封装为取消控制帧发送至服务端；对于已经进入工具调用续跑、审批后自动继续或恢复后续传的 turn，取消控制帧仍使用同一逻辑请求标识或服务端返回的续跑请求标识，使取消动作能够命中正在运行的服务端控制器，而不是仅关闭当前浏览器 reader。

服务端收到取消控制帧后，先依据请求标识查找运行记录和取消控制器；若命中运行中的 turn，则触发取消控制器并向 onChatMessage、模型流读取、工具执行、自动续跑流程和流式分片循环传播同一个取消信号。服务端随后把该 turn 标记为显式取消中，停止继续读取或广播新的响应分片，刷新已缓存分片，向仍在线的观察连接广播终止帧或错误帧，并在完成清理后移除取消控制器。若取消帧晚于 turn 完成到达，则服务端将其作为幂等控制消息处理，不回滚已经持久化的消息。

### 恢复、续传与多观察端协同

为支持刷新或短时断网后的恢复，服务端在 agent turn 开始输出时启动可恢复流，按流标识将响应分片写入持久化缓存，并维护当前活跃请求标识。新连接建立后，客户端先注册消息处理器，再发送恢复探测；服务端若发现仍有活跃流，则返回恢复通知，待客户端确认后按分片序号重放已缓存分片，并在重放结束后继续转发实时分片。若不存在活跃流但存在已完成的同请求流，则服务端可重放完成分片并发送结束标记，使刷新后的客户端能够收敛到已完成状态。

多标签页或多组件同时观察同一 agent turn 时，服务端将各连接视为观察端而非任务所有者。实时分片向除特定排除连接外的观察端广播；正在执行恢复重放的连接临时加入恢复排除集合，避免其同时接收重放分片和实时广播而产生重复。客户端侧通过本地活跃请求标识和重放标记区分“本标签页直接发起的流”“其他标签页广播的流”和“恢复重放的流”，并以累加器方式合并分片，从而在多观察端场景下保持消息状态一致。

对于客户端工具调用、人工审批或工具结果回传后触发的继续生成，服务端将其作为原对话 turn 的续跑阶段处理，并在续跑开始前向客户端发送可恢复流通知。客户端收到工具结果提交或审批响应后，可先返回一个等待续跑的本地流，使界面进入提交中状态；当服务端宣布续跑请求标识后，再绑定该请求标识接收后续分片。若用户在续跑握手前或续跑中明确停止，客户端通过显式取消通道终止续跑；若仅发生页面切换或连接关闭，则续跑继续在服务端执行并可由后续连接恢复观察。

### 可配置策略与兼容边界

本方案提供客户端断开策略配置，用于适配不同应用对资源占用和任务连续性的偏好。配置项可以包括：观察端脱离是否取消服务端任务、断开后允许服务端继续运行的保活时长、是否允许恢复已完成分片、是否允许工具续跑在无观察端时继续执行、主动取消是否需要确认、以及取消控制帧发送失败时是否在重连后补发。默认策略可设为“可恢复优先”，即普通断开只清理本地资源，不取消服务端 turn；对成本敏感或实时性要求高的应用，可配置为“断开即取消”或“宽限期后取消”。

策略判定可以在客户端和服务端共同完成：客户端负责给本地中断事件附加原因码，服务端负责以原因码、请求状态、观察连接数量、恢复能力、保活计时器和应用策略为输入作最终决策。这样即使浏览器在发送原因码前异常断开，服务端也不会把未知断开默认解释为用户停止；而当客户端成功发送主动取消原因码时，服务端能够立即触发取消控制器。对于没有启用可恢复流或未提供请求标识的旧式接入，可退化为原有 reader 取消即结束本地流的行为，以保持兼容。
