## 技术方案

### 总体构思与控制边界

本方案在浏览器侧流式会话与服务端 agent turn 之间设置“连接生命周期”和“任务取消生命周期”两条相互独立的控制链路。浏览器刷新、组件卸载、页面切换、ReadableStream 的 reader 本地 cancel、WebSocket 短暂关闭等事件，默认仅触发客户端本地资源清理和观察流摘除；只有用户点击停止、业务代码调用主动取消接口，或应用策略明确声明断开即取消时，才生成面向服务端的取消意图并发送到对应的 agent turn。由此避免把传输层瞬断误判为任务终止，同时仍保留主动停止长时间推理、工具执行或子 agent 调用的能力。

在实现上，每个 agent turn 以请求标识作为控制对象，服务端为该请求维护可恢复的流状态、已持久化消息、已发送分片、工具调用状态和取消控制器；客户端为同一请求维护本地读取器、事件监听器、去重集合和恢复握手状态。两端通过请求标识相关联，但本地读取器关闭并不等同于服务端取消控制器触发。系统可以提供取消策略参数，例如“仅显式取消”“断开后延迟取消”“最后观察端离开后取消”或“任何断开即取消”，并将其作为应用级配置、会话级配置或单次请求配置，从而兼容不同产品对资源占用和任务连续性的偏好。

### 客户端断开原因识别与本地清理

客户端对关闭事件进行语义分类，而不是把所有关闭都映射为服务端取消。第一类为被动脱离事件，包括页面刷新、路由切换、组件卸载、WebSocket close、网络超时、reader.cancel 用于释放本地 ReadableStream、以及恢复握手等待超时；该类事件只关闭本地 stream controller、移除 message/close 监听器、清理定时器、释放本地 AbortController，并保留请求标识在去重或待恢复集合中的必要状态。第二类为显式取消事件，包括停止按钮、应用主动调用 cancel/stop、清空会话时选择同时终止当前 turn、或配置策略判定某类断开应终止服务端任务；该类事件才构造包含请求标识和原因的取消帧发送给服务端。

为保证该分类在浏览器 API 差异下仍可实施，客户端可在发送请求或建立恢复流时创建带原因的本地控制对象，将“local-cleanup”“resume-timeout”“network-close”“user-stop”“application-cancel”等原因写入临时状态。ReadableStream 的 cancel 回调默认调用本地清理分支，不直接发送取消帧；停止按钮或应用主动取消接口调用服务端取消分支，并在本地以 AbortError 结束当前读取器，使界面立即退出流式等待。若浏览器关闭时无法可靠发送 WebSocket 帧，则可采用 keepalive fetch、下一次连接补发取消意图，或在服务端通过策略延迟窗口处理最后观察端离开后的取消。

### 服务端可恢复运行与显式取消传递

服务端在收到新的 agent turn 后，将请求标识注册到取消控制注册表，并把该注册表产生的 AbortSignal 传入模型推理、消息续写、工具调用编排或子 agent 调用流程。取消注册表只响应结构化取消输入，例如聊天协议中的 request-cancel 帧、服务端业务方法的主动 cancel 调用、父级工具执行信号转接，或配置策略产生的延迟取消判定；普通 WebSocket 关闭、观察端移除或恢复流本地 cancel 不直接触发该注册表。这样，服务端长时间运行的 turn 在没有显式取消意图时继续推进，并持续把输出分片、消息状态和工具状态写入持久层。

当服务端确认收到显式取消意图时，首先根据请求标识定位活动 turn；若存在对应取消控制器，则以取消原因触发 AbortSignal，使模型流读取、工具执行等待、子 agent run 轮询和后续续写逻辑在统一信号下收敛。随后服务端将已产生但未最终合并的分片按可恢复流规则落盘，标记该 turn 的结束状态为 aborted，并广播终止帧或消息同步帧给仍连接的观察端。若请求标识已经完成或不存在，取消操作作为幂等操作处理，不回滚已经持久化的消息，也不影响其他标签页或其他会话的请求。

### 恢复、多观察端与工具调用兼容

对于刷新、短暂断网或多标签页切换后的恢复，客户端重新建立连接后先发送流恢复请求，服务端判断是否存在仍活动或可回放的请求标识。若存在，服务端进入恢复握手状态，暂时把该连接加入待恢复集合，避免正常广播与回放分片重复到达；在收到恢复确认后，按已持久化的分片序号回放缺失内容，并继续把后续实时分片发送给该连接。若不存在可恢复流，则返回无可恢复状态，客户端仅同步持久化消息并进入可输入状态。该机制使浏览器本地流关闭不破坏服务端正在运行的 turn，新标签页也可以作为只读观察端接入同一请求的后续输出。

对于客户端工具调用和服务端自动续写，系统将“工具结果提交后的 continuation 流”和“页面重连后的 resume 流”统一纳入同一恢复/观察模型，但取消语义仍保持独立。客户端提交工具结果后可以创建等待续写的本地流；如果该本地流因组件卸载或 reader.cancel 被关闭，服务端仍可根据已提交工具结果继续执行后续 agent turn。只有工具面板的停止操作、父级 agent 工具执行信号、或应用主动取消接口，才向对应请求标识发送取消意图并联动取消子 agent run。通过该处理，长时间工具调用、子 agent 执行和主对话续写不会因界面暂时离开而丢失，同时用户明确停止时又能沿主请求、工具调用和子请求的链路向下传播。

在可选实施方式中，服务端还可以维护观察端计数、最后断开时间、取消策略和请求状态机。若策略为“仅显式取消”，观察端计数降为零也不取消；若策略为“最后观察端离开后延迟取消”，服务端在宽限时间内允许任一标签页或刷新后的页面恢复连接，超时且仍无观察端时再触发取消；若策略为“断开即取消”，则在连接关闭事件到达时立即触发对应请求的取消注册表。无论选择哪一策略，取消都通过统一的请求标识、取消原因和幂等状态转移执行，从而在流式响应、恢复回放、多标签页广播和工具调用继续执行之间保持一致的控制边界。
