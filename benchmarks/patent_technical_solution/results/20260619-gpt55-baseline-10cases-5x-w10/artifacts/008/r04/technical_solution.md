## 技术方案

### 总体构思与对象关系

本方案在已有基于服务端持久对象的 chat agent、子 agent 路由、流式输出和恢复机制之上，增加一种保留式流式子 agent 工具编排机制。用户仍只连接并感知一个主 agent 会话；主 agent 在处理一次用户请求时，可以把研究、规划、比较、总结等子任务分派给一个或多个专门的子 agent，并将各子 agent 的生命周期事件、流式输出片段和最终结果封装后带回同一主会话视图。

子 agent 不作为主 agent 内存中的临时函数执行，而是作为主 agent 下的真实子持久对象创建或取得。每个子 agent 具有独立 SQLite 存储、独立消息历史、独立模型配置、独立工具集合和独立可恢复流；主 agent 只保存用于编排、呈现和权限判断的轻量索引。这样，子任务可以长时间运行、并行运行或在完成后被单独查看，同时避免把子任务的完整对话、工具调用和中间推理混入主 agent 的会话状态。

### 保留式子运行注册与状态映射

主 agent 在每次分派子 agent 前生成或接收一个稳定的运行标识 runId，并先在主 agent 存储中写入子运行注册记录。该记录至少包含 runId、父工具调用标识、子 agent 类型、输入摘要、运行状态、展示顺序、摘要、错误信息、开始时间和完成时间。该注册记录回答“该子运行由哪个主会话工作触发、应呈现在主会话的哪个工具调用位置、刷新后应如何重放”的问题；子 agent 自身的消息和流式片段仍由子 agent 存储保存。

子 agent 侧保存 runId 与内部聊天请求标识、流标识之间的映射。runId 面向编排、重放、取消、清理和审计；内部请求标识用于 chat agent 的单次推理或中止控制；流标识用于读取已持久化的流式片段。启动子运行时以 runId 作为幂等键：若同一 runId 已存在运行或终态记录，则返回已有检查结果而不重复启动模型调用，由此处理重复请求、重试路径和多标签页并发观察造成的重复触发。

### 流式事件转发与同会话呈现

在执行路径上，主 agent 可通过命令式 runAgentTool 接口或模型可选择的 agentTool 工具包装器启动子 agent。命令式接口适用于确定性工作流、后台报告和并行扇出；工具包装器适用于父模型自主决定何时调用专门子 agent。无论入口为何，框架统一执行以下步骤：写入主侧注册记录，取得以 runId 命名的子 agent，驱动子 agent 进行一次程序化 chat turn，观察子 agent 的可恢复流，将子 agent 的流式片段转发为主会话上的 agent-tool-event 帧，并在子 agent 终止后生成主模型可消费的摘要或结构化结果。

agent-tool-event 帧包括 started、chunk、finished、error、aborted 和 interrupted 等事件类型。started 由主 agent 在子运行可展示前合成，携带 runId、子 agent 类型、输入摘要和展示顺序；chunk 携带子 agent 原生 chat 流中的 UIMessageChunk 编码体，主 agent 不重新定义文本、推理、工具调用等细粒度语义；finished、error、aborted 和 interrupted 表示不同终态。客户端在主 agent 的同一连接上接收这些帧，并使用 runId、父工具调用标识和序号将其归并到对应工具调用下的子面板。

对于一个父工具调用下派生多个子 agent 的场景，主 agent 为每个子运行写入独立 runId 和展示顺序，允许各子 agent 并行执行且独立产出流式片段。客户端以“父工具调用标识、runId、序号”的组合键进行去重和归属判断，而不是仅按父工具调用标识归并，从而避免并行分支均从序号零开始时发生覆盖。主 agent 可在所有分支完成后汇总成功结果和失败结果，也可把部分失败作为结构化失败返回给父模型，使父模型能够基于已完成分支继续生成答复。

子 agent 的流式片段在发送给主会话前已经由子 agent 自身的可恢复流持久化。主 agent 的转发是观察行为，不是唯一存储来源；因此，页面刷新或网络短暂断开不会使已产生的子 agent 过程丢失。用户若需要深入查看某一子运行，可以通过主 agent 的子 agent 路由连接到对应 runId 的子 agent，将其作为普通 chat agent 查看完整对话和后续追问。

### 恢复、去重与访问控制

恢复时，主 agent 先读取自身的子运行注册表，再按每条记录中的子 agent 类型和 runId 找到对应子 agent，并从子 agent 存储中读取与该 runId 绑定的流式片段。主 agent 向重新连接的客户端合成 replay 标记的 started 事件，依序转发已存储的 chunk 事件，再根据主侧注册状态合成 finished、error、aborted 或 interrupted 终态事件。这样，主会话视图能够在刷新后重建已经发生的子 agent 过程，而不要求子 agent 过程被复制到主 agent 的聊天流中。

对于主 agent 崩溃或被回收时仍处于 starting 或 running 的子运行，恢复逻辑区分执行状态和观察状态：若子 agent 不存在或没有对应 runId 的子侧映射，则将该子运行标记为 interrupted；若子 agent 已完成、出错或被中止，则读取其存储片段并把主侧记录修正为相应终态；若子 agent 仍在运行但当前运行环境尚不支持从中途重新挂接实时尾流，则重放已存储片段并标记为 interrupted。该处理避免把不确定状态误报为成功，也避免在恢复时擅自重新执行可能产生费用或副作用的子任务。

访问控制通过主 agent 的子 agent 路由前置钩子实施。外部请求访问某个子 agent 路径时，主 agent 先检查请求的子 agent 类型和 runId 是否存在于本主 agent 的子运行注册表，并结合主 agent 原有身份、租户或会话权限判断是否放行；不存在匹配记录时直接拒绝，不唤醒也不创建新的子 agent。runId 仅作为索引键而非访问令牌，用户必须经由其有权访问的主 agent 路径进入子运行，从而防止猜测 runId 产生空白子 agent 或越权查看其他类别子 agent。

对于无直接父工具调用的后台子运行，主 agent 仍写入同一注册表，但 parentToolCallId 可以为空或使用后台任务分组标识。客户端将此类子运行呈现在独立的后台任务区域或历史列表，而不是挂载到某个 chat 工具调用下。由于后台子运行仍采用相同 runId、状态、序号、重放和访问控制机制，因此其执行过程可以在用户稍后打开页面时被恢复查看。

### 取消、并发与清理策略

取消机制沿主 agent 到子 agent 的方向显式传播。主会话停止、父工具调用中止或应用主动取消某个 runId 时，主 agent 调用子 agent 的取消入口并传递取消原因；子 agent 将该取消转换为本次 chat turn 的 AbortSignal，在线程进入模型推理前或推理过程中均可被检测，从而尽早终止模型调用和工具循环。取消完成后，主侧注册记录和子侧映射进入 aborted 终态，并向客户端发送 aborted 事件。普通浏览器断开或观察流关闭只表示观察者脱离，不自动取消子运行。

并发控制包含两个层次：在同一 runId 上，子 agent 适配器持有排他执行声明，重复启动请求只返回已有运行检查结果，不创建第二个 chat turn；在同一主 agent 上，可配置最大同时运行子 agent 数量或按类型设定配额，超过阈值时立即产生明确的 error 事件而非排队到不可预期状态。该并发控制既防止同一子 agent 的转发器、请求标识和流标识相互污染，也限制父模型一次请求中过度扇出导致的资源消耗。

子运行默认在完成后保留注册记录和子 agent 存储，以支持刷新重放、后续钻取查看和问题诊断。系统提供显式清理入口，可按状态、时间或会话清除子运行；清理仍在运行的子运行时，先执行取消，再删除主侧注册记录和对应子 agent 持久对象，避免留下无人可见但仍消耗资源的孤儿任务。若业务需要只保留摘要或脱敏输入，可将完整输入持久化设为可选，默认仅保存输入摘要和展示元数据。

通过上述机制，主 agent 可以在一次用户请求中可靠地组织多个真实 chat 子 agent，而不是把子任务降级为不可恢复的函数调用。子 agent 的独立上下文保证长任务和并行任务的隔离性；主侧注册表和事件协议保证同会话呈现、刷新重放和后台查看；幂等 runId、排他执行、显式取消、权限门控和保留清理策略共同保证重复请求、并发执行、访问控制和生命周期管理的可实施边界。
