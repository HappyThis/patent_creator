## 技术方案

### 总体构思与系统边界

本方案在既有服务端持久化 chat agent、子 agent 路由、流式输出和恢复机制之上，增加一层“保留式流式子 agent 工具编排”机制。用户仍只连接主 agent 的会话；主 agent 在一次请求处理中，可以将研究、规划、比较、总结等专门任务分派给一个或多个 chat 能力子 agent。每个子 agent 不是主 agent 内部的临时函数调用，而是通过既有子 agent/facet 能力创建或取得的独立持久对象，具有独立 SQLite、消息历史、工具调用、模型配置和可恢复流。主 agent 只负责创建可追踪的子运行、观察其输出、把生命周期事件和聊天块转发回主会话，并在子运行结束后将摘要或结构化结果作为工具结果交还给主 agent 的推理流程。

主 agent 与子 agent 之间设置两种分派入口：一种是由应用代码显式调用的命令式入口，用于确定性工作流、后台任务、阶段化报告和并行扇出/汇聚；另一种是由主 agent 的模型工具定义封装的入口，用于让主 agent 在对话中自行选择调用研究员、规划员等子 agent。两种入口共用同一运行登记、子运行映射、事件转发、取消和清理机制，因此不同触发来源产生的子任务都能以统一方式呈现在同一个主会话视图中。对于无直接父工具调用标识的后台子运行，系统将其登记为未绑定运行并在主会话的独立区域或可查询列表中展示，从而避免后台执行结果脱离会话上下文。

### 保留式子运行登记与身份映射

主 agent 的持久存储中维护框架管理的子 agent 工具运行登记表。该登记表以稳定的运行标识作为主键，记录子 agent 类型、父工具调用标识、展示顺序、输入预览、显示元数据、运行状态、摘要、错误信息、开始时间和完成时间。登记表与已有子 agent 存在性登记分离：已有登记用于判断某个子持久对象是否存在，本方案的运行登记用于判断该子运行由哪次主会话工作触发、应在主界面何处渲染、重连时应如何合成回放事件以及是否允许进入子 agent 查看。为降低敏感数据暴露风险，默认只保存输入预览或脱敏元数据，不把完整提示词、凭据或文件内容复制到主 agent 的编排表中。

子 agent 的持久存储中维护子侧运行映射表，将同一个运行标识映射到子 agent 内部的聊天请求标识和可恢复流标识。该映射使编排标识、聊天请求标识和流存储标识解耦：运行标识用于主子 agent 之间的编排、回放、取消、清理和审计；请求标识用于子 agent 当前聊天轮次的中止和执行控制；流标识用于读取已经持久化的输出块。即使主 agent 在启动子 agent 后尚未收到内部请求标识便发生重启，也可以通过运行标识向子 agent 查询映射并恢复已发生的输出。

- 启动前，主 agent 先插入状态为 starting 的运行登记，再创建或取得以运行标识命名的子 agent，避免子 agent 已开始而主会话没有可回放锚点。
- 子 agent 启动聊天轮次后写入运行标识、请求标识和流标识之间的映射，并把状态更新为 running；同一运行标识再次启动时返回已有状态，不再创建重复聊天轮次。
- 子 agent 正常完成、失败或被显式取消时，主 agent 将运行登记更新为 completed、error 或 aborted；如果主 agent 在恢复时无法安全继续观察仍未终止的运行，则记录为 interrupted。
- 终态具有权威性，迟到的取消、重复请求或恢复流程不得把已经 completed 或 error 的运行改写为 aborted 或 interrupted。

### 流式事件转发与同会话重建

主 agent 将子 agent 的可恢复聊天流作为事实来源进行观察，而不是在主 agent 内再建立一套子任务流存储。子 agent 输出的聊天块以既有 UIMessageChunk 形式保存在子 agent 自己的可恢复流中；主 agent 观察这些块后，封装为 agent-tool-event 类型事件发送给连接到主会话的浏览器。事件至少包括 started、chunk、finished、error、aborted 和 interrupted 等类型，并携带运行标识、父工具调用标识、同一运行内的单调序号、子 agent 类型、展示顺序、摘要或错误信息。客户端使用父工具调用标识、运行标识和序号作为去重键，因此多个子 agent 并行挂在同一个父工具调用下时，也能保持各自输出顺序而不会相互覆盖。

在主会话界面中，普通主 agent 回复和子 agent 事件共用同一连接但保持协议分层。父工具调用对应的消息部件下可聚合一个或多个子运行；命令式或后台触发且没有父工具调用标识的子运行进入未绑定运行集合。客户端侧设置无样式的状态重建器，负责过滤 agent-tool-event 帧、应用聊天块到子 agent 消息部件、按展示顺序排列同级子 agent、合并回放和实时事件、区分失败/取消/中断等终态，并向应用层提供按工具调用查询子运行以及查看未绑定子运行的接口。这样用户刷新页面或短暂断网后，仍能在同一主会话中看到子 agent 已经发生的研究过程、工具调用片段和结果状态，而不需要直接连接所有子 agent 才能恢复上下文。

当用户需要进一步查看某个子 agent 的完整上下文时，系统通过既有嵌套子 agent 路由打开该子 agent，但访问请求必须先经过主 agent 的登记门禁。门禁检查请求中的子 agent 类型和运行标识是否存在于主 agent 的运行登记表，并结合主 agent 已有身份、租户和权限策略判断是否允许访问。运行标识仅作为关联键，不作为可被直接持有的访问凭证；未登记的运行标识不能通过 URL 猜测而创建新的子 agent。通过该方式，子 agent 既能保持可钻取、可长期查看的独立上下文，又不会绕过主会话的身份边界和访问控制。

### 恢复、幂等、并发与后台运行控制

恢复时，主 agent 首先扫描本地运行登记表中 starting 或 running 的非终态记录，再按运行标识查询对应子 agent 的子侧映射和已存聊天块。如果子侧没有对应运行，说明子 agent 尚未可靠启动或已被删除，主 agent 将该记录标记为 interrupted；如果子侧已经 completed、error 或 aborted，主 agent 回放子 agent 持久化的聊天块并同步终态；如果子侧仍在 running，而当前实现不能从中途重新接上实时尾流，则主 agent 回放已经持久化的块并以 interrupted 终态明示观察中断。该恢复策略把“执行是否完成”和“主会话是否仍在实时观察”分离，避免因页面刷新、网络断开或主 agent 重启而错误取消仍在子 agent 内执行的任务，同时也避免在无法保证连续性的情况下伪造成功结果。

为处理重复请求和并发执行，运行入口以运行标识为幂等键。调用方未提供运行标识时由框架生成；调用方在重试、告警恢复或后台任务中提供同一运行标识时，系统先检查主侧运行登记和子侧运行映射。若已有终态结果，则直接返回已有摘要、结构化输出或失败原因；若已有非终态运行，则不启动第二个子 agent 聊天轮次，而是复用已有执行并按当前观察能力进行实时观察或回放。对于同一子 agent 运行标识，框架在子侧持有独占执行声明，钻取查看可以读取过程，但用户直接向正在由框架驱动的子 agent 发送新消息应被延后或明确拒绝，以防多个聊天轮次交错写入同一流。

取消机制沿主 agent 的请求或工具调用中止信号向子 agent 传播：主 agent 收到显式取消后，按运行标识调用子侧取消接口；子 agent 将该取消转换为当前聊天轮次的 AbortSignal，传入模型推理和消息保存流程，并在可恢复流中记录中止结果。观察流断开本身不等同于取消执行，浏览器断线或主 agent 观察者消失只会停止转发，不会自动终止子 agent；只有显式取消、清理正在运行的保留结果或应用策略触发的取消才改变执行状态。该区分使长任务和并行任务能够在临时网络故障后继续执行，同时仍能由用户或系统明确停止。

系统默认保留已完成的子运行登记和子 agent 持久对象，以支持刷新回放、事后钻取、失败排查和审计。清理通过显式接口完成，可按时间、状态或应用生命周期选择待清理运行；对于仍处于 starting 或 running 的运行，清理流程先发起取消并等待或记录取消终态，再删除主侧登记和对应子 agent/facet，避免留下无观察者且无法回传结果的孤儿任务。主 agent 还可配置并发上限和生命周期钩子：并发上限在超过允许同时运行的子 agent 数量时快速产生可见错误事件，生命周期钩子以运行标识为关联键记录审计、计量或成本信息。由此，方案在支持复杂协作的同时，对重复调用、并行消耗、访问边界、取消语义和保留结果治理形成闭环控制。
