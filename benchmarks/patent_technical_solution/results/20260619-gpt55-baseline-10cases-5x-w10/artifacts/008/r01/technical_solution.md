## 技术方案

### 总体构思与组件分工

本方案在既有持久化 chat agent、子 agent 路由、流式输出与恢复能力之上，增加“保留式流式子 agent 工具编排”层。用户侧仍只连接主 agent；主 agent 在一次会话请求中根据模型工具调用或确定性业务流程，将研究、规划、比较、总结等子任务分派给一个或多个专门子 agent。每个子 agent 不是临时内存任务，而是通过既有子 agent/facet 机制创建的独立持久对象，具有独立 SQLite、消息历史、工具集、模型上下文、可恢复流和取消入口；主 agent 只保存编排登记、事件转发关系和访问策略。

编排层提供两类入口：一类是主 agent 代码显式调用的子 agent 运行入口，适用于长报告、后台任务、并行 fan-out/fan-in 或由 HTTP、定时任务、可调用方法触发的流程；另一类是面向模型工具系统的子 agent 工具包装入口，主 agent 的大模型可以像选择普通工具一样选择某个专门子 agent。两类入口共用同一运行创建、状态登记、事件协议和恢复机制，区别仅在于是否绑定主会话中的父工具调用标识。这样既允许主 agent 自主调度多个子 agent，也允许没有直接父工具调用的后台子运行被保留、展示和后续查看。

主 agent 与子 agent 之间采用“执行归子、观察归主”的分离原则。子 agent 负责实际对话回合、工具调用、流式 chunk 存储、最终摘要或结构化输出；主 agent 负责在当前主会话视图中转发子 agent 的开始、增量输出、完成、失败、取消或中断事件，并在刷新页面或网络断开后根据登记表重新合成这些事件。由于子 agent 的执行状态不依赖浏览器连接是否存在，断开观察通道不会自动终止子任务，只有明确的取消信号才会终止执行。

### 保留式运行登记与子运行映射

主 agent 在启动子 agent 前先生成或接收一个稳定运行标识 $runId$，并在自身存储中写入子运行登记记录。该记录至少包含 $runId$、父工具调用标识、子 agent 类型、输入预览、输入是否脱敏、显示顺序、显示元数据、状态、摘要、错误信息、开始时间和完成时间。登记表与既有子 agent 注册表分离：子 agent 注册表用于确认某个持久对象是否存在，子运行登记表用于说明该对象由哪一次主会话工作触发、应渲染到哪个父工具调用下、恢复时应按什么顺序回放以及是否允许访问。

登记记录写入成功后，主 agent 以 $runId$ 作为默认子 agent 名称创建或取得对应持久子对象，并将输入和取消信号传入子 agent 适配器。子 agent 适配器在自身存储中保存 $runId$ 到内部请求标识和流标识的映射，使编排标识、chat 回合标识、可恢复流标识相互独立。这样即使主 agent 在子 agent 已启动但尚未取得内部请求标识时被驱逐，恢复流程也能通过 $runId$ 向子 agent 查询既有映射，而不需要重新发起同一子任务。

子运行状态采用单一权威状态机：$starting$ 表示主 agent 已登记但子 agent 尚未确认运行，$running$ 表示子 agent 已开始 chat 回合，$completed$ 表示正常完成，$error$ 表示执行或结果合成失败，$aborted$ 表示收到明确取消信号，$interrupted$ 表示主 agent 在恢复时无法安全继续观察或确认非终态运行。终态记录一经写入即作为权威结果，后到达的取消或恢复检查不得将已完成、已失败或已取消的记录改写为其他终态。启动、取消和结果检查均按 $runId$ 幂等执行：相同 $runId$ 的重复请求返回既有运行状态，不再创建第二个子 agent 回合。

### 流式事件转发、恢复与去重

子 agent 执行过程中产生的 chat 输出仍由子 agent 自身的可恢复流作为持久事实来源。主 agent 建立观察器读取子 agent 输出 chunk，并将其封装为面向主会话连接的子 agent 事件帧。事件帧包括事件类型、$runId$、可选父工具调用标识、单运行单调序号、子 agent 类型、输入预览、显示顺序、chunk 内容、摘要或错误信息。chunk 内容保持为原有 UI 消息 chunk 的 JSON 表示，主会话客户端用与普通 chat 输出相同的累积逻辑重建文本、推理、工具调用、来源或文件等消息部件，避免为子 agent 输出另建一套不兼容的消息语义。

当一次父工具调用下并发启动多个子 agent 时，主 agent 不把多个输出混入同一文本流，而是按 $runId$ 对事件分组，并按登记记录中的显示顺序排列同级子运行。客户端去重键由父工具调用标识、$runId$ 和事件序号共同构成；没有父工具调用的后台子运行使用空父标识与 $runId$ 组合。该设计使同一父调用下多个子 agent 都可以从序号 0 开始流式输出，同时不会在重连回放与实时转发交叉到达时重复渲染。

恢复时，主 agent 扫描自身登记表中的非终态和近期终态记录，并按 $runId$ 查询子 agent 侧运行映射与已存储 chunk。若子 agent 已完成、失败或取消，主 agent 回放对应 chunk 后合成完成、失败或取消事件并更新登记状态；若登记存在但子 agent 或映射不存在，说明启动阶段发生不确定中断，主 agent 将其标记为 $interrupted$；若子 agent 仍在运行而当前运行环境尚不支持晚到实时追尾，主 agent 回放已持久化 chunk 后发出 $interrupted$ 事件，明确表示输出只恢复到可确认边界。后续实现若支持从指定序号重新追尾，可以在不改变公开编排入口的情况下把该分支替换为继续观察。

### 并发、取消、权限与清理控制

为避免重复请求和并发执行破坏子 agent 上下文，编排层对同一 $runId$ 的框架驱动回合持有排他声明。相同 $runId$ 的并发启动请求只读取并返回既有检查结果；用户通过 drill-in 视图直接连接子 agent 时，若该子 agent 正在执行框架驱动回合，新的人工输入被延后或以明确错误拒绝，不能与进行中的模型回合交错写入同一消息流。主 agent 还可以配置运行中子 agent 的最大并发数，超过阈值时在登记表中记录失败状态并向主会话发出错误事件，从而将 LLM 成本和资源占用限制在可控范围内。

取消控制沿主 agent 到子 agent 的方向显式传播。主会话请求、父工具调用或后台任务收到取消信号后，主 agent 先按 $runId$ 调用子 agent 取消接口，子 agent 将其转换为当前 chat 回合的中止控制信号并传入模型推理和工具执行链路；随后主 agent 停止该运行的实时观察并在登记表中记录 $aborted$ 终态。浏览器刷新、网络断开或观察器关闭只表示观察通道消失，不自动触发上述取消流程，因而长任务可以继续在子 agent 的持久对象中运行并在后续恢复时被回放或检查。

访问控制以主 agent 身份和登记表为准。用于查看子 agent 详情的路由必须经过主 agent 的子 agent 访问门禁，只有当请求中的子 agent 类型与 $runId$ 在主 agent 登记表中存在匹配记录，并且满足应用侧租户、用户或权限策略时，才允许连接到对应子对象；单独持有 $runId$ 不构成访问凭证，也不能通过猜测 URL 创建新的子 agent。登记表默认只保存输入预览和脱敏标记，完整输入或输出是否额外保留由应用策略决定，以减少提示词、凭据或文件内容被重复持久化的风险。

子 agent 运行结果采用显式保留、显式清理的生命周期。完成后的子运行登记记录和对应子 agent 持久对象默认保留，使用户刷新页面后仍能看到已发生的过程，并能进入子 agent 会话查看详细历史。清理接口按时间、状态或会话清理范围筛选登记记录；对于仍处于 $starting$ 或 $running$ 的记录，先执行取消再删除登记记录和子 agent 对象，避免留下无观察者、无登记入口但仍消耗资源的孤立任务。该保留式清理机制同时支持长期查看、失败排查、审计追踪和受控资源回收。
