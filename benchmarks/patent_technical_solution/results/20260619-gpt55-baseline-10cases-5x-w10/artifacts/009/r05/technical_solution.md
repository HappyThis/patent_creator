## 技术方案

### 总体架构与隔离边界

本方案在现有由模型生成异步代码并由执行器编排工具的 codemode 能力基础上，将执行位置扩展到浏览器侧，但不把页面私有能力整体迁移到服务端，也不允许生成代码直接运行在主页面全局环境中。系统包括模型侧代码生成接口、浏览器侧隔离执行容器、主页面工具注册表、受控调用调度器以及执行结果汇聚器。模型只获得经过描述化和类型化后的工具视图，并生成调用这些工具的异步函数；该函数被送入隔离容器执行，容器内仅暴露用于工具调用的代理对象，不暴露主页面对象、组件实例、浏览器会话状态或任意网络能力。

隔离执行容器可以采用 Web Worker、沙箱化 iframe、浏览器内受限运行时或等效的客户端沙箱实现。主页面仅向隔离容器注入一组协议端点，例如消息发送、结果接收、取消和心跳端点；页面真实能力仍保留在主页面工具注册表中。这样，读取当前页面状态、访问前端组件能力、调用剪贴板或地理位置等浏览器私有工具时，由主页面按注册工具的执行函数完成真实操作，隔离容器只发出结构化调用请求，不能直接持有主页面对象引用，从而把“可编排性”和“能力拥有者”解耦。

在一次代码执行开始时，系统创建一次性执行会话，并为该会话生成工具快照、调用白名单和会话标识。隔离容器的生命周期与执行会话绑定，执行完成、超时、取消或发生不可恢复错误后即关闭容器并移除监听器、挂起调用和临时引用。该会话化边界使同一页面中动态变化的工具集不会被历史代码无限期持有，也使多标签页、多会话或连续对话中的工具调用可以按会话隔离和审计。

### 动态工具描述与名称映射

主页面允许业务代码按需注册客户端工具，每个工具至少包含原始工具名、说明、输入参数模式、可选输出模式、执行函数和权限属性。系统在发起模型请求前，从当前页面、前端组件、客户端插件或远端配置中收集可用工具，过滤需要人工批准但本轮不可自动执行的工具，并把剩余工具转换为模型可读的工具描述和类型声明。对于仅在浏览器存在的工具，服务端只接收描述化的工具元数据或工具调用结果，不需要保存工具执行函数本身。

为使模型生成的 JavaScript 能稳定调用不同来源的工具，系统对工具名执行规范化映射：将连字符、点号、空格等分隔符转换为下划线，移除非法标识符字符，对数字开头的名称添加前缀，对 JavaScript 保留字追加后缀，并为每个原始工具名建立规范化名称到真实执行函数的映射表。例如来自 MCP、页面插件或组件树的工具名即使包含点号、短横线或保留字，也只以合法标识符形式暴露给生成代码。若两个工具规范化后产生冲突，系统按命名空间拆分、追加稳定短标识或拒绝本次注册，以避免模型调用落到错误工具。

工具描述可以按命名空间组织，例如默认业务工具、页面状态工具、组件动作工具和外部客户端工具分别形成独立代理对象。模型提示中同时给出命名空间、规范化工具名、输入类型、字段说明和调用示例；隔离容器中则按相同命名空间创建代理对象。该处理方式既保留动态工具的可组合性，又避免把所有工具压平到一个全局对象导致重名、权限边界不清或提示信息难以阅读。

### 生成代码执行与工具调用协议

模型生成的代码在进入隔离容器前先进行规范化处理。系统去除常见代码围栏，解析代码结构，并将表达式、普通语句、命名函数或默认导出统一包装为异步箭头函数；无法完全解析时也将其封装在受控异步函数体内执行。通过该步骤，执行器始终面对统一的入口形态，便于在入口外层加入代理对象、日志捕获、超时竞争和异常捕获逻辑，同时减少模型输出格式差异造成的执行失败。

隔离容器启动后，系统在容器内部为每个工具命名空间生成代理对象。代理对象拦截诸如 `page.readState()`、`component.invoke()` 或 `clientTool.getClipboard()` 形式的属性访问和函数调用，将规范化工具名、序列化参数、调用序号和会话标识封装为调用请求，并通过 `postMessage`、`MessageChannel`、RPC target 或等效浏览器消息通道发送至主页面调度器。主页面调度器校验会话、命名空间、工具名、参数模式和权限属性后，才调用注册表中的真实执行函数，并把成功结果或错误信息序列化返回给隔离容器。

调用协议采用请求—响应相关机制：每个工具调用携带递增调用序号或随机调用标识，主页面维护待完成调用表，返回消息必须匹配会话标识和调用标识后才被交付给对应的 `Promise`。对于对象参数，系统按工具输入模式进行校验和结构化克隆；对于位置参数工具，可把参数数组作为调用载荷并在主页面侧展开。隔离容器不得自行构造未注册工具的执行入口；若代理对象收到的名称不在白名单内，调度器返回“工具不存在”错误，并由代理对象转换为生成代码中的异常。

对于需要组合动态客户端工具的场景，生成代码可以在隔离容器中使用条件分支、循环、并发等待和结果聚合来编排多个工具。例如先读取页面状态，再根据页面中选中的组件类型选择对应组件工具，最后把多个客户端工具的结果合成为返回值。由于每次真实工具执行都必须经由主页面调度器，系统可以在不暴露主页面私有对象的情况下支持多步客户端编排，并能在服务端模型回合中把最终结果作为一次 codemode 工具输出继续使用。

### 错误控制、日志与资源释放

系统在生成代码入口外层设置统一的异常传播规则。主页面工具执行函数抛出的异常、参数校验失败、权限拒绝、工具不存在、消息协议不匹配或浏览器能力不可用等情况，均被转换为结构化错误返回隔离容器；隔离容器代理对象收到错误后抛出普通 JavaScript 异常，使生成代码可以选择捕获并继续，也可以让异常冒泡至执行器。执行器最终向模型侧返回执行结果、错误文本和执行日志，避免错误被吞掉或被误认为正常工具结果。

隔离容器内的 `console.log`、`console.warn` 和 `console.error` 被重定向到会话日志缓冲区，日志项可附带级别、时间戳、调用序号和截断标记。主页面调度器也记录工具调用开始、结束、耗时、参数校验结果和错误类型，但可按策略屏蔽敏感参数值。执行结束时，系统把隔离容器日志与主页面调度日志合并为可审计的执行轨迹；当执行失败时，该轨迹随错误返回给模型或开发者界面，用于定位是生成代码问题、工具参数问题还是页面能力问题。

为防止生成代码长期占用浏览器资源，系统对每个执行会话设置总超时，并可对单次工具调用设置子超时。总超时到达时，执行器拒绝所有未完成调用、向主页面调度器发送取消信号、终止 Worker 或移除 iframe，并清空待完成调用表；单次工具调用超时时，主页面可取消对应浏览器操作或返回超时错误。对于导航、组件动作、剪贴板读取等可能触发用户交互或页面状态变化的工具，调度器还可以根据工具权限属性串行执行、要求用户批准或限制重入，从而避免生成代码并发调用造成页面状态竞争。

在一种可选实现中，服务端仍负责模型对话、代码工具描述生成和最终结果续写，浏览器负责隔离执行与客户端工具调度；也可以把工具描述快照随聊天请求发送给服务端，由服务端提示模型生成代码，再把代码随流式响应或工具调用下发给浏览器执行。无论采用哪种部署方式，真实客户端工具执行函数始终留在主页面，隔离容器始终只能通过受控协议访问工具。该方案由此同时获得代码式多工具编排能力、浏览器私有能力复用能力以及对主页面环境、工具权限和执行资源的隔离控制。
