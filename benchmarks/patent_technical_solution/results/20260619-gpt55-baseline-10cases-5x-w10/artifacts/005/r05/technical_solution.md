## 技术方案

### 总体架构与主从边界

本方案以智能工作台的应用数据库和既有任务看板作为任务主存储与主要操作入口，在项目级别配置一个可选的 Git-native 协作镜像。所述协作镜像可以是 GitHub Issue、代码仓库中的结构化任务文件，或具备提交历史、分支、标签、评论等 Git 托管语义的等价载体。任务的创建、更新、删除、拖拽流转、评论、指派和质量门禁仍先在应用侧完成；同步组件仅在任务所属项目启用镜像仓库后，将任务的可公开协作字段投射到外部载体，使开发者工具和 agent 无需读取应用数据库即可理解任务队列。

系统在应用层设置同步适配器、状态映射器、身份锚定字段、同步历史表和后台轮询器。同步适配器负责在本地任务模型与外部仓库对象之间进行读写转换；状态映射器负责把看板列、优先级、标签和关闭状态映射为外部仓库可表达的标签、状态或结构化字段；身份锚定字段在本地任务记录中保存外部仓库标识、外部对象编号和最近同步时间；同步历史表记录每个项目、仓库、方向、成功或失败状态、拉取和推送数量；后台轮询器按配置周期扫描已启用同步的项目并触发增量同步。

上述结构形成“应用侧主写、外部侧镜像”的边界：本地数据库保存完整任务、项目、订阅、通知、审计和质量评审信息，外部仓库仅保存适合协作和自动化消费的任务标题、说明、当前状态、优先级、仓库内评论、外部编号以及必要的追踪信息。该边界避免外部仓库替代任务看板，也避免因外部同步不可用而阻断应用内部的任务管理流程。

### 任务语义映射与身份锚定

任务语义映射以“可逆、可区分、低歧义”为原则。应用侧六个看板状态 inbox、assigned、in_progress、review、quality_review、done 分别映射为具有专用前缀的外部状态标签，例如 mc:inbox、mc:assigned、mc:in-progress、mc:review、mc:quality-review、mc:done；优先级 low、medium、high、critical 映射为 priority:low、priority:medium、priority:high、priority:critical。状态标签采用独立命名空间，优先级标签采用固定集合，外部仓库原有业务标签在同步时被保留但不参与看板状态判定。

对每个被镜像的任务，系统建立稳定的双向身份锚定。应用侧任务保存外部仓库地址、外部任务编号、最近同步时间以及可选分支或文件路径；外部对象中可以保存应用侧任务引用号或票据前缀。同步时先以“工作区、仓库、外部编号”的组合查找既有任务，并在数据库中建立唯一索引，以阻止同一外部任务被重复导入。对于从外部仓库首次进入应用的对象，系统根据仓库项目配置创建本地任务，并把外部编号写入锚定字段；对于本地首次推送的任务，系统创建外部对象后回写外部编号。

外部状态与应用状态不完全等价时，采用显式优先规则而不是隐式猜测。例如外部对象关闭时映射为 done；外部对象仍为打开状态时，优先读取专用状态标签，缺少状态标签时保持原有本地状态或落入 inbox。这样，Git 工具只需要识别少量稳定标签即可理解任务所处阶段，应用侧也不会因外部平台的 open、closed 二值状态丢失 review、quality_review 等细粒度看板语义。

### 持续同步流程

应用侧新建任务时，系统先在数据库事务中完成项目票号分配、任务记录写入、订阅与通知创建、活动审计和实时事件广播；在本地事务提交后，若任务所属项目启用了外部同步且配置了目标仓库，则异步触发外部推送。推送时，若任务已有外部编号，则读取外部对象并更新标题、正文、状态标签、优先级标签和关闭状态；若任务尚无外部编号，则创建新的外部任务对象，并把外部编号、仓库地址和同步时间回写到本地任务。

外部到应用的同步采用项目级增量拉取。后台轮询器按固定或可配置周期扫描所有处于 active 且启用外部同步的项目，根据同步历史中的最后同步时间请求外部仓库中在该时间之后变更的任务对象。对每个外部对象，系统先执行身份锚定匹配；未匹配到本地任务时创建新任务并写入状态、优先级、标签和外部编号；匹配到本地任务时比较外部更新时间、本地更新时间和最近同步时间，仅在外部对象确认为更新来源时覆盖本地标题、说明、状态和优先级。

为了避免双向同步产生回环，系统在每次成功推送或拉取后记录同步时间戳。后续拉取时，若外部对象更新时间与本地最近同步时间处于预设时间窗口内，则判断该变更大概率来源于本地刚刚推送，跳过本轮覆盖；若外部更新时间早于或等于本地更新时间，也跳过覆盖。该规则使任务在应用侧拖拽、外部仓库编辑和后台轮询之间保持最终一致，同时减少“本地推送—外部回读—本地再写”的抖动。

### 故障隔离与一致性控制

外部同步被设计为故障隔离的附属通道。应用侧任务创建、批量状态更新、完成质量门禁校验、删除或评论写入均不等待外部仓库成功返回；同步调用失败时只记录日志、同步历史和错误状态，不回滚已经完成的本地事务，也不阻断任务看板的实时更新。对于后台轮询中的单个项目或单个外部对象失败，系统捕获该失败并继续处理其他项目或对象，从而避免一个仓库令牌失效、网络超时或单条数据格式异常扩大为全局任务管理不可用。

系统通过同步历史表对外部通道进行可观测控制。每次同步记录目标仓库、项目、同步方向、最近同步时间、处理数量、拉取数量、推送数量、成功、部分成功或错误状态以及错误摘要。界面或 API 可以基于该历史显示外部镜像的新鲜度和失败原因，运维人员也可以手动触发某个项目的重新拉取，而不需要修改应用数据库或直接访问外部任务对象。

在删除和状态收敛场景中，本方案保持语义边界清晰：应用侧删除可以被表示为外部对象关闭、打上归档标签或写入墓碑文件，具体策略由项目配置决定；外部对象关闭默认只表示任务完成，不直接删除本地任务；缺少专用状态标签的外部变更不强行覆盖本地细粒度状态。由此，外部仓库成为面向开发者和 agent 的可读、可追踪镜像，而应用数据库仍是完整任务生命周期和质量规则的权威来源。
