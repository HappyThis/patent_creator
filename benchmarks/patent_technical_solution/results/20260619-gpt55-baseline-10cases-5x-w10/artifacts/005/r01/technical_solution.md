## 技术方案

本方案在现有智能工作台的任务看板和应用数据库之外，增加一个可选的 Git-native 协作镜像层。应用数据库仍作为任务创建、维护、权限校验、通知、质量门禁和看板展示的主存储；Git 仓库、GitHub Issue 或等价 Git 托管对象仅作为外部开发者工具和 agent 工作流可读取、可订阅的任务镜像。系统围绕任务标识绑定、字段语义映射、增量同步、冲突抑制和失败隔离构成同步闭环，使外部工具无需直接访问应用数据库即可理解任务队列、任务状态和优先级，同时不改变应用内部任务生命周期的主导地位。

### 主存储与 Git-native 镜像的分层结构

在数据结构上，每个项目可以配置外部仓库地址、默认分支、同步开关和标签初始化状态；每个任务在原有标题、描述、状态、优先级、所属项目、票号、负责人、标签、元数据、完成时间等字段之外，记录外部镜像定位字段，包括仓库标识、外部问题编号、最近同步时间，以及可选的分支、合并请求编号和合并请求状态。该定位字段从普通元数据中提升为独立列，并在工作空间、仓库标识和外部问题编号上建立唯一约束，从而将一个应用任务与一个 Git 托管协作对象稳定绑定，避免同一外部对象被重复导入为多个任务。

Git-native 镜像对象采用开发者熟悉的可读形式表达任务：任务标题映射为外部对象标题，任务描述映射为正文，任务状态和优先级映射为带命名空间的标签，非本系统产生的仓库标签在同步时保留为普通标签或任务标签。对于 GitHub Issue 型镜像，任务状态为完成时外部对象可关闭，其他状态保持打开；对于文件型或其他 Git 托管载体，也可以采用包含同等字段的 Markdown 或结构化文件，并使用提交历史记录镜像变化。通过将内部主键、项目票号和外部定位字段分层保存，系统既能维持应用内多项目票号和看板顺序，又能向仓库暴露稳定、可追溯、便于 agent 解析的任务入口。

### 同步触发与增量对账流程

同步流程包括出站推送和入站拉取两个方向。出站方向在任务创建、标题更新、负责人变更、优先级变更或状态变更后触发，但触发点位于应用数据库事务完成、活动记录和通知处理之后；同步调用以异步方式执行，外部仓库未配置、项目未启用同步或网络失败时仅记录错误，不回滚已完成的任务创建或更新。新任务在启用同步的项目中创建时，系统根据任务字段创建外部镜像对象，并把返回的外部编号、仓库标识和同步时间写回任务；已有外部编号的任务更新时，系统读取外部对象现有标签，替换本系统命名空间下的状态和优先级标签，保留其他标签，再更新标题、正文、标签和开闭状态。

入站方向由后台轮询器或等价调度器按项目扫描已启用同步且具有仓库标识的项目，并按最近一次同步时间向外部仓库请求增量变化。对于尚未绑定的外部对象，系统解析其标题、正文、开闭状态和标签，创建来源为同步服务的应用任务；对于已绑定任务，系统比较外部更新时间、应用任务更新时间和最近同步时间，仅在外部对象确认为较新时更新应用任务。每轮同步的仓库、项目、方向、结果、错误信息、拉取数量和推送数量写入同步历史表，使增量边界和同步健康状况可以被后续诊断、重试或管理界面复用。

### 状态语义映射与冲突抑制

为避免应用看板状态与外部协作对象状态语义偏离，本方案采用显式映射表，而不是依赖外部平台的自由文本状态。应用任务的 inbox、assigned、in_progress、review、quality_review、done 等看板状态分别映射为带有统一前缀的状态标签；优先级 low、medium、high、urgent 或等价严重等级映射为优先级标签。同步时只解释本系统命名空间内的标签作为状态来源，仓库原有业务标签不会覆盖任务状态；当外部对象缺少可识别状态标签时，打开对象默认落入待处理状态，关闭对象默认落入完成状态，优先级缺省为中等优先级。

同步引擎在每次成功推送或拉取后写入最近同步时间，并在入站处理时执行双重抑制：其一，若外部更新时间与最近同步时间落在预设时间窗口内，则判定为刚由本系统推送形成的回声更新并跳过；其二，若外部更新时间不晚于应用任务更新时间，则以应用数据库为准，不用旧的外部内容覆盖内部任务。对于涉及完成状态的转换，应用侧的质量审核、权限和完成时间规则仍作为主规则；外部对象关闭只能被解释为完成意图，若不满足应用侧完成条件，可以保留任务在审核中或记录为待确认同步事件，以避免外部平台的 open/closed 二值语义绕过内部多阶段看板语义。

### 故障隔离与可观测恢复机制

故障隔离通过同步边界和错误记录共同实现。任务的创建、更新、删除、评论通知、订阅关系和实时看板广播均在应用主流程内完成；外部同步在主流程之后以非阻塞方式执行，单个外部对象获取失败、标签初始化失败、仓库接口限流或网络异常只影响对应项目或对象的镜像新鲜度，不影响任务在应用内的可见性和可操作性。后台轮询器以项目为单位逐个执行同步，单个项目失败时捕获异常并继续处理其他项目，避免一个仓库故障扩散为全局任务队列不可用。

为支持恢复和审计，系统将同步事件与普通任务活动区分记录：普通活动用于说明任务被创建、分配、状态变更或从外部对象更新；同步历史用于说明某次仓库同步的方向、时间、结果和错误。管理端或自动恢复任务可以根据同步历史选择重试失败项目、重新初始化标签、重新拉取自指定时间点之后的外部变化，或者在必要时解除某个任务与外部对象的绑定后重新建立镜像。由于外部仓库被设计为可选镜像，即使长时间同步失败，应用数据库中的任务状态仍保持完整；恢复后同步引擎依据绑定字段、更新时间和命名空间标签重新对账，而不是盲目覆盖两端数据。
