## 技术方案

### 总体构思和任务模型

本方案在持久化、可休眠的 Agent 会话实例外增加程序化任务入口，使 webhook、RPC 或其他外部调用不再直接驱动一次长时间模型推理，而是先被转换为一条具有稳定标识的对话任务记录。任务记录至少包括任务标识、外部幂等键、目标 Agent 实例、用户输入消息、请求上下文、任务阶段、关联的聊天请求标识、创建时间、更新时间以及可选的清理期限。外部入口只负责校验调用方和载荷、定位目标 Agent、写入任务记录并返回“已接收”确认；模型调用、工具调用、流式输出和消息持久化由 Agent 内部的异步执行环节继续完成。

任务阶段采用显式状态机表达，推荐包括已接收、已入队、执行中、等待外部交互、完成、失败、已取消和已清理等状态。该状态机与现有 Agent 的持久状态、对话消息存储、请求取消信号、TurnQueue 串行队列、流式分片存储和恢复回调相连接：任务入口保存的是“应当执行的一次对话意图”，Agent 聊天层保存的是“已经进入对话历史和模型流的执行结果”。通过将任务元数据与聊天消息分层保存，可以在外部快速确认和内部可靠执行之间形成边界，避免外部连接生命周期影响 Agent 推理生命周期。

### 可靠接收与幂等去重

外部提交请求进入系统时，接收器先计算或读取幂等键。幂等键可以由调用方提供，也可以由系统根据目标 Agent 标识、外部会话标识、用户输入内容摘要、调用方标识和业务事件编号组合生成。接收器在同一 Agent 实例的持久存储中以幂等键作为唯一约束执行原子插入：若不存在对应记录，则创建任务并写入已接收状态；若已存在对应记录，则直接返回原任务标识和当前状态，而不再次追加用户消息、不再次创建聊天请求，也不再次启动模型推理。

为避免“任务已接收但用户消息重复写入”的不一致，任务记录与首条用户消息之间设置一次性提交边界。可采用两种等效方式：其一，在同一持久化事务中写入任务记录和待追加消息，并以任务标识作为消息的来源标记；其二，先写任务记录，再由执行器在从已接收推进到已入队时检查任务标识是否已经绑定到消息记录，未绑定才调用消息持久化接口。无论采用哪种方式，消息写入完成后都把消息标识或聊天请求标识回填到任务记录中，使重试请求只能观察已有结果而不能产生第二条用户输入。

接收确认响应不携带模型输出，只返回任务标识、幂等命中标志、当前阶段、状态查询地址或 RPC 方法名以及可选的取消令牌。该响应在持久化提交成功后立即返回，外部调用方即使因 HTTP 超时、网络断开或 RPC 重试再次提交，也会命中同一幂等记录。这样，外部系统的至少一次投递语义被转换为 Agent 内部的至多一次消息追加和至多一次执行启动。

### 异步执行管理与状态查询

任务执行器在 Agent 实例内部运行，并复用现有聊天层的串行化能力。对于已接收任务，执行器将其登记到 TurnQueue 或等效队列，生成聊天请求标识，随后调用程序化对话入口保存用户消息并触发一次模型轮次。队列以请求标识标记当前活动任务，并通过 generation 计数或类似失效标记跳过已经被清理、取消或被会话重置失效的排队任务，从而避免多个外部任务在同一会话中重叠写入同一段对话上下文。

执行过程中，任务阶段随关键持久化点推进：任务写入后为已接收，进入 TurnQueue 后为已入队，模型流开始并写入流元数据后为执行中，出现工具审批、客户端工具结果或其他外部输入依赖时为等待外部交互，收到终止分片并完成消息调和后为完成，发生不可恢复异常时为失败，收到取消请求并传播到推理信号后为已取消。状态查询接口读取任务记录、聊天请求标识、当前队列活动标识、已持久化消息以及流式元数据，向外部调用方返回阶段、进度摘要、错误原因、结果消息引用和可重试建议。

当同一 Agent 在短时间内收到多个外部任务时，任务执行策略可以配置为排队、保留最新、合并或丢弃重叠提交。排队策略保证每个任务按接收顺序成为独立轮次；保留最新策略使较早但尚未开始的任务转为被取代状态；合并策略把多个外部用户输入合成为一次模型轮次但保留各自任务标识与输入来源；丢弃策略仅在业务允许时拒绝重叠任务。策略决策结果写入任务记录，因而状态查询能够解释任务是已执行、等待执行、被取代还是被策略丢弃。

### 中断恢复、取消和清理一致性

为处理休眠、重启或执行中断，任务记录与聊天流元数据共同作为恢复依据。模型流开始时记录流标识、聊天请求标识、创建时间和 streaming 状态，并将输出分片按序号批量写入持久化存储；完成或失败时再把流状态更新为 completed 或 error。Agent 被唤醒后，恢复逻辑扫描未终止任务和仍处于 streaming 的流：若任务只有已接收记录而没有消息标识，则重新进入入队步骤；若已经写入用户消息但尚未开始模型流，则以原聊天请求标识重新排队；若存在流元数据和分片，则先重建部分助手消息，再根据恢复策略决定保存部分结果、继续上一轮次或将任务标记为中断失败。

恢复判定不依赖内存中的 Promise、ReadableStream 或 WebSocket 连接是否仍存在，而是依赖持久化检查点。对于恢复出的孤立流，如果没有活跃模型读取器，则系统将已存分片作为部分输出进行持久化并关闭该流，避免外部查询长期看到执行中状态；对于可以安全继续的任务，系统使用最近一次请求上下文、客户端工具模式和恢复数据调用继续上一轮次的入口，并将任务阶段从中断恢复为执行中。可选地，可设置最大可恢复时长，超过该时长的任务不再自动继续，而是标记为失败或等待人工/外部系统重新提交。

取消接口以任务标识为入口执行阶段化取消。若任务尚未进入队列，则仅把任务阶段改为已取消并释放幂等记录的执行资格；若任务已入队但未成为活动轮次，则推进队列 generation 或设置任务取消标记，使其到达队首时被判定为失效；若任务正在执行，则通过以聊天请求标识为键的 AbortController 或等效取消注册表向模型推理和下游工具传播取消信号，随后保留取消前已经持久化的分片和消息状态，并将任务标记为已取消。取消结果与状态查询共用同一任务记录，外部调用方可判断取消是否已经生效、是否仍在等待执行器确认。

清理接口仅作用于已经到达终态或超过保留期限的任务。清理时先确认任务不在当前活动请求、未占用 TurnQueue、没有待恢复流和未完成的外部交互；满足条件后删除或归档任务元数据、过期流分片和状态查询索引，但保留作为会话历史的用户消息和必要助手消息，除非调用方明确选择清除对话历史。通过上述接收、执行、恢复、取消和清理的分层控制，本方案能够在外部程序化提交场景下提供快速确认、幂等去重、可查询进度、可控取消以及休眠重启后的阶段一致性。
