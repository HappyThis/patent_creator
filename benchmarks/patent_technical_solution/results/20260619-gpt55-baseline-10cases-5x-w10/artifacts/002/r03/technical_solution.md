## 技术方案

### 总体构思与任务账本

本方案在现有基于 Agent 的对话系统外侧增加“程序化对话任务”入口，使 webhook、RPC 或其他外部系统提交的请求不直接占用模型推理链路，而是先被转换为可持久化、可查询和可恢复的任务记录。该入口与现有 WebSocket 对话入口共用会话、消息持久化、串行 turn 队列、可恢复流、取消信号和恢复钩子等能力，但在接收阶段引入任务账本，将“接收请求”和“执行模型推理”解耦。

任务账本可以建立在每个 Agent 实例已有的持久化存储上，例如 Durable Object 的 SQLite 存储。账本至少记录任务标识、外部幂等键、会话或 agent 名称、提交方信息、规范化后的用户消息、请求上下文、当前阶段、对应的内部 chat requestId、流标识、创建时间、更新时间、完成时间、取消标记、错误信息和清理期限。任务阶段可包括 received、persisting、queued、running、streaming、recovering、completed、aborted、failed、cleaned 等，用于把一次外部调用从接收、写入消息、排队、推理、流式持久化、恢复续跑直到终止的状态显式化。

外部入口返回的确认只表示任务记录已经通过原子写入进入账本，并不表示模型推理已经完成。确认内容可包含 taskId、当前阶段、状态查询地址或 RPC 方法名、取消入口和建议轮询间隔。这样既避免外部调用方因长时间模型推理而超时，又使后续状态查询、取消和清理均围绕同一个任务记录进行，保证外部系统观察到的任务生命周期与内部对话执行状态一致。

### 可靠接收与幂等提交

接收端对 webhook、RPC 或其他程序化请求执行统一的规范化处理：解析提交方、会话目标、用户输入、附加 body、客户端工具描述和外部幂等键；若外部未提供幂等键，则可以由提交方标识、会话标识、规范化输入摘要和业务时间窗口生成确定性键。随后在同一事务中按幂等键插入任务账本，并设置唯一约束，只有首次插入成功的请求进入后续执行调度。

当外部系统因网络异常或超时重复提交同一任务时，接收端先查询或尝试插入同一幂等键对应的账本记录。若记录已存在且请求摘要一致，则直接返回原 taskId 和当前阶段，不再追加新的用户消息，也不再创建新的模型 turn；若幂等键相同但请求摘要不一致，则返回冲突状态，避免把不同任务错误折叠为同一执行。通过把幂等判断放在消息持久化和 turn 入队之前，可以从源头避免重复写入用户输入和重复执行。

对于首次接收成功的任务，系统不在请求线程内等待模型输出，而是将账本阶段从 received 原子更新为 queued 或 persist_pending，并通过 Agent 的异步保持机制、零延迟调度或内部队列触发后台执行。外部确认在账本写入完成后立即返回；如果后台触发失败，账本仍保留 received 阶段，恢复扫描器可以根据未推进的阶段重新触发，避免确认已返回但任务丢失。

### 异步执行与状态管理

后台执行器读取 queued 阶段任务后，先以条件更新方式取得执行租约，例如仅当任务仍处于 queued 或 recoverable 阶段且未被取消时，才将阶段更新为 running，并写入 leaseOwner、leaseUntil 和 attempt。取得租约后，执行器使用现有 saveMessages 式的程序化对话入口，将任务中的用户输入按“基于当前最新消息列表追加”的函数形式持久化到会话消息中，再启动内部 chat turn。该方式利用现有 turn 队列的串行化能力，保证程序化任务不会与用户 WebSocket 消息、自动 continuation 或其他任务并发修改同一会话消息序列。

任务执行过程中的状态推进与内部对话阶段绑定：用户消息写入成功后，账本记录进入 persisted 或 queued_turn；内部 turn 实际开始时写入 requestId 并进入 running；可恢复流开始时写入 streamId 并进入 streaming；模型响应结束、错误或外部取消时分别进入 completed、failed 或 aborted。系统可沿用现有 ResumableStream 的流元数据和 chunk 表，把响应分片与 requestId、streamId 关联保存，使状态查询既能返回粗粒度阶段，也能按需要返回已持久化的部分响应摘要或最终 assistant 消息标识。

为避免外部任务与已有对话并发策略冲突，程序化任务默认采用严格串行策略；在允许合并的场景中，也应只在同一幂等键或同一可合并业务键下合并用户输入，并保留每个外部 taskId 到内部 requestId 的映射。若会话中已有正在执行的 turn，任务仅进入队列而不重复启动推理；若任务被后续清空会话操作或队列代际变化失效，则账本阶段更新为 skipped 或 failed，并说明其未执行原因。

### 恢复判定、取消与清理

恢复时，Agent 启动或收到状态查询请求后扫描任务账本、内部 turn 队列状态、可恢复流元数据和已持久化消息，按持久化证据而非内存变量判定任务阶段。若任务处于 received 或 queued 且尚未写入用户消息，则重新触发入队；若账本显示已写入消息但未写入 requestId，则根据消息标识和任务标识确认是否需要重新启动 turn；若存在 requestId 和处于 streaming 的流元数据，则读取已保存 chunk，判定该流是仍有 live reader 的活动流，还是因休眠、重启或中断形成的 orphaned stream。

对于 orphaned stream，系统先将已保存的响应分片重构为部分 assistant 消息并持久化，随后根据恢复策略决定是否调用 continuation 继续生成。恢复策略可使用原始请求 body、客户端工具 schema、checkpoint 数据和任务创建时间等上下文：当中断时间较短且外部任务未取消时，进入 recovering 并调度 continueLastTurn；当任务已超过安全续跑窗口、依赖的外部工具结果不可重放或用户已清理会话时，将任务标记为 failed、aborted 或需要人工处理。恢复完成后，账本阶段与最终消息状态同步更新，避免同一中断流被重复持久化或重复续跑。

取消操作以 taskId 为入口，先在账本中设置 cancellationRequested 和取消原因；若任务尚未取得执行租约，则直接转为 aborted 并阻止后续入队；若任务已获得 requestId，则通过与 requestId 关联的 AbortController 或等效取消注册表向模型推理链路传播取消信号，使已产生的流式分片仍按可恢复流规则落盘，最终状态报告为 aborted。若取消到达时任务已经 completed 或 failed，则取消请求不回滚已完成结果，只返回当前终态。

清理机制对终态任务采用延迟清理而非立即删除：在 completed、aborted 或 failed 后保留账本、幂等键、摘要状态和必要的 requestId 映射一段时间，以便重复提交仍能被识别并返回同一结果；超过保留期后删除大体积流 chunk、临时上下文和过期租约，仅保留可选的最小审计记录。通过“任务账本唯一约束 + 条件状态转移 + 串行 turn 队列 + 可恢复流证据”的组合，本方案能够在外部快速确认、重复提交、运行中断和恢复续跑之间保持一致性。
