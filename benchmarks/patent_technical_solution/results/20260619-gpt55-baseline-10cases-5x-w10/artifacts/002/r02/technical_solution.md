## 技术方案

### 总体构思与任务模型

本方案在现有持久化 Agent 和 AI Chat 能力之上增加面向外部系统的一次性对话任务入口，使 webhook、RPC 或其他程序化调用不直接阻塞在模型推理链路上。外部入口接收包含会话标识、调用方任务标识、用户输入消息、可选元数据和回调信息的请求后，将其转换为统一的任务记录，并以任务记录作为后续写入、执行、查询、取消和清理的唯一协调对象。任务记录至少包括任务标识、幂等键、目标 Agent 或会话、用户消息标识、执行阶段、当前请求标识、创建与更新时间、取消标记、清理期限以及错误摘要等字段。

该任务记录优先存储在 Agent 所属 Durable Object 的 SQLite 存储中，借助每个 Agent 独立状态、消息表、请求上下文表和可恢复流表的既有机制，使外部任务与对话历史处于同一一致性边界内。外部系统只获得“已接收”的确认以及可查询的任务标识，模型调用、流式输出、工具调用和消息持久化在后台串行推进，从而将接收链路与推理链路解耦，并避免外部调用方因长时间等待而反复触发相同的对话处理。

### 可靠接收与幂等写入

外部提交入口先对调用方身份、目标会话和消息格式进行校验，然后计算幂等键。幂等键可以由调用方显式提供，也可以由调用方标识、目标 Agent、会话标识、用户消息内容摘要和业务时间窗口共同派生。系统在同一持久化事务中执行“查找幂等键、创建或复用任务记录、写入或复用用户消息”的操作：若不存在对应记录，则插入状态为 accepted 的任务并写入一条具有稳定消息标识的用户消息；若已存在对应记录，则不再追加用户消息，也不再创建新的执行请求，而是返回既有任务标识及其当前阶段。

为避免确认已返回但后台执行未登记的窗口，任务创建、用户消息持久化和执行触发标记采用先落盘后调度的顺序。系统仅在任务记录和消息记录均成功写入后返回 accepted；后台执行器根据任务表中 accepted 或 queued 阶段的记录启动对话轮次。对于重复提交、网络重试或调用方超时重放，请求处理只读取既有任务记录并返回相同任务标识，因此不会重复写入用户输入，也不会让同一幂等键产生多个模型推理轮次。

### 异步执行、查询与取消

后台执行采用与现有聊天轮次相同的串行队列机制，将每个外部任务绑定到一个 requestId，并在进入模型处理前取得该任务的执行锁。队列通过代际计数或等效的失效标记区分清理前后的任务批次，保证同一 Agent 会话内不会出现多个对话轮次并发修改消息历史。若已有用户对话或程序化任务正在执行，新任务可以按策略进入 queued 阶段；当策略为合并或只保留最新时，仍先持久化必要的用户输入，再由进入锁内的任务基于最新消息历史决定是否实际发起模型推理。

任务状态随执行阶段单调推进：accepted 表示已可靠接收，queued 表示等待串行轮次，running 表示已进入模型或工具调用链路，completed 表示已形成并持久化助手消息，failed 表示不可恢复错误，cancelled 表示收到取消且已停止或跳过执行，cleaned 表示消息、流片段和任务元数据已按清理规则移除。查询接口读取任务记录、消息表和可恢复流元数据后返回阶段、最近更新时间、已产生的输出摘要或流式片段位置；取消接口设置取消标记并通过按 requestId 管理的 AbortController 向模型调用、工具执行和子 Agent 调用传播中止信号。

当取消发生在任务尚未进入执行锁之前，队列在轮到该任务时读取取消标记并将其转为 cancelled，不调用模型；当取消发生在运行中，系统中止当前 requestId 对应的信号，并在 finally 清理中移除控制器、刷新已产生的流片段和更新任务状态。清理接口可按任务标识或到期时间删除任务记录、关联用户消息、助手消息、请求上下文和流式片段；清理同时推进队列代际，使清理前排队但尚未执行的任务被识别为过期任务而跳过。

### 中断恢复与一致性清理

针对 Agent 休眠、重启或执行中断，系统以持久化任务阶段、消息表、请求上下文、可恢复流元数据和后台执行纤程名称共同判定恢复动作。若仅存在 accepted 或 queued 任务且没有对应运行流，则恢复时重新入队执行；若任务为 running 且存在状态为 streaming 的流元数据，则提取已落盘的流片段和部分助手文本，标记为 interrupted，并触发恢复钩子决定是否持久化部分结果、继续最后一轮对话或转为失败；若任务已 completed、failed、cancelled 或 cleaned，则恢复过程只补齐索引和缓存，不再次调用模型。

恢复判断不依赖内存中的队列或 AbortController，因为这些对象会随 Durable Object 休眠而丢失；系统在构造或唤醒时从 SQLite 重建消息历史、请求上下文、可恢复流索引和任务阶段。对于已恢复但无活动读取器的流，系统将其视为孤儿流，只允许基于已持久化片段进行重放或恢复决策，避免把丢失的模型流误判为仍在正常运行。对于超过预设时间仍保持 streaming 或 running 的记录，系统按陈旧中断处理，以防长时间占用任务状态。

通过上述机制，外部提交请求的确认路径只包含校验、幂等判定和持久化登记，能够快速返回；实际推理由持久化任务记录驱动，重复提交被幂等键折叠，取消和清理以 requestId 与任务阶段为边界传播，恢复过程以落盘状态而非瞬时内存状态为依据。由此可以在外部系统重试、网络抖动、Agent 休眠和执行中断并存的情况下，保持“每个幂等任务最多写入一次用户输入、最多启动一次有效执行、恢复后状态可解释”的一致性。
