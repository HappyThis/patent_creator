## 技术方案

### 总体构思与任务闭环

本方案面向外部系统通过 webhook、RPC 或其他程序化入口提交一次对话任务的场景，在有状态执行单元内建立“接收即登记、登记后异步执行、执行过程可查询、取消与清理可追踪、休眠或重启后可恢复”的任务闭环。外部请求到达时，不将网络连接是否持续存在作为任务是否继续执行的依据，而是先形成持久化任务记录，再由后台执行链路驱动对话回合，由此使外部调用方能够以任务标识查询状态、重试提交或发起取消。

该任务闭环可以复用持久化 Agent 的存储、生命周期恢复和 AI Chat 回合处理能力，并在其外层增加面向外部调用的任务登记层。任务登记层保存外部幂等键、内部任务标识、对话 requestId、可恢复流 streamId、关联消息、原始请求上下文摘要以及阶段状态；对话执行层负责把已登记任务转换为一次程序化对话提交，例如通过保存用户消息并触发对话回合；状态协调层根据任务记录、消息持久化结果、流分片元数据、取消信号和恢复上下文确定对外可见状态。上述各层以持久化标识相互关联，而不是仅依赖内存对象关联，从而在执行单元休眠、重启或客户端断开后仍能重建任务进展。

### 接收登记与幂等控制

外部任务接收入口首先规范化请求中的会话标识、用户输入、工具上下文、回调信息和幂等键。幂等键可以由外部系统提供，也可以由接收侧根据外部任务号、会话标识、请求体摘要和提交时间窗口生成；其作用不是鉴权，而是把“同一次业务提交”和“新的业务提交”区分开。接收入口在进入模型推理或工具调用前，以幂等键为唯一性条件写入任务记录，并将任务置为 received 或 persisted 状态；只有完成该登记后才返回 accepted 结果及内部 taskId。

当相同幂等键的请求再次到达时，接收入口不重复写入用户消息、不重复创建对话回合，也不重新启动模型推理，而是读取既有任务记录并返回相同 taskId、当前阶段状态和可选的进度摘要。若重复请求携带的关键请求体摘要与既有记录不一致，则将其判定为幂等键冲突并返回冲突状态，避免把两个不同业务请求合并到同一对话任务。通过这种先登记后执行的顺序，系统可以覆盖网络超时、外部系统自动重试和调用方未收到 accepted 响应后的再次提交等情形。

### 异步执行与状态查询

登记完成的任务由异步执行管理器提交到对话执行链路。执行管理器为每个任务分配或记录对话 requestId，并把外部请求转换为一次可持久化的对话输入：先保存用户消息、请求 body 或必要上下文，再进入对话回合处理。对于同一会话内的多个任务，执行管理器可以采用回合队列进行串行化，确保前一回合完成、取消或被判定为失效后再执行后一回合；对于短时间重叠提交，可按 queue、latest、merge、drop 或 debounce 等策略确定保留、合并、覆盖或延迟执行的任务。

任务状态采用阶段化状态机维护，至少区分已接收、已持久化、已排队、运行中、流式输出中、已完成、已取消、失败和已清理等阶段。状态更新点与实际技术动作绑定：任务记录写入后进入已持久化，进入回合队列后进入已排队，开始模型或工具执行后进入运行中，产生可恢复输出分片后进入流式输出中，助手消息或最终结果持久化后进入已完成，取消信号生效后进入已取消，清理策略删除或归档中间数据后进入已清理。外部状态查询接口仅从持久化状态和可恢复输出摘要生成响应，避免因内存中执行对象丢失而返回互相矛盾的状态。

在流式对话输出场景中，执行管理器将输出分片、流元数据和任务记录关联保存。状态查询可以返回阶段状态、已生成的部分文本或结构化片段、最近更新时间以及是否仍可继续恢复；实时连接存在时可以继续向调用方推送新增分片，实时连接断开时则不立即终止后台回合。这样，外部系统既可以轮询获取任务进度，也可以在重连后从已持久化分片处恢复读取，避免把一次长耗时对话绑定到单个同步 HTTP 或 WebSocket 生命周期。

### 取消清理与恢复一致性

取消机制以 requestId 或 taskId 为索引管理取消信号。外部系统发起取消时，状态协调层先校验任务是否仍处于可取消阶段，再将任务标记为取消中，并把外部取消信号绑定到内部对话回合的取消控制器；正在运行的模型调用、工具调用或流处理观察到该信号后停止继续生成或继续写入新的业务结果。若取消发生在任务尚未进入回合队列之前，则直接使该任务从待执行集合中失效；若取消发生在流式输出过程中，则保留已持久化的分片和取消状态，用于后续查询说明该任务并非正常完成。

清理机制与取消机制解耦。普通客户端连接断开只释放该连接相关的本地读取资源，不默认取消服务器端任务；只有外部系统明确发出取消或清理请求，或者任务达到预设保留期限，才进入取消或清理流程。清理流程可以删除已完成任务的临时流分片、释放取消控制器、移除过期幂等记录或归档任务摘要，但应保留足以解释最终状态的最小记录，例如 taskId、幂等键摘要、完成/取消/失败状态和时间戳，以便外部系统后续重试查询时获得一致响应。

当有状态执行单元休眠、重启或对话流中断后，恢复流程从持久化任务记录开始，而不是从内存队列开始。恢复器读取最近处于已排队、运行中或流式输出中的任务，并结合消息持久化结果、流元数据、已写入分片、原始请求上下文和恢复上下文判断下一动作：若任务已存在完整助手结果，则补写完成状态；若仅存在部分流分片且原 live reader 已丢失，则将该部分结果作为可查询的中间结果，并按配置选择终止为失败/中断状态或基于原上下文续接一个新的回合；若任务尚未真正进入执行链路，则重新入队；若任务已被取消，则不再恢复执行。该恢复判定使系统不会因为重启而重复写入同一用户消息、重复调用模型或把部分输出误报为完整结果。
