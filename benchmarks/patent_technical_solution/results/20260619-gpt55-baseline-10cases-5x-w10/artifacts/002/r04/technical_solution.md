## 技术方案

### 外部任务接收与任务账本

本方案在现有持久化 Agent 与对话 Agent 能力之上增加面向外部系统的对话任务入口。外部系统可以通过 webhook、HTTP 请求、Durable Object RPC 或其他程序化调用提交一次对话任务，提交内容至少包括目标 agent 或会话标识、用户输入内容、调用方提供的幂等键、回调或查询所需的关联信息，以及可选的执行参数。接收端不在请求链路内等待模型推理完成，而是在持久化存储中原子写入一条任务账本记录后立即返回“已接收”确认，确认中携带任务标识、当前状态和后续查询地址或查询方法。

任务账本以调用方身份和幂等键形成唯一约束，并记录任务输入摘要、目标会话、对应的对话消息标识、执行阶段、请求时间、更新时间、重试计数、取消标记和清理期限。接收新请求时，系统先按唯一约束查找既有任务；若已存在且输入摘要一致，则直接返回既有任务标识和状态，不再次向对话历史写入用户消息，也不再次排入推理执行；若幂等键相同但输入摘要不一致，则返回冲突状态，避免把同一外部任务错误映射为不同对话内容。该处理使网络超时、调用方重试或响应丢失不会造成重复用户输入和重复模型执行。

在一种实现中，任务账本与对话消息持久化在同一 Agent 的 SQLite 存储中，或者由负责会话目录的父 Agent 保存任务索引、由具体会话 Agent 保存消息与执行状态。用户输入写入采用稳定消息标识，并在账本中保存该消息标识与任务标识的映射；消息追加采用“按标识插入或忽略”的方式，或在写入前检查账本阶段，从而保证同一任务最多生成一条用户输入消息。

### 异步执行与状态推进

任务被接收后进入异步执行通道。系统可以通过 Agent 的队列、调度回调或内部 RPC 唤醒目标会话 Agent，并在执行前调用会话稳定性检测，确认不存在正在流式输出的模型调用、等待客户端工具结果或审批的交互、以及尚未完成的自动续写任务。若会话尚不稳定，任务保持为待执行或延后状态并记录下一次检查时间；若会话稳定，系统以函数式消息追加方式读取最新持久化对话历史，在此基础上注入与该任务对应的用户消息并触发程序化对话轮次。

对话轮次执行采用串行化的 turn 队列管理。无论任务来源是浏览器对话、webhook、RPC 还是定时任务，同一会话内的模型推理均按队列顺序进入执行区，并在进入、写入用户消息、开始模型调用、产生流式片段、最终持久化助手消息和触发响应回调时更新任务阶段。任务状态可包括已接收、等待会话稳定、已排队、运行中、等待外部交互、已完成、已取消、失败、已清理等；查询接口只读取账本和消息存储即可返回状态、结果摘要、错误原因、创建时间和更新时间，不需要依赖仍然存在的网络连接。

程序化对话轮次复用现有对话 Agent 的消息持久化和流式响应机制。模型输出片段在生成过程中写入可恢复的流式缓冲区，并在轮次完成后形成最终助手消息；响应完成钩子根据请求标识或消息标识回填任务账本。由于外部提交方在接收确认后不保持长连接，系统不要求将流式片段实时返回给提交方，但可将片段用于客户端恢复、审计或任务结果重建；外部系统后续通过查询获得最终结果，或通过回调通知获得完成事件。

### 恢复一致性、取消与清理

为应对 Agent 休眠、重启或执行中断，本方案将任务阶段、消息标识、流式片段和恢复上下文作为可持久化状态保存。Agent 重新激活时先扫描非终态任务，并结合账本阶段、对话消息是否已写入、是否存在活动或遗留的流式缓冲、以及是否存在可恢复的执行纤程来判定任务所处阶段：未写入消息的任务重新进入待执行；已写入用户消息但未生成助手消息的任务进入恢复执行；已存在完整助手消息的任务标记为已完成；存在部分助手输出的任务先持久化部分结果，再按恢复策略决定是否继续补全。

恢复执行采用带目标消息保护的续写机制。系统在恢复上下文中保存原始请求体、请求标识、目标助手消息标识、部分文本或消息片段、创建时间和调用方关联数据；恢复时仅当当前对话最后状态仍与该目标消息匹配，且任务未被取消或清理，才调度一次续写。若任务已超过允许恢复窗口、重复恢复次数超过阈值，或当前对话已经被新的用户输入推进，则系统停止自动续写并将任务标记为需人工或调用方处理的失败/部分完成状态，以避免旧任务在恢复后覆盖新的对话进展。

取消和清理同样以任务账本为准。外部调用方取消任务时，系统将任务标记为取消中或已取消：若任务尚未进入执行队列，则直接阻止后续消息写入；若任务已排队但未运行，则从队列或调度表中移除；若任务正在运行，则触发与该任务绑定的中止控制器，使模型调用沿对话取消路径停止，并保留已持久化的部分片段以供审计或查询。对于已完成、失败或已取消且超过保留期限的任务，清理操作删除任务账本、临时流式缓冲和外部关联数据，但可按配置保留正式对话消息，或者在任务级会话场景下连同对应会话数据一并删除。
