## 技术方案

### 总体构思与执行记录对象

本方案在现有智能工作台的任务、agent、会话、事件、质量评审和工具入口之上增加“agent 运行记录”对象，而不是另建人工日志。每一次由任务分派、会话消息、流水线步骤、外部工具调用或定时调度触发的 agent 执行，均被归一化为一条可寻址的运行记录。该记录以运行标识为主键，同时保存触发来源、执行 agent、关联任务、关联会话、输入摘要、输出结果、执行状态、时间区间、模型或网关信息、令牌或耗时消耗、评估状态以及扩展元数据，使系统能够围绕一次具体执行回答“从哪里来、由谁做、做了什么、结果如何、消耗多少、是否被评估、如何被再次查询”。

运行记录对象与现有数据实体形成引用关系：其 agent 字段优先绑定 agents 表中的 agent 名称或标识，并保留 gateway agent id、session_key、角色和配置快照摘要；其任务字段绑定 tasks 表中的任务标识、项目票号、状态和优先级；其会话字段绑定 agent 返回的 sessionId、聊天 conversation_id 或外部 Claude Code 任务标识；其事件字段记录与 eventBus、activities、audit_log 对应的事件类型和时间戳。这样，运行记录既可以作为一次执行的中心索引，也不会替代既有任务状态、活动流、审计日志或质量评审表。

在一种实现中，运行记录包括两层结构。第一层为稳定索引层，保存 run_id、workspace_id、trigger_type、trigger_id、agent_id 或 agent_name、task_id、conversation_id、session_id、status、started_at、completed_at 等字段，并对 workspace_id、agent、task、session、status 和时间建立索引。第二层为可扩展载荷层，以 JSON 保存触发参数摘要、模型路由结果、网关调用参数哈希、输出摘要、错误摘要、评估摘要、外部系统引用和版本信息。稳定索引层保证查询和关联效率，可扩展载荷层保证后续接入排行榜、评测框架、外部工具或不同 agent 网关时不需要反复改造主业务表。

### 采集、归一化与关联写入流程

执行采集流程设置在现有分派链路的入口和出口处。入口侧，当任务从 assigned 状态被调度给 agent、聊天消息触发 agent、流水线步骤调用 agent 或外部 MCP/CLI 工具创建任务时，系统先根据触发上下文生成或复用幂等键，并创建 pending 或 running 状态的运行记录。幂等键可以由触发类型、任务标识、agent 标识、会话标识、重试次数和时间窗口组合得到，用于避免同一分派在网关重试、页面刷新或调度器重复扫描时生成多条不一致记录。

运行期间，分派模块将已有的任务提示构造、模型复杂度分类、agent 配置解析、OpenClaw 网关调用或直连模型调用视为同一次运行的执行阶段。系统在阶段边界写入结构化事件，例如 prompt_built、model_selected、gateway_invoked、response_received、task_updated、review_requested 等，并把事件追加到运行记录的事件列表或从属事件表。阶段事件仅记录必要摘要、哈希、状态和引用，不直接保存敏感凭据或完整长上下文；对需要复盘的输入输出，可保存截断摘要、内容哈希和外部存储引用，从而兼顾审计可追溯性与安全边界。

出口侧，系统从 agent 响应中提取文本结果、sessionId、错误信息、模型使用量和完成时间，并同步更新运行记录和既有业务实体。若 agent 成功返回结果，则将输出摘要、任务 resolution、完成状态、completed_at、关联会话和 token_usage 的 session_id 写入同一运行记录；若调用失败或超时，则写入失败状态、错误类别、可重试标识和已发生的阶段事件；若进入质量评审，则将运行记录状态标记为 awaiting_review，并在任务状态、活动流和服务端事件中继续广播现有的状态变化。

### 评估附着、成本估算与复用查询

评估附着机制以运行记录为评估对象，以现有 quality_reviews 表和 Aegis 评审流程为事实来源。当任务进入 review 或 quality_review 状态时，系统把待评估的 run_id 传递给评审流程；评审完成后，将 reviewer、评估结论、评估说明、评估时间、重试轮次和评估引用写回运行记录，同时仍保留 quality_reviews 中面向任务的评审记录。由此，一个任务多次被 agent 重做时，每一次运行都可以拥有独立评估结果，排行榜或质量分析可以区分“任务最终通过”和“某次 agent 执行质量”。

成本估算机制复用 token_usage、模型路由结果和运行时间信息。对于直连模型调用，系统将输入令牌、输出令牌、模型标识和 session_id 写入 token_usage，并用 run_id 关联该条用量；对于网关调用，系统从网关返回、代理诊断或补充上报中取得模型、耗时、令牌和估算费用，无法取得精确费用时至少记录调用时长、模型档位、请求次数和估算标记。运行记录中的成本字段采用“已确认值 + 估算值 + 估算依据”的形式，避免把不完整数据误表示为精确账单。

查询与复用机制在现有 REST API、MCP server 和活动流之上提供运行记录查询入口。内部页面可按 agent、任务、会话、触发来源、状态、评估结论、时间窗口和项目票号过滤运行记录；外部工具可通过 MCP 工具或 REST 接口查询单次运行详情、某 agent 的运行列表、某任务的多次尝试、某会话产生的执行链路以及可复用结果摘要。查询返回对象以 run_id 为中心，并包含跳转到任务、agent、会话、活动、审计日志和评审记录的引用，使外部系统能够复用执行结果而不需要解析零散日志。

为了支撑审计和外部集成，运行记录的访问控制沿用工作台的 workspace_id 和角色权限。普通 agent 默认只能查询自身运行或被授权任务的运行；管理员可以按审计场景查询跨 agent 记录；对外部 webhook、MCP 或集成接口输出时，可按字段级策略隐藏 session_key、完整提示词、密钥、内部路径等敏感信息，只暴露结构化引用、摘要和状态。该机制使运行沉淀成为现有执行体系的可查询索引层，并为质量评测、排行榜、运行审计和工具复用提供统一数据基础。
