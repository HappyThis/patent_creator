## 技术方案

### 总体构思与运行记录模型

本方案在现有智能工作台的任务、agent、会话、事件、质量评审和工具入口之上增加统一的 agent 运行记录层。该运行记录层不替代原有任务看板、agent 心跳、会话列表、token 用量、活动流或质量评审表，而是在每次 agent 执行开始、状态变化、产出提交、评审完成和成本统计时形成同一运行标识下的结构化索引，使一次 agent 工作可以被稳定追溯为“触发来源—执行主体—关联任务或会话—过程事件—结果产物—成本消耗—评估结论”的闭环对象。

运行记录可以采用独立的运行主表及若干明细表实现，也可以先以任务 metadata、活动流 data、token_usage、quality_reviews 和 eval_runs 的扩展字段实现，再通过迁移固化为独立表。运行主表至少保存运行标识、工作区标识、触发类型、触发者、agent 标识、任务标识、会话标识、网关或工具来源、开始时间、结束时间、运行状态、产出摘要、结果引用、错误摘要和可扩展元数据；明细表或事件明细至少保存事件类型、事件时间、输入摘要、输出摘要、状态迁移、外部调用引用和幂等键。通过运行标识把既有分散记录连接起来，可以避免仅靠人工日志描述执行过程，也使后续统计、审计和外部查询具有稳定主键。

运行记录的核心技术构思是将“任务生命周期”和“agent 执行生命周期”解耦但关联：任务描述要做什么，运行记录描述某个 agent 在某次触发下如何执行。一个任务可以关联多次运行，例如重试、多人接力、质量评审驳回后的再执行；一次运行也可以关联一个会话、一次 CLI/MCP 工具调用或一次网关派发事件。这样既保留现有任务状态字段用于看板流转，又能精确回答单次执行的来源、主体、产物和消耗，避免把多轮执行混杂在同一个任务状态或评论中。

### 执行触发与过程采集

在执行触发阶段，系统在现有任务队列领取、任务创建或更新、agent 唤醒、会话接入、命令行工具调用和外部网关派发等入口统一调用运行记录创建过程。创建过程先解析工作区、agent 名称、任务编号、会话键、触发接口、请求操作者和上游幂等键；若检测到同一任务、同一 agent、同一会话或同一幂等键已经存在未结束运行，则复用该运行记录并补充触发事件，否则生成新的运行标识并写入运行主表。该机制使系统既能记录从看板派发的工作，也能记录由 CLI、MCP、Webhook 或网关直接触发的工作。

在执行过程中，系统复用现有活动流和实时事件总线，在任务状态从 inbox 或 assigned 进入 in_progress、agent 心跳携带 last_activity、任务字段发生变更、评论或结果写入、会话 token 数据产生、质量评审提交等节点写入运行事件。每条运行事件都带有运行标识、事件来源、事件类型、发生时间、操作者、关联实体和简化负载；简化负载只保留可审计和可复用的摘要、引用、哈希或结构化字段，避免把完整上下文、敏感密钥或过长模型输入输出无边界写入数据库。

当任务进入 review、quality_review、done、failed 或被驳回回到 in_progress 时，运行记录根据状态迁移和结果字段更新结束状态。若任务被 Aegis 等质量门控批准，运行记录标记为已评估且通过；若评审驳回，则将本次运行标记为未通过并记录驳回说明的引用，同时允许后续重新执行产生新的运行记录。对于没有任务编号的会话型执行，系统可以在会话关闭、agent 心跳超时或外部工具显式提交结果时关闭运行记录，并以会话摘要或结果引用作为产出。

### 评估附着与成本归因

本方案将评估结果附着在运行记录而非仅附着在 agent 维度。现有 eval_runs 可以继续保存 output、trace、component、drift 等分层评估结果，新增或扩展字段记录运行标识、任务标识、评估触发方式、评估版本、评估集名称、评分、是否通过和评估详情摘要。对于任务质量评审，quality_reviews 的 task_id 与运行标识建立映射，使人工评审、Aegis 门控评审和自动评测都能归入同一次执行。由此，排行榜可以按 agent 聚合多个运行的得分、通过率、返工率和漂移情况，而审计查询仍能下钻到具体一次运行。

成本归因采用“会话用量归集、任务用量校正、运行用量聚合”的方式实现。系统沿用 token_usage 中的模型、session_id、input_tokens、output_tokens、task_id、workspace_id 和 created_at 字段，并在写入或归集时补充运行标识；当 session_id 形如 agent:chatType 或等于 agent 名称时，先按会话识别执行主体，再结合任务队列领取、任务状态更新时间和 task_id 索引判断该用量属于哪一次运行。对于同一任务下多次执行的场景，按运行开始和结束时间窗口分摊 token 记录；不能可靠归属的用量保留为未归因项，以避免把成本错误计入某次运行。

运行记录还保存成本快照字段，例如请求次数、输入 token、输出 token、估算费用、主要模型、耗时区间和未归因比例。成本快照可由明细记录周期性重算，也可在运行结束时一次性固化；当模型价格表或订阅折扣变化时，系统保留原始 token 数据和价格版本，以便在需要时重算不同统计口径。通过运行级成本快照，系统能够在不扫描全部会话日志的情况下支持任务成本、agent 成本、项目成本和排行榜成本指标。

### 查询复用与权限边界

查询复用层在现有 REST、CLI 和 MCP 工具入口上提供运行记录查询能力。查询条件包括运行标识、agent、任务、会话、工作区、触发来源、运行状态、是否通过评估、时间范围、模型和成本区间；返回结果分为摘要和详情两级，摘要用于列表、排行榜和外部系统同步，详情用于审计和调试。详情中包含时间线事件、关联任务、关联会话、产物引用、评审引用、成本统计和可追踪的活动流引用，但对密钥、完整会话内容和敏感 payload 采用脱敏、裁剪或仅返回引用的方式。

为保持与现有执行体系一致，运行记录写入过程优先挂接在已有 mutation 路径上：任务队列原子领取后写入运行开始事件，任务更新接口记录字段变化和状态迁移，agent 心跳记录活跃状态和用量片段，质量评审接口记录评估结论，事件总线继续向前端和 webhook 推送变更。这样外部工具通过 MCP 或 CLI 查询运行记录时，看到的是系统真实执行过程的结构化投影，而不是另起一套由人工维护的日志。

权限边界采用工作区隔离和自我归因优先原则。普通 agent 或操作者默认只能查询本工作区且与自身相关的运行记录；管理员可以在显式特权参数下查询跨 agent 的运行审计；外部系统只能通过 API key、会话 cookie 或受控 MCP 工具访问授权范围内的摘要或脱敏详情。通过对运行记录建立 workspace_id、agent、task_id、session_id、created_at 和 status 等索引，可以在保持权限过滤的同时支持高频查询、排行榜聚合、质量评测回放和外部系统增量同步。
