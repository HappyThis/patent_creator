## 技术方案

本方案在现有基于 Durable Object 的有状态 agent 会话能力之上，增加面向外部系统的一次性对话任务接入层。外部系统可以通过 webhook、RPC 或其他程序化接口提交任务，请求到达后先完成任务登记、幂等判断和状态初始化，并立即返回已接收结果及 $taskId$，实际消息写入、模型推理、流式输出和后处理在同一会话所属的持久执行环境中异步推进。整个方案以 $taskId$ 作为外部请求、会话消息、异步执行、查询、取消、清理和恢复判定的统一关联键，避免外部重试、运行环境休眠或执行中断导致同一用户输入被重复写入或同一推理任务被重复启动。

### 外部任务接收与幂等登记

外部接入层接收请求后，不直接等待对话模型完成，而是先在任务所属 agent 实例的持久存储中设置外部任务账本。账本以调用方提供的幂等键、或由规范化后的请求体、会话标识和调用方标识计算得到的摘要作为候选键；系统据此生成稳定的 $taskId$，并在同一事务内执行“插入新任务或读取既有任务”的登记动作。若相同幂等键已经存在，则返回原 $taskId$ 和当前状态，不追加新的用户消息，也不再次创建异步执行单元；若不存在，则写入任务元数据并返回已接收确认。

任务账本至少记录 $taskId$、外部幂等键、会话或 agent 标识、规范化请求摘要、待写入的用户消息标识、程序化对话请求标识、执行状态、创建时间、更新时间、取消标记、清理标记、最近检查点和错误信息。用户消息标识可以由 $taskId$ 派生，也可以由调用方传入但需与幂等键绑定。消息持久化阶段采用按消息标识幂等插入的方式：用户消息只在不存在时写入，已经存在时保持原内容；助手消息或流式片段则允许按请求标识增量更新。由此，即使外部调用方因 HTTP 超时、RPC 响应丢失或网络重传再次提交相同任务，系统仍只保留一条权威用户输入。

### 异步对话执行与状态推进

登记成功的新任务不在外部请求线程中直接执行模型推理，而是由任务所属的持久 agent 实例启动异步执行单元。异步执行单元读取任务账本中的规范化输入，先将用户消息按预设消息标识写入会话消息表，再调用程序化对话入口触发一轮对话处理。程序化入口可以采用从最新会话转录派生消息的方式启动，以避免任务登记时和实际执行时之间会话状态发生变化造成上下文丢失；也可以在执行前检测当前会话是否存在等待工具输入、审批或其他交互状态，并将任务保持在等待状态，直至满足继续条件。

任务状态由任务账本统一推进，可以包括已接收、消息已持久化、排队中、运行中、等待交互、已完成、失败、已取消、中断和已清理等状态；具体命名可按工程实现调整，但每个状态均应对应明确的进入条件和退出条件。异步执行单元在关键边界处更新状态和检查点，例如消息写入完成后记录 $messageId$，对话入口返回后记录内部 $requestId$ 及完成状态，流式片段或部分结果持久化后记录最近输出位置，异常捕获后记录错误类型和可重试性。终态状态一旦写入，后续重复启动、重复查询或重复取消只读取并返回该终态，不再触发新的模型推理。

在一种实现中，异步执行单元使用持久 fiber 机制登记正在执行的任务，并在执行期间持有防休眠资源；同时通过检查点接口把 $taskId$、消息写入阶段、内部请求标识、已输出片段位置和最近状态写入 fiber 快照或任务账本。该执行单元可以采用 fire-and-forget 模式启动，使外部接收接口仅承担可靠登记和调度职责。若对话程序化入口返回完成、跳过或取消等结果，执行单元将结果转换为任务账本中的终态或可恢复状态，并释放与该任务关联的临时控制资源。

### 任务查询、取消与清理

查询接口以 $taskId$ 为索引只读取任务账本和必要的会话输出，不直接观察内存中的执行对象。查询结果至少包括当前状态、是否为终态、创建时间、更新时间、内部请求标识、已持久化的用户消息标识、可展示的部分输出或最终输出摘要、错误信息以及下一步可执行动作。由于查询依据持久账本而非长连接状态，同一任务可在外部请求响应丢失、客户端刷新、agent 休眠后唤醒或服务实例迁移后继续被定位和观察。

取消接口同样围绕 $taskId$ 幂等工作。系统接收到取消请求后，先在任务账本中写入 $cancelRequested$、取消原因和取消时间；若任务尚未开始，则将其标记为已取消并阻止后续执行；若任务已经运行，则在任务所属 Durable Object 内部构造或查找与该任务关联的取消控制器，触发对话程序化入口的取消信号或内部请求取消方法，使推理循环停止并保留已经持久化的部分片段。取消请求不依赖跨 Durable Object 传递原始 $AbortSignal$，而是以持久化的取消意图作为恢复后仍可识别的控制事实。

清理接口用于释放已完成或不再需要观察的任务保留数据。清理时先判断任务是否处于已完成、失败、已取消或中断等终态；对于终态任务，可以删除任务与流式片段、临时映射、保留子任务或执行索引之间的关联，并将状态推进为已清理或删除账本行。对于仍处于排队中或运行中的任务，清理接口应先执行幂等取消，再在取消结果落入终态后清理。重复清理同一任务只返回已清理结果，不抛出重复删除错误，也不会重新影响会话消息中已经作为历史事实保留的用户输入。

### 休眠、重启和中断后的恢复一致性

当 agent 运行环境因空闲休眠、重启或运行时异常导致异步执行中断时，恢复逻辑不以进程内活动集合为准，而以持久存储中的任务账本、持久 fiber 残留记录、消息表、流式片段和终态标记为权威依据。恢复扫描发现某个 fiber 残留记录或某个任务处于非终态时，先读取其 $taskId$ 和检查点，再判断该任务已经完成、已取消、仅完成消息写入、正在模型推理、等待外部交互，还是已经超过安全恢复窗口。不同阶段采用不同恢复动作，避免简单地重新提交整轮请求。

若恢复时发现用户消息已经按 $messageId$ 写入而助手响应尚未形成终态，则系统不再重复插入该用户消息，而是根据已保存的内部请求标识、部分输出片段和恢复时间选择继续最后一轮对话、保留部分回复并安排 continuation，或将任务标记为中断待人工或上层系统决策。若任务账本已经处于已完成、失败或已取消等终态，即使还存在过期 fiber 记录，也以任务终态为准并清理遗留执行索引。若恢复时检测到 $cancelRequested$ 已写入，则优先执行取消收敛，防止环境重启后继续处理一个已被外部系统取消的任务。

为保证恢复过程本身不产生并发冲突，恢复扫描设置互斥标记，并在处理单个任务时使用 $taskId$ 或任务行版本进行条件更新：只有当任务仍处于预期非终态时才推进状态，若其他请求已经完成、取消或清理该任务，则当前恢复分支停止。通过上述规则，外部提交、异步执行、取消、查询、清理和恢复均围绕同一持久任务事实收敛，使系统能够向外部调用方提供快速接收、可观察、可取消、可清理且可从中断中一致恢复的一次性对话任务处理能力。
