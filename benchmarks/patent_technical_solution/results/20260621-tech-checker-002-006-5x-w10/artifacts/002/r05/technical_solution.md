## 技术方案

### 外部任务接收与幂等登记

本方案在既有对话式 agent 之外设置面向外部系统的任务提交入口。该入口可以表现为 webhook、HTTP/RPC 调用或其他程序化调用形式，接收调用方标识、目标会话或实体标识、用户输入内容、可选的请求体上下文以及外部幂等键。入口收到请求后，先依据目标会话或实体标识路由到对应的 agent 实例，使同一会话的外部任务、已有对话消息和后续模型推理在同一持久化执行环境中处理，避免多个执行环境并发修改同一份对话状态。

在 agent 的持久化存储中设置外部任务登记记录，用于保存任务标识、调用方标识、幂等键、目标会话、输入消息标识、当前状态、创建时间、更新时间以及与后续执行相关的请求标识。任务提交阶段采用“先登记、后执行”的顺序：系统基于调用方标识与外部幂等键形成唯一约束，或在调用方未提供幂等键时基于规范化后的请求内容生成稳定键；登记时采用忽略重复插入或等效的原子写入方式。若登记成功，则立即返回任务标识和“已接收”状态；若检测到重复提交，则读取已存在的登记记录并返回同一任务标识及其当前状态，而不再次追加用户输入，也不再次启动模型推理。

上述快速确认响应只表示任务已被可靠接收和持久化登记，不表示对话推理已经完成。通过把接收确认与推理执行解耦，外部调用方不需要在一次网络请求中等待大模型输出，系统也可以在后续通过持久化队列、调度任务或对话 turn 队列继续处理该任务。登记记录成为外部请求与内部对话执行之间的权威连接点，用于后续查询、取消、清理和恢复判定。

### 任务状态机与异步执行控制

任务登记后进入可持久化的状态机。状态机至少区分已接收、已入队、运行中、等待外部交互、已完成、失败、已取消和已清理等阶段，并记录每次状态变化的时间与触发原因。任务记录还可以关联对话消息标识、模型请求标识、流式输出标识、队列项标识或持久化执行标识，使系统能够从外部任务追踪到内部对话 turn、用户消息、assistant 回复和执行上下文。

在异步执行阶段，系统将已登记任务投递到 agent 内部队列或对话 turn 队列，由该队列串行化处理同一会话中的外部提交、浏览器对话、工具继续执行和程序化消息保存。执行器在真正写入用户输入前，可以等待当前对话进入稳定状态；若存在正在生成的回复、待处理的工具交互或排队的 continuation，则延后外部任务写入，直至对话上下文可安全读取和修改。这样可以避免外部任务插入到未完成 turn 的中间位置，降低 transcript 基线陈旧导致的消息错序。

用户输入写入采用稳定消息标识进行幂等追加。例如，外部任务的任务标识或幂等键可以映射为用户消息标识，写入时使用唯一约束和忽略重复插入的方式；assistant 的流式回复则使用与该 turn 绑定的回复标识进行追加或冲突更新，以便在流式片段陆续到达时构建同一条回复。若同一外部任务因超时或网络异常被重复提交，任务登记和消息写入两个层面都会命中同一稳定标识，从而不会出现重复用户消息或重复模型调用。

为防止清空会话或重置 turn 后的旧任务误写入新上下文，执行器在入队和执行时可携带会话代际标识或目标 assistant 回复标识等保护条件。若任务开始执行时发现当前会话代际已变化、目标回复已不存在，或任务状态已经变为取消、清理等终态，则该任务不再写入消息或启动模型推理，而是转为跳过、已取消或需要人工处理的状态。

### 状态查询、取消与清理

外部调用方可以通过任务标识查询任务状态。查询结果以任务登记记录为准，返回当前阶段、是否已经写入用户输入、是否正在模型推理、是否等待工具或外部交互、终态结果摘要、错误类别以及可选的对话消息引用。由于状态来自持久化记录，即使原始提交请求已经结束，调用方仍可在后续请求中获得一致的任务进度。

取消请求采用“先记录取消意图、再传播中止信号”的处理方式。系统收到取消请求后，首先在任务记录中写入取消状态或取消待处理状态，并检查任务是否已经处于完成、失败、已取消或已清理等终态；若任务仍处于未执行、排队或运行阶段，则尝试从队列中跳过该任务，或向正在执行的请求传播中止信号，使模型调用、工具调用或流式输出尽快停止。若执行侧稍后返回结果，状态更新仍需检查任务是否已经进入终态，避免迟到的完成事件覆盖取消结果。

清理操作区分终态任务和非终态任务。对于已完成、失败或已取消的任务，可以根据保留窗口删除明细、保留摘要或标记为已清理；对于仍处于排队、运行或等待交互阶段的任务，系统先执行取消或跳过处理，再清理其队列项、流式缓存、临时请求上下文和可删除的任务明细。通过这种顺序，清理不会留下孤立的模型执行或与外部任务记录失联的对话片段。

### 休眠、重启后的恢复一致性

agent 运行环境可能因空闲休眠、运行时重启、代码更新或长时间处理被中断。为使外部任务在恢复后保持一致，本方案将任务登记、消息写入、队列项、执行检查点和流式输出片段均作为可持久化状态处理。执行过程中在关键边界写入检查点，例如已登记但未入队、已入队但未写消息、用户消息已写入但模型尚未开始、模型已开始并产生部分输出、等待工具或外部交互、已经到达终态等。

当 agent 被重新激活时，恢复逻辑扫描未到达终态的任务登记记录，并结合对话消息表、持久化队列、调度记录、执行 fiber 记录和可恢复流缓存判断任务所处阶段。若任务只有登记记录而没有队列项，则补充入队；若用户消息已经存在但模型未开始，则继续启动对应 turn；若模型执行中断但存在目标 assistant 回复和部分流式片段，则在同一回复标识下继续或补偿完成；若任务处于等待工具或外部交互阶段，则保持等待状态并向查询接口暴露该阶段；若恢复数据过旧或连续失败达到阈值，则转为失败或需人工处理状态。

恢复执行同样遵循幂等规则。补充入队、恢复 continuation 或重新触发执行时，使用任务标识、目标回复标识和恢复载荷作为去重依据；写入用户消息时仍使用稳定消息标识；写入 assistant 回复时仍更新同一回复记录。恢复逻辑在每一步状态迁移前检查任务是否已经被取消、清理或完成，防止重启后的迟到恢复把已终止任务重新拉起。

### 可选实施方式与边界

在一种实现中，外部提交入口可以与已有对话入口共用同一 agent 实例和同一持久化对话存储，但外部任务登记表作为独立索引层存在；这样既能复用已有消息持久化、流式回复、取消和恢复能力，又能为外部调用方提供任务级状态语义。在另一种实现中，不同外部系统或租户可以按调用方、实体或会话维度路由到不同 agent 实例，以隔离状态、权限和执行队列。

幂等键可以由外部调用方显式提供，也可以由系统根据调用方、目标会话、规范化输入内容和业务时间窗口计算得到。显式幂等键更适合外部系统能够稳定生成业务事件编号的场景；内容派生键更适合调用方无法提供稳定编号但请求体可以规范化的场景。为避免不同业务事件被过度合并，内容派生键应限定在同一调用方和同一目标会话内，并结合可配置的时间窗口或事件类型。

任务状态的保留期限、可查询字段、失败重试次数、恢复过期阈值和清理策略可以按业务场景配置。对于需要审计的场景，可以保留任务摘要、状态迁移历史和对话消息引用；对于只需短期回查的场景，可以在任务达到终态并超过保留窗口后删除明细。上述配置不改变本方案的核心机制，即外部任务先持久化登记并快速确认，再由同一 agent 按幂等、可取消和可恢复的方式异步推进对话执行。
