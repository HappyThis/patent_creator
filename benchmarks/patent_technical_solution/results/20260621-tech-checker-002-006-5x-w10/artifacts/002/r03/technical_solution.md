## 技术方案

### 总体构思

本方案在现有对话式 agent 处理链路之前增加“外部对话任务”层，将来自 webhook、RPC、HTTP 或其他程序化入口的请求统一转换为可持久化、可查询、可取消、可恢复的任务记录。外部调用方提交请求时，系统先完成身份或来源校验、目标 agent 定位、输入载荷规范化和幂等登记，并立即返回“已接收”的确认信息；模型推理、工具调用和消息流式输出等耗时处理不阻塞外部提交接口。

外部对话任务层与 agent 对话执行层之间通过持久状态、队列、定时唤醒或可恢复执行上下文衔接。任务层负责记录一次外部提交从接收、排队、执行、取消到终态清理的生命周期；对话执行层仍使用既有的消息持久化、程序化对话轮次、可恢复流以及按请求标识取消的能力。二者解耦后，系统能够在外部调用方超时重试、agent 休眠、运行时重启或推理中断时，依据持久化任务事实判断下一步动作，而不是依赖瞬时内存状态。

### 外部任务接收与幂等登记

外部入口接收到请求后，将不同传输方式下的输入统一整理为任务描述。任务描述可以包括调用方标识、目标 agent 标识、会话或租户上下文、待追加的用户消息、请求体中的扩展参数、期望的回调或查询方式，以及由调用方提供或由系统派生的幂等键。幂等键可以由外部请求编号、webhook 事件编号、业务单据编号、请求摘要与目标 agent 的组合等形成，用于表示同一外部意图。

系统在 agent 的持久存储中以原子方式登记任务记录，并对目标 agent 标识与幂等键建立唯一约束或等价的条件写入规则。若登记成功，任务进入已接收状态，并生成内部任务标识返回给调用方；若发现相同幂等键已存在，则不再追加用户消息、不再新建后台执行，而是返回既有任务标识及其当前状态。这样，即使外部系统因网络异常、超时或未收到确认而重复提交，也只会形成一个可追踪的任务事实。

登记阶段不直接执行模型推理，而是只保存足以恢复执行的最小闭环数据，包括规范化后的用户输入、外部上下文、幂等键、创建时间、当前状态、取消标记、关联的队列或可恢复执行标识，以及后续对话轮次的请求标识占位。该记录既是快速确认的依据，也是查询、取消、恢复和清理的统一事实来源。

### 异步执行调度与任务状态机

任务登记完成后，系统将该任务投入后台执行通道。后台执行通道可以由 agent 内置队列、基于 alarm 的定时唤醒、可恢复执行纤程或等价机制实现，其共同要求是任务入口、任务载荷和执行进度均可持久化，且 agent 在休眠或重启后能够重新发现尚未终结的任务。外部提交接口只等待任务已可靠登记和调度，不等待对话轮次完成。

任务状态机至少区分接收、排队、运行、正在取消、已取消、已完成、失败和待清理等阶段。接收阶段表示外部请求已经通过校验并持久化；排队阶段表示任务等待后台执行器领取；运行阶段表示已开始写入对话输入或触发 agent 对话轮次；正在取消阶段表示调用方已经发出取消意图但执行器尚未确认终止；已取消、已完成和失败为终态；待清理阶段用于保留终态结果一段时间后删除中间记录或流缓存。各状态转换均以持久任务记录为准，避免多个入口同时处理同一任务。

后台执行器领取任务时，先通过条件更新将任务从排队状态推进到运行状态，并写入执行开始时间、执行尝试次数和本次执行的关联标识。若条件更新失败，说明任务已被其他执行器处理、已取消或已进入终态，本次领取直接退出。该机制使队列重试、alarm 唤醒、手动恢复和重复提交触发的多个执行机会在同一任务记录上收敛，而不会并行驱动多个相同对话轮次。

### 对话输入写入与 agent 执行衔接

执行器在进入运行阶段后，将外部任务转换为一次程序化对话轮次。对于基于 AIChatAgent 的实现，执行器可以调用保存消息并继续对话的程序化入口；对于其他 agent 实现，执行器可以调用等价的内部方法。关键约束是：只有当任务记录表明该外部输入尚未写入对话历史时，才执行用户消息追加；写入成功后立即在任务记录中保存对话轮次的请求标识、消息写入标记和必要的请求上下文。

对话输入写入与模型执行之间采用“先持久化输入、再触发推理、再记录终态”的顺序。外部请求体中的业务上下文可以作为本次对话轮次的附加 body 持久化，使工具调用、续接执行和恢复处理能够读取同一上下文。模型流式响应、部分输出、工具审批状态或 assistant 消息由既有对话持久化机制保存；任务记录只保存与外部任务管理相关的关联信息和摘要状态，不重复承担完整聊天记录存储。

若程序化对话入口返回已完成、已跳过或已中止等结果，执行器据此更新任务终态；若执行过程中发生可重试异常，则保留任务、执行尝试次数和最近错误信息，并由队列重试或后续唤醒再次处理；若发生不可重试异常，则将任务标记为失败并保留错误摘要。由于用户输入是否已经写入、对话请求标识是否已经生成、对话结果是否终态均分别记录，恢复时可以按阶段精确续接，而不是从头重复执行。

### 状态查询、取消与清理

系统向外部调用方提供基于内部任务标识或幂等键的状态查询能力。查询时读取任务记录，并结合关联的对话请求标识、流式响应元数据、assistant 结果消息和错误摘要，返回任务是否已接收、是否正在执行、是否已经完成、是否被取消、是否失败以及可用于继续获取结果的引用信息。查询操作只读持久事实，不触发新的消息写入或新的模型推理。

取消操作首先在任务记录中写入取消意图，并按任务所处阶段采取不同动作。对于尚未被执行器领取的任务，可以从队列或定时调度中移除，或在执行器后续领取时因取消标记而跳过；对于已经进入对话轮次的任务，系统通过与请求标识关联的取消控制器或外部 AbortSignal 将取消信号传递给推理循环，使正在生成的响应以中止状态结束。已经持久化的用户消息和部分响应不被回滚，而是作为该任务的中止结果保留。

清理操作只针对已完成、已取消、失败或超过保留期限的任务执行。清理前先确认任务不存在仍在运行的对话请求、未关闭的恢复流或未处理的后台执行记录；清理时可以删除幂等登记以外的中间数据、过期流缓存和临时错误详情，也可以保留幂等键与终态摘要一段时间，便于外部系统在重试窗口内仍能获得一致答复。

### 休眠、重启或中断后的恢复一致性

agent 因空闲休眠、运行时重启、代码更新或长任务中断而重新激活时，恢复处理器扫描持久存储中的非终态外部任务，并同时检查队列记录、定时唤醒记录、可恢复执行快照、对话请求标识、流式响应元数据、已持久化消息和取消标记。恢复处理不以进程内变量为依据，而是以这些持久事实组合判断任务当前阶段。

若任务处于已接收或排队状态且没有对话输入写入标记，恢复处理器重新安排队列或 alarm，使任务进入后台执行；若任务已记录消息写入标记但尚无对话请求标识，恢复处理器先核对对话历史中是否已存在对应外部输入，存在时只补齐关联标识或进入续接处理，不存在时才允许重新写入；若任务已有对话请求标识但结果未终态，恢复处理器调用对话恢复或续接机制，继续处理未完成的 assistant 响应、工具调用或部分流。

若恢复时发现对话层已经产生完成、失败或中止结果，而外部任务记录仍停留在运行或取消中状态，恢复处理器将任务状态补偿为相应终态；若任务存在取消标记，则优先传播取消信号或将未开始的任务标记为已取消；若存在可恢复执行快照，则先从快照恢复已保存的中间进度，再结合对话层持久化结果决定是否继续。通过这种按阶段补偿的恢复方式，系统在重复提交、重复唤醒和执行中断之后仍能保持“同一外部任务只写入一次用户输入、至多驱动一次有效对话轮次、最终状态可查询”的一致性。
