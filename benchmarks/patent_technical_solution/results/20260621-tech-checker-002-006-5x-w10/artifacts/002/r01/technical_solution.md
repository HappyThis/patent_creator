## 技术方案

### 总体技术构思

本方案面向由外部系统程序化提交的单次对话任务，在已有对话 Agent 的持久状态、消息存储、队列或可恢复执行、流式响应缓存等能力之上，增设“外部对话任务台账”作为接收、执行、查询、取消、清理和恢复的共同依据。外部调用方可以通过 webhook、RPC 或其他受控程序入口提交任务；接收端完成鉴权、参数校验和幂等登记后即返回已接收确认，不在同步请求链路中等待模型推理、工具调用或流式生成完成。

外部对话任务台账可以存放在对应 Agent 的持久化存储中，并以外部提交的稳定幂等键为主索引。每条任务记录至少关联目标 Agent 或会话、原始输入或输入摘要、用户消息标识、异步执行标识、当前阶段、取消意图、创建和更新时间、结果或错误摘要等信息。由此，接收接口、后台执行逻辑、状态查询接口以及恢复逻辑均读取同一份权威记录，而不是依赖进程内变量判断任务是否存在或执行到何处。

### 外部提交与幂等接收

外部调用方提交任务时，应携带能够在重试之间保持不变的幂等键，例如调用方生成的请求标识、业务事件标识或运行标识。接收端在完成签名校验、权限校验和请求体解析后，先在持久化存储中对该幂等键执行原子登记：若任务记录不存在，则创建任务记录并把阶段置为已接收；若记录已经存在，则不再次写入用户消息，也不再次启动模型推理，而是返回已有任务标识及其当前阶段。

在首次登记成功的情况下，接收端将外部输入转换为对话系统可识别的用户消息，并使用由任务幂等键派生或与其绑定的消息标识写入消息存储。该写入可采用“存在则忽略”的条件写入方式，使外部系统因超时、网络中断或确认响应丢失而重复提交时，只会复用同一条任务记录和同一条用户消息。随后，接收端把任务放入持久队列或创建可恢复的后台执行单元，并立即向外部调用方返回已接收确认、任务标识和查询入口。

### 异步执行与状态管理

后台执行单元从任务台账读取待执行记录，按照阶段前置条件推进状态。例如，任务可以从已接收进入待执行，再进入执行中、流式生成中、等待工具或审批、已完成、失败、取消中、已取消等阶段。每一次阶段迁移均与任务标识、执行标识和必要的上下文快照一起持久化，且只允许从符合前置条件的阶段迁移到下一阶段，避免并发恢复、重复投递或重复回调导致状态倒退。

对话执行过程中，Agent 可以复用既有消息持久化和可恢复流式输出机制：用户消息作为模型输入的一部分被重新加载，模型生成的增量片段写入流式缓存或消息草稿，最终 assistant 消息在完成后以可覆盖更新的方式落库。对于较长的模型推理、工具调用或多步 Agent 循环，执行单元可以通过可恢复执行机制登记运行记录，并在关键阶段保存检查点；检查点至少包括任务标识、当前对话阶段、已写入的消息或流片段位置、待处理工具结果、取消标记等恢复所需信息。

为避免重复执行，创建队列任务、创建后台运行记录、写入用户消息、持久化 assistant 消息以及将任务转入终态等关键动作均绑定同一任务标识或其派生标识。对于可重试的动作，采用条件插入、冲突更新、状态版本或阶段前置条件控制；对于不可安全重试的动作，先查询台账和执行记录是否已有对应结果，再决定继续、跳过或转入人工可识别的失败状态。

### 查询、取消与清理

状态查询接口以任务台账为入口读取任务当前阶段，并根据需要联查消息存储、流式缓存、队列记录或可恢复执行记录，形成面向外部调用方的权威状态响应。查询结果可以包括任务是否已接收、是否仍在排队、是否正在生成、是否等待工具或审批、是否已完成、是否失败或已取消，以及可返回的结果摘要、错误摘要或后续轮询建议。该状态不依赖提交请求是否仍保持连接，因此适用于外部系统异步轮询或回调后的补偿查询。

取消接口不直接删除任务，而是先在任务台账中写入取消意图并进行条件状态迁移。若任务仍在队列中，则移除对应队列项并将任务转为已取消；若任务正在模型推理、流式生成或工具调用中，则通过与该任务绑定的取消信号中止当前执行，并由执行单元在捕获取消后持久化取消结果；若任务已经完成、失败或已取消，则取消请求保持幂等，不覆盖既有终态。这样可以避免迟到的取消请求把已经完成的任务误改为取消。

清理接口用于释放外部任务关联的保留数据，并同样以任务阶段作为边界。对于已完成、失败或已取消的任务，可以按策略清理临时流片段、保留的子运行记录、过期上下文或任务台账索引；对于仍处于执行中的任务，清理前应先发起取消或拒绝清理请求，避免删除恢复所需的检查点。重复清理同一任务时，如果目标数据已经不存在，应返回清理完成或无须清理，而不是产生新的执行分支。

### 中断恢复与一致性处理

当 Agent 因休眠、重启、平台回收或执行中断而重新激活时，恢复逻辑从持久化任务台账、队列记录、可恢复执行记录、消息存储和流式缓存中重建任务阶段，而不是根据内存中的执行对象推断。若任务处于终态，则恢复逻辑只保留查询和清理能力，不再启动新的模型推理；若任务已接收但尚未入队，则补建队列项或后台执行单元；若任务已入队但未开始执行，则继续等待队列处理；若存在运行记录和检查点，则按检查点进入恢复中或执行中，并由恢复钩子决定继续生成、补偿失败或等待外部工具结果。

对于流式生成已经产生部分输出但尚未形成最终消息的情形，恢复逻辑根据已持久化的流片段、消息草稿和任务检查点确定已对外可见的输出边界。若方案配置为继续执行，则从最近检查点恢复或重新创建后台执行单元，并在追加输出时使用同一 assistant 消息标识或流标识，避免外部系统看到重复回答；若方案配置为保守失败，则将部分输出标记为失败或中断结果，并把任务转入可查询的失败终态。

恢复一致性的核心在于把“是否已经接收、是否已经写入用户消息、是否已经启动执行、是否已经产生可见输出、是否已经进入终态”拆分为可持久化、可条件更新的阶段判断。重复提交、队列重投递、运行恢复和取消清理请求都以这些阶段为前置条件执行，因此即使发生网络超时、请求重放、Agent 休眠或运行中断，也能够保证同一外部任务不会重复写入用户输入，不会无条件重复启动模型推理，并且后续查询能够得到与持久化事实一致的状态。
