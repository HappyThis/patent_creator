## 技术方案

本方案在现有支持对话式触发的 agent 运行环境上，增加面向外部系统的任务化接入机制。外部 webhook、RPC 或其他程序化入口不直接等待模型推理完成，而是将一次外部提交转换为可持久化、可查询、可取消和可恢复的对话任务；接收路径只完成身份与参数校验、幂等判定、任务台账写入和后台执行触发，然后向调用方返回任务标识及“已接收”状态。

### 外部任务接收与幂等任务台账

外部入口接收到请求后，先从请求中取得外部任务标识、幂等键或按规范化后的请求载荷计算得到的摘要，并与调用方标识、目标 agent 标识、会话标识和用户输入内容共同形成任务接收记录。该记录写入 Durable Object 所关联的持久化存储中，可采用 SQLite 表作为任务台账；台账至少保存内部任务标识、外部幂等键、载荷摘要、当前阶段、对话消息写入标记、执行请求标识、创建时间、更新时间以及错误或取消原因。

为避免外部系统因超时或网络异常重复提交而造成重复执行，台账对“调用方标识、目标会话、幂等键或载荷摘要”的组合设置唯一约束。首次提交命中空记录时，系统原子地创建内部任务标识并将阶段置为已接收；重复提交命中已有记录时，系统不再次追加用户消息，也不再次启动模型回合，而是返回同一内部任务标识和该记录的当前阶段。若相同幂等键对应的载荷摘要不一致，则将其判定为幂等冲突并拒绝合并，以防不同任务被错误折叠。

任务接收记录与对话输入写入之间采用同一持久化事实源进行约束：只有当台账阶段表明输入尚未写入时，才允许将外部提交内容转换为用户消息并追加到目标会话；写入成功后同步更新消息标识和输入已写入标记。这样，即使接收请求在返回前中断，恢复流程也能根据台账和消息标识判断是否需要补写输入，避免出现“任务已接收但消息缺失”或“消息已写入但重复追加”的不一致状态。

### 异步对话执行与状态机

任务被接收后，系统通过后台持久执行单元驱动对话回合，而不是在外部请求线程内同步推理。该执行单元可以利用 agent 运行环境中的 `runFiber` 或等价 durable fiber 在 SQLite 中登记运行记录、持有 keep-alive 引用，并通过 `stash` 保存检查点；具体对话回合可通过 `saveMessages` 这类程序化入口注入用户消息并触发模型 turn，从而在没有 WebSocket 客户端连接的情况下完成 webhook 或 RPC 触发的对话处理。

执行过程围绕任务阶段状态机推进。一个任务可以依次经历已接收、输入已持久化、推理运行中、已完成、失败、取消请求、已取消、已清理等阶段；阶段字段与执行请求标识、消息标识和检查点一起持久化。每次进入关键阶段前后均先读取台账当前值并进行条件更新，例如仅允许已接收任务写入输入，仅允许输入已持久化且未取消的任务启动推理，仅允许运行中任务写入完成或失败结果。通过条件更新限定阶段迁移，可防止并发重试、恢复执行和人工取消之间相互覆盖。

在一种实现中，后台执行单元启动后先将外部输入追加为会话中的用户消息，并把该消息标识写回台账；随后调用程序化 turn 入口并记录返回的请求标识和结果状态。当程序化入口返回 completed 时，任务阶段更新为已完成；返回 skipped 时，表示回合在执行前或执行中被更高优先级的会话变更失效，任务记录为未完成但不重复写入输入；返回 aborted 时，任务进入已取消或已中止阶段，并保留已经持久化的部分输出片段供查询或后续恢复判断使用。

### 查询、取消与清理控制

对外查询接口以任务台账为主索引返回任务状态，而不是依赖外部调用方保持长连接。查询时根据内部任务标识或外部幂等键读取阶段、创建时间、更新时间、请求标识、错误原因、取消原因以及可公开的输出引用；对于已完成任务返回最终 assistant 消息或结果引用，对于运行中任务返回当前阶段和可选的部分输出位置，对于失败或中断任务返回可重试或不可重试的原因分类。

取消控制采用“持久化取消意图 + 运行中信号传播”的双层机制。调用方请求取消时，系统先以条件更新方式将非终态任务标记为取消请求，并记录取消原因和时间；若该任务已经启动程序化 turn，则将外部取消意图转换为 `AbortSignal` 或按请求标识调用共享的取消控制器，使推理循环沿与内部 chat-request-cancel 相同的路径中止。对于尚未启动推理的任务，执行单元在启动前读取到取消请求后不再发起模型调用，直接进入已取消阶段。

清理控制只作用于已完成、失败、已取消或明确过期的任务，避免误删仍在运行的执行依据。清理时先检查台账终态和关联运行记录，随后删除或归档幂等索引、取消信号、临时检查点、过期部分流引用等可再生数据；对会话消息和已返回结果则按业务保留策略处理，不因任务清理而破坏对话历史的一致性。清理完成后任务可保留最小墓碑记录，使后续重复提交仍能得到确定响应，而不是被当作全新任务重复执行。

### 中断恢复与一致性判定

agent 运行环境可能因休眠、重启或执行中断而丢失内存状态，因此恢复逻辑不以内存队列作为判断依据，而以任务台账、会话消息、程序化 turn 结果和 durable fiber 运行记录共同确定事实。恢复扫描发现遗留的运行记录或非终态任务时，先读取 fiber 检查点、任务阶段、输入写入标记和已持久化消息，再决定继续、补偿、标记中断或结束，不直接重新执行完整任务。

恢复判定按阶段分层处理：对于已接收但输入未写入的任务，重新执行输入写入和后台启动；对于输入已写入但未记录推理请求的任务，只启动推理而不再追加用户消息；对于存在请求标识、部分输出或 chat recovery 数据的任务，优先调用继续上一回合或恢复处理逻辑，使被中断的 assistant 输出能够接续或被固化为部分结果；对于已经处于完成、失败、已取消或已清理等终态的任务，恢复流程只清除遗留运行记录，不再触发模型推理。

为处理长期未恢复或检查点损坏的情况，恢复流程还可以利用 fiber 创建时间、任务更新时间和调用方配置的超时策略识别陈旧任务。陈旧任务不会被静默重复执行，而是被标记为 interrupted、failed 或等待人工/调用方重试的状态，并通过查询接口暴露原因。通过这种以持久阶段和检查点为准的恢复方式，本方案在外部重复提交、网络超时、agent 休眠唤醒和执行中断并存的情况下，仍能保持“同一外部任务最多写入一次输入、最多启动一次有效推理、终态可查询”的一致性。
