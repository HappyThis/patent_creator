## 技术方案

本方案在既有对话式 agent 处理链路之外，增加面向外部系统的一次性对话任务入口。外部系统可以通过 webhook、RPC 或其他程序化接口提交任务载荷，系统在完成鉴权、参数规范化、幂等登记和必要的输入落库后立即返回“已接收”确认以及可公开使用的任务标识，不要求外部调用方保持连接等待模型推理完成。后续的模型推理、工具调用、消息流持久化、状态推进和恢复处理均在 agent 的持久化运行环境中异步完成。

### 外部提交接收与任务登记

外部提交入口接收到请求后，先将调用方身份、目标 agent 会话、外部幂等键、对话输入、上下文参数和回调或查询偏好解析为统一的任务描述。该任务描述与系统生成的任务标识、接收时间、当前状态和内部对话执行标识的映射关系一起写入持久化存储；其中任务标识作为外部查询、取消、清理和日志定位的公共标识，内部对话请求标识、流标识或运行纤程标识仅作为系统内部执行和恢复使用。

任务登记采用“先登记、后执行”的边界：系统在同一持久化操作中确认任务尚未存在并写入初始状态，例如已接收或待执行，然后才将该任务交给对话执行队列或后台运行单元。这样即使外部请求连接在返回前断开，或 agent 在登记后执行前休眠，系统也能够依据已持久化的任务记录判断任务已被接收，而不会把同一外部请求误判为从未提交。

### 幂等标识与重复提交抑制

为处理外部系统因超时、网络重试或回调重放造成的重复提交，本方案为每个外部任务设置幂等判定键。幂等判定键优先采用外部调用方提供的请求编号或幂等键；在调用方未提供时，可以由系统基于调用方身份、目标会话、规范化后的输入内容和业务时间窗口生成摘要键。任务登记表对该幂等判定键设置唯一约束或等价的原子检查，使“查重”和“创建任务”不可被并发请求拆开。

在由系统生成摘要键的实现中，输入规范化可以包括去除传输层无关字段、统一时间和编码格式、稳定化 JSON 字段顺序以及保留会影响模型语义的业务字段。业务时间窗口用于限定“重试”的可接受范围，窗口外的相同内容可以作为新的任务处理。若检测到摘要键相同但规范化载荷、目标会话或调用方身份不一致，系统优选返回冲突错误或要求调用方提供显式幂等键，而不是复用已有任务。

当重复请求命中已有任务时，系统不再次写入用户消息，也不再次启动模型推理，而是返回已有任务标识及其当前状态。若已有任务处于已接收、待执行或执行中状态，重复提交被视为对同一任务的确认查询；若已有任务已完成、失败或已取消，则返回该终态结果或终态摘要。该机制把“外部请求重试”和“用户希望新增一轮对话”区分开，只有幂等判定键不同的提交才会被视为新的对话任务。

### 异步对话执行与消息持久化

任务进入执行阶段时，系统根据任务记录中的目标会话读取最新对话历史，并以程序化对话入口追加一条由外部请求转换得到的用户消息。追加消息优选采用基于最新持久化消息列表的函数式构造方式，而不是使用提交时的旧快照，从而避免多个后台任务排队期间因基线过旧导致消息覆盖或顺序错乱。用户消息持久化成功后，再触发模型响应、工具调用和 assistant 消息生成。

同一目标会话下存在多个外部任务并发进入时，系统以目标会话为串行化粒度对对话 turn 排队；登记操作可以并发完成，但消息追加和模型响应生成按照任务登记时间、调用方指定顺序号或系统分配的单调序号依次进入会话历史。每个 turn 开始前重新读取该会话的最新持久化消息，并在持有该会话执行权期间完成本轮用户消息追加和响应触发，从而避免不同外部任务在同一会话内交叉写入。

对话执行过程复用 agent 的串行化 turn 队列、消息持久化和可恢复流机制。对于程序化任务，执行上下文中可以携带外部调用方传入的业务参数，并将这些参数随对话请求持久化，使工具续跑、自动 continuation 和恢复流程能够读取同一上下文。模型输出的流式片段可以写入可恢复流存储，最终 assistant 消息在流结束或恢复处理后落入会话消息历史，由此保证外部提交的任务与人工对话触发的任务共用一致的消息语义。

### 状态查询、取消与清理

系统围绕任务标识维护任务状态机，至少包括已接收、待执行、执行中、已完成、失败、已取消以及中断待恢复或已中断等状态。状态查询接口以任务登记记录为权威来源，同时可结合内部对话请求标识、流标识和运行记录返回进度摘要、错误信息、已生成消息或可重放片段。对于终态任务，查询结果保持稳定；对于非终态任务，查询结果反映当前可确认阶段，而不要求查询方连接到正在运行的流。

状态转换可以限定为：任务创建后进入已接收或待执行，获得会话执行权后进入执行中，执行成功后进入已完成，执行异常后进入失败，取消请求在非终态阶段可使任务进入已取消，运行环境恢复时可将非终态任务推进为待执行、执行中、中断待恢复或已中断。已完成、失败、已取消和已中断可以作为终态或准终态处理，除显式重新提交新任务外，不再回退到待执行或执行中。

取消接口同样以任务标识为入口，并保持幂等。若任务尚未开始，系统将任务置为已取消并阻止后续入队；若任务正在执行，系统通过与内部请求标识关联的取消控制器向模型推理和工具执行链路传播取消信号，使执行结果进入已取消或中止类状态；若任务已经处于已完成、失败或已取消等终态，迟到的取消请求只返回当前终态，不改写既有结果。清理接口用于删除或归档任务记录、流片段和日志，清理正在运行的任务前应先执行取消并确认状态收敛，避免留下无法观察的后台推理工作。

### 休眠、重启和中断后的恢复一致性

为适应 agent 运行环境的休眠、重启或执行中断，本方案将外部任务记录、内部对话请求映射、流式输出片段和运行检查点分别持久化。执行中的对话 turn 可以由可恢复运行单元包裹，在开始时写入运行记录，在执行过程中保存必要检查点，并在正常完成后删除运行记录。系统重启后扫描未完成的运行记录和任务记录，依据任务状态、内部请求映射、已持久化消息、已写入流片段和检查点数据判断任务处于未执行、执行中断、可续跑或已完成但未回写状态。

恢复时优先保证状态单调和终态权威：已完成、失败或已取消的任务不被迟到的取消、重复提交或恢复协调改写；非终态任务则根据可验证证据推进为继续执行、失败或中断待处理。若存在已持久化的部分 assistant 输出，系统可以先将其固化为部分响应，再在确认会话仍处于稳定状态且目标 assistant 消息未被其他 turn 改变后调度 continuation；若无法安全续跑，则将任务标记为已中断并保留可查询的部分输出和错误原因。该恢复规则使外部系统即使只通过短连接提交任务，也能在运行环境发生休眠或重启后获得一致的任务状态。
