## 技术方案

本方案在已有对话式 agent 处理链路之外，增设面向外部系统的任务接收、持久化登记、异步调度、状态观测、取消清理和恢复协调机制。外部系统通过 webhook、RPC 或其他程序化接口提交一次对话任务后，系统先形成可持久追踪的外部任务记录并快速返回接收确认；模型推理、消息生成和结果持久化在后续异步流程中完成。该机制将外部调用的可靠交付边界与内部聊天请求、可恢复流和持久执行单元解耦，使外部调用方无需保持长连接等待推理完成，同时避免重复提交导致的重复输入写入或重复执行。

### 外部任务接收与持久化登记

本方案设置外部任务接收层作为 webhook、RPC 或定时触发等程序化入口的统一边界。接收层对外部请求进行基础校验和规范化处理，确定目标 agent、目标会话或对话上下文、用户输入内容、调用方提供的幂等键以及自定义上下文参数。接收层不直接同步等待大模型推理结果，而是在持久化事务中写入或确认一条任务登记记录后，即向调用方返回表示“已接收”的响应，该响应至少携带可供后续查询、取消或清理的外部任务标识。

任务登记记录作为外部任务生命周期的权威索引，可以存储外部任务标识、调用方幂等键或请求指纹、目标 agent 和会话标识、待写入消息或消息载荷引用、自定义请求上下文、任务状态、内部聊天请求标识、可恢复流标识、持久执行单元标识、生成代际或清理代际、创建和更新时间、取消标记、错误摘要、结果摘要以及保留期限。外部任务标识用于对外暴露，内部聊天请求标识用于关联一次聊天 turn、取消控制和日志，可恢复流标识用于后续结果片段回放或断点恢复，三者分别承担不同的追踪职责。

其中，可恢复流标识用于指向模型输出过程中已经持久化的流式片段或累积结果，使查询方或恢复流程能够在连接断开后重放已产生内容；持久执行单元标识用于指向被持久化登记和心跳保持的后台执行过程，使运行环境被驱逐或重启后仍可发现未完成任务；生成代际或清理代际用于区分会话历史被清空、结果被归档或旧任务索引失效前后的数据边界，避免旧任务引用到已被替换或删除的消息内容。

### 幂等去重与输入写入控制

本方案将幂等判定设置在用户输入写入之前。接收层优先使用调用方提供的幂等键；未提供幂等键时，可以根据目标 agent、目标会话、规范化后的用户输入、调用方身份、业务时间窗或其他稳定字段生成请求指纹，并将该幂等键或请求指纹映射为唯一的外部任务标识。在同一作用域内已存在相同幂等键或请求指纹的任务记录时，系统返回已有任务的接收结果或当前状态，不再次向会话追加用户消息，也不再次启动模型 turn。

请求指纹的作用域可以限定为同一调用方、同一目标 agent、同一会话或同一业务时间窗，以降低不同业务请求被错误合并的风险。生成指纹时，可以对输入文本、结构化参数和自定义上下文进行规范化，例如去除传输层无关字段、固定字段顺序并保留影响模型处理结果的业务字段。若检测到相同指纹但关键载荷不一致，系统可以拒绝该次提交或返回冲突状态，要求调用方使用新的幂等键，而不是将不同任务合并为同一外部任务。

对于首次出现的外部任务，系统先创建状态为已接收或待写入的任务登记记录，再在受队列或事务保护的步骤中将用户输入写入聊天消息存储，并把任务状态推进为输入已持久化。若在登记之后、消息写入之前发生异常，恢复流程可依据任务记录重新执行写入；若消息已写入但内部聊天请求尚未启动，恢复流程只启动后续聊天 turn，而不重复写入同一用户输入。该边界使重复提交、网络重试和恢复重放均以任务记录为依据，而不是以瞬时内存状态为依据。

### 异步执行、状态查询与取消

异步执行阶段可以复用既有聊天 agent 的程序化 turn 能力。任务调度层在确认输入可写入或已写入后，按目标会话的 turn 队列进行串行化或按预设并发策略处理，将任务携带的消息、请求上下文和内部请求标识传入聊天处理链路。模型推理过程可以由持久执行单元包装，并在关键阶段保存快照，例如任务已接收、输入已持久化、聊天请求已启动、流式输出中、已完成、出错或已取消。正常完成时，系统将最终助手消息、结果摘要或可恢复流信息写回任务登记记录，并将任务状态推进为终态。

状态查询接口以任务登记记录为权威数据源，并可结合内部聊天请求、可恢复流和持久执行单元的状态补充进度信息。对外状态可以包括已接收、待写入、运行中、输出中、已完成、出错、已取消或已中断等。处于已完成、出错、已取消或已中断等终态的任务应保持状态单调性，迟到的取消请求、重复提交或恢复协调结果不得将其改写为非终态或其他不一致终态。查询结果可以同时返回外部任务标识、当前状态、更新时间、错误摘要、结果摘要以及可用于结果片段回放的引用。

| 当前状态 | 允许的主要来源 | 允许的主要去向 | 状态含义 |
| --- | --- | --- | --- |
| 已接收 | 首次登记或重复提交命中已有登记 | 待写入、已取消、出错 | 外部请求已被系统确认，尚未完成输入写入或调度 |
| 待写入 | 已接收 | 输入已持久化、已取消、出错 | 任务已通过幂等检查，等待将用户输入写入消息存储 |
| 输入已持久化 | 待写入或恢复补偿 | 运行中、已取消、出错 | 用户输入已经落入会话消息存储，不应再次追加同一输入 |
| 运行中或输出中 | 输入已持久化、恢复继续 | 已完成、已取消、出错、已中断 | 聊天 turn 已启动，可能已有可恢复流片段或中间快照 |
| 已完成、已取消、出错、已中断 | 运行中、输出中、恢复协调或取消收敛 | 无业务后继，仅可清理或归档 | 任务进入终态，后续重复提交、迟到取消或恢复协调不得改变其终态语义 |

取消接口以外部任务标识定位任务记录，再根据任务记录中的内部聊天请求标识、取消控制句柄或持久执行单元信息执行显式取消。若任务尚未写入输入，则将任务标记为已取消并阻止后续写入；若任务已启动聊天 turn，则触发对应请求的中止信号并记录取消标记；若任务已经进入终态，则取消接口幂等返回既有终态。外部调用方的 HTTP 超时、网络断开或观察连接消失仅表示观察路径中断，不自动等同于取消服务端任务，避免因调用方短暂故障误杀仍可完成的模型执行。

### 中断恢复与一致性判定

agent 运行环境发生休眠、重启或执行中断后，恢复协调层从持久化任务登记记录、持久执行单元遗留记录、已写入消息、可恢复流片段以及内部请求映射中判定任务阶段，而不依赖内存变量。对于非终态任务，系统可以按阶段进行协调：尚未写入用户输入的任务重新进入写入步骤；已写入输入但未启动聊天请求的任务重新调度聊天 turn；已启动且存在可恢复流或请求映射的任务尝试回放已持久化片段、继续处理或等待稳定；已产生最终消息但任务索引未更新的任务补齐终态记录。

对于已启动的任务，是否继续处理可以根据若干持久化条件判定：若存在未到终态的持久执行单元记录、内部请求标识仍可被取消或观察、可恢复流片段仍在增长，或聊天链路提供继续执行入口，则恢复协调层可以将任务保持为运行中或输出中并等待稳定；若已经存在完整助手消息、终态回调记录或终态流片段，则补齐任务终态；若仅存在不完整片段且无法确认原请求是否存活，也不存在安全的继续入口，则将任务收敛为已中断或出错。

当恢复协调无法确认某一运行中的模型请求是否仍会产生输出，或者继续执行可能造成重复生成、重复工具调用或重复消息写入时，系统可以将任务标记为已中断或出错，并向状态查询接口暴露该结果，而不是盲目重新发起同一模型 turn。对于已带有取消标记的任务，恢复流程优先执行取消收敛，确保不会在重启后继续推进已请求取消的任务。该判定策略使恢复后的动作与幂等记录、消息存储和流式输出记录保持一致。

### 清理与保留边界

清理接口用于释放外部任务索引、结果片段、可恢复流记录或其他保留数据。对于已完成、出错、已取消或已中断的终态任务，系统可以按照保留期限删除或归档任务登记记录及其关联索引；对于仍处于已接收、待写入或运行中的任务，清理流程应先执行幂等取消并等待任务进入可收敛状态，再删除对外索引和内部关联关系，避免产生外部已不可见但内部仍在执行的孤儿任务。

在一种实现中，清理策略可以结合生成代际、会话清空代际或保留期限判断旧任务是否仍可被查询和回放。若会话历史被清空或某一代际之前的消息被删除，系统同步失效对应任务的结果引用，并在查询时返回已清理或不可回放的状态说明。由此，外部任务生命周期与聊天消息生命周期、流式输出生命周期和 agent 存储生命周期保持一致，减少长期保留数据对存储空间和恢复判定的影响。
