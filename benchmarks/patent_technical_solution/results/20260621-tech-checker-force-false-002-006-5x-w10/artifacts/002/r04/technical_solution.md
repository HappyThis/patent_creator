## 技术方案

### 总体架构与任务登记

现有对话式 Agent 通常以客户端会话请求触发模型响应，外部系统以 webhook、RPC 或其他程序化方式触发时，容易出现外部请求必须同步等待推理完成、网络超时后重复提交、并发写入基于旧对话上下文、运行实例休眠或重启后内存状态丢失等问题。本方案将“外部接收”和“对话执行”解耦，并以持久化登记、幂等约束和可恢复状态机作为二者之间的衔接层。

本方案在支持对话式触发的 Agent 系统外侧增加“外部任务接收与执行管理”机制，使 webhook、HTTP/RPC 调用或 callable 方法提交的程序化请求能够被转换为一次受控的对话任务。外部入口只负责认证、租户或会话定位、载荷规范化、幂等键提取以及任务登记，不直接等待模型推理结果；实际对话注入、模型调用、状态更新和结果持久化由 Agent 内部的异步执行单元完成。

在一种实现中，系统按照调用方标识、目标 Agent 实例标识、会话标识和外部任务标识确定任务归属，并在 Agent 本地持久化存储中建立任务登记记录。任务登记记录至少包括内部任务 ID、外部幂等键、原始载荷摘要、待注入的用户消息内容、队列任务 ID 或持久执行 ID、当前阶段、取消标记、错误信息、创建时间和更新时间。该记录作为外部请求、队列任务、程序化对话轮次和后续查询接口之间的关联中心，避免仅依赖内存变量判断任务进度。

任务阶段采用单调状态机表示，例如 received、queued、injecting、running、completed、failed、cancelling、cancelled、interrupted 和 cleaned。状态变更由登记记录中的版本号或更新时间保护，只有符合预设前驱状态的更新才能生效；completed、failed、cancelled、interrupted 等终态不会被迟到的取消请求、重复提交请求或恢复流程改写为非终态。

### 幂等接收与快速确认

外部调用到达后，系统先对请求签名、调用方权限、目标 Agent 路由和载荷格式进行校验，再生成或提取幂等键。幂等键可以来自外部系统提供的事件 ID、请求 ID 或业务单据 ID；当外部系统未提供稳定标识时，可以由调用方标识、目标会话、规范化后的消息内容和时间窗口等字段计算得到。系统在写入任何对话消息或启动模型推理之前，先以调用方标识、目标 Agent、会话标识和幂等键为唯一约束执行原子插入。

如果原子插入成功，登记记录进入 received 或 queued 阶段，系统将后台处理任务写入持久队列，或者登记一个可恢复执行的 fiber，并立即向外部调用方返回 accepted 响应、内部任务 ID、当前状态以及后续查询地址。该响应不等待 waitUntilStable、saveMessages、LLM 推理或工具调用完成，从而使 webhook 提供方和上游 RPC 调用方能够在短超时时间内获得确定接收结果。

如果唯一约束表明同一幂等键对应的任务已经存在，系统不再次保存用户输入、不再次排队、不再次启动模型调用，而是读取既有登记记录并返回相同内部任务 ID 及其当前状态。对于载荷摘要与既有记录不一致的重复请求，系统可以返回冲突状态或拒绝接收，防止不同业务请求误用同一幂等键而污染同一对话上下文。

### 异步执行与对话注入

后台执行单元从持久队列或可恢复执行记录中取得任务后，先将登记状态从 queued 推进为 injecting，并检查取消标记和终态标记。若任务尚未取消且未进入终态，执行单元再等待目标会话进入稳定状态，以避免与正在进行的流式响应、待处理工具交互或续写轮次重叠。稳定性检查超时并不丢弃任务，而是将任务保持在可重试阶段或重新排队，等待后续调度继续处理。

在注入对话消息时，系统采用函数式消息保存方式基于执行时刻最新的持久化 transcript 追加合成用户消息，而不是基于外部请求到达时读取到的旧消息数组覆盖写入。合成消息中携带内部任务 ID、外部幂等键或来源元数据；登记记录在消息成功持久化后记录 messageId 和已注入标记。这样即使多个 webhook 或 RPC 请求快速到达，也可以依次基于最新上下文追加，避免并发触发造成消息丢失、顺序错乱或重复注入。

消息注入完成后，任务进入 running 阶段，对话轮次由 Agent 现有的串行化执行机制、流式缓冲机制和模型调用逻辑处理。对于需要跨较长时间或多步骤运行的任务，执行单元可以在 runFiber 内推进，并在关键节点写入 checkpoint；对于短任务，可以由持久队列回调驱动。无论采用哪种执行载体，登记记录均保存外部任务与内部 requestId、队列 ID 或 fiber ID 的映射，使后续查询、取消和恢复能够定位到同一运行实例。

### 状态查询、取消与清理

系统提供以内部任务 ID 或外部幂等键为索引的查询接口。查询时读取任务登记记录、消息注入标记、队列记录、fiber 快照以及必要的响应摘要，返回当前阶段、是否可取消、是否已进入终态、错误信息和结果位置。查询接口只观察持久化状态，不通过重新提交相同载荷来推断进度，因此不会触发新的对话轮次。

取消接口采用显式取消语义，普通客户端断开、观察流关闭或查询超时不等同于取消任务。取消请求到达后，系统先在登记记录中写入 cancelling 状态和取消原因；如果任务仍在队列中，则删除对应队列项并转为 cancelled；如果任务正在执行，则通过与 requestId 关联的 AbortController 或传入 saveMessages、continueLastTurn、模型调用的 AbortSignal 向当前对话轮次传播取消信号，并在执行回调返回 aborted 或捕获取消异常后写入 cancelled。

清理接口用于删除外部任务保留数据、临时载荷、执行快照或结果索引。若被清理任务仍处于 received、queued、injecting 或 running 等活动阶段，系统先执行取消流程并确认状态进入终态，再删除可清理数据或将任务标记为 cleaned；若任务已处于 completed、failed、cancelled 或 interrupted 等终态，则直接按照保留策略清理。该边界避免删除登记记录后仍存在孤立的模型调用或后台任务。

### 中断恢复与一致性判定

Agent 运行环境休眠、重启、代码更新或执行中断后，恢复流程不依据内存中的请求对象判断任务阶段，而是从持久化任务登记、队列任务、fiber 运行记录及其 snapshot、已保存消息和取消标记中综合重建状态。恢复入口可以由 Agent 激活、持久 alarm 或下一次外部查询触发；恢复时先扫描未进入终态的任务，再按登记阶段逐项判定是否需要重新排队、继续执行、标记中断或仅返回既有终态。

对于 received 或 queued 且未发现已注入消息的任务，恢复流程可以重新写入队列或重新启动 fiber，但仍复用同一内部任务 ID 和幂等键；对于 injecting 阶段任务，恢复流程先根据 messageId、消息元数据或 transcript 中的任务标记判断消息是否已经持久化，未持久化时才重新注入，已持久化时直接推进到 running 或结果核验阶段；对于 running 阶段任务，若存在 fiber snapshot 或流式缓冲，则按 checkpoint 继续或调用对话恢复逻辑，若无法确认执行仍可恢复，则将任务标记为 interrupted 并保留已持久化的部分响应。

恢复流程遵循“注入一次、执行一次、终态优先”的一致性规则：同一幂等键对应的对话用户输入最多持久化一次；同一任务只有在未发现有效执行载体且未进入终态时才会重新调度；已经 completed、failed、cancelled 或 interrupted 的任务仅用于查询返回和保留策略处理，不再触发 saveMessages 或模型推理。通过该规则，系统即使面对外部重复提交、网络超时重试、Agent 驱逐或运行时重启，也能保持外部任务与对话上下文之间的一一对应关系。
