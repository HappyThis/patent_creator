## 技术方案

### 总体方案与任务对象模型

本方案在已有对话型 agent 系统之上增加面向外部系统的一次性对话任务管理机制，使 webhook、WebSocket RPC、Worker/Durable Object RPC 或其他程序化入口均先进入统一的外部任务接收层。该接收层不直接等待模型推理结果，而是把外部提交转换为一个可持久追踪的对话任务，再由 agent 内部的异步执行能力驱动后续对话轮次。既有系统中可复用 Durable Object 的持久状态、SQLite 存储、休眠后唤醒、对话消息持久化、程序化写入消息、对话轮次串行队列、请求级中止控制和可恢复流等能力；本方案在这些能力之前和之后补充任务登记、幂等判定、阶段推进和恢复判定规则。

每个外部对话任务可抽象为任务记录与对话轮次记录的组合。任务记录至少包括外部调用方标识、幂等键、输入摘要、目标 agent 或会话标识、内部任务标识、对话请求标识、当前阶段、取消标记、清理标记、创建时间、更新时间以及必要的错误信息；对话轮次记录则关联被持久化的用户消息、assistant 消息、流式输出缓冲和请求上下文。内部任务标识用于状态查询、取消、恢复和清理，对话请求标识用于与程序化对话轮次、串行队列、AbortController 和流恢复机制对应。上述字段名称和存储表结构可以根据项目实现调整，但应保证任务记录先于用户消息写入和模型推理触发而持久化。

### 外部提交的幂等接收与快速确认

外部提交入口接收到任务后，首先对调用方身份、目标会话、输入体和幂等键进行规范化处理。幂等键可以由外部系统显式提供，也可以在缺省时基于调用方标识、目标 agent、会话标识和规范化输入摘要生成，但优先采用外部系统提供的业务幂等键。接收层在同一事务或等效原子区间内查询并插入任务记录：若不存在相同调用方与幂等键对应的未过期记录，则创建状态为已接收或已入队的任务并分配内部任务标识；若已存在对应记录，则直接返回该记录的内部任务标识和当前状态。

快速确认的返回内容可以包括内部任务标识、当前状态、是否为重复提交、状态查询地址或 RPC 方法名、建议重试时间和幂等窗口到期时间。该确认只表示系统已经可靠接收或识别了任务，不表示模型推理已经完成。这样，外部系统在 HTTP 超时、连接中断或 RPC 响应丢失后重复提交时，系统不会再次追加相同用户输入，也不会再次启动相同模型推理，而是复用首次登记的任务记录返回一致结果。

幂等窗口到期后的处理可根据业务约束配置为拒绝重复创建、返回已过期的历史终态，或为同一外部业务键创建带有新代际标识的新任务。无论采用哪种策略，任务记录中均应保留过期时间、代际或版本信息，使到期后的新任务不会覆盖原任务终态，原任务的最小索引也不会在幂等窗口内提前删除。对于外部调用方无法确认首次提交结果的场景，优先在窗口内返回既有任务；只有明确超过窗口且调用方选择重新执行时，才允许进入新的接收登记流程。

### 异步执行调度与对话消息写入控制

新建任务被确认后，通过持久队列、调度任务或 agent 内部的 fire-and-forget 执行单元异步推进。队列或调度项的载荷只需携带内部任务标识和必要的目标信息，真正的输入内容、请求上下文和阶段状态从持久任务记录读取。执行器开始处理前，应以条件更新方式把任务从已接收或已入队推进到写入中或运行中；只有成功取得该阶段推进权的执行器才允许调用程序化对话入口写入用户消息并触发对话轮次，其他重复队列项或过期执行器应退出或仅刷新可观测状态。

对话消息写入采用“任务记录先占位、消息写入后回填”的控制方式。执行器在调用类似 saveMessages 的程序化对话入口之前记录待写入阶段、对话请求标识和输入摘要；程序化入口完成用户消息持久化后，将生成的消息标识、请求标识和写入完成阶段回填到任务记录。由于项目的对话层支持先持久化用户消息再调用消息处理逻辑，并且 assistant 消息在流完成后持久化，因此任务记录可以明确区分“尚未写入用户消息”“用户消息已写入但模型未稳定完成”“assistant 输出已完成或出错”等阶段。

模型推理和工具调用阶段通过对话轮次串行队列进行互斥控制，使同一会话内多个外部任务或外部任务与人工对话不会交错修改消息列表。队列可利用请求标识记录当前活动轮次、排队数量和代际失效信息；当会话被重置或取消时，旧代际的排队任务被跳过。对于需要在休眠或运行时重启后继续的长耗时任务，可将执行过程放入可恢复执行单元，并在关键阶段写入 checkpoint，使恢复逻辑能够从最近一次稳定阶段继续，而不是仅依赖内存中的循环计数、流缓冲或临时变量。

### 状态查询、取消与清理

状态查询接口根据内部任务标识读取任务记录，并结合对话层状态返回统一状态视图。该状态视图可包括已接收、已入队、写入中、运行中、流式输出中、等待工具或人工输入、已完成、失败、取消中、已取消、中断和已清理等状态；同时可返回关联的对话请求标识、最近更新时间、错误摘要、可重试标记和可清理标记。若底层对话层能够提供活动流、活动请求或队列空闲信息，查询接口可将这些信息归并到任务状态中，避免外部调用方只能看到客户端侧的 streaming 状态而无法识别服务端程序化轮次正在执行。

失败、中断和可重试状态可按错误来源区分：输入校验失败、权限校验失败、目标会话不存在等确定性错误直接形成失败终态；模型供应商临时不可用、队列回调暂时失败、网络短时断开等可在重试次数或时间窗口内保持可重试状态；已写入用户消息但无法确认模型推理、工具调用或外部副作用是否完成的任务，不应简单重试，而应进入中断状态并向外部调用方暴露需要人工确认或业务补偿的原因。

取消接口与清理接口分离处理。取消请求首先持久化取消标记和取消请求时间；若对应请求仍在内存中执行，则通过以请求标识索引的 AbortController 或等效中止注册表触发 abort，并把任务推进为取消中或已取消；若 agent 已休眠或重启导致内存中止控制器不存在，则恢复流程读取取消标记后不再继续启动模型推理，并将任务稳定为已取消或中断。终态任务收到迟到取消请求时，不覆盖已完成、已失败或已中断等权威终态，只记录迟到取消事实或返回当前终态。

清理请求用于释放已终止任务的流缓冲、临时上下文、过期队列项或较大的消息附属数据，不应等同于取消执行。清理前应确认任务已经处于终态，或已被明确取消且不会再继续执行；清理后仍在幂等窗口内保留最小化的任务索引，包括外部调用方、幂等键、内部任务标识、终态和到期时间。这样既能降低存储占用，又能避免外部系统稍后因重试同一业务请求而重新创建任务。

### 休眠、重启或中断后的恢复一致性

agent 因休眠、运行时重启、代码更新、网络中断或上游模型连接断开而重新激活时，恢复流程以持久任务记录为主线进行一致性判定。恢复流程扫描非终态任务，并读取其阶段、取消标记、队列项、可恢复执行快照、已持久化用户消息、assistant 终态消息、流式输出缓冲和请求上下文。若任务尚未写入用户消息，则可以重新入队；若用户消息已写入但没有开始模型处理，则以原请求标识继续对话轮次；若已有活动流缓冲或可恢复执行快照，则优先尝试恢复流式输出或从 checkpoint 继续；若无法证明继续执行不会产生重复副作用，则将任务标记为中断并暴露给外部调用方处理。

恢复判定遵循单调阶段推进原则：未写入阶段只能推进到入队或写入中，写入完成阶段不能回退为未写入，终态一旦形成不能被迟到队列项、迟到取消或重复提交覆盖。对包含工具调用、外部副作用或多步推理的任务，可以在每个不可重复副作用之前写入准备阶段，在副作用完成后写入完成阶段；恢复时只有处于准备阶段且副作用未确认完成的步骤才允许重试，处于完成阶段的步骤只能继续后续处理或进入结果查询。该规则保证了同一外部任务在重复提交、队列重试和恢复执行共同存在时仍然最多写入一次用户输入，并尽量避免重复触发同一外部副作用。

对于不同接入方式，本方案保持同一任务语义：HTTP webhook 可由请求处理入口完成验签和任务登记，WebSocket callable 方法可作为外部客户端 RPC 入口，Worker 内部或 agent 间调用可使用 Durable Object RPC；这些入口最终均调用同一幂等登记和异步调度逻辑。队列和调度系统可配置重试策略以处理暂时性失败，可恢复执行单元可在中间结果写入 SQLite 后继续执行，流恢复机制可将已生成的输出片段重新提供给连接方。由此，外部系统获得的是可靠接收、可查询、可取消、可清理且具备恢复一致性的程序化对话任务，而不是一次必须保持连接直到模型完成的普通同步调用。
