## 技术方案

本方案在既有支持对话触发的 agent 系统上，增加面向外部系统的一次性对话任务接收层、会话级异步执行层和任务生命周期控制层。文中将“任务状态”定义为对外查询的生命周期状态，将“内部执行阶段”定义为后台 worker 对任务的处理位置，将“检查点阶段”定义为休眠、重启或中断后用于恢复判定的持久化快照；三者通过同一任务标识关联但不混用。外部系统通过 webhook、RPC 或其他程序化入口提交任务后，系统先完成持久化登记、幂等判定和入队，再立即返回接收结果；模型推理、工具调用和消息流处理在后台继续执行。

### 外部任务接收与幂等登记

外部提交入口接收到任务后，先对调用方身份、目标 agent、目标会话、用户输入内容、附件摘要、工具参数、系统参数、业务关联标识和目标 agent 版本进行规范化，形成任务接收记录。任务记录以 $task\_id$ 为主键，并保存调用方幂等键或请求指纹、$conversation\_id$、规范化用户消息、任务状态、内部执行阶段、取消意图版本、$turn\_request\_id$、用户消息 $message\_id$、结果消息 $assistant\_result\_message\_id$、结果缓存键和 $checkpoint\_id$。其中 $conversation\_id$ 指向会话，$message\_id$ 指向已注入的用户消息，$turn\_request\_id$ 指向一次模型 turn，$assistant\_result\_message\_id$ 或结果缓存键构成对外查询的结果索引。

幂等登记采用同一事务内的“唯一约束写入任务记录并写入待执行队列”机制。幂等键的作用域优选为调用方、目标 agent 和 $conversation\_id$ 的组合；未提供幂等键时，由规范化消息、附件摘要、工具参数、系统参数、业务关联标识和 agent 版本生成请求指纹。若相同作用域下已存在相同幂等键且规范化参数一致，则返回既有 $task\_id$ 和任务状态，不重复入队；若幂等键相同但参数摘要不同，则将本次提交判定为幂等冲突并返回冲突状态或错误，不把不同内容合并为同一任务。若事务提交前入队失败，则任务记录不生效；若事务提交后检测到任务处于已接收但无队列项，补偿扫描器按 $task\_id$ 重建队列项。队列重复投递时，worker 只有在任务仍处于已接收或待执行且未记录 $message\_id$、$turn\_request\_id$ 时才可继续处理，从而由唯一约束、状态条件和注入前检查共同防止重复会话消息。

### 异步对话执行与消息注入

后台执行流程按会话级顺序处理队列项。worker 先通过条件更新认领 $task\_id$，写入执行租约、租约到期时间和心跳时间；认领成功后检查目标 agent 是否可用、目标会话是否存在、任务是否未被取消且未进入终态。目标会话的稳定状态是指该会话没有正在运行的 turn、turn 队列为空、无待处理的工具交互或审批、最近一次消息写入事务已经提交，并且读取到的会话版本号在取得会话执行锁或会话级序号时未变化。多个外部任务和人工对话按会话级队列序号、入队时间或预设优先级排序，除明确配置的高优先级控制任务外，普通外部任务不得绕过已排队的人工 turn。

消息注入以任务记录中的规范化用户消息、读取时的会话版本号和取消意图版本为输入。worker 在会话锁内读取最新持久会话历史，并采用函数式追加生成新消息列表；写入时通过会话版本号或 CAS 条件确认会话未被其他 turn 改写。写入成功后，系统生成并记录用户消息 $message\_id$、递增后的会话版本、$turn\_request\_id$ 和注入完成检查点，再触发模型推理或自动续写。若 CAS 失败，说明会话历史已变化，worker 释放锁并按最新版本重新排队，不使用旧消息数组重试；若取消意图版本在注入前已更新，则不写入消息并把任务迁移为已取消。

推理前置条件包括用户消息已持久化、$turn\_request\_id$ 已写入、检查点已记录、任务状态仍为运行中且取消意图版本未变化。模型推理完成后，worker 依据 $turn\_request\_id$ 只更新对应任务的结果索引，将 $assistant\_result\_message\_id$、错误摘要、中止原因或部分响应位置写回任务表。若模型调用、工具调用或续写返回迟到结果，而任务已处于已完成、失败、已取消或已清理状态，则该结果只能写入审计日志或被丢弃，不得覆盖既有任务状态和结果索引。

### 任务状态查询与状态迁移

任务状态表对外提供可查询的生命周期视图，内部执行阶段和检查点阶段仅用于调度与恢复。任务状态包括已接收、待执行、运行中、待续接、已完成、失败、已取消和已清理；“已注入”不作为对外状态，而是运行中状态下的内部执行阶段，其可验证依据为已记录的 $message\_id$、会话版本和 $turn\_request\_id$。状态查询接口读取任务状态、结果索引、可见结果字段和最小审计字段，不依赖内存执行对象，因此在 agent 已休眠或执行连接断开时仍可返回一致结果。

| 任务状态 | 允许来源 | 允许去向 | 触发事件与前置条件 | 主要写入字段 |
| --- | --- | --- | --- | --- |
| 已接收 | 新任务事务写入 | 待执行、已取消 | 幂等登记成功；若登记后发现取消意图或参数非法则可终止 | $task\_id$、幂等键、$conversation\_id$、规范化消息 |
| 待执行 | 已接收、CAS 重排、租约过期回收 | 运行中、已取消、失败 | 队列项有效，目标会话存在，任务未取消，worker 尚未认领或原租约失效 | 队列序号、重试计数、下次调度时间 |
| 运行中 | 待执行、待续接 | 待续接、已完成、失败、已取消 | 取得执行租约和会话顺序权；用户消息已注入或正在推理 | 租约、$message\_id$、会话版本、$turn\_request\_id$、$checkpoint\_id$ |
| 待续接 | 运行中 | 运行中、已完成、失败、已取消 | 已产生部分响应或中断记录，且可定位续写目标 | 部分响应位置、续写目标消息、恢复计数 |
| 已完成 | 运行中、待续接 | 已清理 | 最终 assistant 消息已持久化且任务未被终态覆盖 | $assistant\_result\_message\_id$、结果缓存键、完成时间 |
| 失败 | 已接收、待执行、运行中、待续接 | 已清理 | 参数非法、会话不存在、权限失效、不可恢复错误或重试耗尽 | 错误类别、错误摘要、失败时间 |
| 已取消 | 已接收、待执行、运行中、待续接 | 已清理 | 取消意图先于终态写入并被条件更新采纳 | 取消意图版本、取消时间、中止原因 |
| 已清理 | 已完成、失败、已取消 | 无 | 任务已终态且可清理字段已删除或脱敏 | 清理时间、保留审计摘要 |

状态迁移采用带版本号的条件更新，条件包括当前任务状态、内部执行阶段、取消意图版本、租约持有者和结果索引是否为空。取消与完成竞争时，以持久化条件更新的提交顺序和终态保护为准：若最终结果已经把任务更新为已完成，则随后到达的取消只能记录为迟到取消，不改写已完成；若取消意图先被采纳并把任务更新为已取消，则随后返回的模型结果不得写入结果索引。清理与执行竞争时，运行中或待续接任务不得直接清理其执行依赖字段，必须先取消或等待终态。

错误映射按可恢复性和阶段确定：外部参数非法、目标会话不存在或权限失效直接进入失败；会话锁超时、CAS 冲突或租约竞争进入待执行并增加重试计数；模型调用或工具调用的临时错误可进入待续接或待执行并设置退避时间；已产生部分响应但无法安全定位续写目标时，任务进入失败或待人工处理的扩展状态；恢复无法确定是否已注入消息时，以是否存在 $message\_id$ 和 $turn\_request\_id$ 为准，不能仅凭内存状态重放注入。

### 取消、清理与观察分离

取消请求采用版本化取消意图。每次显式取消在任务记录中递增取消意图版本并写入取消原因、取消时间和请求方；worker 在认领任务、注入消息前、触发模型前、每轮工具调用前后、自动续写前和写入最终结果前读取并比较该版本。若任务尚未注入会话，检测到取消意图后直接迁移为已取消且不写入用户消息；若任务已经运行，系统将当前取消意图转换为运行时中止信号并传递给模型或工具调用，同时在恢复后继续以持久化取消意图版本为准，而不依赖已丢失的内存 AbortSignal。

观察连接、执行控制和数据清理彼此分离。状态查询或流式观察只读取任务状态表、结果索引和可见结果字段，不持有执行租约，也不能因连接关闭而取消后台任务；只有显式取消接口才能更新取消意图版本。清理时，可删除或脱敏规范化消息明文、临时流片段、结果缓存内容、错误详情和外部回调地址等可见数据；必须保留 $task\_id$、幂等键或其摘要、$conversation\_id$、最终任务状态、取消意图版本、时间戳、结果是否曾存在的摘要和最小审计字段。清理后的查询返回已清理状态、原终态摘要和清理时间，不返回已删除内容。

已清理任务再次收到重复提交、查询、取消或恢复扫描时，系统依据保留的幂等摘要和终态摘要返回已清理或冲突结果，不重新创建推理任务；迟到的取消请求只记录为对已清理任务的无效控制事件；恢复扫描遇到已清理状态时跳过执行依赖字段的读取。该分离使清理不会破坏历史终态，也不会因删除可见结果而导致同一幂等请求被重新执行。

### 休眠、重启和中断后的恢复一致性

后台执行过程被持久执行机制包裹，并通过执行租约、心跳和检查点共同支持恢复。worker 认领任务时写入租约持有者、租约到期时间和心跳时间；正常执行期间周期性续租。恢复 worker 只有在租约过期、心跳超过阈值未更新、对应执行记录被框架报告为中断，且任务未处于终态时，才可通过条件更新认领该任务。若两个恢复流程同时扫描同一任务，只有成功更新租约版本的一方可以继续处理，另一方必须放弃，从而避免双重恢复。

检查点在关键阶段完整替换写入，至少包括 $task\_id$、内部执行阶段、会话版本、是否已注入用户消息、$message\_id$、$turn\_request\_id$、部分响应流标识、续写目标消息、取消意图版本、恢复次数和下一步待执行动作。agent 重新激活后，恢复逻辑同时读取任务表、检查点和会话消息表：对于尚未注入且无 $message\_id$ 的任务，重新进入调度前检查；对于已经记录 $message\_id$ 的任务，禁止再次追加同一用户消息；对于已完成对话但任务状态尚未更新的任务，依据 $turn\_request\_id$ 和已持久化 assistant 消息补写结果索引。

| 检查点阶段 | 恢复动作 | 禁止动作 | 状态写回条件 |
| --- | --- | --- | --- |
| 尚未注入 | 重新检查目标会话、取消意图和会话锁；满足条件后重新排队或注入 | 不得假设旧内存队列仍有效 | 任务仍为已接收或待执行且无 $message\_id$ |
| 已注入未完成推理 | 依据 $message\_id$ 和 $turn\_request\_id$ 查询会话与 turn 结果；必要时进入待续接 | 不得再次追加同一用户消息 | 任务为运行中且存在用户消息但无结果索引 |
| 已产生部分响应 | 定位部分响应流、目标 assistant 消息和续写目标；可安全续接时追加到同一目标，不能安全定位时进入失败或待人工处理 | 不得创建无法关联原 turn 的重复回答覆盖原结果 | 部分响应对应的目标消息和会话版本可验证 |
| 已完成但未更新任务状态 | 从已持久化 assistant 消息补写 $assistant\_result\_message\_id$ 和完成时间 | 不得重新调用模型以生成第二个最终结果 | 任务未处于终态且结果消息存在 |
| 已取消或已清理 | 释放租约并停止恢复 | 不得读取已清理执行依赖字段或重启推理 | 终态保护条件成立 |

部分响应和续接以目标 assistant 消息为边界。若中断前的流片段已经持久化且能够与同一 $turn\_request\_id$、目标 assistant 消息和会话版本匹配，恢复流程可以把片段固化为该消息的已生成前缀，并调用续写流程追加到同一消息；续写完成后只更新同一任务的结果索引。若恢复次数超过阈值、目标消息已被人工分支替换、会话版本无法对应，或取消意图版本已更新，则停止续接并将任务迁移为失败、已取消或待人工处理，避免重复续写、覆盖用户后续对话或产生断裂结果。
