## 技术方案

本方案在现有对话式 agent 的消息持久化、流式响应和可恢复执行能力基础上，增加面向外部系统的一次性对话任务接入机制。$taskId$ 表示外部可查询、取消和清理的稳定任务标识；$runId$ 表示某次后台执行实例或运行代次，任务恢复或重新领取时可以产生新的 $runId$，但仍归属于同一 $taskId$。外部调用方可以通过 webhook、RPC 或其他程序化入口提交任务，系统在完成幂等登记后立即返回“已接收”确认，不把外部请求连接与模型推理过程绑定；后续由持久化任务记录、状态版本、运行代次和消息片段记录驱动查询、取消、清理和恢复，从而避免重复提交、连接断开、休眠或重启导致同一用户输入重复写入、同一对话 turn 重复执行或旧执行结果覆盖新状态。

### 外部任务接收与幂等登记

外部接入层接收调用方提交的对话任务时，为每个任务确定稳定幂等键，并在任务表中以“调用方标识 + 幂等键”建立唯一约束。该幂等键可以由外部系统提供的 idempotency key、业务事件编号、webhook 投递编号，或调用方标识、会话标识和请求内容摘要组合得到。接入层在一个持久化事务中原子写入任务记录、调用方标识、会话标识、请求摘要、输入消息标识、初始状态和调度标记；只有唯一任务记录创建或确认成功后，才允许返回 $accepted$ 和 $taskId$，且不得在事务提交前启动后台执行。

并发重复提交采用原子 upsert 或等效事务冲突处理。首次写入成功的请求创建任务和具有稳定消息标识的用户消息，用户消息写入可采用类似 $INSERT\ OR\ IGNORE$ 的规则；同时到达的相同幂等键请求若遇到唯一约束冲突，则在同一事务边界之后读取既有任务记录并返回该任务状态，不追加消息、不覆盖上下文、不重新启动对话 turn。若同一调用方和幂等键再次提交时，请求摘要、会话标识、输入消息摘要或关键上下文摘要与既有记录不一致，系统返回幂等冲突状态和既有任务摘要，禁止把新内容写入原任务。

任务记录至少包含调用方标识、幂等键、请求摘要、会话标识、输入消息标识、助手消息标识、执行状态、状态版本、取消标记、当前运行代次、创建时间、更新时间、终态原因和数据保留标记。运行记录至少包含 $taskId$、$runId$、worker 标识、租约截止时间、恢复代次、检查点位置和最近心跳时间。消息片段记录至少包含助手消息标识、片段序号或字节偏移、内容哈希、片段内容、是否已对外可见和所属运行代次。上述字段共同构成状态流转、恢复判定和冲突处理的依据。

登记事务同时写入持久化调度信号，例如 outbox 记录、队列表记录或可扫描的 $queued$ 状态。后台 worker 不是依赖接入线程的内存回调启动，而是扫描该持久化调度信号并按版本条件领取任务：只有当任务状态为 $accepted$ 或 $queued$、输入消息已持久化、未设置取消标记且当前租约为空或已过期时，worker 才能通过比较并交换更新将任务推进到 $running$，递增运行代次并写入新的 $runId$ 和租约截止时间。若登记事务已提交但触发后台执行失败，扫描器仍可根据 $queued$ 状态重新调度；若 worker 崩溃或租约超时，后续 worker 只能在旧租约过期后以新代次重新领取，避免任务已接收却永不执行或多个 worker 同时执行。

### 异步执行与状态管理

任务登记完成后，模型推理由后台执行单元异步触发。所谓异步触发，是指请求线程提交持久化调度信号后即释放外部连接，后台 worker 基于队列表或可扫描状态独立执行。执行单元可以复用现有 $runFiber$、$chatRecovery$ 或等效的持久化执行机制；其中持久化执行机制用于在 SQLite 等存储中登记运行行和检查点，在运行环境被回收后由恢复判定函数根据快照和任务状态决定继续、终止或中断。进入模型调用前，worker 必须确认任务记录存在、输入消息已持久化、状态仍为 $accepted$ 或 $queued$、版本和租约领取成功且未设置取消标记。

状态管理层维护任务从接收到终止的权威执行状态。执行状态包括 $accepted$、$queued$、$running$、$completed$、$error$、$aborted$ 和 $interrupted$；其中 $completed$、$error$、$aborted$、$interrupted$ 为终态。$cleaned$ 不作为执行终态参与迁移，而是数据保留标记，表示结果内容、流式片段或中间快照已按策略清理。每次状态迁移均以 $taskId$、状态版本、运行代次和租约条件作为守卫；旧运行实例、迟到回调或恢复流程若发现版本不匹配，只能停止自身执行并记录冲突诊断，不能回滚或覆盖新代次写入的状态。

| 当前阶段 | 允许迁移至 | 守卫条件 | 失败处理 |
| --- | --- | --- | --- |
| $accepted$ / $queued$ | $running$、$aborted$ | 任务记录存在，输入消息已持久化，状态版本匹配，未设置取消标记，租约为空或已过期 | 领取失败则返回既有状态；租约超时后可重新扫描领取 |
| $running$ | $completed$、$error$、$aborted$、$interrupted$ | $runId$ 与当前运行代次一致，租约未失效或已续约，状态版本匹配，写终态前再次读取取消标记 | 版本不匹配或已终态时丢弃迟到片段，并记录冲突诊断 |
| $completed$ / $error$ | 保持原终态，允许设置数据保留标记 | 已写入终态、终态原因和完成时间；后续请求仅能读取或清理 | 迟到取消、重复提交和恢复回调不得覆盖终态 |
| $aborted$ / $interrupted$ | 保持原终态，允许设置数据保留标记 | 取消已确认，或恢复判定无法安全续跑；保留终态原因和诊断信息 | 迟到模型完成或工具结果不得发布为新结果 |

后台执行产生助手内容时，系统为本次任务固化唯一的助手消息标识，并按片段级唯一键写入流式内容。该唯一键可以采用“助手消息标识 + 单调片段序号”或“助手消息标识 + 字节偏移”。写入时先校验当前执行状态、状态版本和运行代次：相同序号或偏移且内容哈希一致的片段视为重复重放并忽略；序号乱序但前序片段尚未确认时先暂存为不可见片段，待缺口补齐后按序发布；相同序号或偏移但内容哈希不一致时标记运行冲突并尝试将任务转入 $interrupted$；终态写入后到达的任何片段不得再追加到助手消息。

模型完成、模型错误、工具错误和取消结果均通过版本化终态写入规则进入任务表。执行单元在写入 $completed$ 前需校验最后确认片段位置、助手消息版本和取消标记；在写入 $error$ 前需记录错误分类、可重试性、错误摘要和发生阶段。错误可分为模型调用错误、工具执行错误、持久化错误、幂等冲突错误和不可恢复一致性错误；可重试错误可以由扫描器在租约过期或重试窗口内重新领取，不可重试错误直接进入 $error$ 终态。查询接口返回错误类型、发生阶段、是否仍可重试、最近一次 $runId$ 和可供外部排查的摘要，不暴露不必要的内部栈信息。

### 查询、取消与清理控制

状态查询接口以 $taskId$ 为主索引读取持久化任务记录、消息表、运行记录和必要的流式片段信息，而不是依赖内存中的执行对象或仍然存在的客户端连接；$runId$ 仅用于定位最近一次或指定代次的执行实例。查询结果可以包含执行状态、数据保留标记、终态原因、已生成的助手消息标识、最后确认片段位置、错误类型、取消标记、当前运行代次和租约摘要。由于查询只读取权威持久化状态，外部系统即使在提交连接断开、agent 休眠或执行迁移后再次查询，也能获得与实际执行阶段一致的结果。

取消控制与观察连接分离。外部调用方关闭 webhook/RPC 连接、查询轮询中断或观察流断开时，只表示调用方暂时不再接收结果，不自动取消后台对话任务；只有携带 $taskId$ 的显式取消请求才会触发任务取消。取消请求先读取当前状态和状态版本：对 $accepted$ 或 $queued$ 任务，系统通过比较并交换直接写入 $aborted$ 并禁止 worker 领取；对 $running$ 任务，系统写入取消标记、取消时间和取消发起方，并触发与当前 $runId$ 绑定的 $AbortSignal$ 或等效取消控制器，使信号沿 $onChatMessage$、模型流式调用和工具调用链路向下传递。

取消、完成和错误之间的竞态通过状态版本控制闭合。模型完成回调、错误回调和取消请求均必须以当前状态版本执行条件写入，谁先成功写入终态，谁即成为权威结果。若取消标记已经写入但模型随后返回最终结果，执行单元在写 $completed$ 前再次读取状态和取消标记；若任务已变为 $aborted$，迟到模型片段、工具结果和完成回调只能写入诊断记录或被丢弃，不得覆盖 $aborted$。若任务已经是 $completed$、$error$、$aborted$ 或 $interrupted$，重复取消仅返回既有终态。

对于 $running$ 任务，取消待处理状态在执行单元捕获取消异常、模型流关闭、工具调用停止或确认未再产生可见片段后转换为 $aborted$。若工具调用已经向外部系统提交副作用但尚未返回，系统根据工具调用记录判断是否等待幂等结果、执行补偿动作或转入 $interrupted$；若超过取消超时仍无法确认模型或工具已停止，任务转入 $interrupted$ 并阻止后续片段对外发布。清理机制不改变原执行终态，$cleaned$ 仅作为数据保留标记；查询已清理任务时返回终态、终态原因和“结果内容已清理”标记。在幂等保留期内，重复提交同一幂等键仍返回既有任务摘要；保留期外可以按策略拒绝复用、创建新任务或要求调用方更换幂等键，但不得把已清理数据误恢复为新结果。

### 中断恢复与一致性判定

为应对运行环境休眠、重启或执行中断，后台执行单元在启动时写入可恢复运行记录，并在关键阶段调用检查点写入机制保存完整恢复快照。快照至少包括 $taskId$、$runId$、会话标识、输入消息标识、当前阶段、助手消息标识、最后确认片段序号或偏移、工具调用记录位置、请求上下文、状态版本、运行代次和租约截止时间。运行时可通过保活心跳降低中途休眠概率，但不以心跳作为正确性的唯一保障；即使内存状态丢失，恢复流程也以持久化任务记录、运行记录、消息记录、片段记录和工具调用记录为准重新判定。

恢复流程由持久化运行记录和可扫描任务状态触发。agent 下次被请求激活或由持久化定时唤醒机制触发后台检查时，系统扫描未终态任务、过期租约和孤立运行记录，并把任务状态、运行代次、租约、最后片段位置、助手消息一致性、工具调用记录以及模型是否支持续传输入恢复判定函数。该函数输出三类决策：一是继续执行，即以新 $runId$ 或续约后的当前 $runId$ 重新进入后台执行；二是补写终态，即根据已持久化的完整助手消息或明确错误结果写入 $completed$ 或 $error$；三是标记 $interrupted$，即在无法证明继续执行安全时保守终止。

重新进入对话 turn 必须满足严格边界。只有在任务仍处于可继续阶段、输入消息存在、$runId$ 或新运行代次通过版本领取、恢复代次未过期，并且满足以下至少一种条件时，才允许继续模型生成：模型提供基于请求标识的续传能力；尚未产生对外可见的助手片段；或者系统能够把已持久化片段作为不可变前缀，并对后续片段的序号、偏移和内容哈希进行一致性校验。若已经产生对外可见片段且模型不可续传、无法校验后续生成与既有前缀一致，或工具副作用状态不确定，系统不得简单重放模型调用，而应补写可确认终态或将任务标记为 $interrupted$。

工具调用采用独立的幂等记录保护外部副作用。每次工具调用生成稳定工具调用标识，并记录 $taskId$、$runId$、工具名称、参数摘要、执行状态、结果摘要、副作用提交状态和外部幂等键。恢复或重试时先读取工具调用记录：已确认成功且副作用已提交的工具不得再次执行，只能复用结果摘要；尚未发起的工具可以重新执行；已发起但成功状态不明的工具，根据该工具是否支持外部幂等查询或补偿操作选择查询确认、幂等重试、补偿后重试或将任务标记为 $interrupted$。该机制避免同一工具调用在恢复或重复执行中重复扣费、重复发送通知或重复修改外部系统。

### 与现有对话和子 agent 机制的兼容

本方案不替换现有对话系统的消息模型，而是把外部任务接入为一种新的对话 turn 来源。外部输入在登记后转换为现有会话中的用户消息，后续仍由 $onChatMessage$、模型流式响应、消息持久化和广播或结果存储机制处理。现有的请求上下文、客户端工具 schema、模型参数或业务扩展字段可以作为任务上下文持久化，使 agent 在休眠或重启后仍能使用与原始请求一致的上下文继续执行。

当一次外部任务需要路由到子 agent、分面实例或多 agent 编排时，$taskId$ 作为跨 agent 的统一关联标识，子任务可以拥有各自的 $runId$ 和运行代次。子 agent 内部保存自身的运行记录、快照和消息状态，父 agent 保存子 agent 地址、子任务标识、路由版本、最近心跳和聚合状态等轻量索引。父任务状态由子任务状态聚合得到：全部关键子任务 $completed$ 后父任务才可写入 $completed$；任一关键子任务进入不可重试 $error$ 或 $interrupted$ 时，父任务写入对应错误或中断摘要；可选子任务失败时可按策略降级但需记录诊断。

跨 agent 取消和恢复同样遵循版本化规则。显式取消先在父任务写入取消标记和状态版本，再向各子 agent 广播携带 $taskId$、子任务标识和目标版本的取消请求；子 agent 已终态时返回既有终态，未终态时按本地规则取消并上报结果。若子 agent 不可达、路由索引过期或取消传播失败，父任务进入取消待处理或 $interrupted$，并保留不可达地址、最后心跳和传播失败原因；后续恢复扫描根据路由版本重新转发取消或查询请求。该规则避免父级观察连接断开、路由过期或部分子任务完成时错误取消仍在执行的子任务。
