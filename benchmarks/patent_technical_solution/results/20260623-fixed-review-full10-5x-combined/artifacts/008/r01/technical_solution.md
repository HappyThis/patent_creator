## 技术方案

本方案提出一种保留式流式子 agent 工具编排机制，用于在用户仍只面对一个主 agent 会话的情况下，使主 agent 能在一次请求中调度一个或多个专门子 agent 执行研究、规划、比较、总结等任务，并将各子 agent 的执行过程、阶段性输出和最终结果带回同一主会话视图。该机制不把子任务降级为内存中的临时函数调用，而是把每个子 agent 工具运行建模为具有独立执行上下文、持久化流和可检查生命周期的 durable work；父 agent 负责登记、观察、转发、恢复协调和权限门控，子 agent 负责真实的推理、工具调用、消息保存和可恢复流持久化。

### 技术问题与处理目标

在普通内存式工具调用中，子任务通常依附于父请求的调用栈和临时流连接。当子任务运行时间较长、多个子任务并行、浏览器刷新、网络断开或父进程重启时，容易出现子任务输出未持久化、重复启动同一任务、父侧状态与子侧实际执行状态不一致、无法恢复观察入口、取消与连接中断难以区分等问题；若把子任务中间消息直接混入主 agent 上下文，还会造成上下文污染，并使用户后续难以进入某个子任务查看完整过程。

本方案围绕上述问题建立 durable work 编排机制：以稳定运行标识约束重复请求，以父侧运行索引和子侧执行索引共同记录任务来源和执行入口，以子侧可恢复流作为输出权威来源，以父侧事件包装和客户端重建恢复主会话展示结构，以显式状态机区分完成、失败、取消和观察中断。由此，避免重复启动依赖唯一键和原子 claim，避免流式输出丢失依赖子侧先持久化 chunk 再转发，避免上下文污染依赖子 agent 独立消息存储和父侧仅保存摘要或事件引用。

### 总体架构与独立执行上下文

总体上，主 agent、父侧运行索引表、子 agent 实例、子侧执行索引表和客户端状态重建器构成一条保留式编排链路。父侧运行索引表简称父运行表，用于记录子运行与主会话、父工具调用、展示顺序和生命周期状态的关系；子侧执行索引表简称子执行表，用于记录 $runId$ 与真实 chat turn、可恢复流和子侧终态之间的关系。父 agent 负责登记、观察、转发、恢复协调和权限门控，子 agent 负责真实推理、工具调用、消息保存和可恢复流持久化。

子 agent 是挂接在父 agent 之下的 chat-capable 持久对象或等价子实例，而不是父 agent 进程内的一段临时代码。每个子 agent 可以具有独立的消息记录、工具集合、模型配置、会话状态、SQLite 存储、可恢复流和 WebSocket 连接；父 agent 可以通过子 agent 路由创建或取得该实例，并在路由进入前执行访问控制。该独立上下文使研究型、规划型、比较型等长任务不会污染主 agent 的消息上下文，也便于后续单独查看子任务的推理轨迹和输出。

该架构中，父 agent 与子 agent 的职责保持分离：父 agent 不直接改写子 agent 的内部消息，也不把子 agent 的中间状态混入主会话上下文；子 agent 只通过约定的启动、检查、取消、读取 chunk 等适配接口向父侧暴露运行信息。这样既保留了子 agent 作为普通 chat agent 的可复用能力，又使父 agent 可以在一个主请求中对多个子 agent 进行统一编排和结果汇总。

### 运行标识与双侧持久映射

每个子 agent 工具运行以 $runId$ 作为编排层标识。$runId$ 用于去重、恢复、取消、检查和清理，同一 $runId$ 的重复启动请求只返回已有运行状态，不重新创建推理任务。父侧还可记录 $parentToolCallId$，用于把子运行挂接到主会话中的某个工具调用部位；对于没有直接父工具调用的后台子运行，该字段可以为空，客户端将其归入独立的未绑定运行集合。

父运行表记录 $runId$、租户或用户范围、父会话标识、$parentToolCallId$、子 agent 类型、输入预览、输入是否脱敏、展示元数据、展示顺序、运行状态、摘要、错误信息、开始时间和完成时间等信息。父运行表不同于普通子 agent 注册表：普通子 agent 注册表用于判断某个子实例是否存在，父运行表用于回答该子运行由哪一次父会话工作触发、应显示在主会话的哪个位置、恢复时需要综合哪些子侧内容。

子侧设置子执行表，记录 $runId$ 与实际 chat turn 的 $requestId$、可恢复流的 $streamId$、子侧状态、摘要和错误信息之间的对应关系。$runId$ 是产品和编排层的稳定标识，$requestId$ 是一次子 agent chat turn 的执行标识，$streamId$ 是读取持久化 chunk 的流标识。子执行表对 $runId$ 设置唯一约束，并与 $requestId$ 形成一对一关系，使恢复过程可通过 $runId$ 查询权威执行入口，避免重复启动或丢失恢复入口。

| 对象 | 生成方/位置 | 约束与更新时机 |
| --- | --- | --- |
| $runId$ | 父 agent 生成或调用方传入；父运行表与子执行表均保存 | 在同一租户、父会话和子 agent 类型范围内唯一；创建 starting 记录时确定，后续不变 |
| $parentToolCallId$ | 父 agent 保存于父运行表 | 可为空；非空时定位主会话工具调用位置，后台运行为空 |
| $requestId$ | 子 agent 启动 chat turn 时生成并保存于子执行表 | 与 $runId$ 一对一；用于取消和检查当前 turn |
| $streamId$ | 子 agent 创建可恢复流时生成并保存于子执行表 | 与本次 turn 的 chunk 序列绑定；父侧重放时按该值读取 |
| $sequence$ | 父 agent 包装事件时确定 | 在同一 $runId$ 内单调递增；重放时保持原序号 |
| 状态、摘要、错误信息 | 父运行表与子执行表分别保存 | 状态按迁移规则更新；摘要在 completed 写入，错误信息在 error、aborted 或 interrupted 写入 |
| 展示顺序、输入预览 | 父 agent 保存于父运行表 | 展示顺序在创建时确定；输入预览写入前截断并脱敏，默认不保存完整输入 |

1. 父 agent 接收 runAgentTool 后，先按租户、父会话、子 agent 类型和 $runId$ 查询父运行表；若存在终态记录，直接返回已有摘要、输出或错误信息。
2. 若存在非终态记录，父 agent 不再启动新的子 turn，而是返回当前状态、观察入口和已知 $streamId$，或者为当前调用附加一个新的观察者。
3. 若不存在记录，父 agent 在唯一键约束下原子插入 starting 行，并写入输入预览、脱敏标记、展示顺序和 $parentToolCallId$；插入冲突时重新读取既有记录并按前两项处理。
4. 父 agent claim 对应子 agent 实例后，调用子 agent 创建子执行表映射；子 agent 以 $runId$ 为唯一键创建 $requestId$ 和 $streamId$，若子侧冲突则返回既有映射而不是新建 turn。
5. 父 agent 将子侧返回的 $requestId$、$streamId$ 或可检查入口回填父运行表，并把状态从 starting 迁移为 running；随后开始观察子侧可恢复流并转发事件。
6. 若子侧映射已创建但父侧回填前崩溃，恢复流程通过 $runId$ 查询子执行表，将 $requestId$ 和 $streamId$ 回填父运行表；若无法查询到子执行表，则按 interrupted 或 error 处理。

### 保留式流式事件转发

子 agent 的流式输出以其自身可恢复流作为权威来源。子 agent 在执行 chat turn 时把模型增量、工具调用片段和消息构造片段保存为有序的 UI message chunk，并按流标识持久化在子 agent 存储中；父 agent 只作为观察者读取这些 chunk，将其包装为面向主会话客户端的 agent-tool-event，而不在父侧复制一套新的权威流。由此，即使父侧观察连接中断，子 agent 已产生的输出仍可从子侧持久化流重放。

父 agent 转发的事件可以统一表示为 agent-tool-event，并携带 $parentToolCallId$、$runId$、事件序号、是否为重放事件以及事件主体。事件主体至少包括 started、chunk、finished、error、aborted 和 interrupted 等类型，其中 chunk 的内容保持为 JSON 编码的 UI message chunk，父 agent 不解析其中的模型文本、工具片段或消息部件结构，只负责排序、包装和转发。

事件序号用于在主会话内稳定合成子 agent 过程。同一父工具调用下可能并行存在多个子 agent，因此客户端去重键至少包括 $parentToolCallId$、$runId$ 和 $sequence$，而不能只依赖序号本身。父侧可在 started 事件中发送子 agent 类型、$runId$、展示顺序和输入预览，在 chunk 事件中发送子侧流片段，在 finished、error、aborted 或 interrupted 事件中发送摘要、错误原因或中断原因。

事件序号采用父侧包装序号与子侧 chunk 序号相结合的规则。started 事件固定为该 $runId$ 的首个父侧事件序号；每个 chunk 事件保留子侧 chunk 的原始索引，同时由父侧分配递增的 $sequence$；finished、error、aborted 和 interrupted 等终态事件使用最后一个 chunk 之后的下一个序号。父运行表可保存最后已转发序号和最后读取的子侧 chunk 游标；重放时仍使用原序号并标记 replay，客户端以 $parentToolCallId$、$runId$、$sequence$ 去重，避免刷新后同一片段重复显示。

chunk 的处理顺序为子 agent 先把 UI message chunk 写入可恢复流并提交，再通知父 agent 观察者读取；父 agent 按 $streamId$ 和游标批量读取，只有读取到连续可校验的 chunk 时才包装转发。若读取到重复 chunk，父侧按序号去重；若发现缺号，父侧短暂重试并重新读取该游标之后的数据；若 chunk 损坏或类型未知，父侧不解析其业务内容，而是记录错误并将该运行标记为 error 或 interrupted。finished、error、aborted 等终态不依赖父侧解析 chunk 文本，而以子执行表状态和子 agent 检查接口为准。

### 多子 agent 编排与后台运行

主 agent 可以通过两类入口调度子 agent。第一类是命令式的 runAgentTool，用于确定性工作流、后台任务、分阶段报告或非模型编排场景，调用方显式提供子 agent 类型、输入、$runId$、展示顺序和取消信号。第二类是 agentTool，用于把子 agent 暴露为父模型可选择的工具，其输入模式用于父模型生成和校验参数，内部仍转换为 runAgentTool，并把子 agent 的摘要、结构化输出或结构化失败信息返回给父模型继续生成主回答。

对于一次主请求需要多个专门子 agent 协作的场景，父 agent 可以为每个分支分配不同 $runId$ 和展示顺序，并在同一 $parentToolCallId$ 下并行启动多个子运行。例如比较任务可以同时派发两个研究型子 agent，分别收集候选方案信息；父 agent 等待各分支完成或失败后进行 fan-in 汇总，并将每个分支的成功、失败或取消状态结构化返回，而不因单个分支失败而丢弃其他已完成分支。

后台子运行通过缺省或空的 $parentToolCallId$ 表示没有直接父工具调用。此类运行仍具有 $runId$、父运行表记录、子执行表记录、可恢复流、取消入口和清理入口，可以用于主 agent 在返回前后继续执行的长任务、定时补充分析或用户稍后查看的研究任务。由于其不挂接到某个父工具调用，客户端通过未绑定运行列表展示其状态，并可按 $runId$ 进入对应子 agent。

为避免重复请求、并发执行和上下文污染，runAgentTool 对 $runId$ 幂等：已有终态时返回已有结果，已有非终态时返回当前检查状态或复用同一观察入口，不启动第二个相同 turn。对于同一个子 agent 实例和同一个 $runId$，框架在子 turn 运行期间保持独占 claim，用户通过 drill-in 发起的新 chat turn可以延迟、拒绝或排队；对于不同 $runId$ 的子运行，父侧允许并行执行，并可通过 maxConcurrentAgentTools 等粗粒度限制在资源紧张时快速产生清晰错误事件。

fan-in 汇总时，每个子分支向父 agent 返回统一结果对象，至少包含 $runId$、子 agent 类型、终态、摘要、结构化输出、错误码、错误消息、是否可重试和完成时间。父 agent 可配置等待全部分支、等待达到最小成功数量或到达超时阈值后提前汇总；默认不因单个分支失败自动取消其他分支，而是保留已成功结果并把失败分支作为结构化失败项返回。多个结果相互冲突时，父 agent 按任务类型、完成状态、结构化输出校验结果、时间新鲜度和预设置信度权重进行合并，并在无法确定时保留冲突项供主回答说明。

并发配额检查优先在父侧 claim 前执行，以避免超额任务写入后又立即失败。配额维度可以包括用户、父会话、租户和全局运行数；已有 running 和 starting 任务计入配额，已终态但未清理任务不计入执行配额。超出配额时，父 agent 可按配置选择排队、拒绝或快速失败；快速失败模式下可写入 error 终态记录并发送 error 事件，使主会话能够显示明确的未启动原因。

### 状态迁移与异常窗口处理

| 状态 | 进入条件 | 允许迁移或终态规则 |
| --- | --- | --- |
| starting | 父运行表原子插入成功，但子侧映射或执行入口尚未完全确认 | 可迁移到 running、error 或 interrupted；若恢复时确认子侧未创建，可迁移到 interrupted 或 error |
| running | 子执行表已创建，$requestId$ 与 $streamId$ 已确认，子 agent turn 正在执行或可被检查 | 可迁移到 completed、error、aborted 或 interrupted |
| completed | 子 agent 已产生完整结果并写入摘要或结构化输出 | 终态，不被迟到取消、重复观察或重放事件覆盖 |
| error | 子 agent 或父侧协调出现不可继续的执行错误、校验错误或持久化错误 | 终态，不被迟到取消覆盖；可保留错误码和错误消息 |
| aborted | 父侧或用户显式取消已被子 agent 确认，或者子 agent 确认因取消信号停止 | 终态，不表示网络断开；保留已持久化的部分 chunk |
| interrupted | 父侧无法安全恢复观察关系、无法确认子侧映射，或未实现实时尾流重附着但子侧仍非终态 | 父侧终态；若实现明确的尾流重附着扩展，可在检查仍为同一 $runId$ 和 $streamId$ 后生成补齐事件，否则不再覆盖 |

父侧状态与子侧状态不一致时，协调优先级为：已确认的子侧 completed、error、aborted 终态优先于父侧非终态；父侧已写入 completed、error、aborted 或 interrupted 时，不被迟到取消或重复启动覆盖；若父侧为 running 而子侧无对应 $runId$，说明映射丢失或创建未完成，父侧转为 interrupted 并停止观察；若父侧为 starting 而子侧已存在同 $runId$ 映射，父侧以子执行表的 $requestId$、$streamId$ 回填并继续协调。该规则通过终态不可覆盖和子侧执行入口回填保证父子状态最终一致。

1. 父运行表写入前崩溃：由于唯一键记录尚未形成，后续同一请求可按新请求重新 claim；若调用方复用同一 $runId$，不会在父侧产生重复记录。
2. 父运行表 starting 已写入但子侧未创建：恢复扫描到 starting 后查询子执行表；若无同 $runId$ 映射且超过启动协调窗口，写入 interrupted 或 error，并记录未创建原因。
3. 子执行表已创建但父侧未保存 $requestId$ 或 $streamId$：恢复时父侧按 $runId$ 调用子 agent 检查接口，读取子执行表并回填父运行表。
4. 子侧已产生 chunk 但父侧未转发：父侧根据 $streamId$ 和游标从子侧可恢复流读取历史 chunk，以 replay 事件补发，避免流式输出丢失。
5. 父侧已转发但客户端未确认：父侧不以客户端确认为权威，重连后仍按最后持久游标或从头重放，客户端用去重键过滤重复事件。
6. 子侧已完成但父侧未收到终态：父侧检查子执行表终态，重放剩余 chunk 后发送 finished、error 或 aborted 事件，并把父运行表更新为相同终态。

### 恢复、重放与中断协调

恢复机制把“执行是否继续”和“观察者是否在线”分离处理。启动子 agent 工具运行后，即使浏览器刷新、网络短暂断开或主会话 WebSocket 重新连接，子 agent 的 chat turn 仍以自己的请求标识和可恢复流继续推进；重新连接时，父 agent 根据父运行表查找未终结或已终结的运行，再根据子执行表取得对应的请求标识和流标识，从子 agent 的持久化 chunk 中重放已产生内容，并继续合成主会话视图。

在父 agent 重启或恢复主会话时，父侧先扫描父运行表中的 starting 或 running 记录并进行协调。若找不到对应子执行表记录，说明启动过程未完成或状态不可安全判定，父侧将该运行标记为 interrupted 并给出原因；若子侧运行已经到达 completed、error 或 aborted 等终态，父侧按 $streamId$ 重放剩余 chunk，并把父侧状态更新为相同终态；若子侧仍在运行且当前实现不支持重新附着到实时尾流，父侧可先重放已有 chunk，再把主会话视图中的该运行标记为 interrupted，以明确表示执行和观察之间的断裂边界。

运行状态至少包括 starting、running、completed、error、aborted 和 interrupted。completed、error、aborted、interrupted 为终态；当父运行表已经写入终态时，该终态作为主会话视图的权威状态，迟到的取消请求或重复观察不会把 completed 或 error 改写为 aborted。interrupted 是父侧用于表达观察或恢复不完整的状态，不要求子 agent 自身产生该状态，由父 agent 在无法安全继续直播或无法确定子侧执行关系时合成。

### 访问控制、取消与保留结果清理

访问控制不依赖 $runId$ 本身作为能力凭证，而是继承父 agent 的租户、认证和会话边界。客户端若通过子 agent 路由直接查看某个子运行，父 agent 先执行 onBeforeSubAgent 门控，检查请求中的子 agent 类型和名称是否对应父侧运行注册表中的合法记录，并可结合当前用户身份、父会话归属和运行状态决定放行、改写请求或拒绝访问。这样可以避免攻击者通过猜测嵌套 URL 任意创建或进入子 agent。

onBeforeSubAgent 门控的输入至少包括当前用户身份、租户、父会话标识、子 agent 类型、$runId$、请求动作、父运行表记录和运行状态。门控先验证租户与父会话归属，再验证子 agent 类型与父运行表记录一致，随后检查该运行是否已清理、是否允许 drill-in、是否存在正在执行的独占 claim；输出可以是 allow、deny、rewrite 或 require-auth。对于非法 $runId$、跨租户访问、类型不匹配或未授权请求，父侧返回通用错误并记录审计日志，避免通过错误差异泄露 $runId$ 是否存在。

取消链路从父会话请求传播到子 agent turn。当父 chat、父工具调用或显式取消接口触发取消时，父 agent 依据 $runId$ 调用子 agent 的取消方法，子 agent 查找该运行对应的请求并触发每 turn 的 AbortController；该取消信号传入消息保存和模型推理循环，使子 agent 停止继续生成，写入 aborted 终态并通知父侧。仅关闭浏览器连接、断开 observer stream 或发生重放连接失败，不视为取消运行，而只解除当前观察者。

取消与完成竞争按终态优先规则处理。父侧发出取消时，若子执行表已经为 completed 或 error，父侧保持该终态并把取消请求视为迟到；若子 agent 正在写入最后 chunk，已经持久化的 chunk 仍保留并可重放，后续以子侧首先确认的 completed、error 或 aborted 为准；若 AbortController 触发后模型或工具仍返回少量 token，子 agent 仅在取消边界之前已提交的 chunk 中保留这些输出，取消边界之后的输出不再进入可恢复流。取消请求失败或超时时，父侧不直接伪造 aborted，而是标记 interrupted 或 error，并保留可检查入口供后续清理。

保留结果清理采用显式生命周期管理。默认情况下，子运行在 completed、error、aborted 或 interrupted 后仍保留父运行表记录、子 agent 实例和子侧可恢复流，以支持刷新重放、后续查看和调试。清理接口可以按时间、状态、会话或数量条件删除保留结果；若目标运行仍处于 starting 或 running，应先按 $runId$ 取消对应子运行，再删除父运行表记录和子 agent 实例，避免留下不可见但仍消耗资源的孤儿推理任务。

清理时先在父运行表中对目标 $runId$ 设置清理中标记或短事务锁，使新的观察者和 drill-in 请求得到稳定的失效响应；若运行仍为 starting 或 running，先发送取消并等待子执行表确认终态。确认终态后，先删除或封存子侧可恢复流和子 agent 实例，再删除父运行表记录或将其改写为已清理占位记录；若取消确认超时，则保留父运行表中的 interrupted 或 error 状态并安排后续清扫，避免在子任务仍可能运行时直接丢失管理入口。清理后，主会话历史中的子运行入口显示为已清理或不可用，而不是尝试读取已删除的 chunk。

### 客户端状态重建与后续查看

客户端侧可以设置纯状态重建器和界面 hook 来处理 agent-tool-event。状态重建器按 $parentToolCallId$、$runId$ 和事件序号去重，将同一父工具调用下的多个子运行按展示顺序分组，并使用与主 chat 相同的 chunk 应用逻辑把子 agent 的 UI message chunk 还原为消息部件。对于没有 $parentToolCallId$ 的后台运行，客户端将其放入 unboundRuns，以便在主会话外的任务列表、侧边栏或通知区域展示。

父侧虽然不保存 chunk 正文作为权威流，但必须保存足以恢复展示结构的轻量信息，包括 $runId$、$streamId$ 或可查询子执行表的入口、$parentToolCallId$、展示顺序、最后转发序号、状态和终态摘要。客户端刷新后先依据父运行表重建主会话中的子运行容器，再按 $streamId$ 和读取游标请求重放 chunk；因此主会话可以稳定显示完整过程，而不需要把子 agent 的全部流式正文复制到父侧存储。

在主会话界面中，子 agent 输出可以呈现为父工具调用下的可展开区域：进行中时显示流式文本、工具片段和状态；完成后保留摘要和完整子运行入口；失败、取消和中断分别显示不同终态，避免把异常误认为空结果。用户需要继续查看细节时，客户端根据状态中暴露的子 agent 类型和 $runId$ 建立嵌套路由连接，进入子 agent 自己的会话视图，从其独立消息、工具记录和可恢复流中查看完整过程。

多个浏览器标签或多个客户端可同时观察同一 $runId$。父 agent 可以为每个观察者维护独立读取游标，也可以从同一子侧流读取后广播给多个观察者；无论采用哪种方式，观察者断开只影响该观察者的游标或连接，不取消子 agent 运行，也不影响其他观察者。某一观察者发起取消时必须通过父侧显式取消接口并通过权限检查，不能仅因关闭连接或停止读取而影响其他观察者。

### 适配条件与可选扩展边界

本方案的适配边界是结构性的 chat-capable agent，而非限定于某一种内部推理框架。可作为子 agent 工具的实例应能够被父侧以程序方式启动一次 chat turn，能够产生可按序持久化和重放的 UI message chunk，能够接受外部 AbortSignal，能够暴露按 $runId$ 检查、取消和读取 chunk 的接口，并能够把自身消息、工具调用和恢复数据保存在独立存储中。在此基础上，父 agent 和子 agent 可以采用相同或不同的 chat agent 实现，只需满足上述适配契约即可纳入同一编排机制。

输入数据的持久化边界由父侧和子侧分别控制。完整输入通过内存调用、RPC 或等价受控通道传递给子 agent，并可作为子 agent 本次 turn 的用户消息或系统化任务消息进入子侧消息记录；父运行表默认只保存截断后的输入预览、脱敏标记和输入哈希或长度等元数据，不保存凭据、文件全文、私密提示词、访问令牌和未脱敏外部数据。敏感字段可由调用方声明，也可按字段名、内容类型或策略规则识别；若预览脱敏失败，父侧应拒绝启动或仅写入不可逆占位预览，并把失败原因写入 error 事件。

drill-in 的普通新 chat turn 默认不得与同一子 agent 实例上的 agent tool turn 并发交错。当子 agent 正在执行 $runId=A$ 时，用户进入子会话发起普通消息，系统默认等待 $A$ 到达终态后再接收，或返回需稍后重试的拒绝响应；若用户选择强制取消，则先通过父侧取消链路终结 $A$，再启动新的普通 turn。排队消息只有在 $A$ 终态后才进入该子 agent 的消息上下文，以免影响父侧仍在汇总的 $A$ 的摘要和结构化输出。

在一种可选扩展中，子 agent 可以提供 tailAgentToolRun 接口，使父 agent 在恢复后不仅重放历史 chunk，还能从指定序号之后重新附着到仍在运行的实时尾流；在未实现该能力的版本中，父 agent 可通过 interrupted 状态明确提示观察已中断但保留已生成结果。另一种可选扩展是为输入全文持久化、结构化输出校验、跨层级 tracing 或更细粒度并发配额提供配置项，但默认仅在父侧保存输入预览和脱敏标记，以降低敏感提示词、凭据或文件内容被重复复制到编排表中的风险。
