## 技术方案

现有智能工作台中，任务派发、Agent 状态、聊天消息、会话成本、活动流、质量评审、评估轨迹和安全审计分别由不同入口产生。如果这些记录仅停留在各自模块内，系统在事后追溯时需要人工拼接任务编号、会话编号、Agent 名称和时间戳，容易出现同一次执行被重复统计、迟到成本无法归因、评估结果覆盖历史记录、外部工具只能看到局部状态等问题。本方案在不割裂既有任务、Agent、会话、事件和工具入口的前提下，设置以 $run\_id$ 为事实粒度的结构化运行记录链路：入口侧负责生成或绑定运行实例，执行侧持续追加运行事件，查询侧由事件折叠得到阶段快照并关联结果、成本、评估和审计记录。由此，系统能够以同一条运行链回答一次 Agent 工作从哪里触发、由谁执行、关联哪个任务或会话、产出什么结果、消耗多少资源、是否经过评估以及能否被其他工具复用。

### 统一 Agent 运行记录模型

本方案设置统一的 Agent 运行记录模型，并将术语边界固定如下：运行实例是一次 Agent 执行的主记录，以系统生成的全局唯一 $run\_id$ 标识；外部运行键是网关、调度器、CLI、webhook 或其他执行侧返回的外部执行标识；运行事件是围绕 $run\_id$ 追加写入的过程事实；阶段快照是由运行事件折叠得到的当前状态缓存；产物引用指向消息回复、文件、任务结果或工具输出等结果对象；评估指针指向质量评审、Agent Eval、MCP 审计或安全审计的原始记录。无论底层采用物理表还是逻辑视图，均应具备运行主记录、外部键映射、运行事件明细、阶段快照、结果/成本/评估关联引用五类最小数据单元。

运行主记录保存 $run\_id$、工作区或租户标识、项目标识、触发入口、触发对象、Agent ID、任务 ID、消息 ID、会话 ID、父运行 ID、执行状态、执行阶段、开始时间、更新时间、结束时间、错误码和重试次数。外部键映射记录以“工作区或租户标识、外部系统类型、external_run_key”为唯一约束，并指向唯一 $run\_id$；当同一外部运行键试图绑定多个内部运行实例时，以最早成功绑定的实例为主记录，后到绑定进入冲突状态并保留引用，不直接覆盖主记录。运行事件表以 event_id 为去重主键，以 $run\_id$ 为逻辑外键；阶段快照以 $run\_id$ 为主键并带有版本号；成本、评估和审计关联表保存原始记录主键、来源系统、采集时间、匹配置信度和关联版本。由此，统一查询和统计均以 $run\_id$ 为事实粒度，以原始记录引用为审计依据，避免仅保存摘要造成的不可追溯。

运行状态采用受控枚举和禁止迁移规则。初始状态为 `created`，入口解析并完成绑定后进入 `bound` 或 `claimed`，Agent 开始执行后进入 `running`；执行完成后进入 `succeeded`，异常结束后进入 `failed`、`timeout` 或 `cancelled`；评审或评估完成后只更新评估状态、评估版本和关联指针，不改变执行终态。`succeeded`、`failed`、`timeout` 和 `cancelled` 为执行终态，普通执行事件不得将终态回退为 `running`。若任务回退或重试，系统记录 attempt 序号并可生成子 $run\_id$，父运行保留原终态和重试指针；只有明确的修正事件且来源优先级高于原终态来源时，才允许更新最终产物引用、结束时间或终态错误码，并同步追加审计事件。

| 字段组 | 示例内容 | 技术作用 |
| --- | --- | --- |
| 触发关联 | 触发类型、触发入口、外部连接标识、消息标识、流水线运行标识 | 还原一次执行从哪里发生，并区分任务队列、会话转发、CLI、调度和外部回调等来源 |
| 执行主体 | Agent 标识、Agent 名称、角色、工作区、项目或租户标识 | 确定由哪个 Agent 在什么边界内执行，便于权限控制、排行榜统计和责任归因 |
| 上下文关联 | 任务标识、会话标识、会话模型、父子运行标识、关联活动标识 | 把任务看板、聊天线程、会话 transcript 和活动流连接为同一次工作 |
| 运行状态 | 状态、阶段、开始/结束时间、耗时、错误码、重试次数 | 支撑实时展示、失败恢复、超时处理和审计回放 |
| 结果与扩展 | 输出摘要、产物引用、成本摘要、评估指针、审计指针、扩展 metadata | 使结果、成本、质量评测和外部系统复用具有稳定索引 |

### 触发归一化与溯源绑定

本方案在各类触发入口设置归一化适配层，并按确定流程处理入口载荷。第一步解析工作区或租户、入口类型、触发对象、Agent ID、任务 ID、消息 ID、会话 ID、流水线运行标识、外部运行键和请求幂等键；其中工作区或租户、入口类型、触发对象以及至少一个可追踪来源键是创建运行实例的前置条件。第二步按优先级查找已有运行实例：先查外部运行键映射，再查请求幂等键，再查任务、消息或流水线唯一标识，最后才允许使用会话、Agent ID 与时间窗口进行候选过滤；时间窗口只能缩小候选范围，不得单独作为幂等依据。第三步根据查找结果执行唯一命中绑定、未命中创建、多个候选冲突处理或无效载荷挂起。由此，运行实例的创建和绑定由稳定键驱动，而不是依赖人工判断或模糊时间匹配。

幂等绑定规则以“唯一命中且边界不冲突”为准。若命中唯一外部运行键、请求幂等键或业务对象唯一键，并且工作区、Agent ID、入口类型和触发对象不存在冲突，则更新该运行实例的绑定信息并追加绑定事件；若未命中，则生成新的 $run\_id$ 和运行主记录；若命中多个候选，或同一外部运行键对应多个内部运行实例，则新到载荷不覆盖既有记录，而是写入冲突队列并保留冲突原因、候选 $run\_id$ 和原始载荷摘要。该规则兼容现有 `tasks`、`agents`、`messages`、`claude_sessions`、`token_usage`、`activities` 和事件总线，使运行记录成为既有业务链路的索引层，而不是替代原有任务、会话或活动表。

并发和重复场景按执行语义区分处理。同一任务被多个 Agent 竞争领取时，只有成功领取者生成或进入执行运行，失败领取者只追加领取尝试事件；若任务被配置为并行执行，则为各 Agent 生成并列子运行并用父 $run\_id$ 关联。同一聊天消息转发给多个 Agent 时，消息 ID 可关联多个运行实例，不强行合并为一个 $run\_id$。webhook 或网关重放到达时，若 event_id 或 payload_hash 相同则去重；若 event_id 相同但 payload_hash 不同，则记录异常事件并拒绝覆盖既有结果。外部网关先返回完成事件、后返回开始事件时，开始事件可补充到事件轨迹中，但不得把已处于终态的阶段快照回退为执行中。由此，通过幂等键、父子运行和冲突队列分别处理重复、并行和异常载荷，避免同一次执行被重复创建或错误合并。

### 事件驱动的执行过程沉淀

本方案将执行过程拆分为追加写入的运行事件和可覆盖更新的阶段快照。每条运行事件至少包括 event_id、$run\_id$、event_type、event_time、producer、sequence 或 version、payload_hash、payload_summary、trace_id、工作区或租户标识和原始载荷引用。写入事件的前置条件是存在有效 $run\_id$，或者入口适配层能够先创建占位运行记录；事件生产方应提供唯一 event_id 或同一 producer 内递增 sequence。事件表作为审计源只追加不原地改写，阶段快照作为查询缓存由事件增量折叠得到，并通过版本号或乐观锁更新当前状态、阶段、最近输出、错误信息、重试次数和更新时间。由此，系统既保留可回放的执行轨迹，又能为看板和 API 提供低成本的实时状态查询。

事件折叠遵循状态机和排序规则。对同一 $run\_id$，系统按照 event_time、producer sequence 和写入时间的组合顺序回放事件；重复 event_id 直接丢弃，payload_hash 相同的重放事件只增加投递记录，不改变快照。乱序或迟到事件允许补充事件时间线，但若快照已经进入 `succeeded`、`failed`、`timeout` 或 `cancelled` 等终态，迟到的普通开始、执行中或阶段输出事件不得回退终态，只能作为补充轨迹或触发修正流程。并发事件更新快照时先比较快照版本，版本不一致则重新读取事件并折叠后重试更新，避免较旧事件覆盖较新状态。

异常恢复以可配置 SLA、Agent 心跳和网关等待结果为依据。若运行超过入口配置的 SLA、Agent 心跳在阈值内未更新，或网关 wait 返回超时，则追加超时事件并将快照置为 `timeout`；超时后可根据入口策略取消下游任务或继续等待迟到结果。迟到的成功结果默认不直接把 `timeout` 改为 `succeeded`，而是作为修正候选或人工/后台恢复事件处理；若策略允许“超时后成功”，则必须追加高优先级修正事件并保留原超时事件。失败重试时记录重试次数、重试间隔和 attempt 标识，未超过上限的重试生成子运行或 attempt 记录，超过上限后保持 `failed` 终态。若工具调用失败但 Agent 仍返回最终结果，运行状态可为 `succeeded`，同时在风险事件、评估状态或工具可靠性指标中记录局部失败。

| 运行阶段 | 触发条件 | 记录内容 |
| --- | --- | --- |
| 创建/绑定 | 任务创建、队列领取、聊天转发、CLI 连接或外部回调进入 | 记录触发源、Agent、任务、会话、外部运行键和初始状态 |
| 执行中 | Agent 状态变化、网关 wait 返回、工具调用或阶段性输出产生 | 记录工具名称、输入输出摘要、执行状态、阶段进度、耗时和错误信息 |
| 完成/异常 | Agent 返回最终结果、超时、取消、失败或任务被回退 | 记录最终状态、结果摘要、产物引用、失败原因、重试次数和结束时间 |
| 评审/评估 | 质量评审、Agent Eval、MCP 审计或安全审计完成 | 记录评审结论、评估层级、分数、轨迹引用、风险事件和可信度变化 |

### 结果、成本与评估附着

本方案把运行结果、资源消耗、质量评估和审计信息作为运行实例的关联数据，而不是把它们混写为一条不可拆分日志。结果附着时，优先使用 $run\_id$ 或外部运行键定位运行实例，写入最终状态、输出摘要、消息回复标识、工具调用标识、产物引用和结果来源；若结果来自聊天、任务或文件产物，则保留原始消息 ID、任务 ID 或产物 ID。最终产物引用、结束时间和终态错误码进入终态后不得被普通迟到事件覆盖，只有更高优先级的修正事件可以更新，并且必须保留更新前后的审计轨迹。由此，任务看板、聊天线程和外部工具引用的是同一份结果事实，同时仍能追溯结果从哪个原始对象产生。

成本、评估和审计的延迟补全采用分支匹配规则。补全记录优先使用 $run\_id$ 或外部运行键绑定；缺失时，再使用会话 ID、消息 ID、工具调用 ID、任务 ID、Agent ID、模型、时间范围和来源系统组合匹配，其中 Agent ID 是强匹配字段，Agent 名称仅作为展示字段或弱匹配字段。匹配结果唯一时，系统补写关联引用、来源系统、原始记录主键、采集时间和匹配置信度；出现多个候选时进入冲突队列，不自动选择；无候选时生成悬挂记录，并在后续运行事件、会话扫描或成本上报到达后重试匹配。由此，异步子系统产生的迟到数据能够最终归并到正确运行实例，又不会因模糊匹配造成误绑定。

成本附着时，系统保留原始 token 用量记录的主键引用，并按模型、token 类型、模型价格版本、时间区间、Agent ID、任务 ID、会话 ID 和 $run\_id$ 计算汇总成本。历史运行的成本报表使用运行发生时或上报时绑定的价格版本；若价格规则更新，可以生成新的重算版本，但不得删除原始 token_usage 引用和旧汇总版本。评估和审计附着时，多轮质量评审、Agent Eval、MCP 调用审计和安全审计分别以评估任务 ID、评估版本、审计记录 ID 或风险事件 ID 关联到同一 $run\_id$，后续评估追加新版本而不是覆盖上一轮结果。由于成本和评估均保存原始记录引用及版本信息，排行榜、成本报表和质量评测能够在口径变化时重新计算并说明来源。

### 工具化查询与外部复用

本方案在统一运行记录之上提供工具化查询和外部复用接口，并规定详情视图的数据组装路径。查询单次运行时，系统先按工作区、项目或租户权限过滤并读取运行主记录，再按 $run\_id$ 读取事件时间线和阶段快照，然后装配结果产物引用、成本关联、评估关联、审计关联和冲突/悬挂记录状态。查询条件可以包括 $run\_id$、Agent ID、任务 ID、消息 ID、会话 ID、状态、时间范围、评估层级和项目标识；任何查询即使持有 $run\_id$，也必须通过工作区、项目或租户边界校验，避免跨租户读取运行详情。由于详情视图从同一运行主记录和事件链派生，内部页面、API、CLI 和 MCP 工具获得的执行状态、结果、成本和评估口径保持一致。

统计视图以运行实例为事实粒度，以事件表、成本关联表、评估关联表和审计关联表为原始数据源，以阶段快照和聚合表为派生结果。系统可以按 Agent ID、任务类型、模型、项目、时间段、评估层级或工作区汇总成功率、平均耗时、平均成本、评审通过率、工具失败率和风险事件数量；当迟到成本、评估或审计数据补写到运行实例时，通过关联版本号、更新时间或事件游标触发统计视图重新计算。由此，排行榜、质量评测、运行审计和成本报表不会各自重复采集数据，而是共享同一 $run\_id$ 事件链和关联引用，减少统计口径不一致。

增量事件接口按照可续传游标输出运行事件。面向单个运行的接口可以使用 $run\_id$ 加 sequence 作为游标，面向工作区的全局事件流可以使用全局递增事件游标；返回结果按游标升序分页，并携带 next_cursor，客户端断线后以最近确认的游标继续拉取。webhook 投递使用 event_id、$run\_id$、event_type 和 payload_hash 形成去重键，投递载荷包含事件类型、时间戳、工作区或租户标识、签名字段和摘要数据；失败投递按配置的最大次数和退避间隔重试，超过上限后记录最终失败状态、响应码、错误信息和持续时间，不再无界重试。由此，外部系统既能实时订阅运行变化，也能在网络中断、重复投递或接收端故障时保持可恢复、可审计的集成状态。
