## 技术方案

本技术方案针对 agent assistant 系统中多会话工作方式的需求，提出一种基于「父级目录代理 + 子级会话代理」组合式架构的解决方法。方案围绕多会话隔离与用户级资源连续性之间的核心矛盾，通过 Durable Object 实例级别的会话隔离、基于 RPC 的跨 DO 资源共享、多层访问控制和安全隔离机制，以及软删除优先的资源生命周期管理，实现同一用户账号下多个聊天会话各自独立运行且共享工作区文件、外部工具连接和授权凭据的目标。以下分六个部分展开说明。

### 1. 总体架构与设计思路

本方案采用「父级目录代理 + 子级会话代理」的组合式架构解决多会话隔离与用户级资源连续性之间的矛盾。核心设计思路是：将一个用户账号下的所有聊天会话组织为一棵树形结构——由一个 Chats 父代理作为用户级目录节点，负责维护会话索引、共享上下文存储和跨会话调度；每个独立的聊天会话作为 Think 子代理部署在各自的 Durable Object 实例中，拥有独立的消息历史、LLM 上下文和执行状态。父代理与子代理之间通过 Durable Object RPC 进行通信，客户端通过嵌套路由直接连接到目标子代理。

### 2. 会话级别的隔离机制

会话隔离是本方案的核心机制之一。每个聊天会话对应一个独立的 Think Durable Object 实例，拥有独立的 SQLite 存储空间和独立的 Session 对象。Session 作为会话的持久化存储层，以树形结构存储消息（每条消息包含 parent_id 字段），支持通过递归 CTE 从最新叶节点向根节点遍历得到完整对话历史。消息的 parent_id 机制同时支持再生（regeneration）场景：当用户要求重新生成某条回复时，新回复作为原回复的兄弟节点挂在同一父消息下，旧回复非破坏性地保留在树中，getHistory() 默认沿最新叶节点路径回溯，从而自动切换到最新分支。

每个 Session 维护独立的上下文块（Context Blocks）系统，包括系统提示、用户记忆、技能索引等，这些上下文块在生成系统提示时被冻结并注入 LLM 调用。Session 还支持独立的压缩（compaction）机制：当会话令牌数超过阈值时，通过 LLM 将中间消息压缩为摘要覆盖层（compaction overlay），原始消息保留在 SQLite 中，仅在读取时被替换为摘要——这是非破坏性的压缩方式，确保历史信息不丢失。

由于每个会话对应独立的 Durable Object，不同会话的 LLM 推理请求天然并行——不会因为某个会话正在进行长推理而阻塞其他会话。这与在单个 DO 内通过 SessionManager 管理多会话的方案形成对比：后者的 DO 单线程特性会导致所有会话的推理被序列化。

### 3. 用户级资源共享机制

用户级资源连续性通过 Chats 父代理实现。Chats 代理维护以下用户级共享资源：

- 会话索引表（chats_index）：记录每个子会话的 id、标题、创建/更新时间、最近消息预览，支持软删除（deleted_at 字段）；
- 共享上下文存储（shared context）：以标签（label）为键的键值对存储，子会话通过 RemoteContextProvider 以 RPC 方式远程读写父代理上的共享上下文；
- 跨会话全文搜索：父代理通过向所有子会话并行发起 session.searchMessages(query) RPC 调用，汇总并排序搜索结果，实现跨会话的消息内容检索；
- 子代理生命周期管理：通过 subAgent() 创建子会话 DO 实例，通过 deleteSubAgent() 销毁子会话 DO。

在资源共享的具体实现上，RemoteContextProvider 是实现跨 DO 上下文读取的关键组件。它是一个实现 WritableContextProvider 接口的远程代理，在子会话的 Session 初始化时被注入。当子会话需要读取共享上下文（如用户偏好设置、全局记忆）时，RemoteContextProvider.get() 通过 DO RPC 调用父代理的 getSharedContext(label) 方法获取内容；写入时则通过 setSharedContext() 或 appendSharedContext()（追加模式，用于避免读-改-写丢失更新）完成。RemoteContextProvider 采用「失败软降级」策略：当父代理暂时不可达时返回 null 而非抛出异常，确保子会话在共享资源短时不可用时仍能正常推理，下一个 turn 会自动重试。

对于文件工作区（Workspace）的共享，系统通过 Workspace 组件提供基于 SQLite + R2 的持久化虚拟文件系统。Workspace 以命名空间（namespace）隔离不同用途的文件区域，支持通过命名空间在同用户的不同会话间共享文件。Workspace 支持文件的读写、目录操作、符号链接、glob 模式匹配、文件差异比较和流式 I/O。小文件（默认 1.5MB 以下）内联存储在 SQLite 中以避免网络延迟，大文件溢出到 R2 对象存储。路径验证防止目录遍历攻击（禁止 .. 和双斜杠），命名空间验证防止 SQL 注入。

外部工具连接和授权凭据的共享同样通过父代理统一管理。MCP（Model Context Protocol）客户端连接、浏览器 CDP 会话、API 密钥等资源在 Chats 父代理中持有，子会话通过 RPC 调用父代理暴露的 @callable 方法间接使用这些资源，无需每个子会话独立配置和维护连接。

### 4. 访问控制与安全隔离

为防止不同会话的上下文相互污染以及浏览器或子会话绕过统一控制直接访问共享资源，本方案在多个层面设置了访问控制机制。

第一层：嵌套路由与父级中间件。客户端通过嵌套 URL 路径 /agents/{parent-class}/{parent-name}/sub/{child-class}/{child-name} 直接连接到目标子代理。请求首先到达父代理，触发 onBeforeSubAgent 中间件钩子。该钩子可执行身份验证、请求修改、缓存短路或拒绝访问等操作。父代理通过框架维护的子代理注册表（基于 SQLite）验证目标子代理是否存在，可选择性启用严格注册表检查。WebSocket 升级请求和 HTTP 请求通过相同的路由路径处理，中间件通过检查 Upgrade 头区分连接类型。

第二层：只读连接控制。系统在连接级别提供只读标记机制。通过 shouldConnectionBeReadonly 钩子，父代理可根据连接来源（如仪表盘查看者、免费层用户）将特定连接标记为只读。只读连接被禁止执行状态变更操作——框架在 setState() 方法内部进行强制检查，不需要开发者在每个 @callable 方法中手动添加权限校验。只读标记通过连接附件的命名空间封装技术存储，对用户代码不可见，不可被意外读取、覆盖或泄露。

第三层：上下文块隔离。每个子会话的 Session 拥有独立的上下文块集合。子会话通过 configureSession 方法配置自己的上下文块（如系统提示、用户记忆、技能），这些上下文块仅影响该会话的 LLM 推理。共享上下文通过 RemoteContextProvider 显式引用父代理中的特定标签（如 "user_memory"），不需要共享的上下文天然隔离。系统提示在生成后被冻结并缓存，同一 turn 内的上下文块变更不会影响当前推理——仅在 refreshSystemPrompt() 被调用时或下一个 turn 边界才拉取最新内容。

第四层：路径与命名空间安全。Workspace 组件对所有文件路径进行规范化校验，禁止 .. 目录遍历和双斜杠，路径最大长度限制为 4096 字符。符号链接目标同样受长度限制且不允许空值。命名空间名称必须以字母开头、仅包含字母数字和下划线，且由于命名空间会被插值到 SQL 表名中，此验证构成 SQL 注入的安全边界。

第五层：子代理隔离与递归支持。父代理的子代理注册表保证不同类名的子代理之间不会发生命名冲突（内部使用 ${className}\0${name} 作为复合键）。子代理支持递归嵌套（例如 Tenant → Inbox → Chat），每一层的父代理只对其直接子代理负责，子代理通过 parentAgent(Cls) 方法可获取直接父代理的引用，但无法跨越层级直接访问祖父代理——需要显式传递引用才能实现跨层通信。

### 5. 删除语义与资源生命周期

删除操作需要精确区分会话级资源与用户级共享资源，确保删除某个会话时不会误删属于用户的工作区文件、授权凭据或其他共享资源。

子会话删除采用软删除优先策略。当用户删除某个聊天会话时，Chats 父代理在会话索引表中将对应行的 deleted_at 字段设置为当前时间戳，并广播更新后的会话列表给所有连接的客户端。此时子会话的 Durable Object 不会立即被销毁——正在进行中的推理写入可能尚未完成。系统依赖 Cloudflare Durable Object 的休眠与 TTL 机制，让子 DO 自然进入休眠并在到期后被回收。软删除窗口内的同 ID 重建操作会清除旧行并重新开始。

在资源归属方面，以下资源属于用户级（存储在 Chats 父代理中），不受单个子会话删除影响：会话索引元数据（Chats 的 chats_index 表）、共享上下文块（如用户记忆 user_memory）、跨会话搜索索引、外部工具连接与授权凭据、Workspace 中位于用户级命名空间下的文件。以下资源属于会话级（存储在 Think 子代理中），随子会话 DO 的销毁而被回收：消息历史与消息树、会话专属上下文块、会话配置参数、会话级 FTS5 索引。

活跃使用中的删除场景通过客户端状态广播处理：用户在标签页 A 中打开会话 X，在标签页 B 中删除会话 X，父代理广播新的会话列表状态，useChats 钩子检测到会话 X 不再存在于列表中后自动断开对应的 WebSocket 连接，客户端 UI 相应更新。子代理在断开连接后继续完成当前推理 turn 的持久化写入，随后进入休眠。

### 6. 运行流程与技术效果

上述架构通过以下运行流程体现了隔离与共享的统一：用户发起新的聊天请求时，客户端通过 useChats 钩子连接到 Chats 父代理获取会话列表，选择目标会话后通过嵌套路由 /agents/{chats-class}/{user-id}/sub/{chat-class}/{chat-id} 建立与子会话 Think DO 的 WebSocket 连接。连接请求经过父代理的 onBeforeSubAgent 中间件进行身份验证和存在性检查后，被转发到子代理。子代理的 onStart 生命周期中通过 Session.create(this).configureSession() 初始化会话存储，注入 RemoteContextProvider 以连接父代理上的共享上下文。

每个推理 turn 中，assembleContext() 方法执行以下流水线：(1) 检查是否配置了上下文块——若有，则通过 session.freezeSystemPrompt() 冻结系统提示（包含从 RemoteContextProvider 远程拉取的共享上下文），否则回退到 getSystemPrompt()；(2) 通过 session.getHistory() 以递归 CTE 遍历消息树并应用压缩覆盖层，获得当前会话的完整消息历史；(3) 对较早的工具输出和长文本执行读取时截断；(4) 将消息转换为模型格式并修剪旧的工具调用。最终将组装好的 system 提示和 messages 历史送入 LLM 进行推理，推理结果通过 WebSocket 流式推送给客户端并持久化到子代理的 Session 中。

通过将隔离职责下放到独立的 Durable Object 实例、将共享职责集中到父代理，本方案在保证会话间上下文严格隔离的同时，实现了用户级工作区文件、外部工具连接、授权凭据和跨会话调度能力的自然共享。独立 DO 的并行执行特性避免了单 DO 多会话方案中推理被序列化的瓶颈；RemoteContextProvider 的失败软降级策略保证了共享资源短时不可用时子会话仍可继续工作；多层访问控制机制（嵌套路由中间件、只读连接控制、上下文块隔离、路径安全校验）防止了跨会话上下文污染和未授权资源访问。
