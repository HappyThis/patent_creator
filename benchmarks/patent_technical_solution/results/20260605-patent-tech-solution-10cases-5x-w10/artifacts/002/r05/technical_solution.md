## 技术方案

本技术方案针对一种基于持久化对象（Durable Object）架构的智能代理（Agent）系统，提出一套支持外部系统通过程序化方式提交对话任务、实现可靠接收、异步执行管理和恢复一致性的完整技术方案。方案在现有 Agent 系统的基础上构建外部任务提交层，利用持久化存储、幂等键去重、任务状态机、持久化执行纤程（Fiber）以及休眠唤醒恢复机制，解决外部调用方快速确认、去重提交、状态查询、取消清理和运行中断后恢复等核心问题。

### 整体架构

本方案的架构在现有 Agent 系统之上增设三个核心层次：外部任务接收入口层、任务管理器层和持久化执行层。外部任务接收入口层对外暴露 HTTP Webhook 端点、RPC 可调用方法和消息队列消费接口等多种程序化提交通道，负责解析外部请求、验证幂等键、将任务写入持久化存储，并在完成写入后立即向调用方返回包含任务标识的“已接收”确认响应，不等待模型推理完成。任务管理器层维护每个任务的状态机，管理任务从“已接收→排队→执行中→已完成/失败/已取消”的完整生命周期，并提供状态查询、取消请求处理和历史任务清理接口。持久化执行层复用 Agent 系统已有的持久化纤程（Fiber）和调度机制，将任务的实际执行与提交过程彻底解耦。

### 外部任务提交接口

外部任务提交接口支持多种接入方式，以适应不同的外部系统集成场景。对于 HTTP 回调场景，在 Agent 所在 Worker 的 fetch 处理器中增加对 webhook 路径的识别和分发；当请求匹配预设的外部任务提交端点时，系统解析请求体中的任务参数（包括对话消息序列、目标 Agent 类名和实例名、可选配置参数），提取或生成幂等键，并将任务元数据写入 SQLite 持久化存储。写入成功后立即向调用方返回 HTTP 202 Accepted 响应，响应体中包含系统分配的任务标识符和状态查询端点地址，不等待 Agent 的模型推理过程完成。

对于 RPC 调用场景，在 Agent 基类或专门的调度类上暴露通过 @callable 装饰器标记的可调用方法，外部系统通过 Durable Object 的 RPC 机制直接调用该方法提交任务。RPC 方法内部同样执行幂等键检查、任务持久化和立即返回的流程。对于消息队列场景，方案支持通过 Agent 系统已有的队列原语（enqueue）接收来自消息队列或事件总线的任务提交，队列回调中执行相同的任务注册逻辑。三种接入方式的共同特点是：提交操作与执行操作在时间上和事务上完全分离，调用方无需维护长连接等待推理结果。

### 幂等性保障机制

外部系统因超时或网络异常重复提交同一任务是本方案需要解决的一个关键问题。方案引入两层幂等性保障机制。第一层：调用方在提交请求时携带一个由外部系统生成的幂等键（Idempotency Key），该键可以是对业务请求唯一标识的哈希值（如订单号+操作类型的组合摘要），也可以是由外部系统生成的 UUID。系统在接收任务时，首先以幂等键为条件查询持久化存储中的任务表，若存在相同幂等键且其状态为非“已取消”或“已清理”的任务记录，则直接返回该已有任务的标识符和当前状态，不再创建新任务记录，也不重复写入用户输入消息。

第二层：在持久化存储的任务表中，对幂等键列建立唯一约束（UNIQUE 约束），使得即使在并发提交的极端情况下，数据库层面也能保证同一幂等键只对应一条有效任务记录。此外，方案还支持在幂等键基础上附加可选的“幂等窗口”配置，即超过指定时间窗口（例如 24 小时）的旧任务记录不再参与幂等匹配，允许外部系统在窗口过期后重新提交相同业务标识的任务。这种方式既保证了重复提交的安全防护，又避免了幂等键的永久占用导致合法重试被拒绝。

对于需要将对话消息写入 Agent 消息存储的场景，消息写入操作采用 INSERT OR IGNORE 语义——每条消息携带自身唯一标识，重复插入相同标识的消息时数据库自动忽略，从存储层面确保即使任务提交层的幂等检查被绕过或不适用（例如外部系统直接通过 WebSocket 发送消息），消息本身也不会被重复持久化。

### 任务状态管理与持久化

方案为每个外部提交的任务定义明确的状态机模型。任务在其生命周期中经历以下状态：已接收（received）、排队中（queued）、执行中（running）、已完成（completed）、失败（failed）、已取消（cancelled）和已清理（cleaned_up）。状态转换由任务管理器层统一控制。任务被成功写入持久化存储后进入“已接收”状态；当系统有可用执行槽位时，任务进入“排队中”状态；执行纤程开始运行后进入“执行中”状态；执行正常结束进入“已完成”；执行异常终止进入“失败”；外部调用方主动请求取消且任务尚未完成时进入“已取消”；任务被清理后进入“已清理”。

所有状态信息连同任务元数据（提交时间、幂等键、目标 Agent 信息、请求参数、状态变更时间戳）存储在一张 SQLite 任务表中。任务表的典型结构包含以下列：任务唯一标识、幂等键（UNIQUE 约束）、目标 Agent 类名和实例名、任务请求载荷（JSON 序列化）、当前状态、状态变更时间戳、创建时间、完成时间、关联的纤程标识、取消请求标志。状态变更采用原子更新操作，每次状态迁移同时更新状态列和对应的时间戳列，保证写入的原子性和一致性。

任务管理器在 Agent 实例每次被唤醒时（即 onStart 生命周期钩子执行期间），扫描任务表中处于“执行中”或“排队中”状态且关联当前 Agent 实例的记录。对于“执行中”的任务，通过检查关联纤程是否仍在运行或纤程快照（snapshot）是否存在来判定任务的实际执行阶段，进而决定是继续等待、触发恢复还是标记为失败。对于“排队中”的任务，按照提交时间顺序启动纤程执行。

### 异步执行与生命周期管理

任务的实际执行建立在 Agent 系统已有的持久化纤程（Fiber）机制之上。当一个任务从“排队中”转为“执行中”时，任务管理器调用 runFiber 方法启动一个以任务标识命名的持久化纤程，在该纤程的回调中执行对话推理流程。runFiber 方法在纤程启动前将一条记录写入 cf_agents_runs 表，纤程完成后自动删除该记录；同时 runFiber 内部自动调用 keepAlive 机制维持 Agent 实例不被休眠驱逐，确保长时间推理任务不会因空闲超时被中断。

纤程回调内部执行标准的对话处理流程：从任务载荷中解析用户消息，通过 INSERT OR IGNORE 将消息写入 Agent 的消息存储表（由底层 AIChatAgent 或 Think 基类管理），然后调用模型推理接口（onChatMessage），将推理结果流式输出并通过 WebSocket 或回调通道推送给已连接的客户端。推理过程中，关键中间状态（如已完成的推理步骤、已生成的部分输出）通过纤程的 stash 方法同步写入 SQLite 快照，形成可恢复的检查点。推理完成后，任务状态更新为“已完成”，任务表中记录完成时间戳和结果摘要。

对于并发执行场景，方案利用纤程的并发能力支持多个任务同时运行。每个任务独立拥有自己的纤程行和快照，互不干扰。keepAlive 采用引用计数机制——只要有任意一个纤程在运行，Agent 就保持活跃；所有纤程完成后，Agent 恢复正常休眠条件。通过 Agent 基类的静态选项，可配置每个 Agent 实例的最大并发任务数，超出限制的新任务保持在“排队中”状态等待。

### 任务查询、取消与清理

方案为外部系统提供任务状态查询和取消控制两类操作接口。状态查询接口支持通过任务标识符或幂等键两种方式进行查询。外部系统发送 HTTP GET 请求到任务查询端点，或在 RPC 场景下调用状态查询方法，系统从 SQLite 任务表中读取任务记录并返回当前状态、状态变更时间、执行进度（若任务执行中且支持进度报告）以及最终结果（若任务已完成）。任务执行中时，可通过纤程快照（stash 存储的检查点数据）向查询方提供粗粒度的执行进度。

取消操作通过 HTTP DELETE 请求或专用的取消 RPC 方法触发。系统接收到取消请求后，首先检查任务当前状态：若任务处于“已接收”或“排队中”状态，直接将状态更新为“已取消”并返回确认；若任务处于“执行中”状态，系统在任务表中设置取消请求标志，同时向正在执行的纤程发送中止信号（通过 AbortController 的 abort 方法）。纤程回调在执行过程中定期检查中止信号，收到信号后执行清理逻辑（包括持久化当前部分结果、将任务状态更新为“已取消”），然后终止执行。若任务已经处于终态（已完成、失败、已取消），则直接返回当前状态。

清理操作允许外部系统在任务完成后（无论成功、失败还是取消）显式清理任务记录和关联数据。清理接口删除任务表中对应行以及关联的大型载荷数据（如完整的推理结果），但可选保留摘要信息用于审计。方案支持配置自动清理策略，例如对已完成超过指定天数的任务进行自动清理。

### 休眠恢复与一致性保障

Agent 运行环境可能因多种原因发生中断——包括 Durable Object 的空闲超时休眠（约 70-140 秒无请求后自动休眠）、代码更新或运行时重启导致的确定性驱逐、以及告警处理器超时（15 分钟）导致的强制终止。方案利用 Agent 系统已有的多层恢复机制来保证外部提交任务在中断后的一致性和可恢复性。

第一层恢复机制：持久化纤程恢复。当 Agent 实例被驱逐时，所有在执行的纤程对应的行记录仍然保留在 cf_agents_runs 表中。在 Agent 下一次激活时（无论是由新的 HTTP 请求、WebSocket 连接、RPC 调用还是定时告警触发），onStart 生命周期钩子调用 _checkRunFibers 方法扫描 cf_agents_runs 表中的孤立行。对每个孤立行，系统调用 onFiberRecovered 回调，传入纤程名称、快照数据和创建时间。恢复回调根据纤程名称匹配到外部任务提交的恢复逻辑：从快照中解析已完成的推理步骤和中间输出，将任务状态从“执行中”修正为适当状态，并可选地重新启动纤程从中断点继续执行。恢复完成后删除孤立行。

第二层恢复机制：任务状态自愈。除了纤程层面的恢复，任务管理器在每次 onStart 启动时额外执行一次任务状态自检：扫描任务表中状态为“执行中”的记录，交叉比对 cf_agents_runs 表中是否存在对应的纤程行。若纤程行已不存在（说明纤程正常完成后已清理）但任务状态仍为“执行中”（状态更新可能未完成），则将任务状态修正为“已完成”；若纤程行存在但其时间戳早于当前 Agent 实例的启动时间，则判定为中断残留，触发纤程恢复流程。这种双重校验机制避免了仅依赖单一恢复路径可能产生的状态不一致。

第三层恢复机制：定时告警保底。对于纯后台执行的 Agent 实例（无客户端连接、无外部请求），上述依赖 onStart 的恢复路径可能无法及时触发。方案利用 Agent 系统的定时告警（Alarm）机制：在任务提交并启动纤程时，同时注册一个超时告警；若纤程在预期时间内未完成，告警触发时执行恢复检查。此外，Agent 系统的 _onAlarmHousekeeping 方法在每次告警触发时也会扫描 cf_agents_runs 表和 cf_agents_facet_runs 表，确保即使没有外部请求唤醒 Agent，中断的任务也能通过告警保底路径得到恢复。

通过上述三层恢复机制的协同工作，方案实现了外部提交任务在休眠、重启或执行中断场景下的可靠恢复：所有任务状态持久化存储于 SQLite 中，不依赖内存状态；纤程快照提供细粒度检查点支持从中断点续执行；双重校验防止状态不一致；定时告警为无客户端连接的纯后台场景提供恢复触发保障。

### 方案技术效果

本方案通过上述技术手段的组合，取得以下技术效果。第一，提交与执行分离的架构使得外部调用方在毫秒级获得“已接收”确认，无需阻塞等待模型推理完成（通常需要数秒至数十秒），显著降低了外部系统的连接占用和超时风险。第二，基于幂等键和数据库唯一约束的双层去重机制，从应用逻辑和存储引擎两个层面共同防止重复提交导致的重复写入和重复执行。第三，持久化任务状态机将所有任务元数据和状态存储在 SQLite 中，使得任务状态在 Agent 休眠、重启或驱逐后完整保留，外部系统可随时查询。第四，基于纤程和快照的持久化执行与三层恢复机制协同工作，保证任务在运行中断后可从中断点附近的检查点恢复执行，而非从头重试。第五，取消信号通过 AbortController 机制传递到正在执行的模型推理调用，实现安全的执行中断和资源释放。
