## 技术方案

本技术方案围绕在具备持久化状态和休眠唤醒能力的 agent 运行环境中，为外部系统提供可靠、可恢复的程序化对话任务提交机制。方案的总体思路是：在 agent 对外暴露的 HTTP 入口处增设异步任务接收层，外部调用方提交任务后立即获得包含任务标识的接收确认，任务的实际执行交由 agent 内部的持久化任务队列在后台异步驱动；同时通过幂等键机制避免因网络重试导致的重复提交，并通过基于持久化存储的任务状态机与告警驱动的恢复检测机制实现运行环境休眠、重启或中断后的任务阶段判定与恢复。

### 整体架构

系统整体架构分为三层：外部接入层、任务管理层和执行恢复层。外部接入层通过 agent 运行环境原生的 HTTP 请求处理机制接收外部系统的程序化提交请求，包括 webhook 回调、RPC 调用或其他基于 HTTP 的远程调用方式。任务管理层基于 agent 的持久化 SQL 存储实现任务记录的创建、状态追踪与去重判定，并通过持久化队列将任务调度至后台异步执行。执行恢复层利用 agent 的告警机制与持久化运行记录，在运行环境从休眠、重启或中断中恢复时，自动检测未完成的任务并判定其所处阶段，触发相应的恢复或清理操作。

### 外部提交的快速接收与确认

外部系统通过向 agent 实例的 HTTP 入口发送 POST 请求来提交一次对话任务。请求体中携带对话输入内容以及调用方生成的任务幂等键。为与面向人类用户的网页交互路径区分，可在 URL 路径中采用特定前缀（例如 /tasks/submit）标识外部任务提交端点。在 agent 的 HTTP 请求处理方法（onRequest）中识别该端点后，系统执行以下快速接收流程。

首先，系统从请求体中提取幂等键。若请求未携带幂等键，可基于请求体内容的哈希值自动生成，作为默认的去重标识。然后系统查询持久化任务表，检查是否存在相同幂等键且未进入终态（已完成、已取消、已失败）的任务记录。若存在，则直接返回已存在任务的状态信息（含任务标识），不再重复写入请求内容，实现去重。

若未命中去重，系统在持久化任务表中原子性地写入一条新记录，包含：系统生成的唯一任务标识、调用方提供的幂等键、请求体内容（对话输入数据）、任务状态标记为「已接收」、创建时间戳。写入成功后，系统将任务标识推入持久化任务队列，并向调用方返回包含任务标识和状态为「已接收」的 HTTP 响应。整个接收流程不触发模型推理，响应时间仅取决于存储写入和队列操作的开销，通常在数十毫秒量级。

### 任务生命周期与状态管理

任务从接收到完成经历多个阶段，每个阶段对应持久化记录中的一个状态值。状态包括：已接收（received）表示任务已写入存储但尚未调度执行；已入队（queued）表示任务已进入后台队列等待执行；执行中（running）表示任务正在由 agent 的业务处理方法处理；已完成（completed）表示任务成功执行完毕；已失败（failed）表示任务执行异常且已达到最大重试次数；已取消（cancelled）表示任务在完成前被主动取消。此外，可设置「已过期」（expired）状态用于超过预设生存时间的任务自动清理标记。

后台队列处理机制从持久化任务表中按创建时间顺序取出状态为「已入队」的任务，将其状态原子更新为「执行中」，然后调用 agent 上预定义的业务处理方法（如对话处理方法）执行实际模型推理。执行期间，agent 通过保持存活机制防止运行环境在执行过程中被空闲回收。执行过程支持可配置的重试策略：当执行发生可重试类异常时，系统按指数退避策略自动重试，重试次数和间隔可配置；当达到最大重试次数后仍未成功，任务状态置为「已失败」。执行成功则将状态置为「已完成」，并在记录中保存执行结果或结果引用。

### 任务状态查询与取消

外部调用方可随时通过任务标识查询任务状态。查询接口同样通过 agent 的 HTTP 入口暴露（例如 GET /tasks/{taskId}/status）。agent 在 onRequest 中识别查询请求后，从持久化任务表中按任务标识查找对应记录并返回其当前状态、创建时间、完成时间等字段。若任务标识不存在则返回未找到。

取消操作通过向 agent 发送 DELETE 或 POST 请求（如 POST /tasks/{taskId}/cancel）触发。系统收到取消请求后，检查目标任务当前状态：若任务处于「已接收」或「已入队」状态，直接将状态更新为「已取消」并从队列中移除，任务不再执行；若任务处于「执行中」状态，系统设置取消标记，业务处理方法在执行过程中定期或在关键检查点查询该标记，若发现已设置则终止执行并将状态更新为「已取消」。已完成或已失败的任务不接受取消操作。清理操作可将指定任务记录及其关联数据从持久化存储中删除，或标记为「已过期」供后续批量清理。

### 休眠、重启与中断后的恢复机制

agent 运行环境基于持久化对象机制，支持在空闲时自动休眠并在收到请求时唤醒。当运行环境因休眠、宿主重启或执行进程异常中断时，内存中的执行上下文丢失，但持久化存储（SQLite）中的任务记录完整保留。系统通过以下机制实现恢复一致性。

首先，系统在持久化任务表中为「执行中」状态的任务同步维护执行开始时间戳。当 agent 从休眠中唤醒或重新初始化时，触发恢复检测流程：扫描任务表中所有状态为「执行中」的记录，检查其执行开始时间戳与当前时间的差值是否超过预设的执行超时阈值。执行超时阈值根据任务类型和预期执行时长配置，超过该阈值即判定原执行进程已不存在（因休眠或中断而丢失）。对于判定为中断的任务，系统进一步检查其重试次数：若未超过最大重试次数，将状态重置为「已入队」并重新调度执行；若已达到最大重试次数，状态置为「已失败」。

其次，恢复检测流程可利用 agent 运行环境原生的告警机制自动触发。agent 在初始化完成后设置周期性告警，告警触发时执行上述扫描检测。此外，在 agent 每次接收外部请求（包括状态查询请求）时，也可在请求处理前附带执行一次轻量恢复检测，以更及时地发现中断任务。任务状态为「已接收」但尚未入队的记录同样在恢复时被识别：系统将其补入队列，确保不会因休眠导致任务丢失。

### 幂等键与去重策略

去重机制的核心是幂等键。幂等键由调用方在每次提交时生成并携带，典型生成方式包括：使用业务层面的唯一标识（如订单号、工单号）；或对请求体内容进行哈希计算（如 SHA-256），保证相同语义的请求产生相同幂等键。系统在持久化任务表中对幂等键建立唯一索引，写入新任务记录时通过数据库的原子插入操作保证：若相同幂等键的记录已存在且未进入终态，插入操作返回冲突，系统转而返回已有任务的状态信息，从存储层面杜绝重复写入。

当任务已进入终态（已完成、已失败、已取消）后，相同幂等键的新提交是否被视为新任务，可通过配置策略控制。在默认策略下，终态任务的幂等键可被复用，即允许以相同幂等键提交新任务；在严格幂等策略下，终态任务同样阻止重复提交，调用方需更换幂等键。此外，系统可在幂等键之外附加任务提交时间窗口参数：对于超过窗口期的旧任务记录，视为过期并允许同键重新提交，兼顾去重需求与重复业务场景的灵活性。

### 执行快照与断点恢复

在任务执行过程中，系统支持执行进度的持久化快照。agent 的业务处理方法可在关键节点调用快照接口，将当前执行状态（如已完成的子步骤、中间结果等）序列化写入任务记录的快照字段。当发生中断恢复时，恢复流程不仅重置任务状态，还将持久化的快照数据传递给业务恢复处理方法，使其能够从中断点附近继续执行，而非从头开始。这对包含多轮模型推理调用的长对话任务尤其重要，可避免重复已完成的计算步骤。

### 任务队列调度与执行分发

任务队列基于 agent 的持久化存储实现。任务记录中维护入队时间戳和状态字段，队列的出队操作通过按入队时间升序查询状态为「已入队」的记录完成。队列的调度驱动采用两种互补方式：其一，在任务写入队列后主动触发一次队列刷新，立即尝试调度；其二，利用 agent 的告警机制设置周期性刷新，确保在无新任务提交时也能处理积压任务。队列刷新过程对每条待处理任务执行前述的状态更新与业务方法调用流程。为防止队列中某条任务的执行阻塞其他任务，系统采用逐条处理模式：每次刷新取出有限数量任务逐一执行，单条任务执行完毕后无论成功与否均继续处理下一条。

### 数据模型

上述机制依赖 agent 持久化存储中的数据表结构。任务主表包含以下核心字段：任务标识（主键）、幂等键（唯一索引）、请求体内容、任务状态、创建时间、执行开始时间、完成时间、重试次数、执行结果或快照数据。此外，可增设任务配置表存储全局配置参数（如默认超时时间、最大重试次数、幂等策略等），以及任务日志表记录每次状态变更和重试尝试的详细日志。所有表均位于 agent 实例独占的 SQL 存储空间中，天然具备与 agent 实例生命周期一致的持久性。

### 执行级防重与并发控制

除通过幂等键在存储写入层面去重外，系统还在执行调度层面设置防护。当队列刷新尝试调度一条状态为「已入队」的任务时，先以原子方式将状态更新为「执行中」并记录执行开始时间，此更新以状态为「已入队」作为前提条件。若更新影响行数为零（说明任务已被另一刷新周期或恢复流程抢先调度），则跳过该任务。此「比较并更新」机制保证每条任务至多被一个执行上下文拾取，防止因并发刷新或恢复检测与正常调度的竞态导致重复执行。

### 边界情形与异常处理

在接收流程中，任务写入存储成功后、推入队列前若发生运行环境休眠或中断，该任务将以「已接收」状态保留在持久化存储中。恢复检测流程在扫描「执行中」任务的同时，也扫描状态为「已接收」且创建时间超过预设阈值的记录，将其状态更新为「已入队」并触发队列刷新。这保证接收成功但尚未入队的任务不会丢失。

在极端场景下，若外部调用方在提交请求后未收到 HTTP 响应（网络中断），调用方重试提交相同幂等键的请求，由去重机制保证只创建一条任务记录。调用方可通过后续状态查询获取任务的实际处理结果，避免因响应丢失导致的重复提交。

为防止已完成或已取消的任务记录无限增长，系统支持可配置的保留策略：基于完成时间的过期清理（定期删除超过保留期的终态记录），或基于数量的上限控制（每个 agent 实例最多保留 N 条历史记录）。清理操作可在告警触发的定期维护流程中执行。
