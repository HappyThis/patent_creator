## 技术方案

### 总体架构

本技术方案在现有 agent 系统的基础上，扩展出一套面向外部系统程序化调用的任务提交与管理机制。核心思路是：利用 agent 系统已有的持久化状态存储、任务队列、调度与恢复基础设施，在外部提交场景下增加任务接收与快速确认层、幂等保障层、任务生命周期状态机、以及恢复一致性判定逻辑，使得外部调用方通过 webhook、RPC 或其他程序化方式提交的对话任务能够在 agent 休眠、重启或执行中断后可靠地继续执行或安全终止。

整体方案由四个协同工作的子系统组成：（1）任务接收与幂等保障子系统，负责接收外部提交并快速确认，同时防止重复提交导致的重复写入或重复执行；（2）任务生命周期状态机，定义任务从接收、入队、执行、完成、失败到取消的完整状态流转，所有状态变更持久化到 SQLite；（3）异步执行与队列管理子系统，复用现有 agent 队列机制将任务调度到 callback 方法执行，并支持重试与主动取消；（4）恢复一致性子系统，在 agent 被唤醒（onStart）或 alarm 触发时检测中断任务，判定其所处阶段并做出相应的恢复或清理动作。

### 任务接收与幂等保障

外部系统通过 HTTP POST 请求向 agent 的入口端点提交任务。请求体中包含对话消息内容、目标 agent 标识和可选的客户端幂等键（Idempotency-Key）。系统在接收层完成以下处理，然后立即向调用方返回 202 Accepted 及任务标识符，而不等待模型推理完成。

幂等接收机制：接收层首先检查请求中是否携带幂等键。若存在，则在 SQLite 中查询该幂等键是否已有对应的任务记录。如果已存在且原有任务处于"进行中"或"已完成"状态，则直接返回已有任务标识符和当前状态，不重复写入用户输入，也不触发新的队列任务。若幂等键不存在或对应任务已失败/已取消，则创建新的任务记录并将幂等键与任务标识符的映射关系写入 SQLite。该映射写入与任务记录写入在同一数据库事务中完成，保证原子性。

无幂等键场景的处理：当外部系统未提供幂等键时，系统基于请求内容的特征摘要（例如对消息内容、目标 agent 和提交时间戳进行哈希计算）生成一个内容指纹，使用该指纹作为内部幂等键执行相同的去重逻辑。指纹的哈希碰撞窗口通过选择足够长的哈希输出（如 SHA-256 的前 16 字节）控制在可忽略的工程范围内。同时为指纹匹配设置时间窗口（如 5 分钟），超时的旧指纹记录可被清理，防止长期累积导致的误判。

快速确认与异步解耦：接收层在完成幂等检查、创建任务记录并写入队列后立即返回 202 响应，响应体中包含任务标识符和初始状态。此后的队列消费、任务执行和状态更新均与接收请求异步进行。这种设计使得接收层的响应时间仅取决于 SQLite 写入延迟（毫秒级），与模型推理耗时（秒级到分钟级）完全解耦。

### 任务生命周期状态机

每个外部提交的任务在系统中维护一个持久化的生命周期状态，所有状态转换记录在 SQLite 的任务表中。任务状态机定义如下状态及其转换规则。

状态定义：（1）received——任务已接收并完成持久化写入，尚未入队执行；（2）queued——任务已写入队列等待被执行，此时可通过 dequeue 操作直接取消；（3）running——队列回调方法已开始执行该任务，任务正在进行模型推理或工具调用；（4）completed——任务正常执行完成，结果已持久化；（5）failed——任务执行失败且已达最大重试次数，失败原因已记录；（6）cancelled——任务在 queued 阶段被外部调用方主动取消，或在 running 阶段被取消信号中断。

状态转换路径如下：received → queued（入队时）；queued → running（队列回调被调用时）；running → completed（执行成功）；running → failed（执行异常且重试耗尽）；queued → cancelled（外部取消请求到达）；running → cancelled（取消信号在任务执行中生效）。其中，received → queued 的转换在接收层将任务写入 cf_agents_queues 表时同步完成，其余转换由队列执行回调在运行时更新。

### 异步执行与队列管理

任务在写入队列后，由 agent 的现有队列机制驱动执行。本方案扩展了队列回调方法，使其在运行时维护任务状态并响应取消信号。

任务入队：接收层在创建任务记录后，调用 this.queue("executeTask", taskPayload) 将任务写入 cf_agents_queues 表，同时将任务状态更新为 queued。queue() 方法内部触发 _flushQueue()，按 FIFO 顺序处理所有待执行任务。队列中的每个任务在开始执行时，回调方法首先将该任务的状态从 queued 更新为 running。

重试与失败处理：队列回调方法使用 this.retry() 或队列内置重试机制执行模型推理调用。每次重试前检查任务的取消标记，若已标记取消则中止重试循环并将状态更新为 cancelled。重试耗尽后状态更新为 failed。重试参数（最大次数、基础延迟、最大延迟）可通过任务级别的 retry_options 配置或 agent 级别的静态默认值控制。

### 状态查询与任务控制

外部调用方在获得任务标识符后，可通过查询接口获取任务当前状态和结果，也可通过取消接口中止尚未完成的任务。

状态查询：通过 HTTP GET 或 RPC 方法（@callable 装饰的 getTaskStatus 方法），外部系统传入任务标识符即可查询该任务的当前状态、创建时间、状态更新时间，以及任务完成后的输出结果或失败原因。查询数据直接从 SQLite 任务表中读取，响应延迟为数据库查询延迟。对于已完成的任务，查询接口同时返回执行结果；对于进行中的任务，返回当前状态和进度信息（如已完成的推理步骤数）。

任务取消：外部系统可通过 HTTP DELETE 或 RPC 方法请求取消指定任务。取消操作的处理分为两种情况。若任务处于 queued 状态，系统直接调用 dequeue(taskId) 从队列中移除该任务，并将任务状态更新为 cancelled，此操作即时生效。若任务已进入 running 状态，则设置该任务的取消标记（持久化到任务记录中）。队列回调方法在每次工具调用或模型推理步骤之间检查该标记；一旦检测到取消标记，回调方法停止后续步骤，将状态更新为 cancelled 并清理临时资源。由于 agent 在模型推理调用（如 fetch 到 AI 服务）期间无法被中断，取消生效的粒度为一个推理步骤结束后。

### 恢复一致性与中断处理

agent 运行环境可能因平台休眠（约 70-140 秒无请求自动休眠）、代码更新、运行时重启或 alarm 超时（15 分钟）而发生执行中断。本方案在现有的持久化恢复基础设施之上，增加了对任务状态的恢复一致性判定逻辑。

恢复触发点：agent 每次被唤醒时（无论由 HTTP 请求、WebSocket 连接、RPC 调用还是 alarm 触发），都会执行 onStart() 生命周期方法。其中调用的 _checkRunFibers() 负责检测上一生命周期遗留的未完成 fiber 任务。本方案扩展该检测逻辑：除检查 cf_agents_runs 表中残留的 fiber 记录外，还扫描任务表中状态为 running 或 queued 且最后更新时间超过合理执行窗口期的任务记录。

中断任务判定：对于状态为 running 的任务，若其最后更新时间距离当前时间超过预设阈值（如 10 分钟），判定为中断任务。系统根据任务是否启用了 fiber 检查点来决定恢复策略。若任务使用了 runFiber() 包装且通过 stash() 持久化了中间检查点，则调用 onFiberRecovered() 从最后一个检查点恢复执行。若任务未使用 fiber 机制或检查点数据已损坏，则将任务状态标记为 failed，并在失败原因中注明"执行中断"，同时可选择性地重新入队重试。对于状态为 queued 的任务，其在队列表中的记录本身就表示尚未开始执行，恢复后 _flushQueue() 会按 FIFO 顺序继续处理。

alarm 兜底恢复路径：对于长期没有客户端连接的 agent（如仅通过 webhook 接收任务的后台 agent），可能没有传入请求触发 onStart() 恢复。为此，本方案利用 agent 现有的 alarm 机制作为兜底恢复路径。在 alarm 处理中 (_onAlarmHousekeeping)，同样执行任务状态扫描和 fiber 恢复检查。当检测到有残留的 running 或 queued 任务时，alarm 处理会触发恢复逻辑。同时，可通过 schedule() 设置周期性的"健康检查"alarm（如每 60 秒一次），确保即使长时间无外部请求，中断任务也能被及时检测和恢复。

### 长任务的检查点-恢复机制

对于涉及多轮模型推理、多步工具调用或人工审批等待的外部提交任务，单纯依赖队列重试无法有效应对 agent 休眠或重启导致的中断。本方案利用现有 runFiber() 持久化执行框架，为长任务提供检查点-恢复能力。

任务执行包装：外部提交的长任务在队列回调方法内部通过 this.runFiber(taskId, fiberCallback) 包装执行。fiber 回调函数在每个关键步骤完成后调用 ctx.stash(snapshot) 将当前执行进度持久化到 SQLite（cf_agents_runs 表）。检查点数据包括已完成步骤列表、中间结果、待执行步骤队列和必要的上下文变量。

恢复回调：在 onFiberRecovered(ctx) 中，根据 ctx.name（即任务标识符）识别被中断的具体任务。从 ctx.snapshot 中还原检查点数据，判断哪些步骤已完成、哪些步骤待执行。对于已完成步骤，跳过重复执行直接使用已有中间结果；对于待执行步骤，从断点继续执行。恢复后的执行再次包装在新的 runFiber() 调用中，确保后续可能的中断仍可恢复。这样，即使 agent 在模型推理返回结果的前一刻被休眠，恢复后也能从最后一个 stash() 检查点继续，而不会重复整个推理过程。

长任务保活策略：在 runFiber() 执行期间，框架内置的 keepAlive() 机制以 30 秒间隔发送心跳 alarm，将 agent 的休眠倒计时重置，防止在任务执行中被休眠。对于预计执行时间超过 alarm 超时限制（15 分钟）的极长任务，建议将任务拆分为多个子 fiber 或通过 schedule() 分段执行，每段独立保存检查点并释放 alarm 资源。

### 任务记录清理策略

为避免 SQLite 存储空间无限增长，系统对任务记录实施定期清理策略。

任务记录保留策略：已完成（completed、failed、cancelled）的任务记录保留预设保留期（如 7 天），超期记录在 alarm 定时清理任务中被删除。保留期内的记录支持外部系统查询历史执行结果。对于 running 或 queued 状态的异常残留记录（创建时间超过最大合理执行窗口但仍未完成），由恢复检测逻辑标记为 failed 并进入正常保留-清理周期。

幂等键记录的清理：幂等键与任务标识符的映射记录同样设置过期时间（如 24 小时），超期的映射记录可被清理。这是因为超过一定时间窗口后，重复提交的请求应被视为新的独立任务而非重复请求，清理旧映射可防止误判。

### 数据模式与集成方式

本方案在现有 agent 系统的 SQLite 存储层基础上新增任务管理相关表，同时复用已有的队列和 fiber 表。

新增任务状态表（cf_agent_tasks）：包含字段 task_id（主键）、idempotency_key（幂等键）、status（状态枚举：received/queued/running/completed/failed/cancelled）、payload（任务载荷 JSON）、result（执行结果 JSON，完成后写入）、error_message（失败原因）、cancel_requested（取消标记，布尔值）、created_at、updated_at。其中 idempotency_key 建立唯一索引以支持快速幂等查询。

与现有表的关系：任务入队时，payload 被写入 cf_agents_queues 表的 payload 字段，callback 字段固定为 "executeTask"，该 callback 方法在 Agent 子类中实现。cf_agents_queues 表的 retry_options 列存储任务级重试配置。对于启用 fiber 检查点的长任务，cf_agents_runs 表中的 name 字段使用任务标识符（task_id），onFiberRecovered 通过 name 匹配定位被中断的任务。

集成方式：本方案不修改 Agent 基类的核心执行路径。所有扩展通过以下方式实现：（1）在 onRequest() 中增加任务接收端点路由；（2）在 Agent 子类中实现 executeTask() 队列回调方法；（3）覆盖 onFiberRecovered() 实现任务级恢复逻辑；（4）在 onStart() 的恢复流程后追加任务状态扫描步骤。这种设计确保现有 agent 功能（实时通信、状态同步、计划调度等）不受影响，同时对调用方暴露统一的任务管理接口。
