## 技术方案

本方案提供一种基于持久化对象（Durable Object）的智能体任务处理系统，使外部系统可通过标准化的程序化接口（包括 HTTP webhook、RPC 远程过程调用、以及基于 WebSocket 的持久连接）提交对话任务，并实现任务的可靠异步执行、状态追踪与中断恢复。系统采用单线程事件驱动模型，以持久化对象实例作为任务处理的基本单元，每个实例绑定独立的 SQLite 数据库和键值存储，通过将任务数据、执行状态和检查点信息持久化到存储层来实现运行环境休眠、重启或意外中断后的恢复一致性。

系统的核心架构分为三层：接入层负责任务接收与快速确认，通过统一的请求入口将外部提交转换为内部任务描述符；调度层负责任务的持久化排队、幂等去重与分配，利用关系型数据库表存储任务队列和定时调度信息；执行层负责任务的耐久运行、检查点保存与异常恢复，通过纤维（fiber）抽象将长时间运行的任务拆分为可恢复的执行单元。三层之间通过持久化对象实例的 SQLite 数据库进行状态传递，避免依赖外部消息队列或缓存中间件。

### 任务接收与快速确认

外部系统通过三种标准化的程序化接口提交任务：HTTP webhook、RPC 远程过程调用和 WebSocket 消息通道。当请求到达持久化对象实例时，系统首先执行请求解析与校验，提取任务类型标识、回调函数名称、载荷数据以及可选的执行选项（包括最大重试次数、重试退避策略、幂等键等）。解析完成后，系统将任务描述符写入 SQLite 持久化队列表（cf_agents_queues），该写入操作在同一个数据库事务中完成，确保原子性。写入成功后立即向调用方返回确认响应，其中包含全局唯一的任务标识符。确认响应的生成不等待任务实际执行，从而将提交延迟控制在数据库写入延迟的量级，实现毫秒级的快速确认。

在写入队列表的同时，系统可选地将请求中携带的幂等键（idempotency key）与任务标识符的映射关系持久化到同一数据库的另一张表中，用于后续的重复提交检测。对于通过 WebSocket 提交的任务，确认响应通过同一连接通道返回，并在响应中包含任务标识符和预估排队位置；对于 HTTP webhook 提交，确认响应为标准的 HTTP 202 Accepted 状态码及包含任务标识符的 JSON 响应体。系统在确认阶段不分配执行线程或内存缓冲区，所有待执行任务以数据库行的形式存在，因此单个持久化对象实例可同时接收并确认大量任务而不受内存限制。

### 幂等去重机制

幂等去重机制用于防止外部系统因网络超时重试、消息重放或客户端重试逻辑导致的同一任务被重复提交和执行。系统提供两种互补的去重策略：基于显式幂等键的请求级去重和基于调度特征值的调度级去重。

请求级去重：外部系统在提交任务时可在请求中携带幂等键，系统在首次收到携带该幂等键的请求时，正常创建任务并持久化幂等键到任务标识符的映射关系。当收到携带相同幂等键的重复请求时，系统通过查询映射表检测该幂等键已存在，直接返回已创建任务的标识符和状态，而不创建新任务。幂等键的映射关系与任务数据存储在同一 SQLite 数据库中，利用数据库事务的原子性和隔离性保证并发场景下仅有一个任务被创建。

调度级去重：对于需要周期性或定时执行的任务，系统在调度表（cf_agents_schedules）中采用复合唯一约束进行去重。去重维度包括调度类型（延迟执行、定时执行、cron 表达式或固定间隔）、回调函数名称、载荷数据的序列化值以及所有者路径键。当调用方以相同的参数重复注册调度任务时，INSERT OR IGNORE 语义确保表中仅保留一条记录，并通过返回值中的创建标志（created）区分新创建行与已有行。调度级去重不依赖调用方提供额外的幂等键，而是从调度参数本身推导去重特征，消除调用方忘记携带幂等键导致的重复调度风险。

### 异步任务调度与耐久执行

任务写入队列表后，系统在同一个事件循环周期内触发队列刷新（flush），按先进先出（FIFO）顺序从队列表中读取待执行任务并开始执行。每个任务的处理分为调度分配和执行运行两个阶段。

调度分配阶段：系统从 cf_agents_queues 表中按 FIFO 顺序获取任务行，根据任务中注册的回调函数名称查找对应的处理函数。支持为任务配置重试策略，包括最大重试次数和指数退避加随机抖动的重试间隔。当任务执行失败时，系统将错误信息记录到任务行中，并根据重试策略计算下次重试时间，更新任务行状态为待重试；达到最大重试次数后标记为永久失败。调用方可通过 dequeue 操作主动移除尚未开始执行或等待重试的队列任务。

耐久执行阶段：对于需要长时间运行且不能因休眠或重启而丢失进度的任务，系统提供纤维（fiber）耐久执行机制。通过 runFiber API 启动的任务在 cf_agents_runs 表中注册一条运行记录，包含纤维名称、创建时间戳和空检查点快照。执行期间，任务可通过 stash() 调用将当前阶段的关键状态数据序列化并更新到运行记录的快照字段中，形成检查点。系统在纤维执行期间持有 keepAlive 锁，防止持久化对象实例在执行中途进入休眠。同时，纤维内部维护一个运行标志，支持外部通过取消信号触发纤维的协作式终止。

### 任务状态查询与取消

系统为每个任务维护完整的生命周期状态，包括：已入队（queued）、执行中（running）、已完成（completed）、失败待重试（retrying）、永久失败（failed）和已取消（cancelled）。所有状态变更通过 SQLite 事务原子更新，外部系统可通过任务标识符查询当前状态及历史状态变更记录。

状态查询接口的设计利用持久化对象实例的单线程特性：查询请求到达时，系统直接从 SQLite 队列表或运行表中读取对应任务行的当前状态字段，无需加锁或跨进程协调，查询延迟等同于单条 SQLite 读查询延迟。对于通过 WebSocket 保持连接的调用方，系统支持服务端主动推送状态变更事件，调用方无需轮询。状态变更事件在任务状态发生转换时由执行引擎同步触发，通过调用方的 WebSocket 连接发送包含任务标识符、新状态和可选结果数据的消息。

任务取消提供三种粒度的操作：按任务标识符取消单个任务（dequeue），按回调函数名称取消所有匹配的待执行任务（dequeueAllByCallback），以及清空全部队列（dequeueAll）。取消操作通过从队列表中删除对应行实现——仅对尚未开始执行或等待重试的任务有效，已在执行中的任务需要通过纤维的协作式取消信号来终止。对于通过 runFiber 运行的耐久任务，系统在纤维上下文中注入取消检查点，任务代码可在关键执行段之间检查取消标志，收到取消信号后保存当前快照并优雅退出。

### 休眠与中断后的恢复一致性

持久化对象实例在空闲约 70 至 140 秒后自动进入休眠状态，或在资源压力下被运行时平台主动驱逐。休眠和驱逐时，内存中的所有变量、运行中的定时器和进行中的网络请求均丢失，仅 SQLite 数据库、键值存储和已注册的定时 alarm 得到保留。系统通过以下机制保证休眠或中断后任务执行状态的一致性恢复。

队列恢复：队列任务以数据库行的形式持久化在 cf_agents_queues 表中，不依赖内存状态。实例重新唤醒时，onStart() 生命周期钩子触发队列刷新，从表中读取所有待处理任务并按 FIFO 顺序恢复执行。已完成和已失败的任务行保留在表中供查询，不参与再次调度。

纤维恢复：对于通过 runFiber 启动的耐久任务，系统在实例唤醒后执行孤儿纤维检测（_checkRunFibers）。该过程扫描 cf_agent_runs 表中所有状态为运行中的记录，并与当前内存中的活跃纤维集合进行比对。在内存中不存在的运行记录被判定为孤儿纤维——这表示该纤维在上一个生命周期中启动但未正常结束（因休眠、驱逐或崩溃中断）。系统读取孤儿纤维记录中的快照字段，调用子类实现的 onFiberRecovered 回调，将快照数据传递给恢复逻辑，由子类根据快照中的阶段标识和数据决定从哪个检查点继续执行。恢复过程不重放已完成的步骤，而是从最后一个检查点之后的逻辑段开始。

定时任务恢复：定时和周期性调度任务存储在 cf_agent_schedules 表中，每个调度行在创建时通过持久化对象实例的 alarm 机制注册唤醒时间。休眠期间，alarm 由运行时平台维护，到达预定时间后触发实例唤醒并执行对应的调度回调。调度任务的去重约束在恢复场景下同样有效：即使实例在 alarm 触发时刻处于唤醒状态且同时收到外部请求触发相同的调度逻辑，数据库层的唯一约束确保不会重复执行。

一致性判定模型：系统采用"持久化即真理"的一致性判定原则。所有任务状态（队列任务、运行记录、调度条目、检查点快照）的权威来源均为 SQLite 数据库中的持久化行，而非内存中的临时变量。实例唤醒时，系统以数据库中的状态为准重建内存执行上下文。对于队列任务，判定依据为任务行中的状态字段和重试计数；对于耐久纤维，判定依据为运行记录中的快照字段和纤维名称与内存的比对结果；对于定时调度，判定依据为调度表中的 alarm 时间是否已到达。这一模型使得恢复判定不依赖运行时平台特定的休眠通知或中断信号，仅依赖实例自身的持久化数据即可独立完成一致性重建。
