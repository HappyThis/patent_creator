## 技术方案

本方案在现有 Agent 运行时框架的基础上，构建了一套面向外部系统程序化调用的任务提交、执行管理与恢复一致性机制。核心思路是将外部提交的一次对话任务建模为持久化任务对象，围绕该对象提供提交即确认、幂等去重、异步执行、状态可查、可取消、中断可恢复的完整生命周期管理。以下分述各组成部分的技术手段与协同关系。

### 整体架构

本方案基于具有持久化状态的智能体（Agent）运行时，为外部系统提供程序化的任务提交与异步执行能力。核心思路是：在现有 Agent 的 HTTP 入口（onRequest）上增设任务提交端点，将外部提交的任务建模为具有明确生命周期的持久化任务对象，利用 Agent 运行时的持久化执行原语（runFiber）保证任务在休眠、重启或异常中断后的可恢复性，同时通过幂等键机制消除重复提交，通过状态查询接口和取消接口为外部调用方提供完整的任务生命周期管理能力。

### 任务提交与快速确认

外部系统通过向 Agent 的专属 URL 发送 HTTP POST 请求提交任务。Agent 在 onRequest 中识别任务提交路径（如 POST /tasks），解析请求体中的任务描述和可选参数，立即生成全局唯一的任务标识符（taskId），将任务元数据写入 SQLite 持久化表（cf_agent_external_tasks），并向调用方返回包含 taskId 和状态为"已接收"（RECEIVED）的响应。该响应的延迟仅取决于请求验证和一次 SQLite 写入，不等待模型推理或任何长时间处理，从而满足外部调用方对快速确认的要求。

### 异步执行与持久化保障

任务提交后进入异步执行通道。Agent 将任务插入持久化任务队列后，使用内部队列调度机制（基于 cf_agents_queues 表或专用任务表）按 FIFO 顺序异步触发执行。执行过程包裹在 runFiber 中：在开始执行前，于 cf_agents_runs 表中写入 fiber 记录；执行期间可通过 stash() 将中间结果落盘为检查点；执行完成后删除 fiber 记录。runFiber 内部自动持有 keepAlive 防止空闲超时驱逐，同时通过定时 alarm 心跳保持 Agent 存活。

### 重复提交去重

外部系统因超时或网络异常可能重复提交同一任务。本方案通过幂等键（Idempotency Key）机制消除重复：外部调用方在请求头（如 X-Idempotency-Key）中携带调用方生成的唯一标识符；Agent 在持久化表中维护幂等键到任务 ID 的映射关系（cf_agent_task_idempotency 表）。收到提交请求时，先以幂等键查询该表：若命中，直接返回已有关联任务的当前状态，不创建新任务也不重复入队；若未命中，在同一个 SQLite 事务中同时写入幂等键映射和任务记录，保证原子性。

### 任务状态管理与查询

每个外部提交的任务在持久化任务表中维护一个有限状态机，状态包括：已接收（RECEIVED）——任务已写入持久化存储但尚未开始执行；排队中（QUEUED）——任务已进入执行队列等待调度；执行中（RUNNING）——任务正在 runFiber 中执行并可附带当前检查点快照；已完成（COMPLETED）——任务成功完成并附有结果摘要或结果引用；已失败（FAILED）——任务执行失败并附有错误信息和重试次数；已取消（CANCELLED）——外部调用方主动取消了任务。状态转换在 SQLite 中原子更新，外部系统可通过 GET /tasks/{taskId} 查询最新状态。

### 中断恢复与一致性保障

Agent 运行环境可能因休眠（hibernation）、运行时重启或异常中断而导致正在执行的任务被强制终止。本方案利用 Agent 框架的 fiber 恢复机制实现执行一致性：Agent 每次被唤醒（onStart 或 alarm 触发）时，系统自动扫描 cf_agents_runs 表中残留的 fiber 记录。对于属于外部任务的残留 fiber，调用 onFiberRecovered 钩子进行恢复判定：若 fiber 记录中包含有效的 stash 检查点快照，则从检查点之后继续执行；若无法恢复（如超时过期或检查点损坏），则将任务状态标记为 FAILED 并记录原因。对于排队中但尚未开始执行的任务，Agent 重启后直接继续处理队列中的待执行项。

### 任务取消机制

外部调用方可通过 DELETE /tasks/{taskId} 请求取消尚未完成的任务。Agent 收到取消请求后，检查任务当前状态：若任务处于 RECEIVED 或 QUEUED 状态，直接从队列中移除并将状态更新为 CANCELLED；若任务处于 RUNNING 状态，通过 AbortController/AbortSignal 机制向正在执行的 fiber 发送中止信号，fiber 内部在执行各步骤前检查中止信号并及时退出，退出前可通过 stash 保存当前进度，最终将状态更新为 CANCELLED；若任务已处于终态（COMPLETED、FAILED 或 CANCELLED），返回当前状态不做变更。

### 任务清理与生命周期管理

为防止持久化任务数据无限增长，系统对已完成或已取消的任务实施生命周期管理：处于终态（COMPLETED、FAILED、CANCELLED）的任务在超过可配置的保留期限（如 24 小时）后，由 alarm 触发的定期清理任务自动删除任务记录及其关联的幂等键映射。外部调用方也可通过 DELETE /tasks/{taskId} 在获取终态结果后主动清理。清理操作仅删除任务元数据，不影响 Agent 自身状态或对话历史中的已写入消息。
