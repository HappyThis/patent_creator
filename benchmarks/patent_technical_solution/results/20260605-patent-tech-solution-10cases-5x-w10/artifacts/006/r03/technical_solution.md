## 技术方案

本技术方案提出一种面向共享知识文件的动态信号分层存储与读取融合方法，用于解决知识管理系统中高频变化的运行时信号反复改写共享知识文件所导致的版本控制状态异常、团队合并冲突增多及知识内容变化被噪声淹没的问题。

### 1. 整体架构

本方案将知识管理系统的存储架构划分为两个逻辑层次：共享知识层（Layer 1）和本机运行时信号层（Layer 2）。共享知识层承载可共享、可审阅、适合版本控制的知识内容，以 Markdown 文件形式存放于项目目录树中，纳入版本控制系统（如 Git）管理。本机运行时信号层承载访问次数、检索命中计数、排序权重（重要性评分 importance、新鲜度 recency）、成熟度等级（maturity）、更新计数和最近使用时间等高频变化的动态信号，以机器本地化方式存储，不纳入共享版本控制。

两个层次通过知识文件的标识符（例如文件在知识树中的相对路径）建立关联。读取知识时，系统从共享知识层获取静态知识正文与元数据，从本机运行时信号层获取对应的动态信号，在读取阶段完成融合，生成统一的知识视图供检索排序、过滤和展示使用。写入知识时，系统根据操作类型将数据路由到对应层次：知识内容的创建、编辑和删除写入共享知识层；搜索命中反馈、重要性衰减、成熟度升降等运行时信号更新仅写入本机运行时信号层，不触发共享知识文件的改写。

### 2. 共享知识层（Layer 1）

共享知识层以 Markdown 文件为载体，每个知识条目对应一个 Markdown 文件。Markdown 文件采用 YAML 前置元数据（frontmatter）加正文的结构。前置元数据中仅保留适合共享和版本控制的静态字段，包括：知识标题（title）、分类标签（tags）、检索关键词（keywords）、关联知识路径列表（related）、摘要（summary）。可选的创建时间戳（createdAt）作为知识条目的诞生时间记录在共享层中，该时间戳仅在知识条目首次创建时写入一次，后续不再因运行时事件更新。

Markdown 正文部分承载知识内容的结构化表述，可包括：变更理由（Reason）、原始概念（Raw Concept，含任务描述、变更列表、涉及文件、数据流描述、时间戳和作者信息）、结构化叙事（Narrative，含架构结构、依赖关系、要点、规则、示例和图解）、事实列表（Facts）以及知识片段（Snippets）。这些内容由用户或 AI 代理通过策展（curate）操作创建和更新，代表项目知识的真实语义内涵。

共享知识层的所有 Markdown 文件存放于项目目录下的指定知识目录（例如 .brv/context-tree/）中，随项目代码一同纳入 Git 等版本控制系统。由于运行时信号不再写入这些文件，文件的变更仅反映真正知识内容的增删改，版本历史干净、可审计，团队成员间的合并冲突大幅减少。

### 3. 本机运行时信号层（Layer 2）

本机运行时信号层独立于共享知识文件存储，每条记录以知识文件的相对路径作为主键，关联一组动态评分信号。信号字段包括：访问计数（accessCount，累计被搜索命中的次数）、重要性评分（importance，0-100 的数值，反映知识的综合使用热度）、新鲜度（recency，0-1 的数值，基于最近更新时间按指数衰减计算）、成熟度等级（maturity，枚举值：draft/validated/core，表示知识从草稿到验证再到核心的生命周期阶段）、更新计数（updateCount，累计被策展编辑的次数）以及最近更新时间（updatedAt）。

运行时信号层可选用多种本地存储实现方式：可以是项目目录下的隐藏数据库文件（例如 SQLite 数据库文件或 JSON 文件），存放于 .brv/ 下的专用子目录中，并通过 .gitignore 排除出版本控制；也可以是操作系统级的本地键值存储。无论采用何种实现，关键约束是：运行时信号文件不纳入版本控制，不在团队间共享，每台机器独立维护自己的运行时信号。

运行时信号的更新时机与机制如下：（1）搜索命中反馈：当用户或 AI 代理执行知识搜索操作时，系统对每条命中结果对应的知识路径累加访问计数，并按预设的重要性增量（例如每次命中增加 3 分，上限 100）提升重要性评分。（2）时间衰减：在读取或刷新运行时信号时，系统根据当前时间与最近更新时间的差值，对新鲜度按指数衰减公式重新计算（例如新鲜度 = exp(-天数/衰减常数)），同时对重要性按日衰减因子递减（例如重要性 = 重要性 × 衰减因子^天数）。（3）策展更新反馈：当知识内容被策展编辑时，系统记录一次更新计数，以预设的更新增量（例如 5 分）提升重要性评分，并将新鲜度重置为 1.0。（4）成熟度变迁：系统根据重要性评分和当前成熟度等级，按带滞回阈值的晋升/降级规则重新判定成熟度等级。这些更新均仅操作本机运行时信号层，不触及共享 Markdown 文件。

### 4. 读取融合机制

读取融合是连接两个存储层次的核心机制。当系统需要检索、排序或展示知识条目时，执行如下融合流程：

第一步，从共享知识层加载知识内容。系统在构建搜索索引时，遍历共享知识目录下的所有 Markdown 文件，解析每个文件的前置元数据和正文，提取标题、标签、关键词、关联路径、摘要和正文文本，构建倒排索引（例如 BM25 索引）。在此过程中，系统同时提取每个文件的相对路径作为后续关联运行时信号的键。

第二步，从本机运行时信号层批量加载动态信号。对于索引中的每条知识路径，查询运行时信号存储层，获取对应的评分字段（accessCount、importance、recency、maturity、updateCount、updatedAt）。如果某个知识文件在运行时信号层中尚无记录（新文件或首次在本机访问），则为其生成默认评分（importance=50，recency=1，maturity=draft，accessCount=0，updateCount=0），并将默认评分写入运行时信号层。

第三步，计算复合排序分数。对于每条搜索结果，系统将 BM25 文本相关性分数（归一化至 [0,1) 区间）、重要性评分（归一化至 [0,1]）和新鲜度（已在 [0,1] 区间）按预设权重加权求和，再乘以成熟度等级对应的排序增益系数（例如 core 级 1.15、validated 级 1.0、draft 级 0.85），得到最终的复合排序分数。该复合分数融合了文本语义匹配和运行时使用信号两个维度的信息，使检索结果既能匹配查询意图，又能反映知识的实际使用热度与可靠程度。

第四步，融合后的结果以统一视图返回给调用方（如 AI 代理或用户界面），包含来自共享知识层的标题、摘要、正文片段、标签和来自运行时信号层的成熟度等级、重要性评分等辅助信息，但运行时信号本身不暴露为共享知识文件的属性。

### 5. 写入分离与路由

写入操作根据操作类型自动路由到对应层次，确保运行时信号永远不会改写共享知识文件。

策展写入（内容编辑）：当用户或 AI 代理执行策展操作创建或更新知识条目时，系统将完整的知识内容（包括标题、标签、关键词、关联关系、摘要、正文各部分）写入共享知识层的 Markdown 文件。同时，系统向运行时信号层发送一次策展更新事件：将更新计数加一、以更新增量提升重要性评分、重置新鲜度为 1.0、记录当前时间为最近更新时间，并重新判定成熟度等级。策展操作也可能触发文件的创建或删除，创建时在运行时信号层建立初始默认评分记录，删除时触发清理流程。

搜索命中写入（访问反馈）：每次知识搜索操作结束后，系统收集本次搜索中每条命中知识路径的命中次数，将这些命中计数累加到内存中的访问命中缓冲区。当缓冲区满足刷新条件（例如搜索索引重建时、或缓冲区达到预设大小阈值时、或经过预设时间间隔后），系统批量将累积的命中次数写入运行时信号层，更新对应路径的访问计数和重要性评分，并根据最新重要性重新判定成熟度等级。批量写入的设计避免了每次搜索都触发磁盘写入，减少了 I/O 开销。写入过程仅操作运行时信号层的存储文件，不涉及任何共享 Markdown 文件的修改。

多源知识合并写入：当系统从远端拉取共享知识（pull 操作）或将本地知识与远端知识合并（merge 操作）时，共享知识层的 Markdown 文件按版本控制规则合并。对于运行时信号，合并策略为：重要性评分取双方最大值，新鲜度取双方最大值，访问计数取双方之和，更新计数取双方之和加一（计入合并操作本身），成熟度取双方中等级较高者，创建时间取双方中较早者。合并后的运行时信号写入本机运行时信号层，不写入共享文件。

### 6. 清理一致性机制

当共享知识层的 Markdown 文件被删除时，本机运行时信号层中与该文件路径对应的评分记录将成为孤立记录。如果不清理，这些孤立记录会白白占用存储空间，且在未来的索引构建中可能引发错误。本方案通过以下机制保证两层的删除一致性：

主动同步删除：当策展服务执行知识条目删除操作时，在删除共享层 Markdown 文件的同时，向运行时信号层发送删除指令，同步移除对应路径的评分记录。这是首选的、最直接的清理路径。

被动核对清理：在搜索索引重建或知识树扫描过程中，系统遍历共享知识层的所有有效 Markdown 文件路径，将其收集为一个有效路径集合。随后遍历运行时信号层中的所有记录，将那些键不在有效路径集合中的记录标记为孤立记录，并予以删除。该核对清理流程可在索引重建时自动触发，也可定期（例如按固定时间间隔或按用户主动触发的维护命令）执行。核对清理保证即便因异常情况（如进程崩溃、手动删除文件）导致主动同步删除未能执行，系统也能在下一次索引重建时自动恢复到一致状态。

此外，从远端拉取知识（pull）后，如果远端删除了某些知识文件而本地共享层同步删除了对应文件，运行时信号层的核对清理机制同样会在下一次索引重建时清除相应的孤立信号记录。

### 7. 可选实施方式

以下给出一种可选的具体实施方式，用于进一步说明方案的可行性。

运行时信号层存储格式：采用 JSON 文件（例如 .brv/runtime/scoring.json），以知识文件相对路径为键，值为包含所有评分字段的对象。文件内容示例：{"auth/jwt-tokens/context.md": {"accessCount": 42, "importance": 78.5, "recency": 0.82, "maturity": "validated", "updateCount": 5, "createdAt": "2025-01-15T10:30:00Z", "updatedAt": "2025-06-01T14:20:00Z"}}。该文件存放于 .brv/runtime/ 目录，通过 .gitignore 排除出版本控制。

访问命中缓冲区：在内存中维护一个 Map<String, Integer> 结构，键为知识文件相对路径，值为自上次刷新以来的累计命中次数。当索引重建（通常每 5 秒触发一次缓存失效检查）或缓冲区大小达到预设上限（如 1000 条）时，触发批量刷新。刷新时对每条记录读取当前 scoring.json 中的对应条目，应用命中增量公式（accessCount += 命中次数，importance = min(100, importance + 3 × 命中次数)），重新判定成熟度等级，然后写回 scoring.json。

时间衰减计算：不通过定时任务持续衰减，而是在每次读取运行时信号时按需计算。读取某条评分记录时，先根据 updatedAt 与当前时间的差值计算天数间隔，对新鲜度应用指数衰减、对重要性应用日衰减因子，将衰减后的值用于复合排序计算。衰减后的值可选择写回或不写回运行时信号层；写回可保证后续读取无须重复计算，但增加了写入频率；不写回则计算开销较小但每次读取均需重算。两种方式均属于本方案的可选变体。

成熟度滞回判定：使用带滞回间隙的阈值规则避免成熟度在阈值附近频繁振荡。晋升规则：importance >= 85 时晋升为 core；importance >= 65 且当前为 draft 时晋升为 validated。降级规则（滞回间隙）：当前为 core 且 importance < 60 时降级为 validated；当前为 validated 且 importance < 35 时降级为 draft。这种滞回设计使成熟度等级具有稳定性，不会因小幅的分数波动而反复变化。

### 8. 技术效果总结

本方案的核心技术构思可概括为：将知识管理系统中的共享知识内容与运行时动态信号进行物理存储分离，在读取阶段通过路径标识符关联实现逻辑融合，在写入阶段按操作类型自动路由到对应层次，并通过主动同步删除与被动核对清理双重机制保证两层的删除一致性。

该方案通过上述分层存储、读取融合、写入分离和清理一致性四个技术手段的组合，解决了共享知识文件因高频运行时信号写入而导致的版本控制异常和团队合并冲突问题，同时保留了运行时信号对检索排序质量的增益作用。从技术效果上看：（1）共享知识文件的版本历史干净可审计，只反映真实知识内容变化；（2）团队多人协作时，各自的本机运行时信号互不干扰，合并冲突大幅减少；（3）搜索排序质量不降级，因为复合排序分数在读取阶段仍融合了文本相关性和运行时信号两个维度；（4）系统具有自愈能力，核对清理机制确保即便出现异常情况也能在下次索引重建时恢复一致状态。
