## 技术方案

本方案提出一种浏览器侧代码模式（Browser CodeMode）系统，将模型生成代码的隔离执行能力从服务端扩展到浏览器环境。系统在浏览器主页面内构建一个与主页面 DOM 和全局状态完全隔离的沙箱执行环境，模型生成的代码在该沙箱中运行，通过受控的桥接协议调用主页面注册的动态客户端工具，从而实现"模型生成代码编排浏览器私有工具，但不暴露浏览器能力到服务端、不污染主页面环境"的目标。方案整体架构由浏览器沙箱执行器（BrowserCodeExecutor）、动态工具注册表（DynamicToolRegistry）、工具桥接协议（ToolBridgeProtocol）和沙箱管理器（SandboxManager）四部分协同构成。

### 整体架构

系统包含以下核心组件：（1）浏览器沙箱执行器，负责在浏览器侧创建与主页面隔离的代码执行环境；（2）动态工具注册表，运行在主页面上，接收并管理页面侧注册的工具描述与执行函数；（3）工具桥接协议，定义沙箱与主页面之间的受控通信规则；（4）沙箱管理器，统一管理沙箱生命周期、超时控制、日志收集和资源释放。模型生成的代码在沙箱中执行，沙箱通过桥接协议向主页面发起工具调用请求，主页面侧的调度器根据工具注册表查找并执行对应的工具函数，将结果或异常通过同一协议返回沙箱。

### 浏览器沙箱执行器

浏览器沙箱执行器在浏览器侧构建一个与主页面全局上下文完全隔离的 JavaScript 执行环境。该沙箱通过 iframe 元素实现：创建具有 null 源的 iframe，使其与主页面不同源，无法访问主页面 DOM 或全局变量。iframe 内部仅注入系统提供的桥接运行时模块，该模块向沙箱代码暴露一组代理命名空间（Proxy Namespace），不暴露任何主页面原生 API。

沙箱内部的桥接运行时模块实现以下机制：首先，劫持 console.log、console.warn、console.error 等日志方法，将其输出重定向到日志收集缓冲区而非浏览器控制台，实现日志的受控收集；其次，对于每个已注册的工具命名空间（如 page、ui、storage 等），运行时创建一个 Proxy 对象，对该 Proxy 的任意属性访问（get）返回一个异步函数，该函数通过 postMessage 向主页面发起带序列化参数的工具调用请求，并等待主页面返回结果后解析为返回值。这一机制使沙箱代码能以自然的方法调用语法（如 page.getState()）调用主页面工具，而工具的实际执行完全在沙箱之外的主页面上下文完成。

模型生成的代码在注入沙箱前，先经过代码规范化处理：去除模型输出中常见的 markdown 代码围栏标记（如 ```javascript...```）；通过抽象语法树（AST）解析识别代码形态，自动将函数声明、导出声明或多语句块包装为可执行的异步箭头函数表达式；对于空输入或不可解析的输入，降级为空异步函数以安全返回。规范化后的代码拼接工具命名空间的 Proxy 初始化代码，构成完整的沙箱执行模块。

### 动态工具注册表

动态工具注册表运行在主页面 JavaScript 上下文中，是主页面工具能力的结构化描述与执行入口。主页面开发者通过注册接口将浏览器私有工具注册到注册表中，每个工具包含以下元数据：工具名称（如 getCurrentPageState）、所属命名空间（如 page）、人类可读的描述文本、参数 JSON Schema（定义输入参数的结构与类型）、以及工具执行函数（在主页面上真实执行的回调函数）。注册表维护一个以命名空间为键、以工具记录列表为值的索引结构，支持注册、注销、按命名空间查询全部工具描述等操作。

工具名称规范化是注册表的关键机制。由于主页面注册的工具名可能包含连字符、点号、空格等不合法的 JavaScript 标识符字符，而沙箱中通过 Proxy 访问工具时要求工具名为合法标识符，系统在工具注册时自动对名称进行规范化处理：将连字符、点号、空格替换为下划线；剔除其余非法字符；对纯数字开头的名称添加下划线前缀；对 JavaScript 保留字（如 class、delete、return 等）追加下划线后缀。规范化后的名称同时用作沙箱中的 Proxy 属性键和桥接协议中的工具标识符。注册表同时保留原始名称到规范化名称的映射，确保工具执行时能正确路由到注册的执行函数。

为支持动态工具描述，系统设计了一套工具描述序列化与类型生成机制。注册表中的每个命名空间，其工具集合的元数据（名称、描述、参数 Schema）被序列化为结构化 JSON 描述符。该描述符可在每次沙箱执行前注入到模型提示中作为可用工具的类型声明，使模型在生成代码时知晓当前可用的全部工具及其调用签名。描述符同时被传递给沙箱运行时，运行时据此生成对应命名空间的 Proxy 和类型声明注释。当主页面在两次执行之间动态增删工具时，描述符随之下次执行更新，确保模型拿到的工具视图始终与当前注册表一致。

### 工具桥接协议

工具桥接协议定义沙箱 iframe 与主页面之间的受控通信规则。协议基于浏览器的 postMessage API 实现，所有消息均为结构化 JSON 对象，通过 MessageEvent.source 校验消息来源（仅接受来自已知沙箱 iframe 的消息，拒绝其他来源），通过 MessageEvent.origin 校验消息域。协议定义了如下消息类型：

| 消息类型 | 方向 | 说明 |
| --- | --- | --- |
| tool_call | 沙箱→主页面 | 工具调用请求，包含命名空间名、工具名、调用 ID、序列化参数 JSON |
| tool_result | 主页面→沙箱 | 工具调用成功结果，包含调用 ID、序列化结果值 |
| tool_error | 主页面→沙箱 | 工具调用失败信息，包含调用 ID、错误消息字符串 |
| register_tools | 主页面→沙箱 | 通知沙箱当前可用的工具集合描述符，供 Proxy 初始化 |
| sandbox_ready | 沙箱→主页面 | 沙箱初始化完成，可接收执行指令 |
| execute | 主页面→沙箱 | 向沙箱注入待执行的代码，携带超时配置 |
| execution_result | 沙箱→主页面 | 代码执行完成，包含返回值、日志数组、可能的错误信息 |
| log_batch | 沙箱→主页面 | 批量上报沙箱中收集的日志条目 |

工具桥接协议中的工具调用采用异步请求-响应模型：沙箱中的 Proxy 代理函数为每次工具调用生成唯一的调用 ID（UUID），将调用 ID、命名空间名、工具名和 JSON 序列化的参数打包为 tool_call 消息发送至主页面，然后创建一个 Promise 并挂起，等待主页面返回带有相同调用 ID 的 tool_result 或 tool_error 消息。主页面侧的调度器收到 tool_call 后，在注册表中按命名空间和工具名查找对应的执行函数：若未找到，直接返回 tool_error（"工具未注册"）；若找到，调用执行函数并捕获其返回值或异常，分别包装为 tool_result 或 tool_error 返回。沙箱 Proxy 收到 tool_result 后解析 JSON 并 resolve Promise；收到 tool_error 后在沙箱中抛出 Error 对象，使模型代码的 try-catch 可正常捕获异常。

### 沙箱管理器

沙箱管理器运行在主页面侧，统一管理沙箱的完整生命周期，包括创建、执行、超时控制、异常处理、日志收集和资源释放。沙箱管理器内部维护一个沙箱实例的状态机：空闲（idle）、执行中（executing）、超时（timed_out）、已释放（disposed）。

沙箱创建时，管理器动态生成一个具有 null 源的 iframe 元素并注入桥接运行时模块。运行时注入完成后，沙箱发送 sandbox_ready 消息，管理器状态切换为空闲。执行时，管理器将规范化后的代码、工具描述符和超时配置打包为 execute 消息发送至沙箱，状态切换为执行中。沙箱内部通过 Promise.race 机制在用户代码执行 Promise 和超时定时器 Promise 之间竞速：若用户代码先完成，返回 execution_result；若超时定时器先触发，沙箱上报超时错误并终止执行。

日志收集采用批量上报策略：沙箱内劫持的 console 方法将日志条目追加到内存缓冲区，每条日志附带时间戳和级别标记（log / warn / error）。当执行完成或发生异常时，完整的日志数组随 execution_result 消息一起返回主页面。对于长时间运行的代码，管理器可主动发送日志查询消息，沙箱以 log_batch 消息返回当前累积的日志。异常传播分为两个层级：（1）工具调用异常——主页面在执行注册工具时捕获的异常，通过 tool_error 消息传回沙箱，沙箱 Proxy 层将其转换为 Error 抛出，模型代码可使用 try-catch 处理；（2）代码执行异常——沙箱代码自身的运行时错误（如语法错误、类型错误），由沙箱 try-catch 捕获后，通过 execution_result 消息中的 error 字段上报主页面。

资源释放遵循确定性清理原则。每次代码执行完成后（无论成功、失败或超时），管理器移除沙箱 iframe 的事件监听器、清空待处理工具调用的映射表、并移除 iframe DOM 节点，确保不产生内存泄漏和残留通信通道。对于连续执行场景，管理器支持沙箱复用模式：在一次执行完成后不移除沙箱，仅重置日志缓冲区和工具描述符，等待下一次 execute 消息——这避免了重复的 iframe 创建开销——但复用次数受可配置的最大复用阈值限制，超过阈值后强制重建以确保隔离性。当管理器被销毁（如页面导航离开）时，所有活跃沙箱统一执行释放流程。

### 执行流程

一次完整的代码执行流程如下：（1）主页面开发者预先将浏览器私有工具注册到动态工具注册表，每项工具附带名称、命名空间、描述、参数 Schema 和执行函数。（2）沙箱管理器创建具有 null 源的 iframe 沙箱，注入桥接运行时模块。（3）沙箱完成初始化后发送 sandbox_ready。（4）管理器从注册表获取当前全部工具的描述符，序列化后通过 register_tools 消息发送给沙箱，沙箱运行时据此构建各命名空间的 Proxy 对象和类型声明。（5）当模型生成代码后，代码经过规范化处理（去围栏、AST 分析、包装为异步箭头函数），管理器将规范化代码与超时配置通过 execute 消息发送至沙箱。（6）沙箱在 try-catch 块中通过 Promise.race 执行代码：代码内部通过 Proxy 调用工具时，Proxy 生成 tool_call 消息发送至主页面并挂起等待；主页面调度器查找注册表、执行工具函数、返回 tool_result 或 tool_error。（7）代码执行完成或超时，沙箱将结果、错误信息和日志数组打包为 execution_result 返回主页面。（8）管理器根据配置决定复用或释放沙箱。

### 工具名称规范化机制

工具名称规范化在注册表注册环节和桥接协议调度环节双重执行。注册时，注册表对原始工具名执行字符替换（连字符/点号/空格→下划线）、非法字符剔除、数字开头加前缀、保留字加后缀的操作，生成规范化名称作为内部键。桥接协议中的 tool_call 消息携带的是规范化名称，主页面调度器直接使用该名称在注册表中查找，无需额外转换。沙箱 Proxy 在构建时，Proxy 的属性访问（get trap）接收到的 toolName 已经是合法的 JS 标识符，但该值可能来源于模型生成的代码中使用了原始工具名（如 page.get-current-state），此时沙箱运行时的 get trap 在访问 Proxy 前先执行一次规范化，确保发送给主页面的 tool_call 中的工具名始终是规范化形式。这种双重规范化保障了无论模型生成何种形式的工具名调用、无论开发者注册何种形式的工具名，桥接协议始终传递一致且合法的标识符。

### 非法工具调用与异常处理

系统对非法工具调用的处理覆盖三个层面。第一，工具未注册：当 tool_call 携带的工具名在注册表中不存在时，调度器返回 tool_error 消息，包含"工具未找到"的错误描述和工具名信息，沙箱 Proxy 将其转换为 Error 抛出。第二，参数不匹配：注册表中的工具执行函数应自行校验输入参数是否符合其声明的 JSON Schema；调度器在调用前可选执行 Schema 校验（作为可配置的开关），校验失败时直接返回 tool_error（"参数校验失败"）而不调用执行函数，避免将非法参数传入真实工具执行。第三，命名空间不存在：当 tool_call 携带的命名空间在注册表中不存在时，调度器直接返回 tool_error（"命名空间未注册"）。所有非法调用均以 tool_error 消息形式返回沙箱，沙箱将此错误作为 JavaScript Error 抛出，使其进入模型代码的正常异常控制流。模型可通过 try-catch 捕获这些错误并编写回退逻辑，如尝试替代工具或向开发者报告错误。

### 安全隔离与资源保护

本方案通过多层隔离机制确保浏览器侧代码执行的安全性。第一层，源隔离：沙箱 iframe 的源设为 null，根据浏览器同源策略，沙箱内代码无法通过 DOM 操作访问主页面文档树、Cookie、localStorage、sessionStorage 或任何主页面全局对象。第二层，网络隔离：沙箱 iframe 通过 sandbox 属性剥夺其网络访问权限（不设置 allow-same-origin 和 allow-scripts 之外的权限标记；fetch 和 XMLHttpRequest 在 null 源 iframe 中受到浏览器安全策略的额外限制），模型代码无法从沙箱中发起任意网络请求。第三层，工具调用控制：沙箱代码只能通过桥接协议调用主页面明确注册的工具，每个工具调用都经过来源校验（验证消息是否来自已知沙箱 iframe），且工具执行函数运行在主页面上下文——沙箱不能直接访问或调用任何未注册方法。第四层，超时保护：每次执行携带独立的超时配置，超时后沙箱内部的 Promise.race 终止代码执行，防止无限循环或长时间阻塞。

### 与服务端代码模式的协同

本方案可与服务端代码模式（如基于 Worker 的 DynamicWorkerExecutor）协同工作。当模型在一次对话中同时需要编排服务端工具和浏览器端工具时，系统可分层调度：模型首先生成服务端代码，由服务端 CodeMode 执行器在 Worker 隔离环境中运行，调用服务端工具；当服务端代码的执行结果表明需要浏览器侧操作时（如需要读取前端页面状态、触发 UI 操作），服务端将控制权交回浏览器侧的 BrowserCodeExecutor，由后者在浏览器沙箱中执行另一段模型生成的代码来编排客户端工具。服务端和浏览器端的工具描述符可以分别生成并注入各自的代码提示中，模型的上下文窗口同时感知两端可用工具，按需选择执行位置。这一分层协同模式避免了将浏览器私有工具描述和实现暴露到服务端，同时保持了模型对全量工具的统一编排能力。
