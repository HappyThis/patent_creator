## 技术方案

本技术方案提出一种浏览器侧代码模式（Browser Codemode）执行系统，使大语言模型生成的代码能够在浏览器隔离环境中安全执行，并通过受控协议调度页面中动态注册的客户端工具。方案围绕以下核心机制展开：以Web Worker为隔离沙箱执行模型生成代码，避免污染主页面环境；以基于postMessage的请求-响应协议实现沙箱与主页面间的受控工具调度；以动态工具注册与类型声明生成机制支持开发者声明浏览器私有能力而不将其搬运至服务端；以工具名规范化、非法调用拦截、异常传播、日志收集、超时控制和资源释放构成完整的执行安全保障体系。本方案还支持服务端工具与浏览器侧工具的统一编排，使模型能够在一个代码块中组合跨端的多步操作。

### 整体技术架构

本方案在浏览器侧构建一套代码模式（Codemode）执行系统，使大语言模型生成的代码能够在浏览器隔离环境中执行，并通过受控协议调度页面中注册的动态客户端工具。系统由以下核心组件构成：（1）浏览器侧隔离沙箱，负责承载模型生成代码的执行；（2）工具注册与描述生成模块，用于收集、规范化并生成可供模型理解的工具类型定义；（3）受控工具调度协议，定义沙箱与主页面之间的工具调用请求/响应通信机制；（4）工具名规范化模块，将动态注册的工具名称转换为合法的JavaScript标识符；（5）非法调用拦截与异常传播机制；（6）日志收集、超时控制与资源释放模块。

### 浏览器侧隔离执行环境

浏览器侧隔离执行环境采用Web Worker作为代码沙箱。与现有服务端方案中利用WorkerLoader动态创建隔离Worker的机制不同，浏览器侧沙箱在客户端页面中创建一个专用的Web Worker实例，模型生成的JavaScript代码在该Worker的全局作用域内执行。Web Worker天然不具备访问主页面DOM、全局变量或前端框架组件的能力，从而确保模型生成代码不会污染主页面环境。

沙箱内部构建一个基于Proxy的工具代理对象。该代理拦截对工具命名空间下任意属性的访问（例如 codemode.getPageState()），将工具名称和调用参数序列化后，通过postMessage通道发送至主页面。主页面侧的调度器接收请求后，查找已注册的工具执行函数并调用，再将执行结果通过postMessage回传至沙箱。此过程对模型生成的代码透明：代码中只需以异步函数调用的形式书写工具编排逻辑，无需感知底层通信细节。

与主页面通过postMessage进行通信时，采用请求-响应配对机制：每条工具调用请求携带唯一标识符，沙箱侧维护一个Promise回调映射表，当主页面返回匹配该标识符的响应消息时，对应的Promise被resolve或reject。此机制支持并发的多工具调用，各调用之间通过标识符隔离、互不干扰。沙箱内的console.log、console.warn、console.error输出被重定向至内部日志缓冲区，执行结束后一并返回，不直接输出至浏览器控制台。

### 动态工具描述与注册

主页面通过工具注册接口动态声明可在沙箱中调用的客户端工具。每个工具包含名称、自然语言描述、JSON Schema格式的输入参数定义和执行函数。工具注册不要求预先将所有工具搬运至服务端；工具的执行函数始终驻留在浏览器侧，只有工具的元数据（名称、描述、参数schema）被收集并用于生成类型定义。

系统根据已注册工具集合自动生成一份类型声明文本，描述各工具的函数签名和参数类型。该类型声明作为prompt的一部分提供给大语言模型，使模型了解当前可用的工具集合及其调用方式。模型据此生成编排代码，代码中通过命名空间代理对象（如codemode.toolName(args)）调用工具，无需在代码中自行构造HTTP请求或postMessage调用。

工具注册支持动态增删：页面可在运行时注册新工具或移除已有工具，下一次代码生成请求将使用更新后的工具集合生成新的类型声明。此设计确保开发者无需将浏览器私有能力（如读取当前页面状态、访问前端组件内部状态、调用浏览器API等）暴露给服务端，所有敏感能力仅存在于客户端，由受控的沙箱调度协议间接访问。

### 受控工具调度协议

沙箱与主页面之间的通信采用基于postMessage的受控请求-响应协议。协议定义了两类消息：工具调用请求（TOOL_CALL）和工具调用响应（TOOL_RESULT）。每条工具调用请求包含：唯一调用标识符（callId）、目标工具名称（toolName）、序列化的调用参数（arguments）。主页面侧的调度器根据toolName在已注册工具集合中查找对应执行函数；若工具不存在，返回错误响应，携带"工具未注册"错误码和消息。

调度器在执行工具前进行合法性校验：首先验证toolName是否在已注册工具白名单中；其次使用工具的JSON Schema定义对传入参数进行结构校验，参数不合法时拒绝执行并返回校验错误。合法调用被包裹在try-catch中执行，执行结果（成功返回值或异常信息）被封装为TOOL_RESULT消息，携带与请求匹配的callId回传至沙箱。沙箱侧根据callId找到对应的Promise回调，完成异步调用的闭环。

为支持并发工具编排，沙箱内生成的代码可使用Promise.all、串行await、条件分支等标准JavaScript异步模式组合多个工具调用。每个工具调用独立生成callId并通过独立的postMessage往返完成，不依赖全局状态或调用顺序。调度器对并发调用无数量限制，但受浏览器事件循环和postMessage通道带宽的自然约束。此外，协议支持在沙箱代码中传入初始化上下文数据（如当前页面URL、用户偏好等），作为只读变量注入沙箱全局作用域，减少不必要的工具往返。

### 工具名规范化

动态注册的客户端工具名称可能包含连字符、点号、空格等不构成合法JavaScript标识符的字符（例如 "get-page-state" 或 "myPlugin.listItems"），这与模型生成代码中直接以属性访问形式调用工具的需求冲突。系统在工具注册阶段和应用阶段各执行一次名称规范化处理。

规范化规则如下：将连字符（-）、点号（.）和空格统一替换为下划线（_）；剔除其余所有非标识符字符（仅保留字母、数字、下划线和美元符号）；若结果为空字符串则使用下划线占位；若结果以数字开头则前缀下划线；若结果与JavaScript保留字（如delete、class、return等）冲突则后缀下划线。例如，"get-page-state"规范化为"get_page_state"，"myPlugin.listItems"规范化为"myPlugin_listItems"，"delete"规范化为"delete_"。

规范化操作在工具注册时即应用于内部映射表，沙箱Proxy拦截的属性名使用规范化后的名称进行查找。同时，模型prompt中展示的类型定义也使用规范化后的函数名，使模型生成代码时使用的标识符与沙箱内实际可用的代理属性精确匹配，避免因命名差异导致的运行时"工具未找到"错误。

### 异常传播与日志收集

系统在多个层级处理异常传播。在沙箱内部，模型生成代码执行过程中的异常（包括语法错误、运行时错误、超时异常）被外层try-catch捕获，异常消息和堆栈信息被封装为错误结果返回。在工具调度层，单个工具调用失败不会导致整个编排流程崩溃：工具执行异常被捕获为带callId的错误响应回传沙箱，沙箱侧Proxy将该响应转为被reject的Promise，模型代码可通过try-catch自行决定对单个工具失败的处理策略（重试、降级、跳过）。在主页面侧，调度器捕获工具执行函数抛出的所有异常并封装为标准错误响应，异常不向沙箱侧泄露原始对象引用。

日志收集通过沙箱内console方法的拦截实现。沙箱创建时，console.log、console.warn、console.error被替换为自定义实现：所有日志输出被追加至一个字符串数组缓冲区，而非输出至浏览器控制台。执行结束后，日志数组作为结果的一部分返回，使调用方能够审查模型代码的运行过程。此设计既保留了模型通过console输出调试信息的习惯，又避免了模型生成代码向用户浏览器控制台随意输出内容的安全和体验问题。日志数组有上限（默认可配置），超出上限时采用环形缓冲区策略丢弃最早条目，防止内存溢出。

### 超时控制与资源释放

为防止模型生成代码陷入无限循环或执行时间过长导致页面无响应，系统在沙箱执行层面实施可配置的超时控制。执行函数使用Promise.race将用户代码与一个超时Promise竞速：当超时Promise先于用户代码完成时，用户代码的执行虽然无法被强制中断（JavaScript单线程特性），但结果Promise被reject并携带"执行超时"错误，后续工具调用响应将被忽略，执行结果立即返回超时错误。超时时长可由调用方配置（默认30秒），且超时后沙箱Worker随即被terminate终止，确保计算资源释放。

资源释放采用多层保障机制。每次代码执行完成（正常返回、异常、超时）后，Web Worker实例被terminate，释放其占用的内存和CPU资源。基于postMessage的事件监听器在Worker终止前被移除，防止消息泄漏。工具执行函数若涉及订阅、定时器或网络连接等长生命周期资源，由工具注册方在execute函数内部自行管理生命周期，调度器不对此类资源的释放负责。系统建议工具注册方在execute函数返回前完成所有内部清理，或通过AbortSignal模式支持取消操作。此外，调度器本身维护一个执行计数器，页面卸载时自动终止所有进行中的沙箱执行并清理注册的工具映射表。

### 代码规范化与执行流程

模型生成的代码通常包裹在Markdown代码围栏（```javascript...```）中，或包含TypeScript类型标注等浏览器无法直接执行的语法。系统在代码注入沙箱前执行规范化处理：首先剥离代码围栏标记；然后通过AST解析（使用轻量级acorn解析器）识别代码结构形态——若已是异步箭头函数则原样通过；若为命名函数声明则自动包裹为异步箭头函数并调用该函数；若为export default声明则提取声明体；若最后一个语句为表达式则自动添加return关键字。经过规范化后，所有代码形态统一为async () => { ... }格式，确保沙箱只需支持单一种类的代码入口。

完整执行流程如下：（1）页面开发者通过注册接口声明客户端工具集合；（2）系统根据工具集合生成类型声明文本，并与系统提示词拼接发送给大语言模型；（3）模型返回包含工具编排代码的响应；（4）系统对代码进行规范化处理；（5）创建Web Worker沙箱，注入Proxy工具代理和console拦截逻辑；（6）沙箱执行规范化后的代码，工具调用通过postMessage协议路由至主页面调度器；（7）调度器查找并执行对应工具、收集结果并回传；（8）执行结束后收集返回值、日志和可能的异常信息，终止Worker释放资源；（9）将执行结果返回给模型或调用方，支持模型基于结果进行后续推理或多轮编排。

### 混合工具编排与Code Tool模式

实际应用中，工具集合通常同时包含服务端工具（如数据库查询、API调用、文件操作）和浏览器侧工具（如读取DOM状态、访问剪贴板、调用前端组件方法）。系统将两类工具统一抽象为"代码模式工具"（Code Tool）：对外暴露为模型可调用的单一工具，模型通过编写一段JavaScript异步箭头函数来编排所有可用工具，而非逐个调用。这种模式使模型能够在一个推理步骤中完成"读取页面表单数据→调用服务端校验API→根据校验结果高亮错误字段"等需要条件判断和顺序依赖的复合操作，大幅减少模型与系统的往复轮次。

在混合工具场景下，工具类型定义同时包含服务端工具和浏览器侧工具的函数签名，模型生成的代码中对两类工具的调用语法完全一致（均为codemode.toolName(args)形式）。系统在执行层根据工具注册来源自动路由：服务端工具在服务端Worker沙箱中通过RPC直接调度执行；浏览器侧工具通过浏览器Web Worker沙箱经postMessage协议调度执行。代码本身不感知工具的实际执行位置，由系统根据工具注册元数据中的执行位置标记完成透明路由。对于需要跨端协同的复杂编排（例如在服务端生成报告再交由浏览器侧工具下载），模型代码可自然地串行组合两类工具调用。
