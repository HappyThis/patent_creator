## 技术方案

本技术方案提出一种在浏览器侧隔离执行模型生成代码并通过受控协议调度页面动态工具的方法与系统。其核心构思是：将模型生成的工具编排代码注入浏览器侧隔离沙箱中执行，沙箱内仅提供对工具名的代理访问，所有实际工具调用通过结构化的跨边界协议转发至主页面执行，从而在不暴露浏览器私有能力、不污染主页面环境的前提下，实现模型对动态客户端工具的灵活编排。

### 整体架构

系统在浏览器侧包含三个核心角色：主页面（Host Page）、隔离沙箱（Isolated Sandbox）和工具调度器（Tool Dispatcher）。主页面是工具的真实持有者与执行者，其上注册有一组动态工具，每个工具包含工具名、输入模式描述和实际执行函数。隔离沙箱是模型生成代码的执行环境，以与主页面分离的 JavaScript 上下文运行（可通过同源 iframe 配合沙箱属性、Web Worker 或浏览器扩展隔离上下文实现），沙箱内默认阻断对主页面 DOM、全局变量及浏览器网络 API 的直接访问。工具调度器是连接沙箱与主页面的桥接模块，负责接收沙箱发起的工具调用请求、校验工具合法性、在主页面执行对应工具并将结果回传沙箱。

### 浏览器侧隔离执行环境

隔离沙箱的构建是实现本方案安全基线的关键。沙箱采用以下机制保证隔离性：首先，沙箱运行在与主页面分离的 JavaScript 上下文中（例如一个具有 sandbox 属性的 iframe 或一个 Web Worker），通过浏览器原生安全策略阻断沙箱对主页面 DOM 和全局作用域的直接引用。其次，沙箱内部不注入任何真实工具的实现代码，而是为每个工具命名空间注入一个 Proxy 代理对象。该 Proxy 拦截对工具名的属性访问（如 codemode.search、state.readFile），将调用信息序列化为结构化请求并通过唯一授权的消息通道发往主页面，而非在沙箱内执行任何实际操作。第三，沙箱默认关闭对浏览器网络 API（fetch、XMLHttpRequest、WebSocket 等）的直接访问能力，所有对外交互必须通过工具调度器的受控通道完成。

模型生成的代码以异步箭头函数的形式传入沙箱。系统在注入前对代码进行语法规范化处理：剥离模型可能附加的 Markdown 代码围栏标记，通过 AST 解析（如基于 acorn 的解析器）识别代码结构，自动将非箭头函数形态的代码（命名函数声明、裸表达式序列等）规整为标准异步箭头函数，确保沙箱内执行一致。若代码无法通过 AST 解析，系统将其包裹为默认箭头函数并保留原始代码体，最大程度兼容模型输出的格式波动。

### 动态工具描述与注册机制

主页面向工具调度器注册的工具是动态的——开发者可在运行时增删或更新工具定义。每个工具的定义包含三个必要信息：工具名（唯一标识符）、工具描述（自然语言说明工具功能与适用场景）和输入模式（描述工具接受的参数结构及其类型，可采用 JSON Schema、Zod schema 或 TypeScript 类型声明等形式表达）。此外，工具定义中还携带实际的执行函数，但该执行函数始终保留在主页面侧，不会传入沙箱。

当模型需要生成编排代码时，系统从当前已注册的全部工具中提取类型描述，生成一份类型声明文本。该文本包含每个工具名对应的函数签名（参数类型与返回类型），按命名空间分组呈现，作为提示词上下文提供给模型。由此模型在不接触任何工具实现细节的前提下，即可了解当前可用工具的调用接口并生成正确的编排代码。类型声明文本的生成是可配置的：若工具提供方（ToolProvider）自行提供了类型声明，则直接使用；否则系统基于工具的输入模式自动推导并生成 TypeScript 风格的接口声明。

进一步地，工具可按命名空间组织。默认命名空间为 codemode，开发者可指定自定义命名空间如 state、github、shell 等。每个命名空间在沙箱中独立暴露为一个 Proxy 对象，模型代码通过 namespace.toolName(args) 的语法调用不同来源的工具。这种命名空间机制使得系统能够融合来自不同应用层、不同 MCP 服务器或多方提供的工具集而不会发生名称冲突。

### 受控工具调用协议

沙箱与主页面之间的工具调用遵循一套结构化的请求-响应协议。当沙箱中的模型代码调用 codemode.toolName(args) 时，Proxy 拦截该调用并执行以下流程：（1）将工具名（toolName）和参数对象序列化为 JSON 字符串；（2）通过唯一定向的消息通道（如 postMessage 通道或专用 RPC 桩）将调用请求发送至主页面的工具调度器；（3）工具调度器解析请求，在校验通过后，在主页面上下文中以原始参数调用对应工具的真实执行函数；（4）执行完成后，将返回值序列化为 JSON 字符串，通过同一消息通道回传沙箱；（5）沙箱侧 Proxy 解析响应，若包含错误信息则抛出异常，否则将结果返回给模型代码。

消息通道的设计确保沙箱与主页面之间只存在一条可控的通信路径。该通道在沙箱初始化时建立，并在沙箱销毁时关闭。通道中传输的消息采用统一格式，每条调用请求至少包含：工具命名空间、工具名、调用标识符（用于关联请求与响应）和参数负载。响应消息至少包含：对应的调用标识符、执行结果或错误信息。通过调用标识符的关联机制，支持沙箱内并发发起多个工具调用而不会发生响应错配。

对于需要传递非 JSON 可序列化数据（如 ArrayBuffer、文件句柄等）的场景，协议支持通过结构化克隆算法或 Transferable 对象机制传输，在消息通道建立时声明可传输类型白名单。

### 工具名规范化

由于工具可能来自不同来源（应用自定义工具、MCP 服务器、第三方插件等），其原始名称可能包含连字符（-）、点号（.）、空格或数字开头等不符合 JavaScript 标识符规则的字符。系统在将工具注入沙箱的 Proxy 之前，对每个工具名执行规范化转换：将所有连字符、点号和空格替换为下划线；剔除其余非标识符字符；若名称以数字开头，则前缀下划线；若名称与 JavaScript 保留字（如 delete、class、new 等）冲突，则后缀下划线。规范化后，沙箱内仍通过原始工具名发起调用（因为 Proxy 的 get 拦截器接收的 toolName 仍是模型写入代码中的规范化名称），而工具调度器在查找真实工具时同样使用规范化键名进行匹配，确保两端一致。

### 非法工具调用拦截

工具调度器在收到来自沙箱的调用请求后，执行多级合法性校验：（1）命名空间校验：检查请求中指定的命名空间是否已注册，未注册的命名空间直接返回错误；（2）工具名校验：在已注册命名空间内查找对应工具名，不存在的工具名返回明确的“工具未找到”错误，包含请求的工具名信息；（3）参数模式校验：若工具定义中提供了输入模式描述，工具调度器在执行前使用该模式对传入参数进行验证，模式不合规的参数在执行前被拦截并返回参数错误详情；（4）审批过滤：系统自动过滤标记为需要用户审批（needsApproval）的工具，此类工具不注入沙箱，模型代码无法调用它们，避免在沙箱执行流程中引入审批停顿。所有校验失败均以结构化错误形式通过协议通道回传沙箱，沙箱内的 Proxy 将其转换为 JavaScript 异常抛出，模型代码可通过 try-catch 捕获并处理。

### 异常传播机制

异常传播采用分层透传机制。在沙箱内，若 Proxy 从工具调度器收到错误响应，则将错误信息构造为 JavaScript Error 对象抛出，模型代码可捕获该异常并决定重试、降级或终止。在主页面侧，工具执行函数抛出的任何异常（同步异常或 Promise rejection）被工具调度器捕获，提取其消息字符串，按统一错误格式封装并回传沙箱，不暴露主页面调用栈或内部状态。若消息通道本身出现异常（如连接断开），系统在沙箱侧触发全局错误处理，将当前所有进行中的工具调用标记为失败并返回通道异常错误。上述分层设计保证了异常信息在隔离边界两侧均可追溯，同时不泄露对侧环境的敏感信息。

### 日志收集

沙箱内的日志收集通过在代码注入时重写 console.log、console.warn、console.error 等全局方法实现。注入的代码执行前，系统在沙箱上下文中创建日志缓冲数组，将上述控制台方法替换为向该数组追加格式化日志条目的函数。日志条目按时间顺序记录，并标注日志级别（普通日志、警告、错误）。代码执行结束后（无论成功、失败或超时），日志缓冲数组随执行结果一并返回，供模型在下一次交互中分析调试，或供开发者查看审计。日志缓冲位于沙箱内部，不会泄漏到主页面控制台。

### 超时控制与资源释放

超时控制采用 Promise.race 机制实现。沙箱内代码执行被包装为一个 Promise，与一个延迟 reject 的定时器 Promise 竞速。超时时长可配置（默认为 30 秒），由系统在沙箱初始化时注入。当超时触发时，定时器 Promise 抛出“执行超时”错误，沙箱内执行流程被中断，已收集的日志随超时错误一同返回。此机制不依赖主页面定时器，避免因主页面阻塞导致超时失效。

资源释放方面，每次代码执行使用独立的沙箱实例——执行完毕后沙箱即被销毁，其占用的内存、事件监听器和消息通道一并释放。沙箱实例的创建通过工厂模式管理（如 WorkerLoader），每次执行分配新的隔离上下文，不使用池化复用，从根本上避免跨次执行的状态污染和信息泄漏。对于涉及外部资源的场景（如浏览器 DevTools 会话、WebSocket 连接等），工具调度器在 finally 块中确保资源关闭，无论执行成功或失败均执行清理操作。工具调度器自身也支持会话级别的生命周期管理：为每次工具编排调用建立独立的会话，调用结束后关闭会话并释放关联的外部资源。

### 整体执行流程

整体执行流程如下：（1）应用在主页面向工具调度器注册一组工具，提供工具名、描述、输入模式和真实执行函数；（2）系统从已注册工具中提取类型声明，构建包含工具接口描述的提示词上下文并发送给模型；（3）模型生成一段 JavaScript 异步箭头函数，其中通过 namespace.toolName(args) 的形式编排多个工具调用，包含条件判断、循环和错误处理逻辑；（4）系统对生成代码进行语法规范化（剥离 Markdown 围栏、AST 规整），然后启动新的隔离沙箱实例；（5）在沙箱内，为每个命名空间创建 Proxy 代理对象，重写 console 方法以捕获日志；（6）沙箱执行模型代码，代码中的工具调用被 Proxy 拦截，转化为结构化请求通过消息通道发往主页面的工具调度器；（7）工具调度器校验命名空间、工具名和参数合法性，然后在主页面上下文中调用工具执行函数，将结果通过消息通道回传沙箱；（8）工具调用的成功结果或错误被 Proxy 透传回模型代码，模型代码可据此继续编排后续调用；（9）代码执行完毕或超时后，沙箱返回执行结果和日志缓冲数据，沙箱实例被销毁，关联资源被释放；（10）执行结果（包括返回值、错误信息和日志）返回给模型，模型可根据结果生成最终回复或调整策略再次发起代码执行。

### 可选实施方式

在上述核心方案的基础上，系统可进一步支持以下可选实施方式：（1）网络隔离控制：沙箱默认阻断所有外部网络访问，但可通过配置化方式为沙箱指定一个受控的出站网关（Fetcher），所有网络请求经该网关审计和转发；（2）自定义模块注入：允许开发者向沙箱注入额外的 JavaScript 模块，模型代码可通过 import 语句引用这些模块，扩展沙箱的计算能力而不破坏隔离性；（3）工具执行审批：对于高风险工具，可在工具调度器侧设置审批拦截点，在工具实际执行前暂停流程并等待用户确认，审批通过后继续执行并将结果回传沙箱；（4）调试日志对外暴露：工具调度器可维护一个调试日志环形缓冲区，记录每次工具调用的发起时间、方法名、参数摘要、耗时和结果状态，供开发者通过专用接口查询，用于诊断模型代码的编排行为。
