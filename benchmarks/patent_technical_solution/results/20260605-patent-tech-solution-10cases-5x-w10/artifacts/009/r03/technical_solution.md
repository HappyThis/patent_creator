## 技术方案

本方案提出一种浏览器侧隔离执行模型生成代码并调度动态客户端工具的系统与方法。其核心构思是：将服务端 codemode 的"模型生成代码→隔离沙箱执行→通过 Proxy/RPC 回调宿主工具"这一架构模式扩展至浏览器环境。模型生成一段 JavaScript 异步箭头函数，该函数在浏览器侧的一个隔离沙箱（如 Web Worker 或沙箱化 iframe）中执行；沙箱内通过 Proxy 机制拦截对工具命名空间的访问，将工具调用序列化为结构化消息，经受控消息通道发送至主页面上下文；主页面根据已注册的工具描述匹配并真实执行对应的客户端工具，再将执行结果回传至沙箱，最终将返回值与日志统一返回给模型。整个过程实现了"生成代码与主页面环境隔离、工具真实执行在主页面的受控调度"。

### 系统整体架构

系统在浏览器侧引入三层协作架构：工具注册层、隔离沙箱层和调度协议层。工具注册层运行于主页面上下文，负责声明和注册可在浏览器中真实执行的工具集合，包括工具的标识名称、输入参数模式、功能描述和实际执行函数。隔离沙箱层是一个独立于主页面的 JavaScript 执行环境，模型生成的代码在此处运行，且默认无法直接访问主页面 DOM、全局变量或浏览器 API。调度协议层是沙箱与主页面之间的受控消息通道，负责将沙箱中的工具调用请求序列化为结构化协议消息发送至主页面，由主页面匹配已注册工具并执行，再将结果或异常以协议消息形式回传。

### 浏览器侧隔离沙箱

浏览器侧隔离沙箱可采用 Web Worker 或具有严格 sandbox 属性的 iframe 实现。沙箱的关键设计包括：（1）模型生成代码被规范化为一个异步箭头函数，规范化的方式与服务端 codemode 一致：先剥离 Markdown 代码围栏标识，再通过 AST 解析识别代码形态——若已是箭头函数则原样保留，若为命名函数声明则自动包装调用，若最后语句为表达式则自动插入 return——从而确保代码可在沙箱中直接作为表达式求值执行；（2）沙箱内通过 Proxy 对象为每个工具命名空间创建拦截代理；当生成代码调用如 codemode.getPageState({selector:'.main'}) 时，Proxy 的 get 陷阱拦截属性访问，将工具名和参数序列化为 JSON，通过受控消息通道发出，而不是在沙箱内执行任何真实操作；（3）沙箱默认阻断外部网络访问（fetch 和 connect），只保留与主页面之间的受控消息通道，防止模型生成代码绕过工具调度直接发起网络请求或操控 DOM。

### 工具动态注册与描述生成

系统支持工具的动态注册与描述生成。主页面可在运行时向工具注册表添加或移除工具，每个工具以"工具名→{描述, 输入模式, 执行函数}"的形式注册。工具描述信息（包括工具名称、功能说明和输入参数的 JSON Schema）被提取并生成 TypeScript 类型声明文本，嵌入 codemode 工具的 description 字段中，使模型在生成代码时能够获得完整的类型提示。对于来自 MCP（Model Context Protocol）服务器的工具，其名称可能包含连字符或点号（如 server.list-items），系统通过名称规范化将其转换为有效的 JavaScript 标识符（如 server_list_items），同时保持类型定义中的语义对应关系，使模型能以规范后的标识符调用工具，调度层再反向映射回原始工具名进行匹配。

### 受控调度协议

沙箱与主页面之间的调度遵循一套受控协议。协议消息为结构化对象，由沙箱侧发起请求、主页面侧返回响应。请求消息包含：目标工具名（已规范化的标识符）、序列化的调用参数、以及唯一调用标识符（callId）。主页面侧的调度器接收请求后，执行以下流程：（1）在工具注册表中按工具名查找对应工具，若不存在则返回包含错误信息的响应；（2）若工具配置了执行前审批（needsApproval），则先挂起并将审批请求通过 WebSocket 发送至客户端 UI 层，等待用户批准或拒绝；（3）审批通过或无需审批时，以请求中的参数调用工具的 execute 函数，执行过程中捕获同步和异步异常；（4）将执行结果或异常信息封装为响应消息，包含原始 callId 以便沙箱侧对应。响应消息沿原消息通道回传至沙箱中的 Proxy 层，Proxy 解析响应：若响应含 error 字段，则在沙箱内抛出对应错误；否则将 result 作为 Promise 的解决值返回给生成代码。

### 异常传播与非法调用处理

系统对工具调用异常采用全链路传播机制。当主页面侧工具执行抛出异常时，调度器捕获异常并将其消息文本封装进响应消息的 error 字段。沙箱中的 Proxy 层在收到带 error 的响应后，构造一个 Error 对象并 throw，使模型生成的代码可以通过 try/catch 捕获并处理该异常。当工具不存在（即注册表中无匹配记录）时，调度器返回明确的"工具未找到"错误，沙箱侧同样以抛出异常的方式暴露给生成代码。这种设计使模型能够在生成代码中编写条件分支和错误恢复逻辑，例如在某个工具调用失败时回退到替代方案或向用户报告具体失败原因。

### 日志收集机制

系统在沙箱中拦截并收集 console.log、console.warn 和 console.error 输出。具体方式为：在沙箱初始化时，将全局 console 对象的三个输出方法替换为自定义实现，该实现将每次调用的参数拼接为字符串，按日志级别添加前缀（普通日志无前缀，警告加 [warn]，错误加 [error]），并追加到内部日志缓冲区。执行结束后，日志缓冲区随执行结果一同返回，使开发者和模型能够获取生成代码的运行时输出。日志收集与主页面 console 完全隔离，沙箱内的日志不会泄露到浏览器开发者工具的控制台。

### 超时控制与资源释放

系统提供可配置的超时控制与确定性资源释放。超时控制通过 Promise.race 实现：将用户代码的执行包装在一个 Promise 中，与一个在指定时长后 reject 的超时 Promise 竞速；若超时先触发，执行被中断并返回超时错误，同时保留已收集的日志。资源释放方面，每次代码执行使用独立的沙箱实例，执行完毕或超时后，沙箱实例被立即终止并释放其占用的内存、事件监听器和消息通道。主页面侧与该沙箱实例关联的调度器代理和消息通道也同步清理，杜绝资源泄漏。工具审批挂起期间，若沙箱因超时或用户取消而终止，挂起的审批状态被自动清除，避免留下悬空等待。

### 工具名称规范化

工具名称规范化是连接模型生成代码与主页面工具注册表的关键环节。由于模型生成代码必须符合 JavaScript 标识符语法，而客户端工具的原始名称可能包含连字符、点号、空格或其他非标识符字符，系统采用以下规范化规则：（1）将连字符"-"、点号"."和空格替换为下划线"_"；（2）剔除所有剩余的非标识符字符；（3）若规范化后的名称为空，使用"_"作为默认名；（4）若名称以数字开头，在此之前添加下划线；（5）若规范化后的名称与 JavaScript 保留字（如 delete、class、new 等）冲突，在末尾追加下划线。规范化仅影响沙箱内的调用标识符，类型定义中的语义描述保持工具原始名称，调度层在接收沙箱调用时执行反向映射：将规范化名称还原为原始工具名以在注册表中查找。

### 多命名空间工具组织

系统支持多命名空间的工具提供者架构。主页面可以声明多个工具提供者（ToolProvider），每个提供者拥有独立的命名空间前缀和工具集合。例如，页面状态工具挂载于 page 命名空间（调用形式为 page.getState()），用户界面工具挂载于 ui 命名空间（调用形式为 ui.showDialog()），默认工具挂载于 codemode 命名空间。每个命名空间在沙箱中对应一个独立的 Proxy 拦截层，各自通过独立的消息通道标识（或共享通道中的命名空间字段）与主页面侧对应的工具分发器（ToolDispatcher）通信。该设计允许将不同来源的工具（页面内置工具、MCP 工具、扩展工具）组织在不同的命名空间下，模型生成代码时可通过命名空间前缀明确区分和调用。

### 代码规范化处理

模型生成代码在进入沙箱执行前，需要经过代码规范化处理，使各种形态的生成结果统一为可直接在沙箱中调用的异步箭头函数。规范化流程为：（1）剥离 Markdown 代码围栏（如 ```javascript 和 ```）；（2）使用 acorn 等 JavaScript 解析器将代码解析为 AST；（3）根据 AST 形态执行不同策略：若代码已是完整的箭头函数表达式，原样保留；若为 export default 导出声明，递归提取其声明体；若为单条命名函数声明，自动包装为"async () => { 原代码; return 函数名(); }"；若最后一条语句为表达式语句，将其转换为 return 表达式后包装；其余情况直接包装为 async 箭头函数体。规范化后的代码保证能在沙箱中作为 IIFE 执行并返回结果。

### 完整执行流程

整体执行流程如下：（1）系统将已注册的浏览器侧工具集转换为 TypeScript 类型声明文本，连同代码编写指引，嵌入 codemode 工具的描述信息中，作为一个特殊的"写代码"工具提供给模型；（2）模型在推理过程中决定调用 codemode 工具，生成一段 JavaScript 异步箭头函数，函数体内通过命名空间调用客户端工具；（3）系统通过 AST 解析对生成代码进行规范化处理；（4）规范化后的代码被发送至浏览器侧隔离沙箱执行，沙箱内预先为每个工具命名空间创建 Proxy 拦截层；（5）沙箱中代码执行时，每次工具调用被 Proxy 拦截，生成包含工具名、参数和调用标识符的请求消息，通过受控消息通道发送至主页面；（6）主页面调度器匹配并执行对应的已注册工具，将结果或异常封装为响应消息回传；（7）沙箱中的 Proxy 层解析响应，将结果返回给生成代码或抛出异常；（8）代码执行完毕或超时后，收集执行结果、日志和可能的错误信息，统一返回给模型。模型可根据返回信息决定下一步操作，形成"模型推理→代码生成→浏览器侧隔离执行→调度客户端工具→结果返回"的闭环。
