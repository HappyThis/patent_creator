## 技术方案

### 总体架构与核心构思

本方案提出一种保留式流式子代理工具编排方法，使主代理在处理单次用户请求时，能够将子任务分派给一个或多个独立的子代理执行，并将子代理的执行过程以流式事件的形式实时呈现在用户的同一会话视图中。核心构思在于：将子代理视为具有独立持久化存储和独立聊天流的完整对话代理，而非内存中的临时任务；主代理维护一个轻量级的运行注册表以追踪子代理的生命周期；子代理的执行结果（包括流式输出块）持久化在子代理自身的存储中；主代理通过框架管理的桥接层将子代理的流事件转发至前端，并在重连或刷新后通过注册表重放历史事件。

系统由三层组件协同工作：（1）主代理端运行注册表，记录每个子代理运行的标识、状态、与父工具调用的关联关系等元数据；（2）子代理端运行映射表，将编排层运行标识映射到对话引擎内部的请求标识和流标识；（3）事件协议层，定义启动、数据块、完成、错误、中止、中断等生命周期事件的统一格式，并通过主代理的WebSocket连接向客户端广播。

### 父代理端运行注册表

主代理在自身的持久化存储中维护一个框架管理的 agent tool 运行注册表，记录每一次子代理分派的关键元数据。该注册表与已有的子代理存在性注册表（回答"该子代理是否存在"）职责分离：运行注册表回答"哪次父操作创建了该运行、其事件应在何处呈现、重放时应合成何种终端事件"。

注册表记录至少包含以下字段：运行标识（runId）、父工具调用标识（parentToolCallId）、子代理类型（agentType）、输入预览（inputPreview）、运行状态（status）、摘要（summary）、错误信息（errorMessage）、显示顺序（displayOrder）、启动时间戳和完成时间戳。其中，输入预览仅存储安全的摘要信息而非完整原始输入，避免将敏感数据（如提示词、凭证、文件内容）在编排表中产生二次拷贝。

运行状态生命周期包括：starting（记录已插入，子代理尚未确认启动）、running（子代理已启动对话轮次）、completed（正常终止）、error（子代理抛出异常或流错误）、aborted（被父代理显式中止信号取消）、interrupted（父代理恢复时发现运行处于非终止状态且无法安全重连实时流）。其中interrupted状态仅由父代理在恢复核对时设定，子代理不会自行声明该状态。一旦运行在注册表中达到终止状态，该状态即为权威状态，后续的延迟取消或重复核对不得覆写。

注册表记录的插入、状态更新、恢复核对均由框架自动完成。应用代码仅控制策略层面：保留与垃圾回收规则、历史清除时是否连带删除运行记录和子代理、钻入访问的授权决策、可选的显示元数据（标签、图标等），以及是否持久化完整输入输出。

### 子代理端运行映射与适配器契约

每个子代理在自身存储中维护一个运行映射表，将编排层的运行标识（runId）映射到对话引擎内部的请求标识（requestId）和可恢复流标识（streamId）。三者职责分离：runId 是面向产品和编排的标识，requestId 是对话轮次/中止注册表的标识，streamId 是可恢复流持久化的标识。这种设计避免将"一次 agent tool 运行等于一次对话轮次"的假设固化到标识体系中，为未来支持单次 agent tool 运行包含多轮对话留出扩展空间。

子代理端映射表是恢复的权威来源。若父代理在子代理启动后、存储生成的 requestId/streamId 之前崩溃，父代理在恢复时必须能从子代理按 runId 查询获得这些内部标识，而非依赖父代理侧的快照。

启动操作按 runId 实现幂等：若子代理已存在该 runId 的运行记录，则返回已有运行状态而不启动重复的对话轮次。取消和重放操作同样按 runId 寻址，由子代理适配器内部完成到 requestId 和 streamId 的查找转换。

### Agent Tool 事件协议与流式传输

主代理通过 WebSocket 连接向客户端广播 agent tool 事件。事件协议定义六种生命周期事件类型，区分执行结果的不同终止路径：

- started：子代理启动事件，携带 runId、agentType、inputPreview、显示顺序（order）和可选 display 元数据（名称、图标）。在子代理实际开始推理之前即由父代理合成并广播，使前端面板可在任何数据块到达前完成渲染
- chunk：子代理流式输出数据块，body 字段承载不透明的 JSON 编码 UIMessageChunk。框架不发明第二套词汇来描述文本、推理、工具调用等不同块类型，而是复用对话引擎已有的 applyChunkToParts 原语
- finished：正常完成事件，携带 runId 和 summary（子代理最终助理消息的文本摘要）
- error：错误事件，携带 runId 和 error 错误信息
- aborted：显式中止事件，携带 runId 和可选 reason
- interrupted：中断事件，表示父代理恢复时发现运行因观察者丢失而无法继续实时跟踪

每个事件在广播时封装为统一的消息帧，包含事件类型标记（agent-tool-event）、父工具调用标识（parentToolCallId）、单调递增序列号（sequence）和可选的重放标记（replay）。序列号按每个 agent tool 运行独立单调递增，作为客户端去重的键。由于并行子代理在同一父工具调用下的多个运行各自从序列号 0 开始，客户端去重键需要包含 (parentToolCallId, runId, sequence) 三元组。

流式传输采用 NDJSON（换行分隔 JSON）帧格式在子代理和父代理之间进行 RPC 通信。子代理将对话引擎产生的每个 UIMessageChunk 编码为 { sequence, body } 行并写入可读流；父代理通过 RPC 可读流读取这些帧，重新加盖父代理侧的序列号（以包含启动/完成等合成事件），并通过 broadcast 广播给所有连接的客户端。同时，子代理的可恢复流机制将每个块持久化到子代理自身的 SQLite 存储中，作为持久化的权威事件日志。

### 执行流程：runAgentTool 与 agentTool

本方案提供两种 API 形态，覆盖两种调用场景：runAgentTool 用于确定性工作流和命令式编排；agentTool 用于 LLM 自主选择分派的工具调用场景。两者共享同一底层机制。

runAgentTool 的命令式执行流程如下：（1）生成或接受调用方指定的 runId；（2）在父代理注册表中插入 status=starting 的运行记录；（3）通过 subAgent(Cls, runId) 获取或创建子代理实例；（4）向父代理客户端广播 started 事件；（5）通过子代理适配器的 startAgentToolRun 接口驱动子代理执行，传入 runId、输入数据和可选的 AbortSignal；（6）子代理在自身存储中持久化 runId→requestId→streamId 映射，启动对话轮次，将每个流式块同时写入可恢复流存储和 RPC 可读流；（7）父代理循环读取 RPC 流中的 NDJSON 帧，逐帧以 chunk 事件广播给客户端；（8）子代理对话轮次完成后，父代理读取最终助理消息文本作为 summary，广播 finished 事件，更新注册表为 completed。若过程中抛出异常，则广播 error 事件并更新注册表为 error。

runAgentTool 按 runId 实现幂等：若调用方传入已有运行记录的 runId，终止运行直接返回已有结果；非终止运行在 V1 中重放已存储块后返回 interrupted 状态，避免重复触发 LLM 推理。此特性使 runAgentTool 可安全用于重试路径、定时告警回调和重连恢复，而不会意外产生重复的模型调用成本。

agentTool 将 runAgentTool 封装为 AI SDK 工具条目：它接收 LLM 传来的 toolCallId 和 abortSignal，将 parentToolCallId 设为 toolCallId，调用 runAgentTool 并返回结果给父 LLM。当父 LLM 的对话轮次被中止时，abortSignal 沿调用链传播至子代理，实现全链路取消。

agentTool 要求调用方提供 inputSchema 用于 LLM 工具选择和输入校验；outputSchema 可选，若提供则框架校验子代理显式返回的结构化输出，若不提供则以子代理的文本摘要作为工具返回结果。模型侧描述（description）和用户界面标签（displayName、icon）分离，前者进入模型提示词，后者通过注册表和 started 事件传递至前端。

### 恢复与重放机制

本方案的恢复机制将执行与观察分离：agent tool 的运行是持久化工作，实时流仅是观察该工作的一种方式。runId 作为跨父注册表、子代理名称、子代理映射表和重放/取消/清理接口的稳定连接键。

当客户端刷新页面或网络短暂断开后重连，父代理在 onConnect 阶段执行以下恢复流程：（1）查询注册表中所有运行记录，按启动时间排序；（2）对每条记录，合成带 replay=true 标记的 started 事件；（3）通过子代理的 getAgentToolChunks(runId) 接口获取持久化的流式块，从子代理自身的可恢复流存储中读取；（4）逐块以 chunk 事件重放，保持与实时广播相同的序列号体系；（5）根据运行记录的终端状态合成对应的 finished/error 事件（若为 interrupted 状态则合成 error 事件说明中断原因）。重放事件携带 replay: true 标记，客户端据此区分重放块和实时块，批量应用重放块后继续接收实时流。

当父代理因崩溃或被动驱逐而重启时，在启动阶段对所有 starting 和 running 状态的记录执行核对：（1）若无对应子代理或子代理运行记录，则子代理从未启动或已被删除，标记为 interrupted；（2）若子代理报告 completed，重放已存储块，读取最终输出，标记父记录为 completed；（3）若子代理报告 error 或 aborted，重放已存储块并标记对应终端状态；（4）若子代理报告 running 且不支持实时重连跟踪（V1 限制），重放已存储块后标记为 interrupted。关键设计原则：观察者消失不应自动取消子代理执行；只有显式的中止信号才触发取消。

子代理自身的对话恢复（如 Think 的 chatRecovery）同样适用：子代理存储自身的 fiber 行和快照，父代理拥有物理 alarm 并通过根侧索引将恢复回调路由回子代理。这意味着即使父代理观察者消失，子代理的对话轮次仍然可恢复并持久化其完整流块，供后续重放使用。

### 取消传播与并发控制

取消操作沿 AbortSignal 从父代理逐层传播至子代理的推理循环，实现全链路精确中止：（1）父代理的对话轮次/工具调用被取消；（2）runAgentTool 接收到 abortSignal 的中止通知；（3）父代理取消与子代理之间的 RPC 可读流；（4）运行时桥接层触发子代理侧流的 cancel 回调；（5）子代理中止其 per-turn AbortController；（6）该 AbortController 的信号已通过 saveMessages({ signal }) 传入对话引擎，推理循环同步终止。信号在线程化时若已被中止，推理工作在启动前即被跳过，消除了信号创建与 cancel 回调之间的竞态窗口。

关键区分：取消观察者流不等同于取消运行。浏览器断开、父代理重启或重放连接失败仅应分离观察者，不应自动终止子代理执行。只有父代理当前活跃操作发出的显式中止信号才触发取消执行。这一设计确保子代理的持久化工作不会因网络波动而被意外丢弃。

显式取消操作具有幂等性：若子代理已到达 completed 或 error 终止状态，延迟取消不得将其改写为 aborted。与此一致，在清除保留历史时若存在 starting 或 running 状态的运行，系统先显式取消该运行再删除注册表记录和子代理，避免遗留无观察者的孤立 LLM 工作。

并发控制方面，框架在父代理级别提供 maxConcurrentAgentTools 选项限制同时运行的 agent tool 数量，超出限制时分派操作以 error 事件快速失败而非排队等待。每个子代理实例在同一时刻仅允许一个框架驱动的对话轮次：子代理内部维护同步声明标记，在 runTurnAndStream 入口检查，防止对同一实例的并发调用损坏转发器状态。

### 钻入访问与安全控制

子代理通过已有的子代理路由原语保持外部可寻址，客户端可通过嵌套 URL（/agents/{parent-class}/{parent-name}/sub/{child-class}/{child-name}）直接连接到子代理进行钻入查看。这使得开发者可以打开完整的对话界面查看子代理的完整历史记录，而非仅看到主视图中转发的流式摘要。

框架在父代理侧通过 onBeforeSubAgent 中间件钩子实现严格的注册表门控：外部 HTTP/WebSocket 请求到达时，父代理查询运行注册表验证 (className, runId) 是否存在匹配记录。若记录存在，表明该子代理是经合法的 _runHelperTurn 流程创建的（注册表记录在广播 started 事件之前即已插入），放行请求；若记录不存在，返回 404 拒绝。内部 subAgent() 调用绕过此钩子，因此父代理自身派生子代理的操作不会被门控阻塞。

runId 本身不作为访问凭证。钻入 URL 始终通过父代理的既有身份体系到达（useAgent({ agent: parent, name: userId, sub: ... })），认证和租户隔离由父代理继承。框架不鼓励将 runId 作为持有者令牌分发。在子代理正在执行框架驱动的 agent tool 对话轮次期间，框架持有对该子代理实例的排他声明：对同一 runId 的并发 runAgentTool 调用返回已有检查结果（幂等启动），而非启动第二个对话轮次。钻入用户在此期间发送对话消息应被延迟或拒绝，而非与进行中的轮次静默交错。

### 保留与清理策略

子代理及其运行记录在完成后默认保留。自动删除不设为默认行为，因为完成时刻恰好是运行后检查最有价值的时刻：刷新重放、钻入查看、失败运行调试和审计追踪都依赖于保留子代理和注册表记录。系统提供显式的清理接口 clearAgentToolRuns()，支持按时间范围（olderThan）和状态集合（status）过滤删除。

clearAgentToolRuns 在删除父代理侧注册表记录的同时，通过 deleteSubAgent 一并删除对应的子代理及其存储。仅删除父记录而不删除子代理将留下无法通过重放或钻入访问的孤立子代理副本，因此清理操作默认同时删除两侧。清理处于 starting 或 running 状态的运行记录时，系统先显式取消该运行再删除记录和子代理，确保不遗留无观察者的孤立推理工作。

应用代码负责制定保留策略：是否在清除聊天历史时连带清除 agent tool 运行、基于时间或数量的垃圾回收阈值、针对已终止状态的清理规则等。框架提供可靠的清理原语而非隐藏默认保留窗口，以便应用根据账户、工作区或聊天历史生命周期灵活决策。
