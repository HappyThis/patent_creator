## 技术方案

本技术方案提出一种将智能工作台应用中的任务数据持续同步至 Git 托管代码仓库的方法，使外部开发工具和 AI agent 能够在无需直接访问应用数据库的情况下，通过标准 Git 操作读取和理解当前任务队列及任务状态。方案的核心构思在于：以应用内关系数据库作为任务的权威主存储和主要操作入口，在外部 Git 仓库中维护一个文件化的任务镜像；通过事件驱动的异步同步通道、结构化文件表示、多层语义映射和故障隔离机制，实现任务数据在主存储与 Git-native 协作镜像之间的持续同步，且外部同步失败绝不阻断应用内的任务增删改操作。

方案通过以下关键机制实现上述目的：（1）以 YAML 前置元数据加 Markdown 正文的结构化文档作为任务在 Git 仓库中的表示单元，使任务信息同时具备人类可读性和机器可解析性；（2）以任务状态为维度的目录分区（inbox/、assigned/、in-progress/、review/、done/），通过文件在目录间的移动操作自然反映任务生命周期的状态变迁；（3）基于应用内事件总线的变更检测与去抖动机制，保障同步实时性的同时避免高频操作引发冗余 Git 提交；（4）发射后不管的异步同步模式与基于内容哈希的冲突检测策略，确保外部同步故障不会传播到应用主流程，同时在并发写入场景下提供可审计的冲突处理路径。

### 整体架构

本方案提供一种将智能工作台应用中的任务数据持续同步至 Git 托管代码仓库的技术方法，使外部开发工具和 AI agent 能够在无需直接访问应用数据库的情况下，通过标准 Git 操作理解当前任务队列和任务状态。方案在应用主存储（如 SQLite 关系数据库）与 Git-native 协作镜像之间建立一条单向或双向的同步通道，其中应用数据库及其内建任务看板始终作为任务的主要工作入口和权威数据源，外部 Git 仓库仅作为可选同步目标。

### 核心组成

同步引擎由四个核心组件构成：（1）任务表示层（Task Representation Layer），负责定义任务在 Git 仓库中的文件格式与目录结构，将应用数据库中的任务记录转换为可被开发者和 agent 工作流直接读取的结构化文档；（2）变更检测器（Change Detector），通过监听应用数据库的写入事件（如任务创建、更新、删除），识别需要向外部仓库同步的变更集合；（3）Git 操作适配器（Git Operation Adapter），封装对目标 Git 仓库的克隆、拉取、文件写入、提交和推送操作，将任务文件变更以 Git commit 的形式写入目标仓库；（4）语义映射器（Semantic Mapper），在应用任务状态语义与 Git-native 文件表示之间建立可逆的双向映射关系，确保外部工具理解的任务状态与应用内部状态不产生语义偏差。

### 任务表示层——文件格式与目录结构

任务表示层将每条应用内任务映射为 Git 仓库中的一个结构化文档文件，文件内容包含任务的全部可同步字段，并以人类可读和机器可解析的双重格式组织。具体而言，每个任务文件采用带有 YAML 前置元数据（frontmatter）的 Markdown 格式，前置元数据承载任务的结构化属性（如任务标识、状态、优先级、指派对象、截止时间、预估工时、标签列表），正文区域承载任务描述和备注。文件在仓库中的路径遵循 schema：{project_slug}/{status_dir}/{task_id}.md，其中 status_dir 为状态语义对应的目录名（如 inbox/、assigned/、in-progress/、review/、done/）。当任务状态变更时，该任务的文件从旧状态目录移动至新状态目录，同时更新前置元数据中的 status 字段，该移动操作体现为一次 Git commit 中的文件重命名。

### 变更检测器——事件驱动的去抖动变更感知

变更检测器通过订阅应用数据库的事务后事件（post-commit hooks）来感知任务变更。当任务在应用数据库中被创建、更新或删除时，事件总线（event bus）发布对应的事件类型（如 task.created、task.updated、task.deleted），变更检测器接收这些事件并提取变更的任务标识和变更类型。为避免高频率细粒度更新（如同一个任务的连续多次编辑）引发过多 Git 操作，变更检测器内置去抖动（debounce）窗口：对同一任务标识在预设时间窗口（可配置，默认 5 秒）内的多次变更事件进行合并，仅以窗口结束时的最终状态触发一次同步。对于删除事件，变更检测器生成对应的文件删除操作，而非保留冗余数据。

### Git 操作适配器——以 commit 为同步单元的仓库写入

Git 操作适配器封装对目标 Git 仓库的完整生命周期操作。首次同步时，适配器对目标仓库执行浅克隆（shallow clone）或使用已有本地克隆；后续同步中，适配器先执行 git pull --rebase 拉取远端变更以最小化冲突可能，再将任务文件写入工作树，生成包含变更说明的 git commit，最后执行 git push 将提交推送到远端。提交信息（commit message）遵循结构化约定，包含变更类型（create/update/delete/move）、涉及的任务标识和关键字段变化摘要，使外部工具和开发者能通过 git log 快速理解任务队列的演化历史。适配器在每次 Git 操作前后记录操作日志，为故障诊断提供可追溯的操作轨迹。

### 语义映射器——状态与优先级的多层可逆映射

语义映射器在应用内部任务状态语义和 Git-native 文件表示之间建立可逆的双向映射。应用侧的状态模型包含 inbox（待处理）、assigned（已指派）、in_progress（进行中）、review（评审中）、quality_review（质量审核）和 done（已完成）六种状态，优先级模型包含 low、medium、high、critical 四级。映射器将这些状态信息同时编码在两个层面：一是文件前置元数据中的结构化字段（status、priority 以原始值保留，确保精确映射）；二是目录结构中的状态分类（文件所在状态目录反映当前状态）。当外部 agent 或工具读取任务文件时，可直接解析前置元数据获得与应用内部一致的状态语义，无需猜测或近似转换。对于可选的逆向同步（外部仓库变更反向流入应用），映射器实施严格的标签（label）约定：通过预定义的前缀命名空间（如 mc:inbox、mc:assigned）标记由应用管理的状态标签，仅识别属于该命名空间的标签进行反向映射，避免与外部仓库中其他项目的标签产生冲突。

### 故障隔离与冲突处理

方案将外部同步操作与应用内部任务操作完全解耦，采用发射后不管（fire-and-forget）模式执行每一次对外同步：当应用内任务创建、更新或删除操作完成后，对应的数据库事务已提交，同步请求被异步投递到同步队列，任务 API 立即向调用方返回成功响应，不等待外部同步结果。同步操作在其自身的执行上下文中独立运行，同步失败（如网络不可达、仓库权限不足、Git push 被拒绝）仅记录错误日志并触发告警，绝不回滚或阻断已完成的应用内任务操作。

为处理同步过程中的并发写入冲突（如外部贡献者直接向仓库推送了任务文件修改，同时应用侧也在推送同一任务的更新），方案采用基于文件内容哈希的冲突检测策略：在每次同步写入前，适配器检查目标文件在远端的最新内容哈希是否与上次成功同步时记录的基准哈希一致；若不一致，则检测到冲突。此时方案不执行强制覆盖，而是将冲突任务标记为 divergent 状态，在应用内生成一条冲突通知供操作者手动裁决；同时保留应用侧的最新版本在仓库的一个独立分支或临时冲突文件中，避免数据丢失。这种策略保证了无论冲突是否发生，应用数据库始终持有完整且自洽的任务状态。

### 同步运行流程

一次完整的任务同步流程如下：（1）用户在应用前端创建一条新任务，应用 API 将任务记录写入 SQLite 数据库并提交事务；（2）数据库事务提交后，事件总线广播 task.created 事件；（3）变更检测器捕获该事件，经过去抖动窗口后，提取任务完整数据；（4）任务表示层将任务数据序列化为 YAML frontmatter + Markdown body 的结构化文档；（5）语义映射器根据任务状态确定目标文件路径，如 proj-general/inbox/task-0042.md；（6）Git 操作适配器对目标仓库执行 pull --rebase、将新文件写入工作树、生成 commit、执行 push；（7）同步完成后更新任务的同步时间戳字段，记录同步日志。当任务状态从 inbox 变更为 in_progress 时，该流程触发文件移动操作：旧路径 proj-general/inbox/task-0042.md 被删除，新路径 proj-general/in-progress/task-0042.md 被创建，同时 frontmatter 中的 status 字段更新为 in_progress，体现为一次包含文件重命名的 Git commit。

### 可选实施方式

任务文件的前置元数据采用标准 YAML 格式，包含以下可同步字段：id（任务唯一标识）、title（任务标题）、status（当前状态，取值为应用状态枚举之一）、priority（优先级）、assigned_to（指派对象，可为空）、project（所属项目标识）、due_date（截止时间，ISO 8601 格式或空）、estimated_hours（预估工时）、tags（标签数组）、sync_version（单调递增的同步版本号，用于冲突检测）。正文区域为任务描述的自由文本。文件编码统一为 UTF-8，行尾使用 LF。

对于逆向同步（外部仓库变更流入应用），方案提供可选支持。当外部 agent 或开发者通过 Pull Request 或直接推送修改了仓库中的任务文件（如更新 frontmatter 中的 status 字段），定期的拉取同步（pull-based sync）会检测这些变更：比对文件的 sync_version 或修改时间戳，仅当外部版本比应用记录的同步版本更新时，才将变更映射回应用数据库。逆向同步仅在项目配置中显式启用时生效，且始终以不覆盖应用内未同步完成的本地变更为原则。
