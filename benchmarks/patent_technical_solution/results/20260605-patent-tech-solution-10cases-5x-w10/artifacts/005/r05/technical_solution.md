## 技术方案

本技术方案提出一种将智能工作台（应用主存储）中的任务数据以 Git-native 文件格式持续同步到代码仓库的方法，使外部开发和 agent 工具可在不直接访问应用数据库的情况下，通过读取仓库中的任务描述文件来理解当前任务队列和任务状态。方案围绕三个核心目标设计：（1）应用数据库和任务看板保持为主工作入口；（2）外部仓库作为可选的协作镜像；（3）同步失败不阻断任务创建、更新或删除，且任务状态语义在系统间保持一致、可追溯。

### 整体架构与分层设计

本方案在应用主存储 SQLite 数据库（任务表、项目表）与目标 Git 仓库之间建立一条非侵入式的同步通道。整体架构分为四层：（1）任务文件序列化层，负责将数据库中的任务记录转换为 Git 仓库内可读、可解析的文本文件；（2）双向同步引擎层，负责在任务生命周期事件驱动下执行文件写入、提交、推送（出站），以及按周期拉取远端变更并回写数据库（入站）；（3）语义映射层，负责应用任务状态字段与 Git 文件中状态标记之间的双向转换，确保语义一致性；（4）故障隔离层，确保同步操作的异步化、非阻塞性和失败可观测性。应用数据库始终是任务数据的权威来源；外部仓库仅作为只读或近实时协作的衍生副本。

### 任务文件的 Git-native 表示格式

每条应用任务对应目标 Git 仓库中指定目录（如 .mc-tasks/ 或项目配置路径）下的一个结构化文本文件。文件命名采用「任务唯一标识 + 标题摘要」的组合方式，例如 TASK-042-refactor-auth-module.md，以确保可读性和人机可解析性。

文件内容采用 Markdown 与 YAML 前置元数据（frontmatter）结合的格式。前置元数据块承载结构化字段：任务唯一标识（来源于应用数据库主键或项目票据编号）、标题、状态（使用带命名空间前缀的标准化取值如 mc:inbox / mc:assigned / mc:in-progress / mc:review / mc:quality-review / mc:done）、优先级（priority:critical / high / medium / low）、指派对象、创建时间戳、更新时间戳、截止日期、标签列表、以及同步元数据（sync_timestamp 和 source_id）。正文区承载任务描述、验收标准、备注等自由文本。

该格式设计具有以下技术特性：（1）完全基于纯文本，天然适合 Git 版本控制、diff 审查和合并冲突解决；（2）前置元数据部分可由标准 YAML 解析器或正则表达式快速提取，无需依赖应用数据库驱动；（3）正文区保持人类可读性，支持任意 Markdown 语法，agent 和开发者可直接在仓库中阅读、编辑或通过脚本批量处理；（4）新增字段时通过扩展前置元数据即可实现向前兼容。

### 双向同步引擎

同步引擎由出站路径（应用→仓库）和入站路径（仓库→应用）两个独立通道组成，两者共享同一套语义映射规则和冲突检测机制，但运行时机和触发方式不同。

出站同步由应用侧任务生命周期事件驱动。当任务被创建、更新（涉及标题、描述、状态、优先级、指派对象等关键字段）或删除时，系统在完成数据库写入事务后，以异步方式触发出站流程。出站流程依次执行：序列化任务当前状态为前置元数据格式的任务文件，在目标仓库本地克隆副本上执行文件写入或删除操作，生成变更描述提交并推送到远程仓库，推送成功后将当前时间戳写入任务记录的 git_synced_at 字段。整个出站流程在独立异步上下文中执行，不阻塞 HTTP 响应返回；推送失败仅记录错误日志而不引发任务操作的事务回滚。

入站同步由定时轮询器驱动，默认按可配置间隔（如 60 秒）对每个启用了同步的项目执行。入站流程依次执行：从远端仓库拉取最新变更，扫描任务文件目录中自上次同步以来新增或修改的文件，解析每个文件的前置元数据提取任务状态字段，通过文件中的 source_id 或文件名中的任务标识符匹配应用数据库中的对应记录。对新建文件，在数据库中创建对应任务；对已存在任务的文件，比较文件的 sync_timestamp 与数据库中的 git_synced_at 字段，仅当远端文件更新且时间戳偏差超出防乒乓窗口（如 10 秒）时才执行数据回写。回写内容覆盖标题、描述、状态、优先级等字段。

### 语义映射层

为确保任务状态在不同系统之间的语义一致且可追溯，系统定义了一套带有命名空间前缀的标准化标签映射规则。应用内部的六种任务状态（inbox、assigned、in_progress、review、quality_review、done）分别映射为 mc:inbox、mc:assigned、mc:in-progress、mc:review、mc:quality-review、mc:done 六个标签值；四种优先级（low、medium、high、critical）映射为 priority:low、priority:medium、priority:high、priority:critical。这种命名空间前缀设计使映射标签不会与仓库中已有的非同步标签产生冲突。

双向转换规则如下：出站时，从数据库状态字段查询对应的 mc: 或 priority: 前缀标签写入文件；入站时，从文件前置元数据中提取这些标签，反向映射为数据库状态字段。当文件中缺少可识别的状态标签时（例如文件由外部工具手动创建而未填写标签），系统将新任务默认设为 inbox 状态。已关闭的 Issue 等价于 done 状态。当文件同时存在多个 mc: 状态标签时（例如合并冲突导致），系统以最后出现的标签为准并向管理员产生告警。

标签映射表在首次启用同步时由系统自动初始化到目标仓库（例如通过仓库的标签定义或 README 说明文件），确保下游工具和开发者能一致理解标签含义。

### 冲突检测与防乒乓机制

双向同步面临的核心挑战是"乒乓效应"——出站同步将应用变更推送到仓库后，入站轮询可能将同一变更再次拉回应用，造成无意义的重复更新和潜在的振荡。本方案通过时间戳窗口比对机制解决此问题。

具体机制：每次出站推送成功后，系统将当前 Unix 时间戳（精确到秒）写入任务记录在应用数据库中的 git_synced_at 字段，同时该时间戳也作为 sync_timestamp 写入任务文件的前置元数据。入站轮询发现一个已存在于数据库中的任务文件时，首先比较文件的 sync_timestamp 与数据库记录的 git_synced_at。若二者之差的绝对值小于预设防乒乓窗口（例如 10 秒），则判定该变更为出站同步的反射，跳过本次入站更新。若远端文件的更新时间戳（从 Git 提交记录中提取）晚于数据库中的 updated_at 字段，且 sync_timestamp 不匹配，则判定为外部变更，执行入站数据回写。

当同一任务在应用侧和仓库侧同时被修改时（真冲突），系统以应用数据库为权威来源：入站同步在检测到冲突后不覆盖数据库记录，而是将冲突信息记录到同步日志表中，并向管理员或任务相关方生成通知，提示需要人工裁决。同步日志记录包含冲突双方的字段快照，便于追溯和审计。

### 故障隔离与可选集成模型

同步操作在架构上被设计为与任务 CRUD 主路径完全解耦的异步附属流程，遵循以下故障隔离原则：（1）出站同步以 fire-and-forget 方式触发，在独立异步执行上下文中运行，同步失败（网络不可达、认证失效、仓库权限不足、合并冲突等）不中断、不回滚已成功的数据库事务；（2）入站同步以独立轮询进程运行，单个项目的同步失败不影响其他项目的同步调度，也不影响应用的任务看板渲染和 API 响应；（3）所有同步失败均以结构化日志记录（包含任务标识、仓库地址、失败原因和时间戳），并可通过同步状态查询 API 暴露给管理员界面。

同步配置以项目为粒度，通过应用内的项目设置页面控制，新增 git_sync_enabled（布尔型开关）和 git_remote_url（目标仓库地址）配置字段。默认情况下同步功能处于关闭状态，管理员需主动为目标仓库配置访问凭证（如 Git SSH 密钥或 Personal Access Token）并手动启用后方可生效。未启用同步的项目中的任务完全不触发任何同步流程，确保零性能开销。

同步状态追踪通过独立的同步历史表实现，每条记录包含项目标识、同步方向（出站/入站）、变更计数、成功/失败状态和错误信息。该表支持按项目聚合查询最近同步时间和累计变更量，为管理员提供可观测的同步健康视图。同时，系统在运行时通过内部事件总线在每次同步完成后广播 github.synced 事件，前端可通过 SSE 连接接收该事件并更新同步状态指示器。

### 任务生命周期与 Git 工作流集成

本方案使任务数据参与 Git 工作流后，支持以下典型协作场景：（1）开发者通过 git clone 获取仓库，直接在本地 .mc-tasks/ 目录中查阅所有任务的当前状态和描述，无需登录应用界面或调用 API；（2）CI/CD 流水线可解析任务文件中的状态标签，在部署前自动检查是否存在未完成的阻塞任务；（3）AI coding agent（如 Claude Code）可在工作目录中直接读取任务描述文件，理解当前任务上下文并自动开始执行，执行完成后通过修改文件中的状态标签为 mc:review 来反馈进展，该变更将在下一轮入站同步中自动回写到应用数据库；（4）代码审查者在 Pull Request 中可同时看到代码变更和关联任务的状态转换，形成完整的变更上下文。

任务文件在仓库中的生命周期与应用中的任务状态保持松散耦合的对应关系：任务在 inbox 状态时可选择性不导出（以减少仓库噪音）；任务进入 assigned 状态时自动创建对应文件；任务标记为 done 时文件保留在仓库中（作为历史记录），但状态标签更新为 mc:done。任务在应用中被删除时，可配置为在仓库中保留文件并标记为 mc:done 和追加删除注释（软删除），或直接移除文件（硬删除），由项目配置决定。
