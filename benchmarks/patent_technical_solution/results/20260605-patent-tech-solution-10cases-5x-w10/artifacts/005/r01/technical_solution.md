## 技术方案

本技术方案提出一种面向智能工作台的任务数据双存储同步方法，在保持应用内置数据库（如 SQLite）作为任务主存储的前提下，自动将任务队列及其状态变化以 Git-native 形式同步至外部代码仓库（如 GitHub 仓库的 Issue 系统），使外部开发者工具和 agent 工作流无需直接访问应用数据库即可理解当前任务队列与任务状态。方案的核心由三部分组成：基于语义标签的双向状态映射机制、基于时间戳窗口的防乒乓冲突仲裁机制、以及基于异步触发与后台轮询的双通道同步引擎。整个同步链路以应用数据库为权威数据源，外部仓库为可选同步镜像，同步失败不阻断任务在主系统中的创建、更新或删除操作。

### 1. 双存储架构与数据权威模型

系统采用“主存储-镜像存储”双层架构。应用内置数据库（主存储）中的任务表（tasks）为所有任务操作的唯一权威数据源。每个任务记录除包含标题、描述、状态、优先级、指派对象、所属项目等业务字段外，还扩展了面向外部同步的专用列：github_issue_number（外部镜像标识）、github_repo（目标仓库）、github_synced_at（最近同步时间戳）、github_branch（关联分支）、github_pr_number（关联合并请求编号）等。这些同步列由同步引擎维护，业务层不直接依赖它们做出任务流转决策。

外部仓库（镜像存储）中的 Issue 作为任务在 Git-native 环境中的等价表示，仅作为可选同步目标存在。每个项目（project）可通过 github_repo 字段指定目标仓库，并通过 github_sync_enabled 标志位控制是否启用同步。未配置或关闭同步的项目，其任务完全存储于应用数据库内，不受外部同步逻辑影响。当 sync_enabled 启用时，系统为该项目的每个新建任务在目标仓库中创建对应的 Issue，并通过 github_issue_number 列建立一一映射关系。

### 2. 基于命名空间的语义标签映射

为确保外部仓库中的任务镜像能够以机器可读的方式准确表达任务语义，方案定义了一套从应用任务状态到 Git-native 载体标签的双向映射规则。应用任务的状态枚举为 inbox（待处理）、assigned（已指派）、in_progress（进行中）、review（审阅中）、quality_review（质量审阅中）、done（已完成），优先级枚举为 low（低）、medium（中）、high（高）、critical（紧急）。映射规则以带命名空间前缀的标签作为语义载体：状态映射为 mc:inbox、mc:assigned、mc:in-progress、mc:review、mc:quality-review、mc:done；优先级映射为 priority:low、priority:medium、priority:high、priority:critical。所有 MC 标签均带有固定前缀（mc: 或 priority:），与目标仓库中已有的其他自定义标签互不冲突。

映射函数支持双向转换。出向映射（statusToLabel / priorityToLabel）将任务状态和优先级转换为对应的标签名称；入向映射（labelToStatus / labelToPriority）从 Issue 的标签列表中提取 MC 标签并还原为应用内部的状态和优先级值。对于出向推送，除 MC 标签外，目标 Issue 在 GitHub 上的 open/closed 状态也参与语义表达：当任务状态为 done 时，Issue 状态置为 closed；其余状态置为 open。对于入向拉取，从 GitHub 拉取的 Issue 若状态为 closed，则任务状态映射为 done；若为 open，则从 MC 标签中解析具体状态，若无匹配标签则默认置为 inbox。

### 3. 双通道同步引擎

同步引擎由两条独立的通道构成：出向推送通道和入向拉取通道。两条通道运行于不同的触发时机和调度策略之下，通过数据库中的 github_synced_at 时间戳字段协同工作，实现防乒乓冲突。

出向推送采用“触发式异步投递”机制。当任务在主系统中被创建或更新时，业务处理器在完成数据库写入、活动日志记录、通知分发和 SSE 事件广播之后，以 fire-and-forget 方式调用出向推送函数。该函数不阻塞业务请求的 HTTP 响应，其执行结果不影响任务在主系统中的创建或更新操作是否已生效。推送函数首先检查任务或项目是否配置了目标仓库；若未配置则直接返回。对于尚未关联 GitHub Issue 的任务，推送函数调用外部仓库 API 创建新 Issue，并将返回的 Issue 编号写回任务记录，同时记录同步时间戳。对于已关联 Issue 的任务，推送函数先拉取目标 Issue 的当前标签列表，保留其中非 MC 前缀的第三方标签，替换 MC 状态标签和优先级标签为最新值，然后调用更新 API 同步标题、描述和状态。推送完成后更新 github_synced_at 时间戳。若推送过程中 API 调用失败，系统仅记录错误日志，不重试、不回滚任务操作、不向用户暴露错误。

入向拉取采用“后台定时轮询”机制。后台调度器以可配置的间隔（默认 60 秒）遍历所有启用了同步且配置了目标仓库的项目。对每个项目，拉取函数查询自上次同步以来在目标仓库中被更新过的 Issue 列表。对于每个 Issue，系统通过 github_repo 和 github_issue_number 列查找对应的任务记录。若未找到对应任务，则视为外部新建 Issue，系统在应用数据库中创建对应的任务记录，并通过语义标签映射设置初始状态和优先级；若找到对应任务，则进入防乒乓仲裁：比较任务的 github_synced_at 时间戳与 Issue 的 updated_at 时间戳——若两者相差在 10 秒以内，判定为系统自身刚刚推送的更新，跳过以避免循环回写；若 Issue 更新时间晚于任务的本地更新时间，则以 Issue 的状态和标签覆盖本地任务记录。每次同步完成后，系统记录同步日志，包括同步方向、Issue 数量、变更数量和错误信息。

### 4. 防乒乓冲突与语义一致性保障

双通道独立运行必然面临同一任务被两端同时或先后修改的风险。方案通过三层机制实现防乒乓冲突与语义一致性保障。

第一层为时间戳窗口过滤。每次出向推送完成后，系统在任务记录上写入 github_synced_at 时间戳（Unix 秒级精度）。入向拉取时，若发现某个 Issue 的 updated_at 与对应任务的 github_synced_at 时间差小于预设阈值（如 10 秒），则判定该 Issue 更新是由系统自身的出向推送引起的，直接跳过不处理。这一机制利用出向推送与入向拉取之间的时间相关性，有效避免了最常见的乒乓场景。

第二层为更新时间比较。对于超出时间戳窗口的候选更新，系统进一步比较 Issue 的 updated_at 与任务在应用数据库中的 updated_at。仅当 Issue 侧更新时间严格晚于任务侧更新时间时，才将 Issue 的状态和内容同步到任务记录。这意味着在双方同时修改的场景下，时间戳较新的一侧生效；若任务侧更新时间更新，则入向同步直接跳过，等待下一轮出向推送将该更新同步至 Issue。

第三层为标签保护。出向推送更新 Issue 时，系统只替换带有 mc: 和 priority: 前缀的 MC 专属标签，保留 Issue 上已有的所有其他标签（如 bug、enhancement、good first issue 等来自仓库维护者或自动化工具的第三方标签）。入向拉取创建或更新任务时，将非 MC 标签作为任务的 tags 字段存储，同时从 MC 标签中解析状态和优先级。这一设计确保语义映射的封闭性：MC 标签的命名空间不与仓库现有标签体系冲突，且双向同步不会丢失任何一侧的标签信息。

### 5. 故障隔离与降级策略

方案将外部同步链路设计为完全可降级的附属通道。故障隔离体现在三个层面。

请求级隔离：出向推送以 fire-and-forget 方式调用。任务创建或更新的 HTTP 请求处理流程在数据库写入和事件广播完成后即返回 2xx 响应，推送函数的 Promise 链独立于请求生命周期执行。推送失败仅触发日志记录，不产生异常传播、不回滚数据库事务、不影响客户端响应。

项目级隔离：同步配置以项目为粒度。每个项目独立指定目标仓库和同步开关。一个项目的同步失败（如仓库被删除或令牌过期）不影响其他项目的同步，也不影响无同步配置的项目的正常运行。后台轮询调度器在遍历项目列表时对每个项目单独执行 try-catch，单个项目的异常不中断整个轮询周期。

启动级隔离：后台同步轮询器的启动和运行独立于主应用服务。轮询器在数据库迁移和调度器初始化阶段以惰性方式启动，其运行状态不影响 HTTP 服务端口监听。若 GitHub API 密钥未配置或失效，轮询器在首次尝试后仅记录错误并继续按间隔空转，不影响应用的任何业务功能。通过环境变量 GITHUB_SYNC_INTERVAL_MS 可调整轮询间隔，设为较大值可降低失败重试频率。

### 6. 同步初始化与全生命周期流程

同步的完整生命周期从项目配置开始。管理员在项目中设置目标仓库并启用同步后，系统首先执行标签初始化：调用目标仓库的标签管理 API，幂等地创建全部 MC 状态标签和优先级标签（共 10 个：6 个 mc: 状态标签 + 4 个 priority: 优先级标签）。初始化完成后设置 github_labels_initialized 标志位，后续不再重复创建。

任务同步的典型流程如下：(1) 用户在智能工作台的任务看板中创建任务；(2) 系统在应用数据库中写入任务记录、分配项目工单编号、记录活动日志、广播 SSE 事件；(3) 系统异步调用出向推送，在目标仓库中创建对应 Issue，Issue 的描述中包含任务详情，标签中包含当前状态和优先级映射标签；(4) 外部开发者或 agent 通过 GitHub Issue 页面或 API 查看和评论该任务，或通过自动化工作流修改 Issue 的标签来改变任务状态；(5) 后台轮询器在下一个周期检测到 Issue 更新，执行防乒乓仲裁后，将状态变化同步回应用数据库；(6) 应用数据库更新后触发 SSE 事件，任务看板实时反映最新状态。

当任务在主系统中被删除时，对应的 GitHub Issue 不自动关闭，而是在任务记录删除时保留 Issue 作为外部讨论的持久记录。这一设计尊重 Git-native 协作环境中 Issue 作为讨论线程的固有属性，避免因任务删除而导致外部上下文丢失。如果需要关闭关联 Issue，可由管理员通过 GitHub Sync 面板手动操作。

### 7. 扩展性与平台适配

上述方案以 GitHub Issues 作为 Git-native 同步目标，但核心架构不限于 GitHub。同步列（如 github_issue_number、github_repo 等）在语义上是“外部镜像标识”和“目标载体定位符”的抽象，可映射到其他 Git 托管平台（如 GitLab Issues、Gitee Issues）或基于 Git 仓库文件的任务表示（如在仓库中以 Markdown 文件形式维护任务队列文件 tasks.md，或按任务拆分为独立文件）。出向推送和入向拉取函数可替换为对应平台的 API 适配器，语义标签映射规则保持不变，防乒乓机制和故障隔离策略无需修改。

在任务状态之外，方案的数据模型还预留了分支关联列（github_branch）和合并请求关联列（github_pr_number、github_pr_state），支持将任务与代码仓库中的开发分支和合并请求建立关联。这使得外部工具可以通过任务唯一标识追溯到对应的开发分支和代码变更，进一步打通任务管理到代码协作的完整链路。
