## 技术方案

本方案提出一种面向智能工作台的任务到 Git 原生协作载体的持续同步方法。该方法以应用内数据库和任务看板为主要工作入口，将任务数据通过结构化文件映射到外部 Git 仓库中，使外部开发工具和 agent 工作流无需直接访问应用数据库即可理解当前任务队列及任务状态。同步过程以事件驱动方式自动触发，在保证应用主存储操作不受外部同步失败影响的前提下，维护应用域语义与 Git 原生表示之间的可理解对应关系。

### 核心技术构思

本方案的核心构思是：在智能工作台的应用数据库之外，构建一个以结构化文件为载体的任务镜像层。该镜像层以 Git 仓库作为存储和版本管理载体，将应用数据库中的每条任务映射为仓库中一个独立的、具有结构化元数据和可读正文的任务文件。任务文件的格式采用带 YAML 前置元数据（frontmatter）的 Markdown 文件，使任务既对机器可解析、也对人类可读，同时兼容现有 Git 工具链和 agent 工作流的自然消费方式。

核心思路是在任务生命周期事件（创建、更新、删除）发生时，由事件驱动的同步引擎将变更转换为对 Git 仓库的文件级操作（新增文件、修改文件、删除文件），并生成描述性提交记录，最终推送到远程仓库。应用的主存储（SQLite 数据库）和任务看板始终保持为唯一写入权威源，外部仓库仅作为只读镜像，不反向写入应用数据库。同步引擎与主业务流程完全解耦，以异步、非阻塞方式运行，确保外部同步失败不阻断应用的正常任务操作。

### 整体架构与运行机制

系统在逻辑上分为三个核心组件：事件监听层、同步调度层和 Git 操作层。事件监听层通过订阅应用内部事件总线获取任务变更事件，将任务标识和变更类型封装为同步请求投递到调度队列。同步调度层维护一个内存中的变更缓冲区，以短时间窗口（例如 2-5 秒）对同一任务的多次变更进行合并去重，避免高频操作产生的冗余 Git 提交。窗口到期或缓冲区达到阈值时，调度层将合并后的净变更批量提交至 Git 操作层。Git 操作层负责将结构化任务数据序列化为目标文件格式、执行 Git 文件操作（add/rm）、生成提交记录、以及对远程仓库执行推送。

此外，系统维护一个独立的重试持久队列（例如基于本地 SQLite 或文件系统）。当 Git 推送因网络故障、认证失败或远程仓库不可达等原因失败时，失败的同步任务及其快照数据被序列化写入重试队列，按指数退避策略（如 30 秒、2 分钟、8 分钟）进行重试。超过最大重试次数后，该同步任务标记为死信状态，并通过应用内通知或日志记录提示管理员介入，但绝不回溯影响任务主存储的状态。

### 任务对象的 Git 原生文件表示

每条任务在 Git 仓库中映射为一个以任务标识符命名的 Markdown 文件。文件采用 YAML frontmatter 承载结构化元数据，正文区域承载任务描述、验收标准和评论等自由文本。文件的存放路径遵循项目分组的目录结构，例如 tasks/{project-slug}/{task-id}.md。

YAML frontmatter 中编码以下关键字段：任务唯一标识（id）、标题（title）、状态（status）、优先级（priority）、指派对象（assigned_to）、创建者（created_by）、创建时间（created_at）、更新时间（updated_at）、截止日期（due_date）、预计工时（estimated_hours）、实际工时（actual_hours）、标签（tags）、所属项目（project）、以及同步元数据（sync_version、sync_timestamp）。同步版本号（sync_version）是一个单调递增的整数，每次同步触发时自增，用于外部消费方判断任务文件的更新新鲜度。正文区域以 Markdown 格式承载任务描述、验收标准、技术备注等自由文本。归属于同一任务的评论、审核记录等附属信息，可选择以嵌套 YAML 列表或独立附属文件的方式表达。

### 语义映射与状态可解释性

应用数据库中的任务状态语义（如 inbox、assigned、in_progress、review、quality_review、done）需要在不依赖应用上下文的情况下被外部工具正确理解。本方案采用双重标记策略：每个任务文件同时在 frontmatter 的 status 字段中保留原始状态值，并在文件内容中通过标准化的 Markdown 状态徽章或状态表格进行可视化呈现。此外，仓库根目录维护一个名为 TASK_STATES.md 的语义说明文件，以表格形式声明各状态值的定义、含义及状态间允许的转换路径。该文件在同步初始化时自动生成，并在应用状态定义发生变更时自动更新。

对于优先级（low/medium/high/critical）和任务状态值中与应用域逻辑强绑定的概念（例如 quality_review 表示需要通过 Aegis 质量审核），同步引擎在映射时保持原值不变，不进行语义转换或简化。这样外部工具读取时获得的是未经扭曲的原始语义标签，避免因语义映射的二次解释产生偏差。同时，仓库中生成一份 INDEX.md 索引文件，以表格形式汇总全部任务的最新状态、优先级、指派对象和更新时间，使外部工具可以通过读取单个文件快速获取任务队列全景视图，无需逐文件解析。

### 故障隔离与容错机制

同步引擎的设计遵循'主路径不依赖辅助路径'的原则。所有任务创建、更新和删除操作都在应用数据库事务中独立完成并立即向客户端返回结果，同步触发仅在数据库事务成功提交之后、以异步非阻塞方式执行。具体来说，应用的事件总线在数据库变更确认后发射任务变更事件，同步引擎以事件消费者身份接收事件，投递到内存变更缓冲区。这一过程不与用户的 HTTP 请求生命周期耦合，不使用分布式事务或两阶段提交协议。

在 Git 操作层，系统设置了以下隔离边界：（1）网络超时——Git 推送操作设置最大执行时间（如 30 秒），超时视为失败并进入重试队列；（2）认证失效——当远程仓库令牌过期或权限被撤销时，同步引擎捕获认证错误并暂停该仓库的同步，避免反复失败占用资源，同时发出应用内告警；（3）仓库冲突——当检测到远程分支存在非本同步引擎产生的提交（即外部人员直接向镜像仓库推送）时，同步引擎不执行强制推送，而是记录冲突日志并暂停同步，等待管理员决策后恢复；（4）磁盘空间——同步引擎监控本地 Git 工作目录的磁盘占用，超出阈值时暂停同步并告警。以上所有故障场景均不产生回滚应用数据库副作用。

### 变更检测与增量同步

同步引擎通过订阅应用事件总线获取任务变更通知。事件总线在每次数据库变更确认后发射事件，事件类型包括 task.created、task.updated、task.deleted 和 task.status_changed。同步引擎监听这些事件，提取变更任务的主键标识和事件类型，投递到内存中的变更缓冲区。

缓冲区采用任务标识符为键进行去重合并：若在时间窗口内同一任务先收到 updated 事件、再收到 deleted 事件，则净操作为删除；若连续收到多次 updated 事件，则仅保留最后一次。窗口到期后，引擎从应用数据库读取受影响任务的当前完整快照（对于 deleted 事件则仅记录任务标识），批量转换为文件操作：（1）对于创建或更新，生成或覆写对应的 Markdown 文件，同步版本号递增；（2）对于删除，移除对应文件并在 INDEX.md 中消除该条目。所有变更以单次 Git 提交（commit）聚合发布，提交信息自动生成为任务变更摘要（如 'sync: 3 tasks updated, 1 task deleted'），随后推送到远程仓库。

### 仓库初始化与骨架文件

每个启用了 Git 同步的项目关联一个目标 Git 仓库。同步引擎在首次启用时执行仓库初始化：克隆远程仓库到本地工作目录，或初始化一个本地裸仓库后设置远程追踪分支。初始化时生成仓库骨架文件，包括：（1）TASK_STATES.md——任务状态语义说明文件，定义各状态的含义及合法转换路径；（2）INDEX.md——任务索引文件，初始为空表结构，包含列：任务 ID、标题、状态、优先级、指派对象、更新时间、文件路径；（3）.mc-sync-meta.json——同步元数据文件，记录同步引擎版本、同步配置、上次同步时间戳和同步版本计数器。骨架文件随仓库初始化一次性写入，后续仅 INDEX.md 在每次同步时更新，TASK_STATES.md 在状态定义变更时更新。

### 外部消费模式

任务镜像仓库部署后，外部工具和 agent 工作流可以通过标准 Git 操作获取任务信息，无需了解应用数据库结构或应用 API：（1）开发者执行 git pull 即可获取最新任务列表，通过阅读 INDEX.md 快速了解任务队列全景，通过查看单个任务 Markdown 文件了解任务详情；（2）CI/CD 流水线可以通过读取特定状态的任务文件触发自动化流程，例如检测到状态为 review 的任务自动拉起代码审查流水线；（3）AI agent 可以通过标准文件读取方式消费任务描述和上下文信息，规划执行步骤并在任务完成后通过更新文件状态反馈进展；（4）外部监控和看板工具可以监听仓库的 Webhook 推送事件，在任务变更时自动刷新展示。

### 同步范围与触发策略

同步引擎支持以项目为粒度的同步范围配置。每个项目可独立设置是否启用 Git 同步、目标仓库地址、远程分支名称和同步触发策略。同步触发策略支持三种模式：（1）实时模式——每次任务变更即时触发同步（经变更缓冲区合并后）；（2）定时模式——按可配置的时间间隔（如每 60 秒）批量同步；（3）混合模式——实时处理高优先级变更，定时批量处理低优先级变更。此外，支持按任务状态过滤同步范围，例如仅将状态为 in_progress 和 review 的任务同步到外部仓库，而将 inbox 中的未分类任务保留在应用内部。
