## 技术方案

本技术方案提出一种可扩展的本地 agent runtime 接入系统，用于在智能工作台（agent orchestration dashboard）中统一接入和管理多种本地 agent runtime 及其关联的会话记录。该方案在已有运行时管理体系基础上，引入运行时适配器（runtime adapter）框架、渐进式能力发现机制和会话格式抽象层，使系统能够识别新 runtime 已有的本地会话记录并在同一工作台中展示和管理，同时避免将未确认能力展示为可用，也不破坏已有 runtime 的管理流程。

### 运行时适配器框架

本方案的核心是一个运行时适配器框架。系统定义统一的运行时适配器描述符（Runtime Adapter Descriptor），每一类本地 agent runtime 对应一个适配器实例。适配器描述符至少包含以下字段：运行时标识（runtime ID）、运行时名称、状态目录的搜索路径列表、支持的操作能力列表及其确认状态、会话格式解析器选择器、以及认证方式检测规则。

适配器描述符中的每一项能力均携带确认状态标记，状态至少包括：已确认（confirmed）、试探性发现（probing）和未支持（unsupported）。系统仅在能力状态为已确认时，才在用户界面中展示对应的操作入口（如继续会话按钮）。对于状态目录路径和会话文件格式，适配器支持多候选配置：系统按优先级依次探测每组候选路径和格式，以第一个成功匹配的配置作为当前运行实例的有效配置。

适配器通过一个注册表（adapter registry）管理。注册表以运行时标识为键，保存所有已安装运行时的适配器实例。系统在启动时和按需刷新时，遍历注册表中的适配器，分别执行检测流程，各适配器的检测结果相互隔离——单个适配器检测失败不影响其他运行时的正常使用。

### 渐进式能力发现机制

针对新 runtime 的状态目录、会话文件格式和继续会话能力尚未完全确定的情况，本方案采用多阶段渐进式能力发现机制，按依赖层级分阶段探测，每一阶段独立执行且不依赖后续阶段的结果。

第一阶段——存在性检测：系统根据适配器描述符中配置的状态目录候选列表和可执行文件候选路径，依次探测 runtime 是否已安装在本地。探测手段包括：检查状态目录下的配置文件是否存在、尝试调用 runtime 可执行文件的版本查询命令。若任一候选命中，则将 runtime 标记为已安装，并记录实际生效的状态目录路径和可执行文件路径。

第二阶段——会话格式探测：在确认 runtime 已安装后，系统进入状态目录，按适配器描述符中配置的会话文件格式候选列表依次尝试解析。候选格式可包括：JSON 映射文件、JSONL 流式记录文件、SQLite 数据库等。每种格式候选对应一个格式检测器和解析器。格式检测器通过检查文件扩展名、文件头部魔数或结构特征（如 JSON 顶层键集合、SQLite 文件头、JSONL 首行结构）判断实际格式。若检测成功，则将对应的解析器绑定到当前 runtime 实例；若所有候选均不匹配，则标记会话功能为不可用但不影响已安装状态的判定。

第三阶段——能力确认：在会话格式确定后，系统进一步探测高级能力是否可用。以继续会话能力为例，系统不直接假设该能力存在，而是通过特定的探测动作确认——例如，向 runtime 可执行文件发送一个带特定标志的探测子命令，或检查会话数据结构中是否存在表示可恢复状态的字段。只有当探测返回了明确肯定的结果时，系统才将该能力标记为已确认。若探测无响应或返回否定结果，该能力保持未确认状态，对应操作入口不在界面中展示。对于不同版本可能存在的差异，每个能力探测项可配置多个候选探测方法，以适配不同版本的运行时行为。

### 会话格式抽象层

为将不同 runtime 的异构会话数据统一映射到工作台的统一会话视图，本方案在会话扫描层引入会话格式抽象层。该抽象层定义统一的会话统计数据结构，各 runtime 适配器的会话解析器负责将各自原生格式的会话记录转换为该统一结构。

统一会话数据结构至少包含：会话标识符、所属 agent 名称、会话类型标签、模型标识、输入 token 数量、输出 token 数量、总 token 数量、首条消息时间戳、末条消息时间戳、活跃状态标志、消息计数、工具调用次数、来源渠道、以及来源 runtime 标识（source 字段）。其中来源 runtime 标识用于在统一会话列表中按来源区分和去重——以 "source:session_id" 为复合键进行去重排序，当同一会话标识在不同来源中出现时，保留最近活跃的一条记录。

会话解析器在执行解析时，对无法识别的字段或格式异常采用防御性策略：跳过无法解析的行或记录项，记录告警日志，但不中断整个扫描流程。对于文件尺寸超限的会话记录文件，解析器设置可配置的文件大小上限（如 50MB），超出上限的文件被跳过并在日志中记录。这种防御性解析确保单个损坏或格式异常的会话文件不会导致整个 runtime 的会话列表不可用。

对于新 runtime 的会话格式尚不确定的场景，适配器描述符支持配置版本感知的格式选择策略。解析器在读取会话文件时，先检查文件中的格式版本标记（如 JSON 顶层 version 字段、SQLite 的 schema version 表、或 JSONL 首条记录的结构特征），再根据版本号选择对应的解析规则分支。当遇到未知版本号时，解析器回退到通用兼容模式——仅提取各版本中确定共有的字段组合，忽略版本特异的扩展字段。这保证了在同一种 runtime 的不同版本共存时，系统仍能最大程度地展示可用的会话信息。

### 多层隔离与安全降级

为确保新 runtime 的接入不影响已有 runtime 的管理流程，本方案在设计层面实施了多层隔离。

第一层——检测隔离：每个 runtime 适配器的检测流程在独立的执行上下文中运行。检测函数的返回值仅影响该 runtime 在注册表中的状态记录，不修改全局状态。当某个适配器的检测抛出异常时，异常被该适配器内部捕获并记录日志，注册表中的其他适配器状态保持不变。

第二层——会话扫描隔离：会话扫描以 runtime 为粒度独立执行。每个 runtime 的会话扫描器仅读取该 runtime 自身状态目录下的文件，不访问其他 runtime 的目录或文件。扫描失败时返回空会话列表，不影响其他 runtime 的会话数据在统一视图中的呈现。

第三层——能力展示隔离：系统的工作台界面根据能力确认状态矩阵决定展示哪些操作入口。未确认的能力不出现在界面中，因此新 runtime 的未确认能力不会产生可点击但实际不可用的操作入口，避免用户误操作。

此外，系统在合并多 runtime 会话列表时，以 "source:id" 为复合键进行去重。即使新 runtime 产生的会话标识与已有 runtime 的会话标识偶然冲突，去重逻辑确保每个会话在统一视图中仅出现一次，不会因命名冲突导致重复展示或数据错乱。

### 能力可用性矩阵

系统在运行时维护一张能力可用性矩阵，以运行时标识为行、以能力类型为列，矩阵中的每个单元格记录该运行时对该能力的确认状态。能力类型包括但不限于：会话列表读取、会话详情查看、继续会话、会话删除、模型参数调整（如 thinking level、verbose level）、会话标签设置等。

能力矩阵的更新与渐进式能力发现流程联动：当某一阶段的能力探测完成并得到确认结果时，矩阵中对应单元格的状态同步更新。状态变更触发工作台界面的增量刷新——仅更新与该 runtime 和能力相关的界面元素，不触发全局重新渲染。

对于"继续会话"这类高级能力，能力矩阵支持设置能力前置条件。例如，继续会话能力的展示需同时满足：runtime 已安装、会话格式已确认、且继续会话探测返回肯定结果。任一前置条件不满足时，该能力在矩阵中标记为不可用，对应的操作按钮不在界面渲染。这种条件化的能力展示避免了因版本差异导致的功能误报。

### 统一会话聚合与展示

工作台通过统一的会话聚合接口获取所有 runtime 的会话列表。该接口的实现流程如下：

首先，系统从注册表中获取所有已确认安装的 runtime 适配器列表。对于每个适配器，调用其会话扫描函数。各扫描函数的执行彼此独立，系统可通过并行或串行方式执行（推荐并行以降低总延迟），单个扫描函数的超时或失败不影响其他扫描函数的执行和结果。

其次，每个扫描函数返回的会话记录列表统一映射为标准会话数据结构。映射过程中，每个会话记录附加来源 runtime 标识（source 字段）和会话类型标签（kind 字段），用于后续去重和分类展示。

然后，系统将所有 runtime 的会话记录合并到一个列表中，以 "source:session_id" 为复合键进行去重：当存在重复键时，保留 lastActivity 时间戳最大的一条记录。去重后的列表按 lastActivity 降序排列，取前 N 条（N 为可配置的展示上限，如 100 条）。

最后，合并后的统一会话列表返回给工作台前端。前端根据每条记录的 kind 和 source 字段渲染对应的运行时类型图标和来源标签，使用户能够区分不同 runtime 产生的会话记录。对于已确认支持继续会话等高级能力的记录，前端渲染对应的操作入口；对于能力未确认的记录，仅展示基本信息而不渲染不可用的操作按钮。

### 新运行时接入流程

基于上述框架，接入一种新的本地 agent runtime 的完整流程如下。第一步：创建适配器描述符，注册 runtime 的基本元信息（名称、描述、认证要求），配置状态目录候选路径列表、可执行文件候选路径列表、会话文件格式候选列表和能力探测规则列表。第二步：适配器注册到系统注册表，无需修改已有适配器的代码或配置。第三步：系统启动时或按需触发时，按渐进式发现流程依次完成存在性检测、会话格式探测和能力确认，各阶段结果写入运行时状态记录和能力矩阵。第四步：会话扫描器根据已确认的格式解析器读取新 runtime 的本地会话记录，映射为统一数据结构后汇入聚合会话列表。第五步：工作台界面根据能力矩阵决定展示哪些操作入口，仅已确认的能力对应的操作按钮可交互。

### 可适配的 Agent 注册与同步

除会话记录外，工作台还需要识别新 runtime 管理的 agent 实体，以便在工作台中以 agent 为单位进行展示和管理。本方案在运行时适配器框架中扩展了 agent 配置同步能力。

每个适配器描述符可选配置 agent 发现规则，包括：agent 配置文件的搜索路径、配置文件格式（JSON、YAML、TOML 等）、agent 实体字段映射关系（将原生 agent 配置中的字段映射到工作台的 agent 统一模型，包括名称、角色、模型、工具权限等）。当 runtime 通过存在性检测且 agent 发现规则已配置时，系统触发 agent 同步流程：读取原生 agent 配置文件，解析 agent 列表，将每个 agent 映射为统一模型后写入工作台数据库（新建或更新已有记录）。

agent 同步流程与上述会话扫描流程共享相同的隔离原则：单个 runtime 的 agent 同步失败不影响其他 runtime。同步结果（新建数量、更新数量、未变化数量）记录审计日志并通过事件总线广播，以便工作台界面实时更新 agent 列表。

对于配置文件结构在 runtime 不同版本之间可能变化的问题，agent 发现规则支持版本分支：适配器描述符可为不同版本配置不同的字段映射规则和文件路径。版本检测在存在性检测阶段完成——当系统通过版本查询命令获取到 runtime 版本号后，从适配器描述符的版本规则表中选取匹配的配置项。若版本未在规则表中显式列出，系统使用默认兼容规则，仅提取通用字段，忽略版本特有的扩展字段。
