## 技术方案

本方案提出一种可扩展的本地 agent runtime 接入架构，使智能工作台能够在无需修改核心代码的前提下，识别并管理新的本地 agent runtime 及其已有的本地会话记录。方案围绕三个核心技术手段展开：运行时可加载的 runtime 描述符机制、基于能力契约的渐进式功能暴露、以及版本感知的多格式会话适配。

### 1. Runtime 描述符机制

系统引入一种结构化的 runtime 描述符（Runtime Descriptor），作为新 runtime 接入的统一声明入口。每个描述符为一个独立的配置文件（例如 JSON 或 YAML），放置于系统预定义的 runtime 注册目录（如 ~/.mission-control/runtimes/）中。系统启动时或按调度周期扫描该目录，动态加载新的 runtime 定义，无需修改核心代码中的类型联合、检测器映射或安装器映射。

描述符至少包含以下字段：（1）runtime 标识（id、name、description），用于在系统中唯一标识该 runtime；（2）检测规则（detection），声明一个或多个可执行命令及其预期输出模式，系统通过依次尝试这些命令来判断 runtime 是否已安装、当前版本号及运行状态；（3）状态目录模式（state_dir），声明该 runtime 在本地文件系统中的状态数据存储位置，支持环境变量展开和通配路径，以兼容不同版本或不同安装方式下的目录差异；（4）会话格式描述（session_format），声明状态目录下会话文件的存放模式、文件扩展名、解析器类型或内联解析规则；（5）能力声明（capabilities），以键值对形式列出该 runtime 支持的能力项及其确认状态。

通过描述符机制，系统将 runtime 的“是什么”与“如何检测/如何解析”解耦。核心代码仅维护一个抽象的 runtime 注册表（Registry），其内部结构为从 runtime id 到描述符对象的映射。注册表在初始化时先加载内置 runtime（openclaw、hermes、claude、codex）的默认描述符，再扫描外部注册目录，将外部描述符合并入注册表；若外部描述符的 id 与内置 runtime 冲突，采用“内置优先”或“显式覆盖”策略（由系统配置决定），确保已有 runtime 的管理流程不被意外替换或破坏。

### 2. 能力契约与渐进式暴露

为解决新 runtime 能力不确定、不同版本能力存在差异的问题，方案引入能力契约（Capability Contract）机制。每个 runtime 描述符中的 capabilities 字段不仅声明能力名称，还携带一个确认状态枚举值：confirmed（已确认可用）、unconfirmed（尚未确认）、unavailable（确认不可用）。系统在工作台界面中仅展示状态为 confirmed 的能力入口，对于 unconfirmed 的能力，系统仅在内部维护其声明但不渲染对应的用户操作入口；对于 unavailable 的能力，系统完全不暴露。

能力项采用预定义的标准化能力词汇表，包括但不限于：session_list（会话列表浏览）、session_detail（会话详情查看）、session_continue（继续会话）、memory_read（记忆读取）、memory_write（记忆写入）、task_dispatch（任务分发）、heartbeat（心跳检测）、agent_sync（agent 自动同步）。新 runtime 在描述符中按实际确认情况逐项声明。当 runtime 版本升级导致能力变化时，只需更新描述符文件中的 capabilities 映射并触发注册表刷新，无需修改系统代码。

进一步地，描述符支持可选的版本映射表（version_capability_map），以版本号或版本号范围为键，以对应的能力确认状态为值。当系统通过检测规则获取到 runtime 的实际安装版本后，先在版本映射表中查找该版本对应的能力覆盖，再与默认 capabilities 合并，版本映射表中的条目优先级更高。这使得同一 runtime 的不同版本可以自动呈现不同的功能集合，例如：v1.x 版本仅确认 session_list，而 v2.x 版本同时确认 session_list 和 session_continue。

### 3. 版本感知的多格式会话适配

针对新 runtime 的会话文件格式不确定、不同版本可能采用不同格式的问题，方案在会话扫描层引入版本感知的多格式适配器链。runtime 描述符的 session_format 字段可声明一个格式适配器列表，每个适配器包含：（1）文件匹配规则（glob 模式或文件名正则），用于在状态目录中定位候选会话文件；（2）格式探针（probe），一段轻量逻辑（例如读取文件头部若干字节并匹配特征模式），用于判断文件是否属于该格式；（3）解析器引用，指向一个标准的会话解析函数或内联解析规则定义。

系统在扫描会话时，首先根据文件匹配规则在状态目录中收集候选文件，然后对每个候选文件依次尝试格式适配器列表中的探针，以首个匹配成功的适配器作为该文件的解析方案。若所有探针均不匹配，系统将该文件标记为“未识别格式”，在内部记录其存在但不尝试解析详细内容，从而避免因格式不兼容导致的解析异常扩散到整个会话列表。

解析器将各 runtime 的原生会话格式映射到系统统一的会话数据结构（Unified Session Model），该结构包含标准字段：会话标识、会话标题、模型标识、用户消息数、助手消息数、工具调用次数、输入 token 数、输出 token 数、首条消息时间、末条消息时间、活跃状态、来源 runtime 标识。对于新 runtime 会话中无法映射到标准字段的专有信息，解析器将其序列化到扩展字段（metadata）中保留，不丢失原始数据。

### 4. 隔离式扫描与容错调度

为确保新 runtime 的接入过程不影响已有 runtime 的管理流程，方案在 runtime 注册表的调度层为每个 runtime 分配独立的扫描上下文。每个扫描上下文包含：独立的错误边界（try-catch 包裹整个扫描周期）、独立的超时控制（每个 runtime 的会话扫描设有最大执行时间，超时后自动中断并记录）、独立的文件访问范围（仅限该 runtime 描述符声明的状态目录及其子目录）、以及独立的缓存键空间（各 runtime 的会话缓存相互隔离，一个 runtime 的缓存失效不会触发其他 runtime 的重新扫描）。

调度器在每次扫描周期中遍历注册表中的所有 runtime，对每个 runtime 依次执行：检测刷新（重新评估安装状态和版本）→ 若已安装且 session_list 能力为 confirmed，则执行会话扫描 → 将会话数据写入该 runtime 对应的数据库存储分区（例如按 runtime id 分表或通过 runtime_id 列区分）。任一步骤失败仅影响当前 runtime，调度器记录错误日志后继续处理下一个 runtime。内置 runtime 和外部 runtime 在调度器中处于同等地位，共享相同的调度周期和错误隔离机制。

### 5. 工作台统一展示与会话聚合

在工作台展示层面，系统通过统一的会话查询接口聚合所有 runtime 的会话数据。查询接口接受可选的 runtime_id 过滤参数，前端在渲染会话列表时按 runtime 分组或混合展示（取决于用户选择的视图模式）。每个会话条目附带来源 runtime 的标识和图标，使用户能区分不同 runtime 产生的会话记录。能力契约在此环节再次发挥作用：前端在渲染每个 runtime 的会话条目时，根据该 runtime 当前生效的 capabilities 决定是否展示“继续会话”“查看详情”“查看记忆”等操作按钮——仅当对应能力为 confirmed 时才渲染。

### 6. 整体运行时流程

综合上述机制，整体技术方案的运行时流程如下：（1）系统启动，初始化 runtime 注册表，加载内置 runtime 默认描述符；（2）扫描外部注册目录，解析并合并外部 runtime 描述符；（3）对注册表中每个 runtime 执行检测刷新，获取安装状态和版本；（4）根据检测到的版本，合并版本映射表中的能力覆盖，生成该 runtime 的最终能力确认表；（5）调度器按固定周期（例如每 60 秒）对已安装且 session_list 能力为 confirmed 的 runtime 执行会话扫描；（6）每次扫描时，根据描述符中的 session_format 配置选择适配器链，解析会话文件并写入统一会话存储；（7）工作台通过统一查询接口获取跨 runtime 的会话列表，并根据各 runtime 的能力契约渲染对应的操作入口。在整个流程中，任何新 runtime 的接入仅需提供一个描述符文件，不涉及系统代码变更。

### 7. 可选实施细节

描述符中的检测规则支持多种检测策略组合：二元组检测（检查特定文件或目录是否存在）、命令检测（执行命令并匹配 stdout/stderr 模式）、端口检测（尝试 TCP 连接以判断服务是否运行）。系统按描述符中声明的顺序依次尝试，以首个成功的策略结果为准。对于新 runtime 状态目录尚未确定的情形，描述符的 state_dir 可声明多个候选路径，系统按优先级依次探测，取首个存在的路径作为有效状态目录；若所有候选路径均不存在，系统标记该 runtime 为“状态目录未就绪”，暂不触发会话扫描。
