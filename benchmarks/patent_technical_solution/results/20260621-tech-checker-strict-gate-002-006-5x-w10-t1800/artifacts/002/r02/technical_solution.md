## 技术方案

### 外部任务接收与幂等登记

本方案在现有基于 Durable Object 的 Agent 实例上设置外部任务接收入口，使 webhook、RPC 或其他程序化调用不直接等待模型推理结果，而是先完成任务登记。接收入口对外部请求进行鉴权、签名校验、会话或业务实体定位以及请求规范化处理，并将请求路由到对应的 Agent 实例；该实例以 SQLite 持久存储作为任务登记簿，记录外部提交标识、内部任务标识、目标会话、规范化后的用户输入、请求摘要、接收时间、当前状态和恢复阶段等信息。

任务接收采用“先持久化、再确认”的顺序。外部调用方提交任务时需携带幂等键；在未携带幂等键的实现中，可由系统根据调用方身份、目标 Agent、目标会话、用户输入正文和关键参数生成规范化摘要作为提交键。同一调用方、同一目标范围内的相同提交键通过唯一约束或等效的冲突处理映射到同一任务记录。若首次提交成功，系统写入状态为 accepted 或 queued 的任务行并返回任务标识、当前状态和查询地址；若重复提交命中既有任务行，系统返回同一任务标识及其当前状态，而不追加第二条用户消息，也不启动第二次模型推理。

为避免“已确认但未入库”或“重复入库后重复执行”的不一致，任务登记和幂等判定位于同一 Agent 实例的持久事务边界内。快速确认只表示任务已被可靠接收并可被后续调度，不表示模型处理已经完成。确认响应中不携带最终助手回复，只携带外部提交键、内部任务标识、可查询状态以及可选的取消令牌或访问控制信息。

### 异步执行与对话轮次绑定

完成登记后，任务执行由 Agent 内部异步驱动。系统可采用内置持久队列保存待执行任务，或采用 fire-and-forget 的 durable fiber 启动后台处理；两种方式均使外部 HTTP/RPC 响应与模型推理生命周期解耦。执行器从任务登记簿读取状态仍为 accepted 或 queued 的记录，将其更新为 running，并生成或绑定一次内部 chat requestId、streamId 或 runId，用于关联对话轮次、流式输出、取消控制和恢复检查。

对话轮次的触发复用现有 AIChatAgent 或 Think 的程序化对话能力。在一种实现中，执行器调用 saveMessages 的函数式形式，在轮次真正进入队列时基于最新持久化会话追加一条由外部任务构造的用户消息并触发 onChatMessage；在 Think 子 Agent 场景中，也可通过 chat RPC 发起一次完整轮次。函数式追加用于避免后台任务在排队期间基于过期 transcript 写入消息，从而使多个外部任务、定时任务和用户侧 WebSocket 消息仍按 Agent 的 turn queue 串行进入同一会话。

执行期间，任务记录与对话消息、可恢复流元数据和执行快照保持关联。用户消息的写入应使用稳定消息标识和幂等插入规则；助手消息或流式片段可按 requestId 或 streamId 持续更新。轮次完成时，Agent 的响应完成回调将任务状态更新为 completed，并保存助手消息标识、完成时间、输出摘要或结果读取位置；若程序化轮次返回 skipped、aborted 或 error，则分别将任务标记为 skipped、aborted 或 failed，并保留已经持久化的部分输出及错误原因。

### 状态查询、取消与清理

任务状态采用持久化状态机管理。非终态可包括 accepted、queued、running、recovering 和 cancelling；终态可包括 completed、failed、aborted、skipped、interrupted 和 cleaned。状态查询接口只读取持久状态、关联的 requestId/runId、进度阶段、最近更新时间、错误原因、已完成消息或可恢复流位置，不依赖调用方原始连接是否仍然存在。由此，外部系统在超时、断线或重试后可以通过同一任务标识获得权威状态，而不需要重复提交任务。

取消操作与查询或观察连接断开相互区分。普通客户端断开、外部调用方读取超时或状态查询中止，仅停止该调用方的观察，不自动取消服务器端轮次；只有外部系统提交显式取消请求且通过权限校验后，系统才将任务置为 cancelling，并通过任务记录中的 requestId 或内部取消句柄触发 AbortController。该 AbortSignal 被传入 saveMessages、continueLastTurn、chat RPC 或底层模型调用，使推理循环尽早停止并保留已经生成和持久化的部分片段。

状态更新遵循终态保护规则：completed、failed、aborted、skipped、interrupted 和 cleaned 一旦写入，晚到的重复提交、取消请求或恢复扫描只能返回该终态或执行只读清理，不得把终态回退为 running 或 queued。清理操作用于删除、归档或压缩已终结任务的索引和流片段；对于仍处于 running 或 recovering 的任务，清理前应先执行取消、标记 interrupted 或确认已有可恢复接续策略，避免残留孤儿模型调用或不可解释的任务缺口。

### 休眠、重启与中断恢复

针对 Agent 运行环境可能休眠、重启或在流式推理中被驱逐的情况，本方案将“执行阶段”与“网络连接”解耦，并将阶段信息写入持久层。对于尚未开始执行的任务，持久队列或任务登记簿中的 queued 状态足以在 Agent 下次激活时重新调度；对于已经进入模型轮次的任务，执行器在关键阶段调用 stash 或等效 checkpoint，记录已写入用户消息、已创建 requestId、已启动 stream、已获得外部 provider 响应标识、已生成部分输出、已请求取消等恢复数据。

当 Durable Object 重新激活时，恢复检查读取持久队列行、任务状态行、chat fiber 行、可恢复流元数据和 checkpoint 快照，按阶段判定处理动作：若任务尚未追加用户消息，则重新入队执行；若用户消息已写入但未完成推理，则依据 requestId/streamId 恢复部分助手消息并决定继续最后一次轮次、重新发起补偿轮次或标记 interrupted；若已经存在 completed、aborted 或 failed 等终态，则仅补齐索引或清理临时句柄。该判定避免把同一外部任务恢复为多个用户输入，也避免在终态之后再次发起模型推理。

恢复策略不假定被驱逐前的外部 LLM、HTTP 或 RPC 连接可以原样续接。对于支持从服务端响应标识取回结果的 provider，可根据 checkpoint 中的 provider 标识拉取已完成输出；对于支持 assistant prefill 或继续最后轮次的场景，可在持久化部分输出后调用 continueLastTurn；对于工具状态过期、调用方已不存在、恢复次数超过阈值或中断时间过长的场景，系统应停止自动续跑并将任务标记为 interrupted 或 failed。这样既保留可见的部分结果，又避免恢复循环长期占用 turn queue。

### 可选实施方式与实施边界

本方案可以按接入方式形成多种实现。webhook 实现中，入口根据外部事件来源、仓库、客户、设备或其他业务实体选择专用 Agent 实例，使每个来源拥有独立状态和任务登记簿；RPC 实现中，可通过 callable 方法或 Think 子 Agent 的 chat 接口提交任务，并在调用侧仅接收任务标识或流式观察通道；批处理实现中，可将外部任务先写入持久队列，由 Agent 按 FIFO 或配置的优先级逐一转换为程序化对话轮次。

在消息并发方面，可以沿用 Agent 对 chat turn 的串行化机制，使 WebSocket 用户消息、程序化 saveMessages、自动 continuation 和外部任务注入按同一队列协调；当业务要求外部任务必须等待人工工具审批或前一轮工具交互完成时，可在追加消息前调用稳定性检测并设置超时，超时后保持任务为 queued 或 retryable，而不是在不稳定 transcript 上强行插入。对于允许多个独立会话并行的场景，可通过不同 Agent 名称、不同会话标识或分片键隔离状态。

需要确认的工程边界包括幂等键的有效期和作用域、任务结果保留周期、取消后是否允许继续查询部分输出、清理时是否保留审计记录、以及不同模型 provider 对中断恢复的支持程度。上述边界不影响核心机制成立：外部请求先被幂等持久登记，再由 Agent 内部异步转换为受状态机约束的对话轮次，并通过持久状态、取消信号和恢复 checkpoint 保证重复提交、连接中断和运行环境重启时的执行一致性。
