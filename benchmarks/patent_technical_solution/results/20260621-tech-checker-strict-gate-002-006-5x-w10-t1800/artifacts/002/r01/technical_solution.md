## 技术方案

### 总体架构与任务对象

本方案在既有基于持久化 Agent 的对话系统之外，增加面向外部系统的一次性对话任务接入层。外部系统可以通过 HTTP webhook、REST 接口、WebSocket RPC 或同一运行环境内的对象 RPC 提交任务；接入层不直接等待模型推理完成，而是将本次提交转换为持久化任务记录，快速返回任务标识和接收结果。任务记录与 Agent 的会话消息存储、状态存储、执行队列、取消控制器以及持久执行纤程相连接，使外部触发的对话任务能够复用已有 AIChatAgent 的消息持久化、串行 turn 执行、流式响应恢复和状态同步能力。

一次外部任务至少包括外部调用方标识、幂等键、目标 Agent 或会话标识、待写入的用户输入、提交参数、创建时间、状态、关联的对话 turn 请求标识、取消标记和清理时间等字段。接入层负责校验任务是否可被当前 Agent 接收；任务调度层负责把已接收任务在合适时机写入对话历史并启动模型 turn；执行管理层负责查询、取消、状态迁移和结果关联；恢复层负责在 Agent 休眠、重启或执行中断后根据持久化记录和检查点判断任务应继续、跳过、标记失败还是等待人工或外部系统重新触发。

### 外部提交的快速接收与幂等登记

外部请求到达时，接入层先生成或读取调用方提供的幂等键，并以调用方标识、目标会话标识和幂等键作为唯一约束查询持久化任务记录。若不存在对应记录，则在 Agent 的 SQLite 存储或等效持久状态中原子创建一条状态为“已接收”的任务记录，记录原始输入、归一化后的消息内容和任务参数，然后立即向外部调用方返回确认信息；确认信息可以包括任务标识、当前状态、可查询地址或 RPC 方法名以及可用于取消的凭证。该返回不依赖模型推理完成，因此可避免外部系统因长时间等待大模型响应而超时。

若查询到相同唯一约束下已有任务，接入层不再追加新的用户消息，也不再创建新的模型执行请求，而是根据已存在记录返回相同任务标识及其当前状态。对于网络中断、调用方重试、网关超时重放等场景，重复提交最多只会命中同一任务记录；只有幂等键或目标会话发生变化时，才被视为新的外部对话任务。通过把“接收任务”和“写入对话输入”分离，本方案将防重复边界前移到外部请求入口，避免同一外部事件在对话历史中形成多条用户输入，进而避免重复触发工具调用、模型推理或后续业务动作。

### 对话输入的延迟提交与串行执行

任务被登记后，由任务调度层在 Agent 内部异步启动对话 turn，而不是在外部请求处理线程内同步等待模型输出。调度时可以先调用等待稳定的机制，确认当前会话不存在正在流式输出、等待工具交互或排队续接的对话 turn；也可以根据业务策略选择排队执行。到达可执行条件后，调度层使用 AIChatAgent 的程序化消息写入能力把外部任务转换成合成用户消息，并以函数式消息更新方式基于最新会话历史追加输入，从而避免多个后台任务在排队期间各自使用陈旧消息快照。

对话 turn 的执行由串行队列控制。队列为每个 turn 分配请求标识并按 promise 链顺序执行，在前一 turn 未结束前不启动后一 turn；当发生清空会话、重置 turn 状态或其他代际失效事件时，队列递增 generation，使旧 generation 下尚未开始的任务在轮到执行时直接跳过。外部任务记录在写入消息前由“已接收”迁移为“排队中”，真正开始模型推理时迁移为“执行中”，并保存返回的 requestId。这样，外部查询到的任务状态能够与内部 turn 队列和模型执行阶段对应，而不会把已登记但尚未写入的任务误认为已经完成。

模型 turn 完成后，Agent 将 assistant 消息持久化到会话存储，并通过响应生命周期回调取得本次 requestId、结束状态、错误信息以及是否为续接执行等结果。执行管理层根据 requestId 反查外部任务，将任务更新为“已完成”“已取消”“已跳过”或“执行失败”，并记录生成的 assistant 消息标识、摘要或错误原因。对于外部任务触发的工具调用或自动续接，本方案保持与普通 WebSocket 对话相同的序列化和消息协调规则，使人工对话、webhook 任务和 RPC 任务共享同一条会话历史而不发生消息顺序错乱。

### 任务状态查询、取消与清理

本方案提供以任务标识或幂等键为索引的状态查询接口。外部调用方可查询任务是否处于已接收、排队中、执行中、等待外部交互、已完成、已取消、已跳过、执行失败或已清理等状态，并可获得关联 requestId、提交时间、开始时间、结束时间、错误原因、可重试标记和输出消息引用。状态查询直接读取持久化任务记录和必要的会话消息索引，不要求重新执行模型推理，因此可用于 webhook 回调后的轮询、RPC 调用方的补偿查询以及监控系统的运行观测。

取消接口根据任务所处阶段采取不同处理：对于尚未写入会话历史的“已接收”或“排队中”任务，直接把任务标记为“已取消”，后续调度器发现该状态后不再调用消息写入；对于已经启动的“执行中”任务，执行管理层通过 requestId 查找对应的取消控制器，或者把外部 AbortSignal 连接到内部取消控制器，使推理循环以与普通对话取消相同的方式中止，已流式产生并持久化的部分内容仍保留在会话历史中，任务最终记录为已取消。对于已经完成或已经失败的任务，取消请求不回滚既有消息，只返回当前终态。

清理机制用于删除或归档已经达到保留期限的任务元数据，同时保留必要的会话消息或审计索引。对于已完成、已取消、已跳过和执行失败的终态任务，可按保留时间、调用方、会话或任务数量上限进行批量清理；对于仍处于非终态但长时间未推进的任务，清理前先执行恢复判定，避免把可恢复任务误删。清理完成后，状态查询可返回“已清理”或仅返回最小化审计信息，以降低持久存储膨胀并防止历史幂等键无限增长。

### 基于持久检查点的恢复一致性

为了适配 Agent 休眠、重启和执行中断，本方案把外部任务执行包裹在持久执行单元中。执行单元启动前在持久存储中写入运行记录，并在关键阶段通过检查点保存任务标识、幂等键、当前阶段、关联 requestId、已写入的用户消息标识、已生成的响应片段、最后推进时间和可恢复参数。检查点以阶段化快照形式覆盖更新，保证在运行环境被驱逐或进程中断前已经完成的阶段可以被后续激活过程识别。

Agent 重新激活时，恢复层扫描未正常删除的运行记录和非终态外部任务记录，并结合检查点、会话消息存储和 turn 请求标识进行阶段判定。若任务仅完成接收登记而尚未写入用户消息，则可重新进入调度；若用户消息已经写入但模型 turn 尚未产生终态，则根据是否存在可恢复流、部分响应和恢复策略决定继续最后一轮对话、持久化部分响应后标记失败，或等待外部系统重新提交同一幂等键查询结果；若 assistant 消息已经持久化但任务状态尚未更新，则直接补写任务终态而不重新执行模型。该判定规则使恢复过程以持久事实为准，而不是以重启前内存中的回调是否执行完成为准。

恢复执行重新启动时不复用已经失效的内存闭包，而是根据持久化快照重新构造后续动作，并再次创建新的持久执行单元。对已提交给对话历史的用户输入，恢复层通过消息标识、外部任务标识或内容校验确认其是否已经存在，存在时只续接或补偿状态，不再追加第二条用户消息；对未提交的任务，则重新检查幂等记录、取消标记和会话稳定状态后再写入。由此，即使发生请求超时、重复提交、Agent 休眠和执行中断的组合情况，系统也能维持“同一外部任务至多写入一次用户输入、至多产生一个有效执行链路”的一致性边界。
