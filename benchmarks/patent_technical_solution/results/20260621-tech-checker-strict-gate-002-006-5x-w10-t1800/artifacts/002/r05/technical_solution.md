## 技术方案

本方案在已有支持对话式触发的 agent 系统基础上，增加面向外部系统的程序化任务提交机制。外部调用方可以通过 webhook、RPC 或其他服务端入口提交一次对话任务；系统在接收路径仅完成调用校验、任务登记和异步执行触发，随后立即返回“已接收”的确认，不在同步请求中等待模型推理、工具调用或流式输出完成。后续执行、状态查询、取消和清理均围绕同一持久化任务记录展开，从而对外提供幂等的一次逻辑任务语义。

### 外部任务接收与幂等登记

外部入口接收请求后，先确定目标 agent 或目标会话，并生成用于识别一次逻辑任务的去重键。去重键可以由外部调用方显式提供的幂等键形成，也可以由来源系统标识、业务事件标识、目标会话标识和规范化后的请求载荷摘要组合形成。系统同时计算载荷摘要并与去重键一并写入外部任务登记表，登记表以去重键或由其派生的任务标识设置唯一约束，用于区分“同一任务的重复提交”和“不同任务的相似内容”。

任务登记在 agent 的持久化存储事务中完成。若去重键不存在，系统创建任务记录并写入接收阶段状态、目标 agent、目标会话、载荷摘要、创建时间、可选回调信息以及后续执行所需的请求上下文，然后触发异步队列或调度机制；若去重键已经存在且载荷摘要一致，系统不再重复写入用户消息、不再启动新的对话轮次，而是返回既有任务标识及当前状态；若去重键相同但载荷摘要不一致，系统返回冲突或拒绝结果，避免将不同业务请求错误合并为同一任务。

接收路径返回的确认信息至少包括任务标识、接收状态和用于后续查询的访问位置或方法。该确认仅表示任务已经被可靠登记并进入异步处理流程，不表示模型已经完成推理。通过将“接收确认”与“执行完成”解耦，外部系统在网络超时、调用重试或 webhook 平台要求快速响应的场景下，仍可依赖同一任务标识获得一致的处理结果。

### 异步对话执行与消息物化

异步执行器从任务登记表或队列中取得待处理任务后，先检查任务是否仍处于可执行阶段以及是否存在取消意图，再将外部提交内容物化为对话中的用户消息。物化时使用与任务绑定的固定消息标识，并采用按消息标识幂等追加的方式写入持久化消息表；对于已经物化过的任务，执行器只复用既有消息标识和阶段状态，不再次追加同一用户输入。

在外部入口注入消息前，执行器等待目标会话达到稳定状态，避免与正在进行的流式输出、工具交互或未完成的对话轮次交叠修改同一消息序列。消息写入采用基于最新持久化会话记录的函数式更新方式，使快速连续到达的多个外部任务不会基于过期的消息列表覆盖彼此。消息物化成功后，任务状态由已接收推进到已物化或已排队，并记录消息标识、请求标识、对话轮次标识、队列代次等可用于后续恢复和查询的执行关联信息。

对话推理由串行化的 turn 队列或等效互斥执行机制驱动。同一会话内的外部任务与普通用户对话轮次按照队列顺序进入模型调用和工具调用流程，队列通过活动请求标识、代次校验或失效标记识别过期任务，防止清空会话、取消任务或恢复后遗留的旧执行项继续写入结果。对于可重试的队列或调度执行，重试参数随任务上下文持久化保存，使 agent 休眠或重启后仍能按同一策略继续尝试，而不是重新解释为新的外部提交。

### 任务状态查询、取消与清理

系统为每个外部任务维护持久化状态机。状态可以包括已接收、已物化、已排队、运行中、等待外部交互、已完成、失败、请求取消、已取消和已清理等阶段；状态记录还可以保存任务标识、去重键、载荷摘要、目标会话、消息标识、活动请求标识、流标识、重试次数、终态结果或错误摘要、时间戳以及清理墓碑。状态推进以持久化记录为准，瞬时内存中的队列活动状态、可恢复流状态和模型输出只作为推导当前运行态的补充依据。

查询接口根据任务登记表、消息表、turn 队列活动标识、可恢复流状态以及终态 assistant 消息综合返回任务状态。对于已完成任务，查询结果可以返回最终回复摘要、完整结果引用或回调投递状态；对于运行中任务，查询结果返回当前阶段、是否可取消以及可选的进度提示；对于重复提交获得的既有任务标识，查询接口与首次提交返回同一状态视图，使外部系统不需要区分首次请求和重试请求。

取消操作采用幂等的取消意图记录。外部调用方请求取消时，系统先在任务状态中写入取消意图；若任务尚未物化或尚未进入队列，则阻止后续消息注入或队列执行并转为已取消；若任务正在执行，则根据活动请求标识触发对应的中止控制，并允许执行器在安全边界处停止模型流、工具调用或后续消息写入；若任务已经完成或失败，迟到的取消请求只返回既有终态，不将终态回退为取消。清理操作优先在任务进入终态后执行软删除或墓碑保留，在去重窗口内保留任务标识、去重键和载荷摘要，以便迟到重试仍能被识别为同一逻辑任务。

### 中断恢复与一致性判定

agent 运行环境发生休眠、重启、网络中断或执行中断后，恢复流程首先读取外部任务登记表、持久化消息表、队列记录、可恢复流记录以及已有终态消息，并据此判定每个任务所处阶段，而不是仅依赖内存中的执行标记。该判定以“任务是否已登记、用户消息是否已物化、是否已入队或正在运行、是否已经产生终态结果、是否存在取消或清理标记”为主线，形成可重复执行的补偿规则。

对于已登记但尚未物化消息的任务，恢复流程重新执行消息物化，并依靠固定消息标识和去重键避免重复写入；对于已物化但未确认入队的任务，恢复流程重新入队或直接进入串行化 turn 执行，并记录新的活动请求关联；对于处于运行中但未检测到终态结果的任务，恢复流程结合可恢复流、原始请求上下文和对话恢复钩子继续未完成轮次，或者将任务标记为可重试的中断状态后重新调度；对于已经存在终态 assistant 消息或终态任务记录的任务，恢复流程仅补齐状态映射和查询结果，不再启动新的模型推理。

恢复补偿在每一步执行前后都重新读取持久化阶段并进行条件更新，使重复恢复、并发恢复或外部重复提交不会造成重复执行同一逻辑任务。对于已经请求取消或已经清理的任务，恢复流程不再重启推理；对于清理后仍处于去重窗口内的任务，系统通过墓碑记录返回已清理或已终止状态。由此，系统不承诺底层网络或模型调用绝对只发生一次，而是在任务登记、消息物化、状态推进和终态映射层面对外提供一致的一次逻辑任务结果。

### 可选实施方式与边界

在一种实现中，外部任务登记表与 agent 既有的持久化 SQLite 存储部署在同一 Durable Object 边界内，使任务状态、消息物化和队列触发可以在同一实例中顺序处理；在另一种实现中，登记表也可以与外部队列、工作流或关系型存储配合使用，只要去重键唯一约束、载荷摘要校验和阶段状态条件更新保持一致。目标 agent 可以按外部事件来源、租户、仓库、设备或会话标识路由，不同目标实例之间的任务状态相互隔离。

外部提交内容可以直接映射为一条用户消息，也可以在物化前经过模板化、权限校验、签名校验、上下文补全或附件引用解析。无论采用何种入口形式，进入对话执行前均统一转换为带有任务标识和消息标识的持久化消息，并由同一串行化 turn 机制处理。对于需要回调外部系统的场景，回调投递可作为任务状态机的附加阶段处理；回调失败不改变模型推理的终态，只影响投递状态和后续重试策略。

去重窗口、任务保留时间、可取消阶段、重试次数和失败后的保留策略可以根据外部调用方的业务要求配置。若任务载荷较大，登记表可以只保存规范化摘要、对象存储引用和必要的恢复上下文；若任务需要严格顺序处理，去重键之外还可以引入会话级序号或业务事件序号，用于在同一目标会话中确定任务进入 turn 队列的顺序。上述可选方式不改变核心机制，即先可靠登记外部任务，再以幂等消息物化和持久化状态机驱动异步对话执行，并在恢复时基于阶段状态进行补偿。
