## 技术方案

本方案在具备持久化 Agent、SQLite 状态存储、后台队列、程序化对话轮次入口以及可恢复流式输出能力的运行环境上，增设面向外部系统的“任务接收—幂等登记—异步执行—状态协调—恢复补偿”控制层。外部系统可以通过 webhook、RPC 或其他程序化入口提交一次对话任务，接收层只完成鉴权、规范化、幂等登记和入队触发，即向调用方返回已接收结果，不在同一 HTTP/RPC 生命周期内等待模型推理完成；后续执行、查询、取消、清理和恢复均围绕持久化任务记录进行。

### 外部任务接收与幂等任务账本

外部入口首先将不同来源的 webhook 请求、RPC 调用或内部程序化调用统一转换为标准任务描述。该任务描述至少包含外部调用方标识、目标 Agent 或会话标识、用户输入内容、可选上下文参数、回调或查询偏好，以及由调用方提供的幂等键；当调用方未提供幂等键时，可以对规范化后的提交内容、目标会话标识和调用方标识计算摘要，作为替代幂等键。规范化过程应在写入任务前完成，使字段顺序、无关 header 或重试时间差异不会导致同一业务请求被识别为不同任务。

接收层在 Agent 的持久化存储中设置外部任务账本，并对“调用方标识、目标会话标识、幂等键”建立唯一约束。账本记录可包括 $taskId$、$idempotencyKey$、$conversationId$、$inputMessageId$、$queueId$、$requestId$、$streamId$、$status$、尝试次数、创建时间、更新时间、最近错误和清理截止时间等字段。对于首次提交，系统在同一持久化事务中创建任务记录并将状态置为 accepted 或 queued；对于重复提交，唯一约束命中后直接读取已有记录并返回相同 $taskId$ 及当前状态，不再次追加用户消息、不再次创建后台队列项，也不再次触发模型推理。

任务登记与入队之间采用阶段标记防止半完成状态。若任务记录已创建但队列项尚未写入即发生异常，记录保持 accepted 并可由后续恢复扫描重新入队；若队列项已经创建，则回填 $queueId$ 并置为 queued。外部调用方收到的响应只表达系统已可靠接收任务，例如返回 $taskId$、幂等键、当前状态、查询地址和取消入口，而不承诺推理已经开始或完成。

### 异步排队与对话轮次执行管理

异步执行采用两层控制。第一层是持久化后台队列，用于将外部接收请求与模型推理生命周期解耦；接收层完成任务账本登记后只需创建或确认对应队列项，由队列在后续时机调用执行回调。第二层是会话内对话轮次串行控制，用于避免同一 Agent 或同一会话下多个 chat turn 重叠写入消息、交错流式输出或相互覆盖。后台队列解决“何时开始处理”的问题，轮次队列或程序化对话入口解决“同一会话内按何种顺序写入并推理”的问题。

队列回调开始执行时，先按 $taskId$ 读取任务账本并进行二次幂等检查。只有状态仍为 accepted 或 queued 的任务才允许进入 running；若记录已经是 running、streaming、completed、aborted、failed 或 cleaned，则说明该任务已被其他恢复流程、重试流程或重复请求处理，当前回调直接结束。状态从 queued 切换到 running 时同时记录执行尝试次数和开始时间，使后续查询和恢复能够区分“尚未开始”“已取出队列但未写入用户消息”和“已经进入模型轮次”等阶段。

进入对话轮次时，执行层通过程序化消息保存入口追加本次外部提交对应的用户消息，并触发一次模型响应。为避免排队期间读取到过期消息基线，追加消息优选采用基于最新持久化消息列表的函数式更新；写入用户消息后，将生成的 $inputMessageId$、服务端 $requestId$ 和可能产生的 $streamId$ 回填至任务账本。若对话入口返回 completed、skipped 或 aborted 等结果，则按返回结果更新任务终态或中间态；其中 skipped 表示该轮次因串行队列代际变化等条件未实际执行，不应被误判为成功完成。

任务账本与消息写入之间保持单调阶段推进：未登记任务不得写入用户消息；已写入用户消息的任务不得在重复提交时再次写入相同用户消息；已获得 $requestId$ 的任务不得因外部网络重试再次启动新的模型轮次。对于确需重试的失败任务，也应创建新的尝试记录或提升尝试序号，并保留原 $taskId$ 与原始幂等键的关联，以便外部调用方能够看到同一业务任务的完整执行历史。

### 状态查询、取消与清理

状态查询接口以外部任务账本为主索引，而不是要求调用方理解内部 WebSocket 连接状态或流式传输细节。查询时，系统读取任务记录，并按记录中的 $queueId$、$requestId$、$streamId$、$inputMessageId$ 关联后台队列项、对话轮次活动状态、流式输出元数据和已持久化消息，汇总为外部可理解的状态，例如 accepted、queued、running、streaming、completed、aborted、failed、interrupted 或 cleaned。对于 streaming 状态，可以返回已生成输出的摘要、可重放流标识或最后更新时间；对于 failed 或 interrupted 状态，可以返回错误类别、是否可重试以及下一步处理建议。

取消接口根据任务所处阶段执行不同动作。对于 accepted 或 queued 任务，系统删除或跳过对应队列项，并将任务状态更新为 aborted，保证后续队列回调即使被触发也会因账本状态不匹配而退出。对于 running 或 streaming 任务，系统使用任务记录中的 $requestId$ 关联当前内存中的取消控制器或外部取消信号，向正在执行的推理轮次发送取消请求；取消后保留已经持久化的用户消息、部分输出块和流元数据，并将任务标记为 aborted 或 interrupted。若运行环境重启后原内存取消控制器已经不存在，则取消动作转化为持久化的取消意图，由恢复扫描在重新进入该任务时阻止继续执行或补记中断状态。

清理机制仅作用于已经达到终态且超过保留期限的任务数据。系统可按任务记录中的清理截止时间删除幂等索引、队列残留项、过期流式输出块或查询缓存，但不得删除仍处于 accepted、queued、running、streaming、interrupted 等可能需要恢复、重放或状态核对的数据。对于需要审计或排障的场景，可以将完整消息内容与任务控制元数据分开设置保留策略，使外部系统既能释放过期执行资源，又不会破坏未完成任务的一致性判断依据。

### 休眠、重启或中断后的恢复一致性

为适配 Agent 休眠、运行时重启、代码更新或推理中断，本方案将恢复逻辑设计为基于持久化事实的阶段判定，而不是依赖内存状态。Agent 在启动、闹钟触发、下一次外部请求到达或恢复回调执行时，扫描任务账本中未处于终态的记录，并结合后台队列表、持久化运行记录或快照、流式输出元数据以及已持久化消息，判断每个任务最后可靠完成的阶段。恢复处理只从该阶段之后继续补偿，避免因无法区分阶段而重复写入用户输入或重复发起模型推理。

恢复扫描可按以下阶段执行补偿：任务为 accepted 且没有 $queueId$ 时，重新创建队列项并置为 queued；任务为 queued 但队列项不存在时，根据取消意图、重试次数和创建时间决定重新入队或标记 failed；任务为 running 但没有 $inputMessageId$ 时，说明尚未可靠写入用户消息，可以回退为 queued 重新执行；任务已有 $inputMessageId$ 但没有 $requestId$ 时，不再重复追加用户消息，而是通过继续最后一轮或专门的补偿入口推进模型响应；任务已有 $requestId$ 或 $streamId$ 时，优先根据流式元数据判断该轮次是否仍可重放、已经完成、发生错误或成为孤儿流。

对于流式输出中断的任务，若存在可重放的 completed chunks，则查询或客户端重连时按 $requestId$ 重放已完成输出，并将任务置为 completed；若存在仍标记为 streaming 但已经没有活动模型读取器的孤儿流，则先将已持久化的部分输出补成可查询的部分消息，再按照策略标记为 interrupted、aborted 或调用继续最后一轮的入口补足响应。该处理使系统能够区分“输出已经生成但终态未回填”和“模型执行确实中断”两种情况，避免外部调用方反复重提同一任务。

恢复逻辑与幂等账本共同形成一致性闭环：外部重复提交只能命中同一任务记录，后台重复调度只能在状态允许时进入下一阶段，对话轮次串行化保证同一会话内消息追加和推理不重叠，流式输出持久化保证断连或休眠后仍能重放或判定中断。由此，外部系统能够以低延迟方式提交对话任务，同时获得可查询、可取消、可清理且可恢复的一次性执行语义。
