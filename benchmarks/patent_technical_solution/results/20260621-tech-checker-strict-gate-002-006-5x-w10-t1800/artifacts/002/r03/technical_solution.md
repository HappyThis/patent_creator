## 技术方案

### 总体架构与持久化任务账本

本方案在既有对话式 agent 能力之外，增加面向外部系统的一次性对话任务通道。外部 webhook、RPC 或其他程序化入口不直接同步调用模型推理，而是先按照目标会话或目标 agent 标识路由到同一个持久化 agent 实例，由该实例完成任务登记、排队执行、状态维护和恢复判定。这样，外部调用与模型执行被拆分为“可靠接收”和“后台执行”两个阶段，调用方只需等待接收结果，不需要占用连接直到大模型输出完成。

该通道包括外部接收层、任务账本、执行调度器、对话注入器、状态控制接口和恢复协调器。任务账本存储在 agent 的持久化存储中，例如 SQLite 或等价的持久状态，而不是存储在进程内存中。任务账本至少记录任务标识、调用方标识、幂等键或请求指纹、规范化后的用户输入、目标会话标识、当前阶段、阶段更新时间、取消标志、执行尝试次数，以及与后续对话 turn 关联的请求标识、消息标识、流标识或持久执行标识。

任务阶段采用可恢复的有限状态表示，至少包括 accepted、queued、injecting、running、completed、failed、cancel_requested、cancelled 和 cleanup。accepted 表示外部请求已被可靠持久化；queued 表示等待进入对话 turn；injecting 表示正在把外部输入转换为会话消息；running 表示模型推理或工具调用正在进行；completed、failed、cancelled 为终态；cleanup 表示终态记录进入可清理窗口。阶段变化与必要关联信息在同一持久化边界内更新，使 agent 在休眠、重启或执行中断后能够根据账本重新判断任务位置。

### 外部接收与幂等登记

外部接收层接收到一次程序化任务提交后，先进行请求规范化和幂等识别。若调用方提供 idempotency key，则将调用方标识、目标会话标识和该 idempotency key 组合为幂等索引；若调用方未提供幂等键，则对规范化后的请求体、目标会话标识和关键业务字段生成请求指纹。规范化处理应排除传输时间戳、临时签名、随机 nonce 等不影响任务语义的字段，保留用户输入、任务类型、目标会话和必要上下文引用，以减少网络重试导致的误判。

任务登记通过原子写入完成：系统以幂等索引作为唯一约束写入任务账本，初始阶段为 accepted，并保存规范化输入及返回所需的 taskId。若写入成功，接收层立即向调用方返回“已接收”确认、taskId 和当前状态；若写入时发现相同幂等索引已经存在，则不追加新的用户消息，也不启动新的模型执行，而是直接读取既有任务的 taskId、状态和可查询地址并返回。该处理使调用方因 HTTP 超时、RPC 断连或网关重试而重复提交时，系统仍只保留一个逻辑任务。

接收阶段不等待对话稳定、不等待模型开始，也不依赖打开的网络连接保存执行上下文。接收成功后，系统通过持久化调度、后台 fiber 或等价队列触发后续执行，并把 accepted 任务推进为 queued。若接收后立即发生实例休眠或重启，任务记录和幂等索引仍存在，下一次外部请求、定时唤醒或恢复扫描均可发现该任务并继续推进。

### 异步执行与对话注入

执行调度器从任务账本中选择 accepted 或 queued 且未被取消的任务，将其作为后台工作单元执行。执行前，调度器先检查同一会话是否存在活跃的模型流、待处理客户端工具调用或排队的 continuation；若存在，则等待会话进入稳定状态或将任务保留在队列中。该机制避免外部注入的消息与用户正在进行的对话 turn 交错写入，从而保持会话消息序列和模型上下文的一致性。

当会话满足注入条件后，对话注入器把任务中的规范化输入转换为一条服务端生成的用户消息或等价的程序化 turn，并采用“执行时读取最新消息列表”的函数式写入方式计算新增消息。也就是说，任务排队时不固定旧的 transcript，而是在真正开始注入时基于已经持久化的最新会话消息追加本次外部输入。该方式能够适应多个外部任务连续排队或用户在其间继续对话的情形，避免后提交任务基于过期上下文生成回复。

在注入开始前，系统将任务阶段更新为 injecting；消息持久化成功并取得对话 turn 的请求标识后，将任务阶段更新为 running，并记录 taskId 与 requestId、消息标识、流标识或持久执行标识之间的映射。模型输出、工具调用结果和可恢复流仍由既有对话 agent 机制持久化，任务账本只保存外部任务维度的控制信息和关联索引。对话 turn 完成后，执行器根据返回结果把任务置为 completed 或 failed，并保存完成时间、错误摘要或结果引用。

对于长时间运行的模型推理，执行工作单元可以包裹在持久执行机制中，并在关键阶段写入 checkpoint，例如“已领取任务”“已等待会话稳定”“已完成消息注入”“已绑定请求标识”“已收到终态”。checkpoint 与任务账本共同构成恢复依据：任务账本回答外部任务是否存在、是否已取消以及处于哪个业务阶段，持久执行记录回答后台执行是否在某个阶段中断。

### 状态查询、取消与清理

状态查询接口以 taskId 或幂等索引为查询条件，只读取任务账本和必要的对话结果引用，返回当前阶段、是否终态、最近更新时间、错误摘要、取消状态以及可选的结果位置。查询接口不重新触发执行，也不重新写入消息，因此调用方可以在收到 accepted 后按需轮询，或者在业务侧通过回调、事件通知等方式接收状态变化。

取消接口采用阶段化处理。若任务仍处于 accepted 或 queued，系统将其更新为 cancelled 或 cancel_requested 后阻止执行器领取，且不向会话写入用户消息；若任务处于 injecting，则先检查消息是否已经完成持久化，未完成时阻止注入，已完成时转入 running 的取消流程；若任务处于 running，则持久化 cancel_requested 标志，并通过与该 turn 关联的取消信号请求中止模型推理或工具链执行。执行器收到取消结果后将任务置为 cancelled；若模型侧已经产生不可回滚的终态回复，则保留对话历史并把任务标记为 completed 或 failed，同时在任务账本中记录取消请求已晚于终态。

清理接口和周期性清理任务仅处理 completed、failed、cancelled 等终态记录以及过期的幂等索引，不清理 accepted、queued、injecting、running 或 cancel_requested 状态的任务。清理时可以保留最小审计信息，例如 taskId、幂等索引摘要、终态、完成时间和结果引用，也可以在满足保留期限后删除详细请求体。对于会话消息和模型流片段，清理任务应遵循对话系统自身的历史与可恢复流保留策略，避免因外部任务记录清理而破坏用户可见的对话上下文。

### 中断恢复与一致性判定

agent 从休眠、重启或执行中断中恢复时，恢复协调器扫描任务账本中所有非终态任务，并结合持久执行 checkpoint、会话消息记录、可恢复流记录和取消标志判定下一步动作。恢复判定遵循“可重试接收、不可重复注入、终态优先”的原则：接收阶段可以安全重放调度动作，但一旦外部输入已经作为会话消息持久化，后续恢复不得再次写入相同用户输入。

若任务处于 accepted 或 queued 且不存在消息标识，说明外部请求已可靠接收但尚未进入对话，可重新排队执行；若任务处于 injecting 但未发现已持久化的消息，则回退到 queued 并重新注入；若任务处于 injecting 且已经存在消息标识，则将任务推进为 running 或等待对应对话 turn 的恢复结果，不能再次追加消息；若任务处于 running，则根据 requestId、流记录或持久执行记录判断 turn 是否仍可恢复、是否已经完成或是否需要标记失败并等待人工或上层策略重试。

对于已设置 cancel_requested 的任务，恢复协调器优先执行取消语义：尚未注入消息的任务直接转为 cancelled；已注入但未完成的任务重新建立或查找对应取消控制信号，并请求对话 turn 停止；已经完成的任务以对话终态为准，同时保留取消请求的审计记录。对于因异常失败的任务，系统可以根据错误类型、尝试次数和幂等索引决定是否自动重试；重试仅允许从未完成注入的阶段重新开始，或者恢复同一个持久执行，不允许通过再次追加相同用户消息来制造第二个对话 turn。

通过上述恢复规则，系统把外部任务的可靠性边界从“请求连接是否保持”转移到“任务账本、会话消息和持久执行记录是否一致”。外部调用方重复提交时由幂等索引合并，执行中断时由阶段和 checkpoint 恢复，取消和清理则受终态与关联记录约束。由此可以在 webhook、RPC 等外部提交场景下同时满足快速确认、避免重复执行、可查询控制以及休眠重启后的状态一致性。
