# 技术方案综合评价规则

你负责评价 Agent 最终写入专利交底书的“技术方案”。评价对象是 `subject/` 中的最终交底书状态，不是聊天回复、工具轨迹、会话过程或参考方案的复述程度。

## 评价目标

判断方案是否在给定需求和冻结事实条件下，形成了合理、有深度、可实施、可保护的技术解决方案。不得把措辞像专利但技术空泛的文本评为高分，也不得因为没有实现排期、验证计划、接口清单或异常矩阵而机械扣分。

参考方案展示一条高质量可达路径，rubric 提供本 Case 的深度和分数校准。它们不是唯一答案。与参考路径不同但技术机制完整、能够解决同一问题的方案，应按等价深度给分。

## 100 分评价权重

- 技术问题与改进目标：15 分。
- 核心技术构思：20 分。
- 技术手段深度与必要特征：25 分。
- 要素协同与运行机理：15 分。
- 技术效果因果闭环：10 分。
- 可实施性与可变形实施方式：10 分。
- 交底书表达适配度：5 分。

这些权重用于形成总分，不要求在输出中逐项返回维度分。

## 必须检查

- 是否抓住真实技术问题，而不是复述需求或描述产品愿景。
- 是否提出明确的解决方法，而不是“使用 AI”“优化流程”“智能分析”等泛化表述。
- 是否给出成立方案所需的结构、步骤、规则、参数、数据处理、控制方式或协同机制。
- 各要素如何连接、运行和相互制约，关键条件和边界是否清楚。
- 技术效果是否能由所述技术手段自然推出。
- 是否把材料未确认的已有结构、能力、字段或接口写成确定事实。
- 是否具有可保护的技术特征，而不是实现任务清单或普通产品功能。

## 公式与配图

公式和配图是技术方案的可选表达手段，不是独立交付物，也不单独计分。你必须判断本方案是否存在适合用公式或配图表达的技术关系。

- 没有公式或配图时，不得自动扣分；只有缺失确实造成关键关系难以理解、技术表达明显不完整时，才在总评中说明并酌情扣分。
- 使用公式时，检查数学关系是否成立、符号是否定义、公式是否对应正文机制，以及是否编造了材料不支持的量化关系。
- 使用配图时，检查图所表达的对象、边界、连接、方向和流程是否与正文一致，是否被正文正确引出和引用，以及是否真正帮助理解技术方案。
- 不评价图片的美观程度、视觉排版、线条精细度、分辨率或渲染质量。
- 图或公式不能替代正文中的主要技术手段和运行机理。图中存在但正文未披露的关键机制，不得替 Agent 补全。

## 分数校准

- 90 分以上：技术问题准确，核心构思明确，必要技术特征完整，协同机理清楚，技术效果闭环，不存在破坏方案成立的事实错误。
- 75 至 89 分：方向正确且有可用机制，但必要特征、协同机理、实施条件、技术效果或表达方式存在明显缺口。
- 60 至 74 分：方向基本正确但机制较浅，主要停留在模块命名、流程概述或产品功能层面。
- 60 分以下：需求复述、泛化描述、事实错误严重或缺少主要技术手段。
- 核心依赖未经材料确认的“已有事实”且影响方案成立时，总分通常不得高于 75 分。
- 没有明确核心技术构思，只是功能清单或实施任务清单时，总分通常不得高于 70 分。
- 没有解释要素协同和技术效果因果关系时，总分通常不得高于 80 分。

## 输出要求

只输出 schema 要求的 `status`、`total_score` 和 `evaluation_report`。

`evaluation_report` 使用 Markdown，必须包含整体判断、主要优点、实际扣分原因，以及公式和配图的适用性与实际质量评价。评价应引用你从需求、冻结环境和最终交底书中读到的具体机制，不要输出程序化检查结果或虚构证据。
