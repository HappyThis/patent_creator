## 技术方案

本方案提供一种将 Mission Control（以下简称 MC）任务看板中的任务数据以机器可读文件形式同步到代码仓库的技术机制，使任务状态可跟随代码仓库流转，并允许外部 agent 工具在不直接访问 MC 数据库的情况下读取、追踪任务队列，同时保持 MC 任务看板作为主要工作入口不受外部同步故障影响。方案在现有 GitHub Issue 同步通道之外，新增基于 Git 仓库内任务文件的协作格式同步能力，核心包括：任务文件结构定义、稳定任务标识到文件路径的映射、MC 任务生命周期事件驱动的同步触发、Git 操作编排、冲突与删除同步处理，以及失败隔离和容错机制。

### 技术问题

MC 的任务数据（标题、描述、状态、优先级、指派对象、标签、元数据等）存储在应用自有的 SQLite 数据库中。外部 agent 工具（如 Claude Code、Codex、自定义 CI 流水线中的检查脚本）无法直接读取该数据库，因此无法在不通过 MC API 的情况下感知当前任务队列。当团队希望在代码分支中附带当前开发任务的状态、在不同 agent 工具间传递任务上下文、或将任务生命周期与 Git 工作流绑定（例如 feature 分支关联特定任务）时，缺少一种无需依赖 MC 在线 API 即可读取的、可随代码仓库流转的机器可读任务表示。

### 整体架构

方案在 MC 现有架构上新增一个任务文件同步层，位于 MC 的 HTTP API 路由层与 Git 远端仓库之间。MC 任务创建、更新、删除操作在完成本地数据库写入后，通过事件驱动方式触发同步任务，由同步引擎将任务状态转换为仓库内的结构化任务文件，执行 Git 提交与推送。同步层与现有 GitHub Issue 同步引擎共享 Github API 客户端与仓库配置（如 github_repo、github_default_branch），但采用独立的文件格式、路径映射和冲突处理逻辑，两者互不干扰。

### 任务文件结构定义

每个 MC 任务在仓库中对应一个以任务唯一标识命名的目录，目录内包含一个结构化任务清单文件。目录命名采用任务的项目前缀与自增编号的组合（如 PROJ-001），以保证跨仓库和跨项目的全局稳定性。任务清单文件采用 YAML 格式，存储任务的全部可同步字段：标题、描述、当前状态、优先级、指派对象、创建与更新时间戳、标签列表、估计工时、实际工时、完成时间、产出摘要、反馈评分、重试次数，以及对应的 MC 任务 ID 和项目 ID 等溯源信息。YAML 格式兼顾人类可读性和 agent 工具的机器解析便利性。

### 稳定任务标识到文件路径的映射

任务文件在仓库中的路径由项目配置的同步根目录（如 .mc-tasks/）和任务标识组成。具体路径规则为：{sync_root}/{project_slug}/{task_ticket_ref}/task.yaml。其中 task_ticket_ref 是 MC 为每个任务分配的项目前缀加自增编号（如 PROJ-001），在任务创建时由数据库事务内的 ticket_counter 自增机制保证唯一性和稳定性。即使任务的标题、状态或其他属性发生变化，该路径标识保持不变。任务被删除时，同步引擎通过该路径定位并移除对应的目录及文件。

### 任务变更检测与同步触发

同步触发采用事件驱动加轮询的双模机制。近实时同步路径：在 MC 的 POST /api/tasks（创建）、PUT /api/tasks/[id]（更新）、DELETE /api/tasks/[id]（删除）路由处理函数中，完成本地数据库写入后，以 fire-and-forget 方式将同步任务推入异步队列，不阻塞 API 响应。异步队列处理函数负责生成或更新任务文件、执行 Git 操作。定时对账路径：复用现有 github-sync-poller 的轮询框架，以可配置间隔（默认 60 秒）扫描所有启用了文件同步的项目，将自上次同步以来发生变更的任务批量生成文件并提交，处理异步路径中可能因进程重启等原因丢失的同步事件。

### Git 操作编排

Git 操作由同步引擎通过以下步骤编排执行：(1) 基于仓库默认分支（如 main）执行 git fetch 获取远端最新提交；(2) 创建或切换到以同步批次命名的临时分支（如 mc-sync/{timestamp}-{batch_id}）；(3) 在临时分支上执行任务文件的增、改、删操作（写入 YAML 文件或删除目录）；(4) 执行 git add 与 git commit，提交信息包含同步批次标识、受影响任务数量和操作类型（create/update/delete）；(5) 通过 GitHub API 的 Git refs 端点（现有 createRef 能力）或直接 git push 将临时分支推送到远端；(6) 通过 GitHub API 创建 Pull Request 或直接合并到默认分支，取决于项目配置的同步策略（PR 模式或直接推送模式）。整个流程在数据库事务内记录同步状态和批次元数据，确保可追溯。

### 冲突检测与处理

冲突场景包括三类：(1) 文件级写入冲突——当两个并发的 MC 任务更新触发生成同一任务文件时，同步引擎通过 MC 内部的 SQLite 写锁和 batch_id 序列化保证同一任务在一个同步批次内只被处理一次；(2) Git 推送冲突——当远端在同步批次执行期间收到其他提交时，推送被拒绝。引擎检测到推送失败后，执行 git fetch --rebase 将远端变更合并到临时分支，若 rebase 成功则重新推送；若 rebase 产生文件冲突（即远端存在对同一任务文件的外部修改），引擎采用"MC 优先"策略：以 MC 数据库中的任务状态覆盖冲突文件，重新提交并推送。MC 数据库始终是权威数据源；(3) 外部修改与 MC 状态不一致——定时对账路径扫描已同步的任务文件，对比文件中的 updated_at 时间戳与 MC 数据库，若发现文件时间戳晚于 MC 记录且文件内容与 MC 不一致，则记录异常但不下游覆盖 MC 数据库，保持 MC 的单向权威。

### 删除同步

MC 中任务被删除时，同步引擎在 DELETE 路由处理完成后触发删除同步流程：根据任务的 ticket_ref 和项目 slug 计算出对应的仓库文件路径（{sync_root}/{project_slug}/{ticket_ref}/），在临时分支上执行 git rm -r 删除该目录及内部所有文件，生成提交信息标记为 delete 操作，随后按 Git 操作编排流程推送。如果任务在首次同步前即被删除（即仓库中不存在对应文件），则跳过删除操作并记录日志。为处理远端已有对该任务文件的独立修改但本地任务已删除的情况，删除操作同样采用 MC 优先策略：远端存在该目录时直接执行 git rm；不存在时跳过。

### 失败隔离与容错

方案设计遵循"同步失败不影响 MC 日常操作"的原则，具体措施包括：(1) API 路由中的同步触发全部采用 fire-and-forget 异步模式，同步失败仅记录错误日志，不向 API 调用者返回错误，不阻塞任务创建、更新或删除的响应；(2) 同步引擎在执行 Git 操作前检查项目级同步开关（file_sync_enabled），关闭时不执行任何同步动作；(3) Git 操作设置超时（默认 30 秒），超时后放弃当前批次并记录失败状态，由下一轮定时对账补处理；(4) 所有同步操作的状态（进行中、成功、失败、跳过）和错误信息写入同步历史表，可通过管理面板或 API 查询；(5) 连续失败超过阈值时触发告警通知，但不自动停止同步，避免因短暂远端故障（如 GitHub API 限流）导致长期中断。

### 技术效果

本方案的技术效果包括：(1) 任务数据可携带性——任务状态以机器可读 YAML 文件形式存储在代码仓库中，可随仓库克隆、分支、归档等 Git 操作自然流转，外部 agent 工具通过文件系统即可读取任务队列，无需依赖 MC 在线 API；(2) 任务与代码工作流绑定——每个任务的 ticket_ref 直接对应仓库文件路径，开发者在分支中可直观看到关联任务的状态文件，CI/CD 流水线可基于任务文件中的状态字段触发差异化行为；(3) 同步隔离——同步失败不影响 MC 本地任务操作，fire-and-forget 异步模式加定时对账双路径保证最终一致；(4) 单向权威——MC 数据库始终是任务数据的权威源，冲突时以 MC 为准，避免跨系统状态歧义；(5) 与现有架构兼容——复用现有 GitHub API 客户端、仓库配置和轮询框架，新增文件同步能力作为独立可选的同步通道，不影响现有 GitHub Issue 同步。

### 风险与待确认问题

方案在现有代码基础上需确认以下风险点：(1) 当前 MC 的 github-sync-poller 仅轮询启用了 github_sync_enabled 的项目；文件同步方案是否需要独立的轮询器或复用现有轮询器增加同步类型标记，取决于性能评估；(2) 大量任务（数百以上）的文件同步批次可能产生较大的 Git 提交，需评估分批策略和提交粒度；(3) YAML 文件对特殊字符（如任务描述中的代码块、多行文本）的转义处理需要制定规范以保证机器解析一致性；(4) 任务 ticket_ref 在跨项目迁移时是否会变化——当前 MC 中 project_id 变更时会重新分配 ticket_counter，这可能影响已同步文件的路径稳定性。建议在文件同步启用后锁定 ticket_ref 或采用 MC 内部自增 ID 作为辅助路径锚点。
