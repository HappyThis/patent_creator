## 技术方案

本方案提出一种任务数据的代码仓库镜像同步机制，使 Mission Control 中创建和维护的任务能够以机器可读的任务镜像文件形式存在于 Git 托管仓库中，供外部 agent 工具和开发工作流在不直接访问 Mission Control 数据库的情况下读取、同步和追踪任务状态。该机制作为现有 GitHub Issues 同步能力的补充和替代路径，核心区别在于同步目标不是 GitHub Issues API 资源，而是仓库内的结构化任务文件。

### 整体架构

系统在 Mission Control 现有任务管理栈之上新增一个任务镜像同步模块。该模块独立于现有 GitHub Issues 同步引擎运行，通过项目级配置开关启用。同步模块由三个核心组件构成：镜像序列化器（负责将任务对象转换为仓库文件格式）、路径映射器（负责建立稳定任务标识与文件系统路径之间的确定性映射）、Git 操作适配器（负责文件读写、提交、推送与拉取）。这三个组件通过同步调度器协调，既支持任务变更事件触发式即时同步，也支持定时批量同步。

### 任务镜像文件结构

任务镜像文件采用结构化格式（JSON 或 YAML），每个任务对应仓库中的一个独立文件。文件包含任务的完整可机器读取表示，至少包括以下字段：唯一标识符（task_id）、标题（title）、描述（description）、状态（status）、优先级（priority）、负责人（assigned_to）、创建时间（created_at）、更新时间（updated_at）、标签列表（tags）、所属项目标识（project_id）、以及由 Mission Control 生成的稳定任务标识（stable_task_key）。稳定任务标识是文件路径映射的核心输入，在任务创建时生成且在其整个生命周期内不变。

### 稳定标识到文件路径的映射机制

路径映射器采用确定性哈希映射策略。以任务的稳定任务标识（stable_task_key）为输入，通过 SHA-256 哈希取前两位十六进制字符作为第一级目录、第三四位作为第二级目录，将任务文件分散到多层目录结构中，避免单目录文件数过多导致的文件系统性能退化。最终文件路径格式为：{repo_root}/.mission-control/tasks/{hash[0:2]}/{hash[2:4]}/{stable_task_key}.json。该路径完全由 stable_task_key 决定，不依赖任何外部状态，确保任何 agent 工具在不访问 Mission Control 数据库的情况下也能通过已知的 stable_task_key 计算出文件的确定位置。

### 双向同步机制

同步分为上行（Mission Control → 仓库）和下行（仓库 → Mission Control）两个方向。

上行同步采用触发式 + 批量双重模式。当 Mission Control 中任务发生创建、更新或删除操作时，系统通过事件总线捕获变更事件，在事务提交后异步触发镜像文件的写入或删除操作，然后执行 Git add、commit 和 push。为防止高频变更导致的 Git 操作风暴，系统维护一个短时间窗口内的变更集合，在窗口关闭后合并为单次 commit。对于删除操作，系统不从仓库中物理移除文件，而是在任务文件中标记 deleted 状态并清空可清除字段，保留一个墓碑记录以指示该任务已被删除。同步调度器同时支持定时全量对账，遍历 Mission Control 中的所有活跃任务与仓库中镜像文件进行比较，修复因网络中断或其他异常导致的不一致。

下行同步通过定期拉取仓库中 .mission-control/tasks/ 目录下的所有镜像文件实现。系统遍历文件树，解析每个任务文件，将其与本地数据库中对应任务进行比较。比较以文件中的 updated_at 时间戳和本地任务的 github_synced_at（此处复用于镜像同步的时间戳）为判断依据：若文件时间戳更新且差值超过阈值，则将文件内容回写至 Mission Control 数据库；若文件中的任务标识在本地数据库中不存在且文件无墓碑标记，则作为新任务导入。为防止同步乒乓效应，上行同步写入文件时在文件中记录同步来源标识和精确同步时间戳，下行同步在发现同步来源为自身且时间戳差在阈值内时跳过该任务。

### 冲突处理与失败隔离

同步模块采用严格的非侵入式设计，确保外部同步失败不影响 Mission Control 内部日常任务操作。具体机制如下：

- 任务创建、更新、删除操作在 Mission Control 本地数据库中首先完成事务提交，同步操作作为事务后异步钩子执行。同步失败仅记录错误日志和失败计数，不回滚本地任务操作，不向用户返回同步错误。
- Git 操作层面的冲突（如 push 被拒绝因为远程有新提交）通过先 fetch 再 rebase/merge 后重试 push 的标准 Git 工作流处理。若多次重试仍失败，记录失败事件并等待下一轮定时对账修复。
- 文件内容层面的冲突（同一任务在 Mission Control 和外部 agent 同时修改）以 Mission Control 为主数据源。下行同步在发现文件中的任务被外部修改时，若本地任务也在同一时间段内被更新，采用"最后写入者胜出"策略，以时间戳较新的一方覆盖另一方，同时在同步日志中记录冲突事件供审计。
- 网络故障或仓库不可达时，同步操作静默失败。变更在本地缓冲区中保留，待下一轮触发或定时对账时重试。缓冲区基于 SQLite 的同步队列表实现，每条记录包含变更类型、任务标识、目标仓库和重试次数。

### 删除同步与墓碑机制

当 Mission Control 中的任务被删除时，同步模块不在仓库中物理删除对应的任务镜像文件，而是采用墓碑标记策略。具体流程：将任务文件内容替换为一个最小化的墓碑记录，包含原始 stable_task_key、status 字段固定为 deleted、deleted_at 时间戳以及一个 tombstone 布尔标记置为 true。原有任务描述、标签等业务字段被清空。墓碑文件保留在仓库中，使外部 agent 工具在读取文件树时能够识别任务已被删除，而非任务文件意外消失。墓碑文件的保留期可配置，过期后由清理任务物理移除。

### 技术效果

本方案相比现有方式带来以下技术效果：第一，任务数据的可携带性显著增强，任务状态以标准化机器可读文件形式随代码仓库流转，不再绑定于 Mission Control 数据库实例。第二，外部 agent 工具无需访问 Mission Control API 或数据库即可通过 Git 仓库获取任务队列完整视图，降低了系统耦合度和集成成本。第三，Git 自身提供天然的变更历史、审计追踪和分布式协作能力，每次任务变更对应一次 commit，可追溯谁在何时改了什么。第四，同步失败不影响 Mission Control 内日常任务操作，通过异步触发、本地缓冲和定时对账实现最终一致性。第五，确定性路径映射使任何知道 stable_task_key 的工具都能直接定位任务文件，无需依赖索引服务或数据库查询。

### 风险与待确认问题

以下为方案中需要后续确认的技术风险点：第一，stable_task_key 的生成策略需与现有任务 ID 体系协调。若直接复用数据库自增 ID，在多实例部署场景下可能导致 ID 冲突，建议采用 UUID 或带实例前缀的复合键。第二，大规模任务集（数万级别）下的全量定时对账可能产生显著的 Git 仓库遍历开销，需评估是否采用增量扫描（基于 Git diff）替代全量文件遍历。第三，墓碑文件的保留策略需要在可追溯性与仓库清洁度之间取得平衡，建议允许项目级配置墓碑保留天数。第四，多 Mission Control 实例同时向同一仓库写入时可能产生 push 竞争，需要在实例间协调或接受偶然的 push 重试。
