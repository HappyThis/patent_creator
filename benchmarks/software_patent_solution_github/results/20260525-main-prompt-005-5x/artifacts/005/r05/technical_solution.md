## 技术方案

### 技术问题概述

Think agent 现有的交互模式面向同步对话：用户（或前端）发起一次请求，系统创建会话和消息、启动模型推理，过程中可能通过流式事件逐步返回工具调用、推理内容和最终回复。外部系统（webhook、RPC 调用方、异步 Worker）在这种模式下难以将 Think agent 作为可编程任务执行器使用，因为调用方必须在一次请求-响应连接中等待全部推理完成，无法在提交后立即得到确认并断开连接。

### 整体架构

本方案在 Think agent 现有会话、消息、流式执行、恢复和取消语义之上，增加一层任务（Task）抽象。任务是对一次外部提交的完整生命周期管理单元，包含：一个幂等键用于去重，一个关联的会话标识，一个持久化的状态字段，以及可选的取消/清理标记。现有会话和消息模型保持不变；任务层在会话之上提供异步提交-追踪-控制能力。

系统引入任务记录（TaskRecord）数据结构，包含以下关键字段：task_id（系统生成的唯一任务标识）、idempotency_key（由调用方提供或系统基于请求指纹生成的幂等键）、session_id（关联的会话标识，任务受理后创建会话并写入此字段）、status（任务状态，取值包括 PENDING、RUNNING、COMPLETED、FAILED、CANCELLED）、created_at/updated_at（时间戳）、cancel_requested_at（取消请求时间）、result_summary（完成后的结果摘要）。任务记录持久化在任务表中，与会话和消息的存储位于同一持久化层。

### 任务提交与幂等去重

外部调用方通过任务提交接口向 Think agent 提交一次对话任务。请求至少包含：待发送的用户消息内容、幂等键（由调用方指定，如消息队列的消息 ID 或业务流水号）、可选的会话复用标识（如果希望追加到已有会话而非创建新会话）。系统按以下流程处理提交请求。

第一步，幂等检查。系统以幂等键为索引查询任务表。若已存在匹配的任务记录，根据规则返回：若已有任务状态为 COMPLETED 或 FAILED 且未超过保留窗口，直接返回已有任务的 task_id 和当前状态，不创建新任务也不重复插入用户消息；若任务处于 PENDING 或 RUNNING 状态，返回已有 task_id 和状态，告知调用方任务正在处理中。若不存在匹配记录，进入第二步。

第二步，原子写入任务记录与会话。系统在同一个持久化事务中完成：创建任务记录（状态为 PENDING，写入幂等键和时间戳）、创建或复用会话（若调用方未指定复用则创建新会话）、将用户消息写入会话的消息存储。事务提交成功后，系统立即向调用方返回包含 task_id 和状态 PENDING 的确认响应。此时模型推理尚未开始，调用方可在毫秒级获得确认并断开连接。

### 任务执行调度与状态管理

任务提交并持久化后，由任务调度器（Task Dispatcher）负责将 PENDING 任务投入执行。调度器采用条件领取机制：以原子操作将任务状态从 PENDING 更新为 RUNNING，并记录领取时间和执行者标识。只有成功完成该原子更新的调度器实例才获得该任务的执行权，避免并发领取同一任务。

领取成功后，调度器将任务关联的会话和消息加载到 Think agent 的现有执行引擎中。执行引擎复用已有的消息处理管线：读取会话历史、调用模型推理、执行工具调用、产生流式事件。任务执行期间，调度器定期更新任务记录的 updated_at 时间戳作为心跳，外部可通过状态查询接口观察任务是否仍在运行。

模型推理正常完成时，调度器将任务状态更新为 COMPLETED，写入结果摘要（包含最终回复的快照或关键结论），释放执行资源。若推理过程中发生可恢复异常（如模型服务暂时不可用），调度器可将任务状态回退为 PENDING，由后续调度周期重新领取执行，并记录重试次数。若超过最大重试次数或发生不可恢复异常，任务状态更新为 FAILED，同时记录失败原因。

### 崩溃恢复与一致性保障

系统需要处理提交过程、执行过程和状态更新过程中任意时刻的进程崩溃或存储不可用。

提交阶段的崩溃恢复依赖任务记录的原子写入。若在任务记录写入事务提交前崩溃，调用方不会收到确认响应（或收到超时错误），调用方使用相同幂等键重试时，系统按幂等规则处理——因事务未提交，任务表中不存在该幂等键的记录，系统将重新创建任务并写入消息。若在事务提交后、返回确认响应前崩溃，调用方同样会重试，此时任务表中已有 PENDING 记录，系统按幂等规则直接返回已有 task_id 和状态，不重复插入消息。

执行阶段的崩溃恢复通过任务状态机保证。调度器启动时扫描任务表中状态为 RUNNING 但心跳超过阈值（如两倍心跳周期）的记录，将其判定为已失联的遗留任务。对于遗留任务，系统检查其关联会话中消息的完整性：如果用户消息已完整写入但模型尚未产生回复，则将任务回退为 PENDING 重新调度；如果模型已产生部分推理结果（如中间工具调用结果已持久化），系统利用 Think 现有的会话恢复机制从最后一个检查点继续执行，而不是从头重放。任务状态在恢复时更新为 RUNNING 并绑定新的执行者。

### 状态查询、取消与清理

系统向外部调用方提供三个管理面接口：状态查询、取消和清理。

状态查询接口接受 task_id 或幂等键作为输入，返回任务当前状态、创建时间、最后更新时间、结果摘要（已完成时）以及执行进度指示（如已产生的工具调用次数）。查询操作是只读的，不改变任务状态。

取消接口接受 task_id 并设置 cancel_requested_at 标记。对于 PENDING 状态的任务，调度器在下一次尝试领取时检查该标记，若已设置则跳过执行并将任务状态直接更新为 CANCELLED。对于 RUNNING 状态的任务，取消信号通过 Think 现有的取消机制传递到执行引擎：执行引擎在下一个可中断点（如工具调用完成后、下一轮推理开始前）检查取消标记，若已设置则终止推理、将任务状态更新为 CANCELLED，并将已产生的中间结果保留在会话中供后续审计。已处于 COMPLETED、FAILED 或 CANCELLED 终态的任务不接受取消。

清理接口接受 task_id，将任务记录标记为已删除并从任务表中移除，同时可选择是否清理关联的会话和消息。清理操作仅对终态任务（COMPLETED、FAILED、CANCELLED）生效，处于 PENDING 或 RUNNING 状态的任务必须先取消再清理，防止清理正在执行的任务导致状态不一致。已清理的任务记录在保留窗口内可通过归档日志审计，超过保留窗口后物理删除。

### 与现有聊天路径的兼容

本方案的关键设计原则是不重写 Think agent 现有的普通聊天路径。具体而言：会话创建、消息写入、消息读取、模型推理、工具调用执行、流式事件产生、会话恢复和取消语义均保持现有实现不变。任务层作为薄层位于现有会话层之上：任务提交时，任务层调用现有的会话创建和消息写入接口（与普通聊天使用的是同一代码路径）；任务执行时，调度器将任务关联的会话标识传递给现有执行引擎，执行引擎以与处理普通聊天完全相同的方式处理该会话。

普通聊天会话与任务关联会话在存储层面完全统一：两者使用相同的会话表和消息表，区别仅在于任务关联会话在任务表中有一条对应的任务记录。普通聊天会话不经过任务提交接口，因此不存在对应的任务记录，不受任务状态机和调度器影响。这保证了已有交互方式完全不受任务系统引入的影响。

### 技术效果

本方案通过引入任务抽象层，在不大幅改动 Think agent 现有架构的前提下实现了以下技术效果。

第一，快速确认与异步解耦。外部调用方在任务记录和用户消息持久化后即获得确认，响应延迟从模型推理的秒级或分钟级降低到持久化写入的毫秒级。调用方与执行引擎在时间上解耦，不再需要维持长连接等待推理完成。

第二，精确一次语义。幂等键机制确保同一请求的多次重试不会导致重复插入用户消息或重复创建任务，保证在提交层面达到精确一次效果。结合任务状态机和条件领取机制，执行层面也避免同一任务被多个调度器实例重复执行。

第三，完整的生命周期可观察与可控。通过状态查询接口，外部系统可以在任务生命周期的任意时刻获知当前进度。通过取消和清理接口，外部系统可以在不需要等待推理完成时主动终止任务并回收资源，而非只能被动等待超时。

第四，崩溃恢复一致性。任务状态机与持久化任务记录结合，确保进程崩溃后系统可以自动发现遗留任务并决定恢复策略（重新调度或从检查点继续执行），不会丢失已提交的任务，也不会因崩溃而产生幽灵任务。

第五，对现有路径零侵入。任务层复用现有会话、消息、执行引擎和取消机制，普通聊天会话不经任务提交接口，其消息写入、推理执行和流式事件产生路径完全不受影响。系统只需新增任务表、任务提交接口和管理面接口，无需修改现有核心路径的任何代码。

### 风险与待确认问题

以下为当前方案中需要后续确认的技术风险点：第一，幂等键的保留窗口长度——需根据业务场景确定幂等键在任务表中保留的时长，平衡去重需求与存储成本；过短的保留窗口可能导致超出窗口的重试被当作新任务处理。第二，心跳周期的选择——需要在假阳性（正常任务被误判为失联）和恢复延迟之间权衡，建议心跳周期为 5-10 秒，失联判定阈值为两倍心跳周期。第三，取消操作的粒度——当前方案在工具调用完成后的检查点响应取消，若单次工具调用本身耗时较长（如大型代码搜索），取消延迟可能较大；是否需要支持工具调用执行过程中的中断取消，取决于底层工具执行框架是否支持中断信号。
