## 技术方案

### 技术问题与整体架构

Think agent 的现有会话模型以 user_input 事件为驱动入口，用户通过交互界面发送消息后，系统同步等待模型推理完成并返回结果。当外部系统（如 webhook、RPC 调用方或其他 Worker）需要向 Think agent 提交对话任务时，调用方无法仅得到一个快速的接收确认，而必须阻塞等待完整推理过程，这导致调用方资源占用、超时风险高，且在超时重试时可能重复插入消息或重复执行工作。

本方案在现有会话-轮次-消息-事件四层模型之上引入一个轻量级任务管理层，核心思路是：将外部提交建模为一次异步任务（Task），任务接收与模型推理执行在持久化层面解耦，通过任务表的持久状态作为快速确认与最终完成之间的唯一状态边界。整个方案由以下模块协作完成：(1) 任务提交与幂等去重模块；(2) 持久状态边界与崩溃恢复模块；(3) 执行领取与恢复模块；(4) 状态查询、取消与清理模块。

### 任务提交与幂等去重

系统新增一个任务提交接口（如 POST /tasks），接收外部调用方的任务请求。调用方在请求中提供目标会话标识、用户消息内容，以及一个由调用方生成的幂等键（idempotency_key）。系统处理流程如下：

- 接收请求后，首先以幂等键为索引查询任务表。若已存在相同幂等键的任务记录，则根据该记录的当前状态决定返回策略：若任务仍在运行或已成功完成，直接返回已有任务标识和当前状态，不创建新任务也不重复插入消息；若任务已失败或被取消，则启动新的执行尝试。
- 若幂等键不存在，系统在任务表中创建一条新记录，初始状态为 received，同时生成全局唯一的任务标识（task_id）。任务记录包含：task_id、幂等键、会话标识、原始用户消息载荷、状态（received）、创建时间、状态更新时间。
- 任务记录落盘成功后，系统立即向调用方返回 HTTP 202（Accepted），响应体中包含 task_id 和当前状态 received。至此，调用方确认接收完成，无需等待模型推理。
- 任务记录落盘后，系统异步将用户消息写入目标会话的事件日志（JSONL），写入格式复用现有 user_input 事件结构，事件中附加 task_id 字段以建立可追溯关联。消息写入成功后，任务状态从 received 变更为 queued，等待执行器领取。

### 持久状态边界与崩溃恢复

快速确认接收与模型推理最终完成之间的持久状态边界是方案的核心。该边界由任务表中的任务记录承载，任务状态机作为整个生命周期的权威状态源，消息写入和模型执行均为状态机推动的副作用操作。

任务状态机包含以下状态及转换规则：

- received：任务记录已创建、幂等键已登记，但用户消息尚未写入会话事件日志。此状态下崩溃恢复时，系统扫描 received 状态的任务记录，重新执行消息写入操作。由于幂等键已持久化，即使提交请求被重试，也不会创建重复任务记录。
- queued：消息已写入会话，任务等待执行器领取。此状态是任务进入执行调度队列的标志。
- running：执行器已领取任务，模型推理正在进行中。任务记录中写入 worker_id 和领取时间戳，用于崩溃恢复时的孤儿任务检测。
- completed：模型推理成功完成，agent_message 事件已写入会话事件日志。任务记录中写入完成时间和最终消息标识。
- failed：模型推理失败。任务记录中写入失败原因。调用方可通过重试接口触发新的执行尝试，系统将任务状态重置为 queued 并递增尝试计数。
- cancelled：调用方通过取消接口主动终止任务。已在执行的推理操作被通知停止，任务状态变更为 cancelled。

所有状态写入均为先写任务表、再执行对应副作用操作（消息写入、模型调度、结果回写）的顺序。若副作用操作失败而状态已更新，恢复机制通过检测状态与副作用产物的不一致来自动补偿。

### 执行领取与恢复

系统设置一个后台执行器（Executor），以轮询或条件触发方式从任务表中选取状态为 queued 的任务进行执行。执行领取采用原子条件更新机制：执行器以"UPDATE tasks SET status='running', worker_id=?, claimed_at=? WHERE status='queued' LIMIT 1"的模式领取任务，保证同一任务不会被多个执行器实例并发领取。

模型推理执行路径直接复用现有 Think agent 的会话执行逻辑。执行器通过 task_id 关联到目标会话，从会话事件日志中定位到该任务对应的 user_input 事件，然后以该事件为起点调用现有的对话轮次执行函数。执行过程中产生的 agent_message、tool_call、tool_result 等事件按现有路径写入会话事件日志，仅在这些事件的 payload 中附加 task_id 以便追溯。

崩溃恢复场景下，系统启动时扫描状态为 running 且 claimed_at 超过预设超时阈值的任务记录，将其状态重置为 queued 并清空 worker_id，由执行器重新领取。对于 received 状态的任务，重新触发消息写入。对于 queued 状态的任务，由执行器正常领取。这种设计确保了任务表是崩溃后可恢复的唯一持久状态源。

流式执行方面，外部调用方可通过状态查询接口轮询或通过 webhook 回调获得中间推理片段（reasoning_content）。执行器在流式输出过程中，将中间状态和 token 流暂存于任务记录关联的临时缓冲区，查询接口可返回已生成的部分内容。

### 状态查询、取消与清理

系统提供以下管理接口：

- 状态查询（GET /tasks/{task_id}）：返回任务当前状态、创建时间、状态更新时间、尝试次数，若任务处于 running 状态则额外返回已生成的部分推理内容（流式片段）。该接口仅读取任务表，不触发副作用。
- 取消接口（POST /tasks/{task_id}/cancel）：将 received 或 queued 状态的任务直接标记为 cancelled，消息不被写入或不被执行。对于 running 状态的任务，系统向对应 worker 发送取消信号，复用现有 Think agent 的会话取消语义（中断当前轮次的推理流程），待 worker 确认终止后将任务状态变更为 cancelled。
- 删除/清理接口（DELETE /tasks/{task_id}）：对于 completed、failed 或 cancelled 的终态任务，将其任务记录标记为 deleted 或物理删除。对 running 状态的任务，先触发取消再标记删除。已写入会话的消息事件按现有保留策略处理，任务清理不影响会话的历史事件完整性。
- 列表查询（GET /tasks?session_id=...&status=...）：按会话和状态筛选任务列表，用于管理面观测。

### 与现有消息保存路径的兼容设计

本方案的关键设计原则是不重写现有普通聊天消息的保存和执行路径。具体兼容策略如下：

- 现有 user_input 事件驱动的交互式对话路径完全保留。用户通过交互界面发起的会话继续以同步方式工作，不受任务管理层影响。
- 任务提交路径仅在 user_input 事件写入前增加了一层任务记录包装，user_input 事件的存储格式与现有格式完全兼容。任务在会话事件日志中产生的 user_input 事件与交互式产生的 user_input 事件共享同一事件序列（seq），通过 task_id 字段区分来源。
- 模型推理执行路径不变。执行器领取任务后调用的仍是现有对话轮次执行函数，agent_message、tool_call、tool_result 等事件的生成和持久化路径无任何修改。
- 取消语义复用现有会话的 round 级取消机制，不引入新的取消协议。
- 会话的恢复（resume）逻辑不变。会话恢复时，系统按事件序列重放历史事件；若某条 user_input 事件关联的 task_id 对应的任务尚未完成，恢复时可选择仅重放已生成的响应事件或等待任务完成后继续。

### 技术效果与风险确认

本方案带来的技术效果包括：(1) 调用方解耦：外部系统提交任务后立即获得确认，无需阻塞等待推理完成，消除了长时间连接的超时风险和资源占用；(2) 幂等安全：基于幂等键的任务去重机制确保网络重试不会造成重复消息插入或重复执行，保证了外部触发场景下的数据一致性；(3) 崩溃可恢复：任务表作为快速确认与模型推理完成之间的唯一持久状态边界，任何阶段的崩溃均可通过任务表状态扫描自动恢复；(4) 路径兼容：现有交互式聊天、消息保存、流式执行、恢复和取消路径均无需重写，仅在事件中增加可选的 task_id 关联字段。

待确认的风险点：(1) 任务表的存储后端选择——若采用关系数据库，需要评估与现有 JSONL 事件日志之间的一致性保证策略；若采用与事件日志相同的文件存储，则需要设计合适的索引结构以支持按幂等键和状态的快速查询；(2) 执行器的领取机制在高并发场景下的性能表现，特别是原子条件更新的锁竞争；(3) 流式执行中间片段在任务表中的暂存策略对存储空间的影响。
