## 技术方案

本技术方案针对外部系统（如 webhook、RPC 调用方、后台 Worker）向 Think agent 提交对话任务的场景，设计了一套可靠的任务提交、追踪和控制机制。核心思路是在现有会话-消息-流式执行架构之上，引入一层轻量级的"任务接入层"，将外部调用的接收确认与模型推理执行解耦，并通过幂等键、持久化任务状态机和条件领取机制，覆盖从快速确认到最终完成之间的全部持久状态边界。

### 技术问题分析

在 Think agent 的现有交互模式中，外部调用方通过会话接口提交用户消息后，需要同步等待模型推理完成才能获得响应。当模型推理耗时较长（如复杂推理、长文本生成）时，调用方必须维持长连接或持续轮询，增加了客户端的实现复杂度和资源占用。此外，如果网络中断或调用方超时重试同一请求，现有机制缺乏幂等保障，可能导致同一用户消息被重复写入会话并触发重复推理。

需要解决的核心技术问题是：在"向调用方快速返回已接收确认"与"模型推理最终完成"之间存在一段异步执行的持久状态边界。系统需要在这个边界内可靠地管理任务的全生命周期——包括提交去重、执行前崩溃恢复、执行中状态追踪、取消与清理——同时不重写现有的会话消息保存路径和流式推理机制。

### 整体架构

方案在现有 Think agent 架构之上增设以下关键模块，整体采用"接收层—存储层—执行层"三层分离的设计：

- 任务接入端点（Task Ingestion Endpoint）：对外暴露 HTTP/RPC 接口，接收外部调用方提交的对话任务请求，负责幂等校验、生成任务标识，并在任务记录持久化完成后立即返回"已接收"确认。
- 任务存储层（Task Store）：以持久化存储（如数据库或持久化日志）维护任务记录，每个任务记录包含任务标识、幂等键、关联会话标识、消息载荷、当前状态、创建时间、更新时间及执行结果引用。该层是"快速确认"与"推理完成"之间的持久状态载体。
- 任务执行器（Task Executor）：以后台工作循环方式运行，通过原子条件领取（conditional claim）从存储层获取处于"待执行"状态的任务，驱动其进入现有会话-消息-推理管线完成执行，并在执行完成后更新任务最终状态。
- 任务管理接口（Task Management API）：提供状态查询、取消和清理能力，供外部调用方在任务提交后追踪和控制任务生命周期。

### 任务状态机与持久化边界

任务在其生命周期内经历以下状态，每个状态转换均以持久化写入为边界条件：

| 状态 | 含义 | 写入时机 | 可转换至 |
| --- | --- | --- | --- |
| PENDING | 任务已持久化、已向调用方返回确认，等待执行器领取 | 任务接入端点完成幂等校验和任务记录写入后 | RUNNING, CANCELLED |
| RUNNING | 执行器已领取任务，正在驱动会话推理 | 执行器通过原子条件更新（PENDING→RUNNING）成功后 | COMPLETED, FAILED, CANCELLING |
| COMPLETED | 模型推理成功完成，会话中存在完整的用户消息和助手回复 | 推理管线正常结束后，执行器更新任务状态 | （终态） |
| FAILED | 推理过程中发生不可恢复错误 | 执行器捕获异常后更新 | （终态） |
| CANCELLING | 外部调用方请求取消，等待当前推理停止 | 任务管理接口收到取消请求后更新 | CANCELLED |
| CANCELLED | 取消完成，推理已停止且资源已释放 | 执行器检测到取消信号并完成清理后更新 | （终态） |

关键持久化边界如下：（1）任务记录必须在向调用方返回"已接收"确认之前完成持久化写入，避免确认发出后崩溃导致任务丢失；（2）状态从 PENDING 到 RUNNING 的转换必须通过原子条件更新实现，防止多个执行器实例并发领取同一任务；（3）用户消息写入会话的操作不要求在任务确认前完成——消息写入是执行器领取任务后的职责，复用现有会话消息保存路径。

### 幂等提交与快速确认机制

外部调用方在提交任务请求时，必须携带一个由调用方生成的幂等键（idempotency key）。任务接入端点按以下流程处理：

1. 以幂等键查询任务存储层：若已存在相同幂等键的任务记录，则直接返回该任务的当前状态和任务标识，不创建新任务，不重复写入消息——实现提交层面的幂等。
2. 若幂等键不存在：生成唯一的任务标识（task_id），构造包含幂等键、关联会话标识（可复用已有会话或由系统自动创建）、消息载荷、初始状态 PENDING 和时间戳的任务记录。
3. 将任务记录原子写入持久化存储；写入成功后立即向调用方返回 HTTP 202 或等效的"已接收"响应，响应体中包含 task_id 和初始状态。
4. 写入失败时向调用方返回错误，调用方可安全重试（重试因幂等键保护不会产生副作用）。

幂等键的保留窗口由系统配置决定（例如 24 小时或 7 天），超出保留窗口的幂等键可被清理以回收存储空间。在保留窗口内，同一幂等键的重复请求始终返回幂等结果。幂等键与任务标识的映射关系也持久化存储，以支持崩溃恢复后的幂等查询。

### 任务执行、领取与崩溃恢复

任务执行器采用后台工作循环，通过原子条件领取机制从存储层获取待执行任务，具体流程如下：

1. 条件领取：执行器以原子操作执行"UPDATE tasks SET status='RUNNING', claimed_by=<executor_id>, claimed_at=<now> WHERE status='PENDING' LIMIT 1"（或等效的乐观锁/行级锁操作），确保同一任务不会被多个执行器实例同时领取。
2. 会话复用或创建：领取成功后，执行器检查关联的会话标识。若会话已存在（如调用方指定复用已有会话），则使用已有会话；若不存在，则通过现有会话创建路径新建会话。
3. 消息写入：执行器通过现有的会话消息保存路径，将任务携带的消息载荷写入会话。写入操作本身具备幂等性——在写入前检查该轮（round）内是否已存在内容相同的用户消息，防止崩溃恢复时重复写入。
4. 推理驱动：消息写入完成后，执行器通过现有的流式推理接口触发 agent 推理，复用现有的流式执行、工具调用、中间步骤回传等全部语义。
5. 终态更新：推理完成后（成功或失败），执行器更新任务状态为 COMPLETED 或 FAILED，并在任务记录中写入结果引用（如消息标识列表）或错误信息。

崩溃恢复机制：系统启动时，执行器扫描存储层中所有处于 RUNNING 状态且 claimed_at 超过可配置超时阈值（如 5 分钟）的任务——这些任务对应的执行器实例可能已崩溃。对于每个候选恢复任务：（1）检查关联会话中消息写入的完成情况：若用户消息已写入但无助手回复，则直接重新驱动推理（消息写入已完成，无需重复）；（2）若用户消息尚未写入，则通过幂等键检查是否已有相同消息——如有则跳过写入，如无则写入后驱动推理。恢复执行器通过原子条件更新重新认领任务（更新 claimed_by 和 claimed_at），防止多个恢复执行器同时处理同一任务。

### 状态查询、取消与清理

状态查询接口（GET /tasks/{task_id}）返回任务的当前状态、创建时间、最后更新时间、关联会话标识以及（若已完成）结果引用。查询操作仅读取任务记录，不修改状态，可被任意频次调用。对于处于 RUNNING 状态的任务，查询接口可选地返回推理进度信息（如已生成的 token 数、中间工具调用步骤），该信息从现有的流式推理状态中获取，不额外维护进度存储。

取消机制复用现有的推理取消语义：当外部调用方通过取消接口（POST /tasks/{task_id}/cancel）请求取消时，系统先将任务状态更新为 CANCELLING，然后向正在执行的推理会话发送取消信号。取消信号沿现有的推理取消路径传播——中止模型调用、清理工具调用中间态、释放执行资源。推理管线确认取消完成后，执行器将任务状态更新为 CANCELLED。若任务尚处于 PENDING 状态尚未被领取，取消操作直接将状态从 PENDING 转为 CANCELLED，无需经过 CANCELLING。

清理接口（DELETE /tasks/{task_id}）用于移除已完成终态（COMPLETED、FAILED、CANCELLED）的任务记录。清理操作可选择仅删除任务记录而保留会话数据，或同时清理关联会话（由调用方通过参数指定）。系统还运行后台清理任务，定期移除超过保留期的终态任务记录，防止任务存储层无限增长。处于 PENDING 或 RUNNING 状态的任务不可被清理，必须先取消至终态。

### 与现有系统的兼容关系

本方案的设计核心原则是不重写现有系统路径，具体兼容策略如下：

- 会话管理：任务执行器通过现有的会话创建/查询接口操作会话，不引入新的会话存储格式或管理逻辑。外部任务创建的会话与普通聊天创建的会话在存储层面没有区别。
- 消息保存：用户消息和助手回复的写入完全复用现有的会话消息保存路径。任务执行器在消息写入环节仅充当"触发者"角色，消息的持久化格式、索引和查询方式均不变。
- 流式推理：推理执行完全通过现有的流式推理接口驱动，复用流式 token 输出、工具调用往返、中间推理步骤等全部机制。任务层不干预推理管线内部逻辑。
- 取消语义：取消操作通过现有的推理取消路径传播，任务层的 CANCELLING→CANCELLED 状态流转仅作为对现有取消机制的外层包装和可观察接口。
- 普通聊天路径：直接通过会话接口发起的普通聊天不受任何影响——消息写入、推理执行和响应返回的路径完全不经过任务层。

通过以上设计，任务接入层作为一个薄层叠加在现有系统之上：它只负责任务的持久化生命周期管理和外部可观察接口，所有核心执行路径——会话、消息、流式推理、取消——均沿用现有实现。

### 技术效果

本方案带来的技术效果包括：

- 接收与执行解耦：外部调用方在任务记录持久化完成后即获得确认，延迟从模型推理时长缩短为单次持久化写入时长，显著降低客户端等待开销和连接占用。
- 可靠的状态边界：从 PENDING 到终态的每个状态转换均以持久化写入为前提，崩溃恢复机制确保任何时刻的系统崩溃不会导致已确认任务丢失或重复执行。
- 端到端幂等：幂等键机制从提交入口即拦截重复请求，结合消息写入前的重复检查，确保无论调用方重试多少次、在哪个环节重试，都不会产生重复消息或重复推理。
- 并发安全：条件领取（原子状态转换）机制保证多个执行器实例并发运行时不会重复领取同一任务，无需引入分布式锁。
- 兼容现有路径：会话、消息、流式推理和取消的现有实现完整保留，任务接入层作为独立薄层叠加，降低引入缺陷风险和改造工作量。
- 外部可观察性：通过标准化的任务状态查询接口，外部调用方可以异步追踪任务进展，无需维持长连接或自行实现轮询逻辑。

### 风险与待确认问题

以下事项需要在具体实施前结合现有代码库确认：

- 幂等键生成策略：方案假定幂等键由调用方生成。需确认是否需要系统也支持服务端生成的幂等键（如基于请求内容哈希），以及两种模式的共存策略。
- 执行器并发模型：原子条件领取依赖存储层提供"SELECT ... FOR UPDATE"或等效的原子操作。需确认当前项目使用的数据库或持久化日志是否支持该能力；若不支持，需要引入替代方案（如单实例执行器 + 故障转移）。
- 流式推理中的取消传播延迟：取消信号传播到模型推理停止之间存在时间窗口，需确认现有推理管线是否支持在工具调用间隙检查取消信号，以及最坏情况下的取消延迟是否可接受。
- 任务与会话的生命周期耦合：删除任务记录时是否同时删除关联会话需要明确的策略。若保留会话数据，需确认会话查询接口能否区分"由外部任务创建"和"由普通聊天创建"的会话。
- 幂等键保留窗口与存储膨胀：需根据实际调用量评估幂等键映射表和任务记录表的存储增长速率，设定合理的保留窗口和清理策略。
