## 技术方案

### 技术问题概述

本方案要解决的核心问题是在具备单一 agent 执行能力的系统中，构建支持同一用户下多个独立聊天会话的 assistant 系统。现有系统中，agent 以单一执行上下文运行，所有消息历史、配置和工具调用共享同一命名空间。当用户需要同时处理多个独立任务时（例如一个会话用于前端开发、另一个用于数据分析），单一 agent 上下文会导致消息历史混杂、会话配置互相干扰、工作区文件操作冲突等问题。

具体而言，方案需要解决以下技术子问题：第一，如何在共享用户级资源（workspace 文件、MCP 连接、OAuth 凭据）的同时，保持各会话的 agent 执行上下文完全隔离；第二，如何防止子会话绕过父级控制直接访问共享资源或执行原始 MCP 工具调用；第三，如何实现文件变更的实时多端同步，减少前端轮询开销；第四，如何防止用户通过猜测会话标识访问或创建未授权的子会话；第五，如何合理分配定时任务和跨会话全局任务的执行职责。

### 整体架构：用户级父Agent与会话级子Agent

本方案在现有单一 agent 执行体系之上引入两层实体结构：用户级父 Agent（UserParentAgent）和会话级子 Agent（SessionChildAgent）。父 Agent 以 Durable Object 风格持久存在于用户账号生命周期内，负责管理用户级共享资源、协调子 Agent 生命周期、执行全局任务调度以及对外暴露管理面接口。每个子 Agent 同样以 Durable Object 风格独立持久化，对应一个聊天会话，拥有独立的消息历史、执行上下文、分支状态和个性化配置。

父 Agent 的核心职责包括：(1) 维护用户级会话注册表，记录该用户下所有子会话的标识、元数据和生命周期状态；(2) 持有用户级共享资源的真实状态，包括 workspace 文件系统引用、MCP 服务器连接池和 OAuth 令牌缓存；(3) 作为子会话访问共享资源的唯一代理入口，所有子会话的资源读写和工具调用请求必须经过父 Agent 的路由和鉴权；(4) 管理全局定时任务调度器，负责跨会话摘要、定期清理等不隶属于任何单一会话的后台任务；(5) 广播文件变更事件至已订阅的浏览器标签页或会话面板。

子 Agent 的核心职责包括：(1) 维护本会话独立的消息历史、对话分支树和 Think agent 推理状态；(2) 持有会话级配置，如系统提示词、模型偏好、温度参数和启用的扩展列表；(3) 通过父 Agent 提供的受控代理接口访问 workspace 文件和 MCP 工具，子 Agent 自身不持有任何 MCP 连接句柄或 OAuth 令牌；(4) 执行本会话范围内的 agent 推理和工具调用编排，但工具的实际执行由父 Agent 代理转发。

### 会话隔离机制

每个会话级子 Agent 以独立的 Durable Object 实例运行，拥有独立的存储分区。会话隔离分为以下几个维度：(1) 消息历史隔离——每个子 Agent 维护自己的消息日志（如 sess_{id}.jsonl），消息的追加、读取和恢复操作仅作用于本会话分区；(2) 配置隔离——系统提示词、模型参数、扩展列表等配置以会话为粒度存储于子 Agent 的状态中，不同会话可拥有完全不同的配置而互不干扰；(3) 分支隔离——对话分支树（用于支持用户回溯和重新生成回复）按会话独立管理，分支节点引用本会话内的消息标识。

(4) 记忆隔离——每个会话可拥有独立的长期记忆存储（如向量索引或摘要缓存），父 Agent 不合并子会话的记忆数据；(5) 执行状态隔离——子 Agent 的 chat recovery 检查点、Think agent 推理中间态、当前运行轮次标识（running_round_id）均在子 Agent 的 Durable Object 状态内管理，一个会话的崩溃或恢复不影响其他会话。会话之间的数据隔离边界明确：消息历史、配置、分支、记忆和执行状态是会话私有的；workspace 文件、MCP 连接、OAuth 凭据和文件变更事件是用户共享的。

### 共享资源代理层

为解决子会话安全访问共享资源的问题，方案在父 Agent 内部设立共享资源代理层（ResourceProxy）。该代理层是子会话访问 workspace 文件、MCP 工具和 OAuth 授权结果的唯一通道。子 Agent 在执行过程中需要读写文件或调用外部工具时，不直接持有文件句柄或 MCP 客户端连接，而是向父 Agent 发起受控代理请求，由父 Agent 的资源代理层完成实际 I/O 操作或工具调用后返回结果。

Workspace 文件代理：父 Agent 持有用户级 workspace 根目录的文件系统引用。子 Agent 通过代理请求指定读/写路径和操作类型，父 Agent 在执行前进行路径合法性校验（确保操作范围不超出用户 workspace），然后将操作结果返回子 Agent。多个子会话对同一文件的并发写入由父 Agent 内的文件锁机制协调，避免写冲突。文件变更完成后，父 Agent 生成文件变更事件并通过发布-订阅通道推送给已连接的浏览器标签页。

MCP 工具代理：父 Agent 维护用户级的 MCP 连接池，管理所有已配置的 MCP 服务器连接的生命周期（建立、心跳、重连、关闭）。当子 Agent 的推理过程需要调用某 MCP 工具时，子 Agent 生成工具调用意图（包含工具名称和参数），通过代理请求发送至父 Agent。父 Agent 从连接池中获取或创建对应的 MCP 连接，执行工具调用，并将结果返回子 Agent。子 Agent 在整个过程中不接触 MCP 服务器的连接凭据、端点地址或原始协议握手。

OAuth 授权代理：用户通过任意子会话触发的 OAuth 授权流程，其授权回调由父 Agent 统一接收和处理。父 Agent 将授权获得的访问令牌和刷新令牌以用户为粒度安全存储（如加密后存入用户级令牌缓存），并为所有子会话提供统一的令牌获取接口。子会话在需要访问 OAuth 保护的外部服务时，通过父 Agent 获取有效令牌（父 Agent 负责判断令牌是否过期并自动刷新），子会话自身不存储任何第三方授权凭据。

### 访问控制与安全机制

方案设计了多层访问控制机制，防止用户绕过父 Agent 直接操作子会话或共享资源。第一层：会话注册表校验。父 Agent 维护的会话注册表是用户下所有合法子会话的唯一权威来源。任何对子会话的访问请求（包括通过会话 ID 的读取、写入和管理操作）必须先经过父 Agent 的注册表查询校验；若会话 ID 不在当前用户的注册表中，请求被拒绝并记录安全事件。

第二层：子 Agent 创建管控。新会话的创建必须通过父 Agent 的会话管理接口（如 createSession），由父 Agent 生成不可预测的会话标识（使用密码学随机数生成器），并将新会话注册到用户级会话注册表中。前端或 API 层不允许直接构造会话 ID 或绕过父 Agent 创建子 Agent 实例。第三层：工具调用代理强制。子 Agent 在执行工具调用时，框架层面确保工具调用的实际执行路径必须经过父 Agent 的资源代理层。子 Agent 的 Durable Object 实例中不包含任何 MCP 客户端连接对象或文件系统直接访问能力，从架构层面杜绝绕过代理的可能性。

第四层：会话生命周期绑定。每个子 Agent 的 Durable Object 在创建时记录其归属的用户标识和父 Agent 引用，运行时的每一次状态读写和外部交互请求都附带该归属校验。当用户账号被禁用或删除时，父 Agent 负责级联清理该用户下所有子会话的持久化状态。第五层：操作审计。父 Agent 对所有子会话的资源访问和工具调用进行日志记录，形成按用户维度的统一审计追踪，便于异常检测和安全回溯。

### 实时同步机制

方案设计了基于发布-订阅模式的文件变更实时同步机制，避免前端轮询带来的延迟和资源浪费。父 Agent 作为事件发布中心，在每次 workspace 文件发生变更（创建、修改、删除、重命名）后，生成标准化的文件变更事件（包含文件路径、变更类型、时间戳和可选的变更摘要），通过 WebSocket 或 Server-Sent Events 通道推送至已建立连接的浏览器标签页和会话面板。

每个浏览器标签页在建立与父 Agent 的连接时，向父 Agent 注册自己的订阅信息（包含用户标识和当前活跃会话标识）。父 Agent 维护一个用户级的订阅者列表。当文件变更事件产生时，父 Agent 遍历该用户的订阅者列表，向每个在线订阅者推送事件。订阅者（前端）收到事件后，根据事件中的文件路径判断是否需要刷新当前视图（例如文件树、编辑器内容或预览面板），实现精准刷新而非全量重载。

对于因网络断开而错过事件的订阅者，父 Agent 维护一个按用户维度的事件序列号（递增计数器）。订阅者重连时携带最后收到的事件序列号，父 Agent 返回该序列号之后的所有未推送事件，实现断线重连后的事件补推。该机制复用了现有系统中 chat recovery 的序列号管理思路，将事件序列号与会话消息序列号统一在同一序列空间内管理。

### 定时任务与全局调度机制

方案将定时任务和跨会话全局任务的执行职责明确划归父 Agent，避免任务调度逻辑散落在各子 Agent 中。父 Agent 内嵌一个轻量级定时任务调度器（Scheduler），支持 cron 表达式和固定间隔两种触发模式。调度器维护一个用户级的任务定义表，每条任务记录包含任务标识、触发条件、任务类型、目标会话范围（全局或指定会话列表）和执行负载描述。

典型的全局任务类型包括：(1) 跨会话摘要——父 Agent 定期读取用户下所有活跃子会话的近期消息摘要，生成用户级工作日报或周报；(2) 过期会话清理——父 Agent 根据会话的最后活跃时间，对长期未活跃的会话执行归档或状态冻结；(3) 定时提醒——用户在任意会话中设置的定时提醒，由父 Agent 统一调度，到期时向对应会话或用户通知通道推送提醒。定时任务的触发和执行在父 Agent 的 Durable Object 生命周期内完成，不依赖任何特定子会话的存活状态。

调度器的持久化与恢复：任务定义表作为父 Agent Durable Object 状态的一部分持久存储。当父 Agent 因升级或崩溃重启时，调度器从持久化状态中恢复所有任务定义，并基于当前时间与任务上次执行时间的关系判断是否需要立即补偿执行错过的任务。对于需要跨会话收集信息的全局任务，父 Agent 通过子 Agent 暴露的标准查询接口获取所需数据（如近期消息摘要），而非直接读取子 Agent 的原始存储，保持访问路径的规范性。

### 关键处理流程

以下描述本方案中若干关键流程的详细执行步骤。

会话创建流程：(1) 前端发起创建会话请求，携带用户标识和初始配置（如会话名称、系统提示词等）。(2) API 层将请求路由至对应用户的父 Agent。(3) 父 Agent 校验用户标识合法性后，生成密码学随机会话 ID，在会话注册表中创建新条目（包含会话 ID、名称、创建时间、状态等元数据）。(4) 父 Agent 触发子 Agent Durable Object 的初始化，传入会话 ID 和初始配置。(5) 子 Agent 完成自身状态初始化（包括空消息历史、默认配置和初始分支根节点），返回创建成功确认。(6) 父 Agent 将新会话信息返回前端，前端在侧边栏中展示新会话条目并自动切换至该会话。

工具调用代理流程：(1) 子 Agent 在推理过程中决定调用某 MCP 工具或读写文件，生成工具调用请求（包含工具名称、参数和调用标识）。(2) 子 Agent 将工具调用请求通过内部代理通道发送至父 Agent 的资源代理层。(3) 父 Agent 校验请求来源的会话 ID 是否在注册表中且状态正常，校验工具名称是否在用户已配置的 MCP 工具白名单中。(4) 对于 MCP 工具调用，父 Agent 从连接池获取对应 MCP 服务器的连接，发送工具调用请求并等待响应。(5) 父 Agent 将工具执行结果（成功结果或错误信息）返回子 Agent。(6) 子 Agent 将工具结果纳入推理上下文，继续生成后续回复内容。(7) 若工具调用涉及文件变更，父 Agent 在工具结果返回后额外发布文件变更事件。

会话切换与状态恢复流程：(1) 用户在侧边栏点击目标会话，前端向父 Agent 发起会话激活请求。(2) 父 Agent 校验目标会话归属和状态后，将该会话标记为用户当前活跃会话，同时保存前一会话的执行检查点。(3) 父 Agent 向目标子 Agent 的 Durable Object 发送激活信号，子 Agent 从持久化状态中恢复消息历史、分支树和 Think agent 推理状态。(4) 若子 Agent 存在未完成的执行轮次（通过 running_round_id 和 is_busy 标记判断），子 Agent 执行 chat recovery 流程，从最近的检查点恢复并重放未完成的消息。(5) 前端收到激活确认后，加载该会话的消息列表和配置，建立与该会话对应的事件订阅通道。

### 与现有系统的复用关系

本方案在现有系统的基础上进行扩展，最大程度复用已有组件。具体复用关系如下：(1) Durable Object 运行时——父 Agent 和子 Agent 均基于现有 Durable Object 风格的 agent 运行时构建，复用其持久化状态管理、自动恢复和序列号机制。project.json 中已有的 active_session_id、running_session_id、running_round_id 和 is_busy 字段扩展至子 Agent 粒度，每个子 Agent 独立管理这些状态字段。(2) Chat Agent 和 Think Agent——子 Agent 直接复用现有 chat agent 的消息处理和 Think agent 的推理链路，不需重新实现对话生成和推理逻辑。

(3) Workspace——现有 workspace 的文件管理能力由父 Agent 统一持有，子 Agent 通过代理接口间接使用，workspace 的核心实现（文件树构建、读写操作、路径解析）不需修改。(4) MCP 工具连接——现有 MCP 客户端连接管理逻辑提升至父 Agent 的资源代理层，连接池管理、心跳检测和重连策略复用，仅将调用入口从子 Agent 的直接调用改为代理转发。(5) Chat Recovery——现有 chat recovery 的检查点保存和恢复机制按子 Agent 粒度独立运行，恢复逻辑本身复用不改动。(6) 子 Agent 路由——现有子 agent 路由机制扩展为支持按会话 ID 路由至对应子 Agent Durable Object。

### 技术效果

本方案带来的技术效果包括：(1) 会话级强隔离——通过为每个会话分配独立的 Durable Object 实例和存储分区，消息历史、配置、分支和记忆在物理层面隔离，一个会话的状态异常不会污染其他会话，用户可同时进行多个独立任务而不产生上下文混淆。(2) 共享资源安全复用——通过父 Agent 的资源代理层，MCP 连接和 OAuth 令牌实现用户级复用，用户授权一次即可在所有会话中使用相同工具，同时杜绝了子会话直接持有敏感凭据的安全风险。

(3) 低延迟实时同步——基于发布-订阅模式和事件序列号的推送机制，文件变更可在毫秒级通知到所有在线订阅者，消除前端轮询的带宽和延迟开销；事件补推机制保证断线重连后状态最终一致。(4) 安全的多会话管理——会话注册表、密码学随机 ID 生成和归属校验构成纵深防御，防止会话 ID 猜测、越权访问和绕过父 Agent 直接创建子会话的攻击面。(5) 全局任务集中调度——定时任务和跨会话摘要由父 Agent 统一管理，避免任务逻辑在多子 Agent 中重复实现，任务状态在父 Agent 持久化存储中集中可审计，系统重启后任务可自动恢复。(6) 架构演进平滑——方案以最小侵入方式扩展现有 agent 体系，核心推理、消息处理和恢复机制无需重写。

### 风险与待确认问题

以下列出方案中需要后续确认和关注的风险点：(1) 父 Agent 单点性能——所有子会话的工具调用和文件操作均经过父 Agent 代理，在高并发场景下父 Agent 可能成为性能瓶颈。建议后续对父 Agent 的资源代理层进行压力测试，必要时对连接池和文件操作引入异步队列和批量处理机制。(2) 跨会话事务一致性——当一次用户操作涉及多个子会话的状态变更时（如批量删除会话），需要确认现有 Durable Object 体系是否支持跨实例的事务协调，或是否需要引入补偿型最终一致性方案。

(3) 会话迁移与负载均衡——当用户会话数量增长时，不同子 Agent 的 Durable Object 可能分布在不同的物理节点上，需要确认现有 Durable Object 路由机制是否支持按用户亲和性调度以减少跨节点代理延迟。(4) MCP 连接池上限——每个 MCP 服务器类型可能需要独立的连接，当用户配置了大量 MCP 服务器且多个子会话同时使用时，连接池规模需要合理限制和淘汰策略。(5) 事件推送的浏览器兼容性——Server-Sent Events 和 WebSocket 在不同网络环境（代理、防火墙）下的可用性需要验证，可能需要提供降级到轮询的兜底方案。(6) 现有系统接口兼容性——方案对现有 agent 工具调用路径的改造范围需要进一步评估，确认是否影响现有的单会话模式下的功能和性能。
