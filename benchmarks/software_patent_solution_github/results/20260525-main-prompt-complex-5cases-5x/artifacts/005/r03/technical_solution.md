## 技术方案

本方案在 Think agent 现有会话管理、消息持久化、流式执行、恢复与取消机制的基础上，增加一个异步任务层，使外部系统（webhook、RPC 调用方或其他 Worker）能够以非阻塞方式提交对话任务、快速获得接收确认，并在后续对任务进行状态追踪与控制，同时保证重复提交的幂等性和崩溃恢复的安全性。

### 1. 技术问题概述

在现有 Think agent 体系中，外部系统触发一次 agent 对话任务通常意味着调用方需要同步等待模型推理完成。这带来两个问题：一是调用方长时间阻塞，占用连接和计算资源；二是当网络不稳定或调用方超时重试时，缺乏机制防止同一请求被重复插入为多条用户消息、导致重复推理。本方案要解决的核心问题是：在"快速确认接收"和"模型推理最终完成"之间建立可靠的持久状态边界，使得外部调用方可以异步提交、追踪和控制 agent 对话任务，同时不重写现有普通聊天消息的保存路径和会话管理逻辑。

### 2. 整体架构与核心数据结构

本方案在 Think agent 现有会话（Session）层之上引入一个独立的任务（Job）层。任务层负责管理异步任务的完整生命周期，包括接收、去重、持久化、领取执行和终态管理；会话层继续负责消息存储、流式推理、取消和恢复等现有语义。两层之间通过任务状态机进行耦合，任务层不修改会话内部的消息写入逻辑。

核心数据结构包括：

- 任务记录（Job Record）：包含任务标识、幂等键、关联会话标识、任务状态、输入载荷、创建时间、最后更新时间、领取者标识等字段，持久化在可靠存储中。
- 幂等键（Idempotency Key）：由外部调用方在提交时提供，或由系统根据请求内容摘要生成，用于判定重复提交。
- 任务状态机：覆盖"已接收（received）→ 已领取（claimed）→ 执行中（running）→ 已完成（completed）/ 已失败（failed）/ 已取消（cancelled）/ 已清理（cleaned）"等状态，并明确每个状态的进入条件、持久化时机和转换规则。

### 3. 任务提交与快速确认流程

外部调用方通过统一的异步提交接口（如 POST /tasks）向 Think agent 提交一次对话任务。提交时需提供：会话标识（或由系统新建会话）、用户消息内容、以及幂等键。系统处理流程如下：

1. 幂等检查：系统以幂等键查询任务存储，若已存在相同幂等键的任务记录，则直接返回已有记录的当前状态，不创建新任务、不写入新消息。这解决了因网络超时或调用方重试导致的重复提交问题。
2. 创建任务记录：若幂等键不存在，系统在任务存储中原子写入一条状态为"已接收（received）"的任务记录，包含生成的任务标识、幂等键、关联会话标识、输入载荷和时间戳。此写入操作是后续所有流程的基础持久化点。
3. 快速返回确认：任务记录成功持久化后，系统立即向调用方返回 HTTP 202 Accepted 响应，携带任务标识和当前状态，无需等待模型推理开始或完成。此时用户消息尚未写入会话，推理尚未触发。

### 4. 持久状态边界与崩溃恢复

本方案的关键创新在于明确定义了任务状态机中每个状态的持久化时机和崩溃恢复行为，使系统在任意时刻崩溃后均可正确恢复，不会出现消息重复写入或任务丢失。

状态转换规则如下：

- 已接收（received）→ 已领取（claimed）：由执行器（Executor）在原子领取任务时转换。领取操作使用条件更新（compare-and-swap），仅当当前状态为 received 且领取者标识为空时才成功。领取成功后写入领取者标识和时间戳并持久化，再向会话写入用户消息。若在写入用户消息前崩溃，恢复后其他执行器可重新领取该任务；若在写入用户消息后、更新状态为 running 前崩溃，恢复时通过消息去重逻辑保证不会重复写入。
- 已领取（claimed）→ 执行中（running）：在用户消息成功写入会话、推理已触发后转换。此转换持久化 running 状态。若在消息写入后、状态更新前崩溃，恢复时执行器检查会话中是否已存在对应用户消息，若已存在则跳过消息写入并继续推进到 running。
- 执行中（running）→ 已完成（completed）/ 已失败（failed）：推理正常结束或异常终止时转换，终态持久化。
- 任意非终态 → 已取消（cancelled）：外部调用方通过取消接口请求取消。若任务尚未被领取，直接标记为 cancelled；若已被领取或正在执行，系统复用现有会话级取消机制中断推理，然后将任务标记为 cancelled。
- 已取消/已完成/已失败 → 已清理（cleaned）：通过清理接口移除关联资源后转换，或由定时清理任务自动完成。

消息写入与任务状态的关键时序边界在于：用户消息只有在任务状态从 received 成功转换为 claimed 之后才被写入会话。这确保了"快速确认接收"时系统尚未写入任何用户消息，而一旦写入消息，系统已持有该任务的独占执行权，不会出现并发重复写入。

### 5. 执行领取与恢复机制

执行器（Executor）通过轮询或监听机制从任务存储中拉取状态为 received 的待执行任务。领取过程采用原子条件更新：使用数据库事务或分布式锁，将任务状态从 received 更新为 claimed，同时写入当前执行器实例的标识作为领取者。

执行器领取成功后执行以下步骤：

1. 检查关联会话中是否已存在与该任务幂等键对应的用户消息（崩溃恢复场景）；若已存在，跳过消息写入步骤。
2. 若不存在，调用现有会话的消息写入路径，以内部触发方式写入用户消息。消息元数据中记录关联的任务标识，但不修改现有消息格式和存储逻辑。
3. 触发模型推理：复用现有流式执行路径启动推理，任务状态更新为 running。
4. 推理过程中，模型输出通过现有流式通道逐步返回（如果外部调用方订阅了流式结果），同时正常写入会话消息历史。
5. 推理完成后，根据结果将任务状态更新为 completed 或 failed，并记录完成时间、输出摘要等信息。

执行器崩溃恢复：若执行器在持有 claimed 或 running 状态的任务时崩溃，系统通过超时检测机制回收这些任务。对于 claimed 状态超时的任务，其他执行器可重新领取；对于 running 状态超时的任务，系统检查关联会话的状态（是否已有完整回复），决定是恢复执行还是标记为 failed。

### 6. 状态查询、取消与清理

系统向外部调用方暴露以下管理接口，覆盖任务的完整生命周期：

- 状态查询（GET /tasks/{task_id}）：返回任务的当前状态、创建时间、最后更新时间、关联会话标识。若任务已完成，还返回模型输出的摘要信息。查询仅读取任务记录，不触发任何状态变更，支持高并发查询。
- 列表查询（GET /tasks?session_id={sid}）：按会话或时间范围列出任务，支持分页。用于管理面查看历史提交记录。
- 取消任务（POST /tasks/{task_id}/cancel）：将非终态任务标记为 cancelled。若任务处于 received 状态，直接原子更新为 cancelled；若任务处于 claimed 或 running 状态，先通过现有会话取消机制中断推理，再更新任务状态。幂等：对已处于终态的任务返回现有状态。
- 清理任务（DELETE /tasks/{task_id}）：仅对处于终态（completed/failed/cancelled）的任务执行清理。清理操作移除任务记录和关联的临时资源，但不删除会话中的消息历史。对非终态任务返回错误。
- 定时清理：后台任务定期扫描超过保留窗口（如 7 天）的终态任务记录并自动清理，防止存储膨胀。

所有管理接口均通过幂等键或任务标识进行操作，不依赖调用方维护连接或会话状态。外部调用方可以在提交任务后断开连接，随后通过任务标识在任何时间点查询或控制该任务。

### 7. 与现有系统的兼容集成

本方案在设计上遵循最小侵入原则，不对现有 Think agent 的核心路径进行重写：

- 会话与消息路径不变：任务执行器调用现有会话的内部消息写入接口写入用户消息，消息格式、存储方式、索引结构均保持不变。普通聊天（非异步提交）的消息写入路径完全不受影响。
- 流式推理路径不变：任务触发推理后，流式输出的生成和传输完全复用现有流式执行通道。外部调用方可通过 WebSocket 或 SSE 订阅与任务关联的会话的流式输出，该订阅机制为可选增强。
- 恢复路径不变：执行器崩溃后的会话级恢复（如未完成推理的续接）复用现有恢复逻辑。任务层仅在必要时（如 claimed 超时）触发重新领取，不重复实现恢复机制。
- 取消语义不变：任务的取消操作最终委托给现有会话级取消机制，保证已写入的消息历史和模型状态的一致性清理。
- 鉴权与多租户不变：任务接口的鉴权复用现有 API 鉴权层，任务记录中可记录提交者标识以支持多租户隔离，不新增独立的鉴权体系。

任务层仅新增了任务存储表（或集合）、任务状态机逻辑、执行器领取循环和管理接口路由。这些新增组件与现有系统通过接口耦合而非代码侵入，现有代码路径无需修改即可正常运行。

### 8. 技术效果

本方案相比现有同步调用模式，带来以下技术效果：

- 异步解耦：外部调用方提交任务后立即获得确认（毫秒级响应），无需保持连接等待模型推理完成（可能持续数十秒至数分钟），显著降低调用方的连接资源占用和超时风险。
- 重复提交安全：通过幂等键机制，即使外部系统因网络抖动或超时重试同一请求，系统也仅创建一次任务、写入一次用户消息、执行一次推理，从根本上消除重复执行问题。
- 崩溃恢复可靠：任务状态机的每个状态转换均有明确的持久化时机和恢复策略。在"已接收"到"消息写入"之间的关键边界，系统通过原子领取和消息去重双重保障，确保不会因崩溃导致消息丢失或重复写入。
- 可观察与可控制：外部调用方在提交后可随时查询任务状态，必要时取消或清理任务，无需维护长连接或会话状态。任务的完整生命周期均有持久化记录，支持审计和问题排查。
- 向后兼容：普通聊天路径完全不受影响。现有会话、消息、流式执行、恢复和取消逻辑均被复用而非重写，降低了引入新功能的风险和测试成本。

### 9. 风险与待确认问题

以下为当前方案中需要在实际实现时进一步确认的技术点：

- 任务存储选型：任务记录的持久化存储需要支持原子条件更新（compare-and-swap）。在具体实现中需确认使用数据库行级锁、Redis Lua 脚本或 ETCD 事务等方式，选型取决于现有基础设施。
- 幂等键保留窗口：幂等键映射需要设置合理的保留时间（如 24 小时至 7 天），过期后可释放存储。保留窗口的确定需结合实际业务场景的重试周期。
- 执行器领取的并发控制：在多执行器实例部署场景下，领取任务时的并发竞争需要精细调优，避免大量执行器同时争抢同一任务导致的数据库压力。可考虑使用消息队列（如通过数据库 LISTEN/NOTIFY 或专用消息中间件）替代轮询。
- claimed 状态超时阈值：执行器崩溃后，claimed 状态任务需要经过超时窗口才能被其他执行器重新领取。该超时阈值需要在"快速故障恢复"和"避免误判正常慢执行"之间平衡。
- 流式结果订阅：外部调用方订阅流式推理结果需要额外的连接管理机制（WebSocket 或 SSE），该机制是否纳入当前方案范围需确认。
- 现有 Think agent 内部接口确认：方案假设现有系统提供了内部消息写入接口、会话取消接口和恢复逻辑。在实际实现前需确认这些内部接口的具体签名和行为，确保任务层可以正确调用。
