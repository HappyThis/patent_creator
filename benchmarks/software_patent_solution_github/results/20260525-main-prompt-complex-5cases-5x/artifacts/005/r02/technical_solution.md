## 技术方案

### 技术问题概述

Think agent 系统当前以交互式会话为主要使用模式：用户通过前端界面逐轮输入消息，系统将消息写入会话日志后触发模型推理，并在推理完成后将结果返回用户界面。该模式下，用户与模型推理过程是同步耦合的——用户提交消息后必须等待推理完成才能获得响应。

当 Think agent 需要对外部系统（如 webhook 回调、RPC 调用方或异步 Worker）开放能力时，上述同步模式面临以下技术问题：（1）外部调用方通常期望提交任务后快速获得确认，而不必等待模型推理完成；（2）外部系统因超时或网络抖动可能重试同一请求，系统必须避免重复插入用户消息或重复执行同一任务；（3）调用方需要能够查询提交任务的执行状态，并在必要时取消或清理任务；（4）上述所有能力必须沿用在系统崩溃后仍能正确恢复，且不能重写现有的会话、消息保存和普通聊天路径。

### 整体架构

本方案在 Think agent 现有架构之上增加一个轻量的外部任务管理层，不修改现有会话存储格式、消息事件类型和模型推理循环。核心思路是引入"外部任务记录"作为独立持久化实体，在"快速确认接收"与"模型推理最终完成"之间建立明确的状态边界。

系统架构分为三层：（1）外部任务接口层，接收 webhook / RPC 提交，生成或识别幂等键，立即持久化任务记录并返回确认；（2）任务调度与领取层，异步从持久存储中领取待执行任务，将其桥接到现有会话-消息-推理路径；（3）任务管理面，提供状态查询、取消和清理接口。这三层均复用现有 project.json 中的 is_busy 标记、会话 JSONL 事件存储和 round/message 生命周期。

### 外部任务数据模型与状态机

外部任务记录是与会话事件日志平行的独立持久化结构，每条记录包含以下关键字段：task_id（系统生成的唯一标识）、idempotency_key（调用方提供的幂等键，用于去重）、session_id（关联的会话标识）、round_id（关联的轮次标识）、status（当前状态）、payload（原始任务输入）、result_summary（执行结果摘要）、created_at / updated_at / completed_at 等时间戳。任务记录可以存储在独立的 JSONL 文件中，也可以作为会话事件日志中一种新增事件类型（如 external_task_created）写入，以保持与现有存储体系的一致。

任务状态机包含以下状态及其转换规则：

- accepted：外部任务记录已持久化，但用户消息尚未插入会话。此状态是调用方收到快速确认的持久化保证。
- pending：用户消息已插入会话日志，任务等待执行领取。从 accepted 到 pending 的转换由异步写入 Worker 在消息插入成功后触发。
- running：任务已被 Worker 领取并开始模型推理。由任务调度器在成功获取执行权后写入。
- completed：模型推理成功完成，结果已写入会话日志。由推理 Worker 在正常结束后写入。
- failed：模型推理过程中发生不可恢复错误。由推理 Worker 在捕获异常后写入。
- cancelled：任务被调用方主动取消。可从 accepted、pending 或 running 状态转入。

accepted 和 pending 之间的边界是本方案的关键持久状态边界。在 accepted 状态下，任务记录已落盘但消息尚未写入；如果此时系统崩溃，恢复后任务调度器通过扫描 accepted 状态的任务可安全重试消息插入——插入前需检查会话中是否已存在同一 idempotency_key 对应的消息，避免重复写入。

### 两阶段提交与快速确认机制

外部调用方通过 submit 接口提交任务时，系统执行以下两阶段处理流程，实现快速确认与异步执行的分离。

第一阶段（同步确认）：系统收到外部提交请求后，首先基于调用方提供的 idempotency_key 检查是否已存在相同任务。若存在且状态为 accepted、pending 或 running，直接返回已有 task_id 和当前状态，不创建新任务。若不存在，系统生成 task_id，创建状态为 accepted 的任务记录并立即持久化到存储中。持久化完成后，系统向调用方返回 {task_id, status: accepted}。整个第一阶段不涉及消息写入和模型推理，延迟仅取决于一次持久化写入。

第二阶段（异步执行）：系统通过后台调度器（可基于定时轮询或消息队列事件触发）扫描状态为 accepted 的任务。对于每个 accepted 任务，调度器执行以下步骤：首先检查关联会话中是否已存在同一 idempotency_key 对应的用户消息（防止上一轮写入在消息插入后、状态更新前崩溃导致的不一致）；若消息不存在，则在会话日志中追加一条 user_input 类型事件，其 payload 包含任务输入内容，并在事件中附加 idempotency_key 标记；消息写入成功后，将任务状态从 accepted 更新为 pending，表示消息已就绪、等待执行。

第二阶段继续：任务调度器随后通过检查 project.json 中的 is_busy 标记和 running_session_id 判断当前是否有空闲的执行槽位。若系统空闲，调度器将任务状态从 pending 更新为 running，设置 running_session_id 和 running_round_id，然后触发现有模型推理循环。推理过程复用当前 agent_message、tool_call、tool_result 事件类型和流式输出机制。推理完成后，调度器根据推理结果将任务状态更新为 completed（成功）或 failed（失败），并清除 is_busy 标记。

### 幂等性与重复提交去重

幂等性通过 idempotency_key 在任务记录层和消息层两个层面保证。

任务记录层去重：在提交接口的第一阶段，系统以 idempotency_key 为索引查询已有任务记录。若命中且任务未处于终态（completed、failed、cancelled），直接返回已有 task_id，不创建新记录。若命中且任务已处于终态，可配置为返回已有结果或创建新任务。idempotency_key 的保留窗口可由系统配置（如 24 小时），超期后可被清理，此后相同 key 的请求视为新任务。

消息层去重：在第二阶段消息写入前，系统检查会话日志中是否已存在携带相同 idempotency_key 的 user_input 事件。该检查覆盖了以下崩溃场景：上一轮执行在消息已写入但任务状态未从 accepted 更新为 pending 时崩溃。恢复后调度器重新扫描到 accepted 任务，尝试插入消息时发现消息已存在，遂跳过插入，直接将任务状态推进到 pending 并继续后续流程。

### 崩溃恢复与持久状态边界

系统在以下关键边界处均设计了崩溃恢复机制，保证即使在任意时刻崩溃，恢复后系统状态一致且不产生重复执行。

边界一——任务记录写入与消息插入之间：这是本方案最关键的持久状态边界。外部任务记录以 accepted 状态持久化后、用户消息插入会话之前，系统可能崩溃。恢复时，调度器扫描所有 accepted 状态的任务，对每个任务检查会话中是否存在对应 idempotency_key 的消息。若不存在，执行消息插入并将状态更新为 pending；若已存在，说明崩溃前消息已写入但状态未更新，直接将状态推进到 pending。两种情况下都不会产生重复消息。

边界二——消息插入与执行领取之间：任务处于 pending 状态时，消息已安全落盘。若此时崩溃，恢复后调度器会扫描 pending 任务并按照执行领取机制继续处理。由于 pending 任务对应的消息已存在于会话日志中，恢复后只需重新领取执行即可。

边界三——执行进行中崩溃：任务处于 running 状态时崩溃，恢复后调度器通过 project.json 中的 is_busy 标记和 running_round_id 判断崩溃前是否有未完成的推理。此时沿用了 Think agent 现有的会话恢复机制：从会话日志中定位到未完成的 round，检查其最后一个事件类型，若推理未完成则从断点恢复执行。任务状态保持 running，完成后正常推进到终态。

### 异步执行领取与恢复

任务执行领取采用条件获取模式，避免多个 Worker 并发处理同一任务。领取逻辑如下：

调度器首先检查 project.json 中的 is_busy 标记。若 is_busy 为 true 且 running_session_id 非空，表示当前有任务正在执行，调度器跳过本次领取。若 is_busy 为 false，调度器将 is_busy 设置为 true，写入当前 running_session_id 和 running_round_id，然后将目标任务从 pending 更新为 running。这一写入操作是原子性的条件更新——只有当任务当前状态确为 pending 时才执行更新，避免并发场景下重复领取。

领取成功后，调度器触发模型推理循环，该循环直接复用 Think agent 现有的 agent_message、tool_call、tool_result 事件流。推理过程中产生的所有中间事件按现有机制写入会话 JSONL 日志。推理完成后，调度器将任务状态更新为 completed 或 failed，清除 is_busy 标记，并释放 running_session_id。若系统配置了多个 Worker 实例，每个 Worker 在执行领取前需通过文件锁或数据库行级锁保证互斥。

### 状态查询、取消与清理

系统提供以下管理接口，供外部调用方追踪和控制已提交的任务。

状态查询：调用方通过 task_id 查询任务当前状态。系统读取任务记录中的 status、created_at、updated_at 等字段。若任务处于 running 状态，可额外返回推理进度信息（如已完成的 tool_call 数量、已产生的输出事件数量）。若任务处于 completed 状态，返回结果摘要或结果在会话日志中的引用位置。查询接口为只读操作，不修改任务或会话状态。

取消：调用方请求取消指定任务。若任务处于 accepted 或 pending 状态，系统直接将任务状态更新为 cancelled，不启动推理。若任务处于 running 状态，系统向当前推理循环发送取消信号——该信号复用 Think agent 现有取消语义（如通过检查项目级取消标记或中断当前 round），推理循环在下一个安全检查点停止执行，保存已产生的中间结果，然后将任务状态更新为 cancelled。取消操作是终态转换，不可逆。

清理：调用方请求清理（删除）指定任务。清理操作将任务记录标记为已清理状态，但不会删除底层会话日志中的消息和事件。这样既释放了任务管理层的索引和元数据存储空间，又保留了完整的审计追踪。对于已清理的任务，状态查询接口返回"已清理"或"不存在"。已完成任务的自动清理可由定时任务根据 completed_at 时间戳和配置的保留周期触发。

### 与现有聊天路径的兼容

本方案的关键设计原则是不重写现有聊天路径。具体兼容措施包括：

会话存储格式不变：外部任务产生的用户消息仍然以 user_input 事件类型写入会话 JSONL 日志，与普通聊天消息使用相同的存储格式和追加写入路径。唯一区别是事件 payload 中附加了 idempotency_key 字段，普通聊天消息中该字段为空或不存在。这保证了现有消息查询、读取、回放逻辑无需修改即可处理外部任务产生的消息。

推理循环复用：外部任务触发模型推理后，推理循环使用的 agent_message、tool_call、tool_result 事件类型和流式输出逻辑与普通聊天完全一致。project.json 中的 is_busy、running_session_id、running_round_id 字段被外部任务和普通聊天共用——当 is_busy 为 true 时，新的外部任务提交和普通用户输入都不会立即触发推理，而是排队等待当前执行完成。

取消与恢复语义沿用：外部任务的取消信号通过项目级标记传递，与普通聊天中的取消机制共用同一取消检查点。会话恢复时，系统从 JSONL 日志中定位未完成的 round，无论该 round 是由外部任务还是普通聊天触发的，恢复逻辑相同。这意味着现有的会话 resume/reset/clear 操作对两种来源的消息行为一致，不需要为外部任务单独实现一套生命周期管理。

### 技术效果

本方案通过引入外部任务记录和两阶段提交机制，在不大幅修改现有架构的前提下实现了以下技术效果。

- 快速确认与异步解耦：调用方提交任务后仅需等待一次持久化写入即可获得确认，模型推理的耗时不再阻塞提交接口。
- 可靠去重：通过 idempotency_key 在任务记录层和消息层双重去重，保证外部系统重试不会产生重复消息或重复执行。
- 崩溃安全：在任务记录写入与消息插入之间的关键边界设计了基于 idempotency_key 的恢复检查，保证任意时刻崩溃后系统可自动恢复到一致状态。
- 状态可观测：调用方可通过 task_id 实时查询任务从 accepted 到 completed 的完整生命周期状态。
- 可控生命周期：支持取消进行中的任务和清理已完成任务，取消操作复用现有推理中断机制。
- 架构兼容：外部任务产生的消息、推理事件、取消和恢复行为与普通聊天完全一致，不需要为外部任务单独维护一套代码路径。

### 风险与待确认问题

以下问题需要在具体实现阶段进一步确认和细化，但不影响方案整体可行性。

- 任务记录的存储位置选择：可独立 JSONL 文件、嵌入会话 JSONL 作为新事件类型、或使用独立数据库表。不同选择影响查询性能和实现复杂度，需根据部署环境确定。
- idempotency_key 的保留窗口时长：需根据业务场景设定合理的过期时间，平衡去重可靠性与存储开销。
- 多 Worker 并发领取的锁粒度：在单机部署下文件锁足够，在多机部署下需数据库行级锁或分布式锁，具体方案依赖实际部署架构。
- 调度器的触发机制：基于定时轮询还是事件驱动（如消息队列或文件系统监控事件），影响任务从 accepted 到 running 的延迟。
- 取消操作的及时性：若推理循环中 tool_call 执行时间较长，取消信号可能在当前 tool_call 完成后才被检查到，需评估是否需要支持 tool_call 级别的中断。
