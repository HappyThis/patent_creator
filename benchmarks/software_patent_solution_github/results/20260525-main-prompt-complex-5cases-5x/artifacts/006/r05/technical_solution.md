## 技术方案

本方案提出一种面向 agent 对话系统的客户端-服务端生命周期解耦控制方法，通过引入 turn 级取消意图通道和可配置的生命周期策略，将浏览器端本地资源清理（刷新、卸载、reader cancel、网络断开）与服务端 agent turn 取消明确区分为两条独立控制路径，从而在保持服务端 durable 执行不被意外中断的前提下，仍允许用户主动取消服务端正在运行的 agent turn。

### 1. 技术问题分析

在基于流式响应（SSE/WebSocket）的 agent 对话系统中，浏览器端通过 useAgentChat 等 hook 建立与服务端的持久连接以接收 agent 的流式输出。当浏览器刷新、React 组件卸载、用户切换页面或网络短暂断开时，浏览器端的 ReadableStream reader 会被取消（reader.cancel()），HTTP 连接或 WebSocket 会断开。现有方案通常将这类客户端断开事件直接映射为服务端任务取消信号，导致已在 Durable Object 中长期运行的 agent 对话被意外终止，已产生的中间状态丢失且无法恢复。

另一方面，用户确实需要一种明确的"停止生成"能力。当用户点击 Stop 按钮时，其意图是终止本次 agent turn 的服务端执行，而非仅仅关闭本地显示。但现有方案中 stop 行为与浏览器刷新、组件卸载等触发的 reader cancel 共享同一代码路径，服务端无法区分"用户主动取消"与"浏览器被动断开"，导致开发者无法为两种场景配置不同策略。

### 2. 核心技术方案：双通道解耦架构

本方案的核心思路是在客户端与服务端之间建立两条独立的控制通道：一条是用于传输 agent 流式响应的数据通道（data channel），另一条是用于传达取消意图的控制通道（control channel）。两条通道在语义和生命周期上完全解耦。

数据通道承载 agent 流式输出的文本增量、工具调用事件和状态更新。该通道的生命周期与浏览器连接（HTTP 请求/WebSocket）绑定：当浏览器刷新、组件卸载或网络断开时，数据通道的 reader 被取消，浏览器停止接收流式数据，但此行为不影响服务端 agent turn 的继续执行。服务端仅将数据通道断开记录为"客户端暂时不可达"，agent 在 Durable Object 中继续运行，产生的输出写入持久化缓冲区。

控制通道专门用于传递用户主动触发的取消意图。当用户点击 Stop 按钮或应用调用 stop() 方法时，客户端通过控制通道向服务端发送一个携带当前 turn 标识（turnId）的取消消息。服务端收到该消息后，在 Durable Object 中设置对应 turn 的取消标记，agent 执行循环在下一个检查点检测到该标记后终止执行。控制通道独立于数据通道，即使数据通道已断开（如网络中断），只要客户端恢复连接即可发送取消消息。

### 3. 生命周期语义区分机制

本方案在客户端对以下五类事件做语义区分，每类事件触发不同的处理路径：浏览器刷新（beforeunload）、React 组件卸载（useEffect cleanup）、ReadableStream reader 取消（reader.cancel()/AbortController）、网络断开（navigator.onLine 变化）、用户点击 Stop 按钮（stopGeneration）。

前三类事件（刷新、卸载、reader cancel）统一归类为"本地清理事件"。这些事件的共同特征是：触发源为浏览器或框架的生命周期管理，不反映用户对服务端任务状态的意愿。处理路径为：取消本地 reader 和 AbortController → 清理组件状态 → 关闭本地流显示 → 记录当前 turnId 到 sessionStorage → 不发送取消消息到服务端。服务端 agent 继续在 Durable Object 中执行，输出写入持久化缓冲区。

网络断开事件单独归类为"连接中断事件"。处理路径为：保留本地 reader 引用和 AbortController → 进入重连等待状态 → 监听 navigator.onLine 恢复事件 → 在恢复后通过 turnId 重新订阅服务端流式输出（从持久化缓冲区中的断点继续）。如果在配置的重连超时窗口内未恢复，则降级为本地清理事件处理。

用户 Stop 按钮点击事件归类为"主动取消事件"。处理路径为：客户端生成携带当前 turnId 的取消消息 → 通过控制通道（独立 HTTP POST 或 WebSocket 控制帧）发送到服务端 → 服务端在 Durable Object 中将对应 turn 的状态标记为 CANCELLED → 服务端 agent 执行循环在下一个检查点（如下一个工具调用返回后、下一个 LLM token 生成后）检测到取消标记 → 执行清理并终止 turn → 客户端收到取消确认后清理本地状态。

### 4. 双模式设计：Durable 模式与 Request-Lifetime 模式

为适应不同应用场景对"客户端断开是否取消服务端任务"的不同偏好，本方案提供两种生命周期模式，开发者通过配置项进行选择。

Durable 模式（默认）：服务端 agent turn 的生命周期独立于客户端连接。当客户端数据通道断开（包括浏览器刷新、组件卸载、reader cancel、网络断开），服务端 agent 继续在 Durable Object 中运行直到自然完成或被主动取消。客户端重新连接后，通过 turnId 恢复订阅，从持久化缓冲区中的断点继续接收流式输出。该模式适用于需要长时间运行、包含多轮工具调用的 agent 对话，确保即使客户端暂时不可达也不会丢失执行进度。

Request-Lifetime 模式（可选）：服务端 agent turn 的生命周期与客户端 HTTP 请求/WebSocket 连接绑定。当客户端数据通道因任何原因断开（包括浏览器刷新、组件卸载、reader cancel、网络断开），服务端自动将对应 turn 标记为取消，agent 在下一个检查点终止执行。该模式适用于短对话、无状态问答场景，可节省服务端计算资源。但即使在 Request-Lifetime 模式下，通过控制通道发送的主动取消消息仍然有效，且其优先级高于连接断开触发的自动取消。

### 5. 多标签页协调与恢复兼容

在多标签页场景中，同一用户可能在多个浏览器标签页中打开了同一 agent 对话。本方案通过以下机制确保各标签页的本地清理行为不会相互干扰，同时保证主动取消的全局性。

每个标签页维护独立的本地数据通道连接和 reader 实例。当单个标签页关闭或刷新时，仅该标签页的本地 reader 被取消，其他标签页的数据通道不受影响。服务端通过连接标识（connectionId）区分不同标签页的连接，关闭一个连接不会触发 turn 取消。

当用户在一个标签页中点击 Stop 时，通过控制通道发送的取消消息携带全局 turnId，服务端收到后对所有订阅该 turn 的标签页广播取消状态，各标签页统一更新 UI。跨标签页的取消状态同步通过 BroadcastChannel API 或服务端推送实现。

对于工具调用继续执行（tool continuation）场景：当 agent 在执行工具调用过程中客户端断开（Durable 模式），工具调用在服务端继续完成，工具返回结果写入持久化缓冲区。工具调用期间若收到主动取消消息，取消标记在工具调用完成后（下一个检查点）生效，agent 不再将工具结果发送给 LLM 进行下一轮推理，而是直接终止 turn。

### 6. 迟到服务端消息处理

由于 Durable 模式下服务端 agent 可能在客户端断开后继续运行相当长的时间，当客户端重新连接时可能面临大量积压消息。本方案通过以下机制处理迟到消息。

服务端为每个 turn 维护一个持久化的消息缓冲区（message buffer），按序列号（seq）存储所有已生成的增量输出。客户端恢复连接时发送最后已接收的序列号（lastReceivedSeq），服务端从该序列号之后开始投递消息，避免重复传输。

若客户端在 turn 已自然完成后才重新连接，服务端返回 turn 的终态（COMPLETED/CANCELLED）及完整的消息历史，客户端直接渲染最终结果。若 turn 仍在执行中，服务端将缓冲区中已有的消息批量推送后，继续以流式方式推送新产生的消息。

对于主动取消后服务端可能迟到的消息（即取消消息已发送但服务端在检查点前仍产出了少量输出），服务端在收到取消消息后立即在缓冲区中追加一个取消边界标记（cancellation boundary marker）。客户端恢复连接后，以该标记为界：标记之前的消息正常渲染，标记之后的消息丢弃。该机制确保即使用户取消了回答，已输出的部分仍然可恢复查看。

### 7. 技术效果

第一，客户端生命周期与服务端任务生命周期解耦。浏览器刷新、组件卸载、reader cancel 等本地清理事件不再导致服务端 agent turn 被意外终止，显著降低长时间 agent 对话因客户端不可控事件而丢失执行进度的概率。

第二，取消语义精确化。通过独立的控制通道和 turnId 标识，服务端能够明确区分"用户主动取消"与"客户端被动断开"，为两种场景提供不同的处理策略，同时为开发者提供可配置空间。

第三，恢复能力增强。Durable 模式下，客户端重连后可通过 turnId 和序列号从断点恢复流式输出，已产生的消息不会丢失或重复，支持长时间工具调用链路的完整恢复。

第四，多标签页场景协调。不同标签页的本地清理互不干扰，主动取消通过全局 turnId 广播到所有标签页，保证多标签页体验一致。

第五，开发者可配置性。通过 Durable 模式和 Request-Lifetime 模式的切换，开发者可以根据应用场景选择合适的生命周期策略，无需修改核心逻辑即可适配不同产品需求。

### 8. 风险与待确认问题

（1）取消检查点粒度：服务端 agent 的取消标记检测依赖于检查点（如工具调用返回后、LLM token 生成后）。若 LLM 单次生成耗时极长且期间无检查点，用户感知的取消延迟可能较大。需要在 LLM 流式生成过程中引入中间检查点或在 token 级别嵌入取消检测。

（2）控制通道可靠性：取消消息通过独立控制通道发送，若控制通道本身不可达（如网络完全断开），用户 Stop 操作无法传达至服务端。需考虑控制通道的重试机制或与数据通道共享底层连接时的降级策略。

（3）持久化缓冲区容量：Durable 模式下长时间运行的 agent turn 可能在缓冲区中积累大量消息，需设定缓冲区上限及溢出策略（如仅保留最近 N 条消息或压缩历史）。

（4）Durable Object 生命周期与 turn 生命周期的映射：需要明确 Durable Object 实例的存留策略——turn 完成后 Durable Object 是否立即释放、多个 turn 是否共享同一 Durable Object 实例、以及 Durable Object 在无活跃 turn 时的休眠策略。
