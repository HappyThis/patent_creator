## 技术方案

本方案提出一种面向浏览器端 agent 对话 Hook（如 useAgentChat）的客户端-服务端取消语义区分机制，解决浏览器刷新、组件卸载、网络断连等本地生命周期事件与服务端 agent turn 取消之间的语义混淆问题。方案引入两种执行模式：默认的 Durable 模式（客户端断连不终止服务端执行）和可选的 Request-Lifetime 模式（客户端断连即终止服务端执行）。通过显式取消信令通道、取消令牌机制和多标签页协调策略，实现本地清理与远程取消的明确区分，同时兼容流式响应、断线重连、工具调用继续执行和迟到消息投递。

### 技术问题与设计目标

在现有 useAgentChat 实现中，浏览器端的流读取器（reader）关闭与服务端 Durable Object（DO）中 agent turn 的终止之间存在语义耦合。当浏览器刷新、React 组件卸载、页面路由切换或网络短暂断开时，客户端会触发 reader.cancel() 或底层 TCP 连接关闭。服务端若将此事件一律解释为"用户希望取消"，会导致 DO 中正在执行的 agent turn 被误终止，包括正在进行中的工具调用链（tool call chain）。反之，若用户通过 UI 点击"停止"按钮，仅关闭本地 reader 而不通知服务端，则 DO 仍继续占用计算资源执行已无意义的 turn。

本方案的设计目标是：(1) 明确区分本地生命周期清理事件与用户主动取消服务端 turn 两类语义；(2) 提供默认 Durable 模式和可选 Request-Lifetime 模式，满足不同应用场景偏好；(3) 兼容流式响应、断线重连、工具调用继续执行、多标签页观察和迟到服务端消息处理。

### 生命周期清理与取消的语义区分机制

本方案在客户端 Hook 层引入"断开原因标记"机制，将导致客户端流读取中断的事件划分为两类：

- 被动生命周期事件：浏览器刷新（beforeunload）、React 组件卸载（useEffect cleanup）、页面路由切换、网络连接超时/断开。这些事件触发时，Hook 内部生成一个 reason=lifecycle 的断开标记。
- 主动取消事件：用户点击"停止"按钮、应用调用 Hook 暴露的 stop() 方法。这些事件触发时，Hook 内部生成一个 reason=user_cancel 的断开标记，并触发显式取消信令。

区分的关键在于：被动生命周期事件仅执行本地资源清理（取消 reader、清理定时器、移除事件监听），不向服务端发送取消意图；主动取消事件在本地清理之前或同时，向服务端发送携带取消令牌（cancellation token）的显式取消信令。

### 取消信令的端到端传递机制

显式取消信令是一条独立于流式响应通道的控制消息，携带唯一标识当前 agent turn 的取消令牌（turn_id）。当用户触发主动取消时，客户端执行以下步骤：

1. Hook 层生成包含 turn_id 的取消令牌；
2. 通过独立 HTTP 请求（如 POST /api/agent/cancel）或 WebSocket 控制帧将取消令牌发送至服务端；
3. 服务端路由层根据 turn_id 定位到对应的 DO 实例，调用 DO 的 cancel(turn_id) 方法；
4. DO 在执行 agent turn 的检查点（如每次 LLM token 生成后、tool call 前后）检查取消标志位，若已设置则终止执行并释放资源。

取消令牌 turn_id 是方案的核心数据结构，包含：agent session ID、turn 序号、客户端实例标识（用于多标签页区分）和取消时间戳。DO 在执行 agent turn 期间周期性检查该标志位，确保及时响应取消请求。

### Durable 模式下的断线重连与恢复

在 Durable 模式下，DO 中 agent turn 的生命周期独立于客户端 HTTP 连接。客户端因任何原因断开时，DO 继续执行当前 turn 并将输出缓冲到持久化存储中。

断线重连流程如下：(1) 客户端重新建立连接时，携带上次接收到的最后一条消息序号（last_seq）和 session_id；(2) 服务端根据 session_id 定位 DO，DO 从持久化存储中检索 turn 执行状态和输出缓冲区；(3) 若 turn 仍在执行，DO 从 last_seq 之后的消息开始继续推送流式输出；(4) 若 turn 已执行完毕，DO 返回完整的输出缓冲区内容并标记 turn 为已完成状态。

对于迟到服务端消息（客户端断连期间 DO 产生的消息），DO 在重连后从客户端指定的 last_seq+1 位置开始推送，确保不丢失任何消息。若客户端未提供 last_seq，DO 默认从当前缓冲区起始位置推送全量消息。

### Request-Lifetime 模式

Request-Lifetime 模式适用于对实时性要求高、不希望服务端继续执行已无人监听的 turn 的场景。在此模式下，客户端连接断开（无论是被动生命周期事件还是主动取消）均触发 DO 取消当前 turn。

实现上，Request-Lifetime 模式复用相同的取消信令通道，区别在于：当 Hook 检测到被动生命周期事件时，在 Durable 模式下不发送取消信令，而在 Request-Lifetime 模式下自动构造并发送取消令牌（reason=lifecycle_disconnect）。服务端 DO 收到该令牌后，与收到 user_cancel 令牌执行相同的终止流程。

开发者通过 Hook 的配置参数（如 mode: 'durable' | 'request-lifetime'）在初始化时选择模式，该参数通过请求头或查询参数传递至服务端，服务端据此决定 DO 在连接断开时的行为策略。

### 多标签页协同机制

多标签页场景中，多个浏览器标签页可能通过各自的 useAgentChat 实例连接到同一 DO session。方案通过以下机制协调取消行为：

- 每个标签页拥有独立的客户端实例标识（client_instance_id），注册到 DO 的观察者列表中。
- DO 维护当前 turn 的观察者计数。标签页连接时计数+1，标签页断开且为非取消原因时计数-1。
- 主动取消采用"任一即取消"策略：任一标签页发送显式取消信令（reason=user_cancel），DO 即终止当前 turn 并向所有观察者广播 turn_cancelled 事件。
- 被动断开在 Durable 模式下仅递减观察者计数，不触发取消。当观察者计数降为零时，DO 继续执行但不再推送实时更新（仅写入持久化缓冲区）。
- 标签页 B 重连时，DO 根据其携带的 session_id 和 last_seq 恢复推送，与单标签页重连流程一致。

### 工具调用继续执行的保障

Agent turn 中可能包含多轮工具调用（tool call），每轮工具调用涉及 LLM 决定调用工具、执行工具函数、将工具结果返回 LLM 继续推理的循环。在 Durable 模式下，工具调用链的执行不受客户端连接状态影响：DO 在每个 tool call 执行前检查取消标志位，仅在收到显式 user_cancel 信令时才中止工具调用链。

具体保障机制：(1) 工具函数在 DO 内部执行，不依赖客户端连接；(2) 工具调用结果和后续 LLM 输出均写入 DO 持久化缓冲区；(3) 若客户端在工具调用期间断开并重连，重连后可获取已完成的工具调用结果和继续生成的 LLM 输出；(4) 对于有副作用的工具调用（如发送邮件），取消信令的检查点设在工具调用发起前，一旦工具调用已发起，DO 允许其完成以保证状态一致性。

### 开发者配置接口

方案在 Hook 初始化参数中暴露以下配置项：

- mode: 'durable' | 'request-lifetime' — 选择客户端断连时服务端行为模式，默认为 'durable'。
- cancelOnUnmount: boolean — 是否在组件卸载时自动触发取消信令（仅在 request-lifetime 模式下有意义），默认为 false。
- reconnectTimeout: number — 断线后客户端等待重连的最大时间（毫秒），超时后放弃恢复并清理本地状态。
- heartbeatInterval: number — 心跳间隔（毫秒），用于服务端检测客户端是否永久离开。

服务端对应配置通过 DO 初始化参数或环境变量指定，包括：默认执行模式、观察者超时阈值、消息缓冲区最大容量和取消检查点间隔。开发者在不同应用场景中可按需调整：例如实时客服场景可能偏好 request-lifetime，而异步数据分析场景偏好 durable。

### 技术效果

与现有方案相比，本方案具有以下技术效果：

- 语义解耦：首次在浏览器 agent 对话场景中明确区分本地生命周期清理与远程 turn 取消，消除两类事件的误传播。
- 计算资源保护：Durable 模式下避免因浏览器刷新等高频操作导致的 DO 重复执行，减少 LLM API 无效调用。
- 无缝恢复体验：断线重连后客户端可续接收流式输出，不丢失断连期间的消息，用户无感知。
- 工具调用完整性：工具调用链不受客户端断连中断，避免因断连导致的工具调用状态不一致。
- 灵活部署：双模式设计满足不同应用场景，开发者无需修改服务端核心逻辑即可切换模式。
- 多标签页安全：任一标签页可主动取消，同时单个标签页的断开不影响其他标签页的观察体验。

### 风险与待确认问题

以下问题需在具体实施前确认：

- 取消信令通道选择：取消信令采用独立 HTTP 请求还是 WebSocket 控制帧？独立 HTTP 请求在连接已断开时仍可发出，但需确保到达 DO 的路由可靠；WebSocket 控制帧延迟更低但依赖连接存活。建议结合使用：连接正常时通过 WebSocket 帧发送，连接断开时降级为 HTTP 请求。
- 多标签页取消策略细化：当前采用"任一即取消"策略，是否需支持"全部同意才取消"的可选策略？后者适合协作编辑场景。
- DO 取消粒度：当前方案采用 hard cancel（终止执行并释放资源），是否需要 soft detach（仅停止推送但保留执行结果）作为中间选项，需确认。
- 网络断开判定超时：心跳超时阈值与 reconnectTimeout 的关系需明确，避免在短暂网络波动时误触发观察者移除。
- 工具调用副作用处理：对于已发起且不可回滚的副作用（如已发送的 API 请求），取消信令到达后 DO 是否应等待其完成并记录结果，需确认业务语义。

注意：当前项目环境中未找到 useAgentChat 及 DO 相关源码实现，上述方案基于需求描述以通用架构模式撰写。实际落地时需根据现有代码结构调整 Hook API 签名、DO 通信协议和取消信令的具体传输格式。
