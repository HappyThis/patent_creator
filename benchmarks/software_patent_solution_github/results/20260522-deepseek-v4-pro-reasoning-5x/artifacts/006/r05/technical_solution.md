## 技术方案

本方案提出一种面向长时间 Agent 对话的客户端-服务端生命周期解耦机制。核心思想是将「客户端本地流生命周期管理」与「服务端 Agent Turn 取消」分离为两个独立的信令通道：客户端因浏览器刷新、组件卸载、reader.cancel() 或网络断开等本地事件而执行的资源清理，不自动传播为服务端任务取消；服务端 Agent Turn 的终止仅由显式的「停止」信令触发。该机制默认运行在 Durable 模式（即服务端任务在客户端断开后继续执行），同时为开发者提供可选的 Request-Lifetime 模式（客户端断开即取消服务端任务），以适应不同应用场景的偏好。

### 客户端生命周期清理与服务端 Turn 取消的语义区分

系统明确定义两类不同语义的操作，并通过独立的信令路径实现。

第一类：客户端本地生命周期清理。包括以下场景：(a) 浏览器刷新或关闭标签页——浏览器销毁当前页面的 JavaScript 执行环境，所有内存中的 ReadableStream reader、fetch 请求的 AbortController 以及 React 组件状态随之销毁；(b) React 组件卸载——useAgentChat hook 所在的组件因路由切换或条件渲染而被 React 卸载，触发 useEffect 清理函数；(c) reader.cancel()——客户端主动取消对服务端响应流的读取，释放本地流资源；(d) 网络短暂断开——WebSocket 或 SSE 连接因网络波动断开，浏览器端的 EventSource 或 WebSocket 实例触发 onerror/onclose。上述所有场景的共同特征是：它们仅代表客户端侧不再消费服务端输出流，并不必然代表用户希望终止服务端的 Agent 推理过程。

第二类：服务端 Agent Turn 取消。这是用户或应用层的显式意图，通过以下方式触发：(a) 用户点击 UI 中的「停止生成」按钮；(b) 应用调用 stop() 方法（例如 useAgentChat 返回的 stop 函数）；(c) 超时策略或安全管理策略主动中止。该操作向服务端发送一条独立的取消信令（例如 HTTP POST /api/chat/{turnId}/stop），服务端在收到该信令后中止对应 Durable Object 中正在执行的 Agent Turn。

关键设计在于：客户端本地生命周期清理事件（第一类）不会自动触发取消信令（第二类）。当 useAgentChat 的清理函数执行时（例如组件卸载），它仅执行本地资源释放——包括 abort 当前 fetch/SSE 连接、清理 reader、重置本地消息缓冲区——但不会向服务端发送取消请求。这保证了浏览器刷新或页面切换不会意外终止服务端正在执行的重要 Agent 任务。

### 双模式运行机制：Durable 模式与 Request-Lifetime 模式

系统提供两种运行模式，通过 useAgentChat 的配置参数（如 lifecycleMode: 'durable' | 'request-lifetime'）进行选择，默认采用 Durable 模式。

Durable 模式（默认）：服务端 Agent Turn 的执行生命周期独立于客户端连接生命周期。当客户端因刷新、卸载或网络断开而断开连接时，服务端的 Durable Object 继续执行当前 Agent Turn——包括 LLM 推理、工具调用和结果处理。服务端将生成的消息持续写入持久化存储。当客户端重建连接（例如刷新后重新加载页面、或网络恢复后自动重连）时，客户端携带恢复令牌（resumption token，包含上一次接收到的消息序号或 turnId），服务端从持久化存储中定位到该 Turn，并将未投递的消息流式推送给客户端。此模式下，服务端 Turn 仅在以下条件之一满足时终止：(a) 收到显式取消信令；(b) Agent 正常完成并输出最终响应；(c) 服务端超时策略触发。

Request-Lifetime 模式（可选）：服务端 Agent Turn 的生命周期绑定在客户端请求的生命周期上。当客户端断开连接时（无论是主动还是被动），服务端通过检测 HTTP 请求上下文的中断（如 Request.signal 的 abort 事件）来感知客户端断开，并同步取消正在执行的 Agent Turn。此模式适用于对服务端资源消耗敏感、或业务逻辑要求客户端在线才能继续的场景。开发者可以通过配置参数显式选择此模式。

两种模式的切换不影响客户端 API 的使用方式。无论在哪种模式下，useAgentChat 返回的 stop() 方法均发送显式取消信令；客户端本地清理逻辑在两种模式下保持一致。区别仅在于当本地清理发生时，服务端是否同步终止执行。

### 恢复与重连机制

在 Durable 模式下，恢复与重连是保证用户体验连续性的核心机制。其处理流程如下：

(1) Turn 标识与消息序号：每个 Agent Turn 在服务端创建时分配唯一 turnId。服务端在流式推送过程中为每条消息（文本增量、工具调用请求、工具结果、完成信号等）分配递增的消息序号（messageSeq）。客户端在接收每条消息时记录最新的 messageSeq。

(2) 断线检测与重连触发：客户端通过 AbortController.signal 的 abort 事件、fetch 请求的 TypeError（网络错误）、或 EventSource/WebSocket 的 onerror 事件检测连接中断。检测到中断后，客户端启动指数退避重连策略，携带 turnId 和最后接收的 messageSeq 向服务端发起恢复请求。

(3) 服务端恢复投递：服务端收到恢复请求后，在 Durable Object 中定位到对应 turnId 的执行上下文。若该 Turn 仍在执行中，服务端从 messageSeq+1 开始，将已生成但未确认投递的消息重新流式推送；若该 Turn 已执行完毕，服务端将剩余未投递消息一次性推送并发送完成信号。若 turnId 不存在或已过期，返回错误提示用户重新开始。

(4) 恢复令牌安全：turnId 和 messageSeq 组成恢复令牌，存储在客户端内存中。为避免跨会话信息泄露，恢复令牌绑定当前浏览上下文，不持久化到 localStorage。浏览器刷新场景下，客户端通过服务端会话 cookie 或 URL 参数重新获取当前活跃 turnId。

### 工具调用继续执行机制

Agent Turn 在执行过程中可能涉及多次工具调用（function calling），每次工具调用后 Agent 需要接收工具返回结果才能继续推理。在 Durable 模式下，工具调用的执行和继续（continuation）具有以下特性：

(1) 工具调用不因客户端断开而中断：当服务端向客户端推送工具调用请求后，即使客户端此时断开连接，服务端的 Durable Object 仍保持该 Turn 的活跃状态，等待工具调用结果。客户端重连后，服务端将已发出的工具调用请求重新推送。客户端执行该工具调用（如前端工具函数或经服务端代理的工具）并提交结果。

(2) 工具结果回传的幂等处理：服务端为每个工具调用分配唯一的 toolCallId。若客户端重连后重复提交同一工具调用结果，服务端通过 toolCallId 去重，确保 Agent 不会因重复的工具结果而产生错误推理。

(3) 前端工具与服务端工具的区分：对于前端工具（在浏览器中执行，如访问 DOM、读取本地存储），客户端负责执行并将结果回传；对于服务端工具（在 Durable Object 或外部 API 中执行），工具调用和结果处理完全在服务端完成，不依赖客户端连接。本方案中，服务端工具的执行天然不受客户端断线影响；前端工具的结果回传通过恢复机制得到保障。

### 多标签页协同机制

在多标签页场景下，同一用户可能打开多个标签页访问同一 Agent 对话。系统通过以下机制保证多标签页下的状态一致性：

(1) 共享会话标识：同一浏览器会话下的所有标签页共享同一会话标识（sessionId），通过会话 cookie 或服务端会话状态维护。每个标签页通过 useAgentChat 创建独立的本地 hook 实例，但底层对话状态（消息列表、活跃 turnId）在服务端统一管理。

(2) 停止操作的广播：当任一标签页发起 stop() 显式取消信令时，服务端标记当前 Turn 为已取消状态。其他标签页通过以下两种方式之一感知取消事件：(a) 轮询模式——各标签页在恢复或心跳请求中获取最新 Turn 状态，发现已取消后更新本地 UI；(b) 推送模式——通过 BroadcastChannel API 或 SharedWorker 在同一浏览器内的标签页间广播取消事件，各标签页同步更新状态。

(3) 多标签页观察：在 Durable 模式下，多个标签页可同时观察（observe）同一个正在执行的 Agent Turn。服务端将流式消息同时推送给所有活跃连接的标签页。当某一标签页断开时，不影响其他标签页的流接收；当所有标签页均断开时，服务端继续执行（Durable 模式）。该行为与单个标签页的语义完全一致。

(4) 状态竞争处理：当多个标签页几乎同时发送冲突操作（例如一个标签页发送消息而另一个标签页点击停止）时，服务端以先到达的请求为准，后续冲突请求返回状态冲突错误（409 Conflict），客户端据此更新本地状态。

### 迟到服务端消息处理

在 Durable 模式下，服务端可能在客户端已执行本地清理后仍生成消息（例如 Agent 在客户端断开期间完成了推理并产生了最终回复）。这些「迟到消息」需要被妥善处理：

(1) 迟到消息的暂存：服务端将迟到消息按 turnId 和 messageSeq 持久化存储在 Durable Object 的存储中，等待客户端恢复连接时投递。

(2) 客户端恢复时的消息对齐：客户端重连时携带最后接收的 messageSeq。服务端从该序号之后开始投递所有未确认消息。客户端收到消息后按 messageSeq 排序，过滤已接收的重复消息，将新消息追加到本地消息列表。

(3) 已完成 Turn 的迟到发现：若客户端重连后发现该 Turn 已完成（收到完成信号），客户端将最终消息一次性渲染到 UI，并更新本地状态为 idle。若客户端重连后发现该 Turn 已被取消（通过其他标签页或超时策略），客户端丢弃迟到消息并更新状态。

(4) 超时清理：为避免迟到消息无限累积，服务端为每个 Turn 设置最大保留时间（如 5 分钟）。超过保留时间且无客户端恢复连接的 Turn，其迟到消息随 Durable Object 的存储清理策略被回收。

### 技术效果

相比现有方案（客户端断开即无条件终止服务端任务），本方案具有以下技术效果：

(1) 减少无效重复计算：在 Durable 模式下，浏览器刷新或网络波动不会导致已进行到一半的 Agent 推理和工具调用被丢弃，用户重连后可继续接收剩余输出，避免了从头重新执行 Agent Turn 带来的 token 消耗和延迟。

(2) 语义精确性：通过将客户端本地清理与服务端取消分离为独立信令通道，消除了「关闭标签页是否等于用户想停止回答」的语义模糊性。用户意图（停止生成）与应用框架行为（组件卸载清理）不再混淆。

(3) 开发者可控性：通过 lifecycleMode 配置参数，开发者可根据应用场景选择 Durable 或 Request-Lifetime 模式，无需修改业务代码。

(4) 多标签页一致性：停止操作在所有标签页间保持一致，避免了一个标签页停止而另一个标签页仍在等待输出的不一致状态。

### 风险与待确认问题

以下为当前方案中需要后续确认的风险点和待确认问题：

(1) Durable Object 资源占用：Durable 模式下，客户端断开后服务端继续执行，可能导致 Durable Object 实例的活跃时间延长。需要评估在大量并发用户断开但不取消的场景下，对服务端计算和存储资源的压力。建议结合 Durable Object 的超时策略和最大并发限制进行压力测试。

(2) 恢复令牌的安全边界：恢复令牌（turnId + messageSeq）允许客户端恢复接收服务端消息流。需确认是否存在跨用户恢复的潜在风险——即恶意用户通过猜测或枚举 turnId 获取其他用户的对话内容。建议在服务端校验恢复令牌与会话 cookie 或用户身份凭证的绑定关系。

(3) Request-Lifetime 模式下的取消传播延迟：在 Request-Lifetime 模式下，服务端依赖 HTTP 请求的 abort 信号感知客户端断开。在网络分区场景下（如客户端网络断开但服务端 TCP 连接尚未超时），取消传播可能存在秒级延迟。需确认该延迟是否在可接受范围内。

(4) 与流式响应的兼容性：当前方案假设使用 SSE 或 HTTP 流式响应（ReadableStream）作为传输协议。若后续引入 WebSocket 作为传输层，断开检测和重连逻辑需相应调整。

(5) 移动端和应用内 WebView 场景：移动端浏览器和应用内 WebView 的生命周期与桌面浏览器存在差异（如后台冻结、内存回收更激进）。需验证 useAgentChat 的清理和恢复逻辑在这些环境下的表现。
