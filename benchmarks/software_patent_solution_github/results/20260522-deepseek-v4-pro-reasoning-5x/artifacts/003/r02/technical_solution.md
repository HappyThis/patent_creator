## 技术方案

本方案在 Mission Control（以下简称 MC）现有任务看板和主数据库不变的前提下，增加一套可选的异步同步机制，将任务数据以机器可读的镜像文件形式写入指定的 Git 仓库，供外部开发者和 agent 工作流无数据库依赖地读取与追踪。核心原则为：主数据库始终是任务数据的唯一权威写入入口；外部 Git 仓库为只读镜像；同步过程与主业务 CRUD 操作完全解耦，同步失败不阻塞、不回滚任何日常任务操作。

### 技术问题

Mission Control 的任务数据存储在应用自身的数据库中。外部 agent 工具、CI/CD 流水线或开发者若要获取任务状态，通常需要直接访问 MC 数据库或调用其 API，这带来三类问题：(1) 耦合性——外部系统必须了解 MC 的数据模型和接口语义；(2) 可达性——在无网络或受限环境中外部系统无法访问 MC 实例；(3) 可追踪性——任务变更历史与代码仓库的版本历史互相孤立，难以在代码审查或自动化流水线中关联任务状态。

本方案要解决的核心技术问题是：如何在保证主数据库为唯一权威写入入口、同步失败不影响主业务的前提下，将任务数据以确定性的、机器可读的文件形式自动同步到 Git 仓库中，使外部系统能通过标准 Git 操作获取任务镜像，且任务标识、状态语义和删除事件在两边保持一致。

### 整体架构

系统在 MC 主数据库一侧增加同步事件 outbox 表，在应用层增加同步调度器与镜像序列化器，并在独立的 Git 操作引擎中维护目标仓库的本地工作副本。整体数据流为单向：MC 主库 → outbox 事件 → 异步消费 → 序列化镜像 → Git 提交推送。外部系统仅通过 clone/pull 仓库读取镜像文件，不反向写入。

### 关键模块

系统包含以下七个关键模块，各模块职责明确、边界清晰：

（1）同步配置管理器：管理每个项目的同步开关、目标 Git 仓库地址、认证凭据、镜像文件格式（YAML 或 JSON）和仓库内镜像根目录路径。未启用同步的项目完全不触发后续流程。

（2）同步事件总线（Outbox）：在 MC 主业务事务提交任务 CRUD 操作时，同步向 outbox 表写入一条事件记录，包含任务 ID、变更类型（created/updated/deleted）和操作时间戳。该写入与主业务在同一数据库事务中完成，保证不丢失事件。事件的消费完全异步，由独立调度器轮询处理。

（3）任务镜像序列化器：根据事件中的任务 ID 从主库读取完整任务数据，生成结构化镜像文件。文件包含任务标题、描述、状态、优先级、指派人、标签、自定义字段、父子关系等完整字段。状态等枚举值直接使用主库原始值，不做语义映射转换。

（4）路径映射器：实现确定性函数 f(task_id, project_key) → repo_path，根据任务的不可变标识和所属项目键值计算仓库内的文件路径。典型映射规则为 {root}/{project_key}/{task_id}.task.{yaml|json}，外部系统使用相同函数可在本地独立计算出同一路径。

（5）Git 操作引擎：管理目标仓库的本地工作副本缓存，按顺序执行 pull --rebase → 写入/更新镜像文件 → git add → git commit → git push。提交信息包含任务 ID、变更类型和操作时间戳。推送失败时采用指数退避重试策略。

（6）冲突处理模块：处理两类冲突。Git 层面 push 被拒时，执行 pull --rebase 后重推。语义层面若外部系统意外修改了仓库中的镜像文件，以主库数据覆盖写入并产生告警通知，不阻塞同步流水线。

（7）同步状态追踪器：记录每条同步操作的（任务 ID、Git commit SHA、同步时间戳）三元组，支持增量同步判断和断点续传。

### 处理流程

以下分别描述任务创建/更新同步、删除同步和冲突处理三条关键流程。

【创建与更新同步流程】：(1) 用户在 MC 看板创建或更新任务，应用层在提交主库事务时同步向 outbox 表写入事件记录（task_id、change_type、timestamp），同事务提交。(2) 异步调度器轮询 outbox 表获取未处理事件，检查对应项目的同步配置是否启用；未启用则标记事件为已跳过。(3) 若同步已启用，调度器调用镜像序列化器从主库读取任务最新数据，生成 YAML/JSON 镜像文件。(4) 路径映射器计算目标文件路径。(5) Git 操作引擎对本地工作副本执行 pull --rebase，将镜像文件写入计算出的路径，执行 git add 和 git commit（提交信息包含任务 ID 和变更类型），最后 git push。(6) 推送成功后同步状态追踪器记录（task_id、commit_sha、timestamp）；推送失败则将事件放回重试队列，按指数退避策略等待后重试。整个过程完全异步，用户在 MC 看板的 CRUD 操作不感知同步状态。

【删除同步流程】：当任务在 MC 中被删除时，outbox 写入 task.deleted 事件。由于主库中任务记录已不存在，序列化器无法读取原数据。系统提供两种可配置策略：(A) 物理删除模式——在仓库中删除对应镜像文件，提交删除操作，外部系统 pull 后文件消失；(B) 墓碑模式——在任务原路径写入仅含 task_id 和 deleted: true 标记的墓碑文件，保留删除审计痕迹。墓碑文件可配置 TTL 自动清理。

【冲突处理流程】：Git 操作引擎在执行 push 时若收到 rejected 响应（远程有新提交），执行 pull --rebase 将远程变更合并到本地。若 rebase 过程中发现远程对镜像文件有内容级修改（语义冲突），系统以主库当前数据覆盖远程修改、重新提交并推送，同时向管理员发送告警通知。该策略确保主库始终为权威数据源，语义冲突不阻塞同步。

### 技术效果

本方案相比现有任务同步方式，带来以下技术效果：

（1）零耦合外部访问：外部 agent 工具仅需 clone Git 仓库并解析结构化文件，无需了解 MC 数据库模型或 API 协议。路径映射的确定性保证外部系统可独立定位任意任务的镜像文件。

（2）同步与主业务完全解耦：outbox 模式将事件写入与主业务事务绑定（不丢事件），但消费完全异步。Git 推送失败仅进入重试队列，不影响用户在 MC 看板的任何 CRUD 操作。

（3）状态语义一致性：镜像文件中的状态字段直接使用主库枚举原值，不做映射翻译，消除因状态转换表不一致导致的含义偏差。冲突场景以主库覆盖为原则，保证仓库镜像最终与主库收敛。

（4）版本可追踪性：每次同步操作记录对应的 Git commit SHA，可将任务变更与代码仓库的提交历史关联。删除操作通过墓碑文件或文件删除记录保留审计痕迹。

（5）可配置与可扩展：同步开关按项目粒度控制，文件格式（YAML/JSON）、删除策略（物理删除/墓碑）和仓库地址均可配置。未来如需支持双向同步，可在现有镜像文件基础上增加变更检测和合并策略。

### 风险与待确认问题

以下问题建议在实施前确认或在设计阶段预留扩展点：

- 仓库规模与性能：单仓库承载十万级任务镜像文件时，Git 操作（status、pull、push）可能出现性能退化。可考虑按项目（project_key）拆分独立仓库以降低单仓库文件数。
- 附件与二进制数据：任务描述中可能包含图片、文件附件等二进制内容。需确认是直接 base64 嵌入镜像文件（增大文件体积），还是仅保留附件引用 URL 而附件仍由 MC 原有存储服务提供。
- 事件乱序处理：在极端情况下，同一任务 ID 的 deleted 事件可能因重试延迟而在 created 事件之前被消费。需引入事件版本号或时间戳的乱序检测与丢弃机制。
- 双向同步扩展：当前方案为 MC→Git 单向同步。若未来需要支持外部 agent 通过修改仓库文件反向更新 MC 任务，需额外设计变更检测、冲突解决和权限控制机制。
- 认证凭据管理：Git 仓库的访问凭据（SSH Key 或 Access Token）需支持定期轮换，并在凭据失效时产生可操作的告警而非静默丢失同步。
- 墓碑文件生命周期：墓碑模式下需定义清理策略（TTL 到期自动删除或手动批量清理），避免仓库中墓碑文件无限累积。
