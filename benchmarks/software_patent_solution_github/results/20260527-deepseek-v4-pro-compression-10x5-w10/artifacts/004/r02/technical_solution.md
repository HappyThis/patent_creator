## 技术方案

本方案针对基于 Markdown 文件的共享知识库（如 ByteRover context tree）中，团队协作与运行时动态信息之间的矛盾，提出一种「静态知识文件 + 本地动态信号叠加层」的双层架构。核心思想是：将项目知识的结构化描述、语义说明、关系定义等可审阅、可版本对比的内容保留在共享的 Markdown 知识文件中；而将检索命中次数、使用频率、排序权重、本机缓存热度和成熟度评分等频繁变化的运行时信号，从 Markdown 文件中迁出，存入各用户本地的动态信号存储中。系统在知识检索、排序和展示时，透明地融合两层数据，对上层使用者呈现统一视图。

### 字段分类与迁出规则

系统将每条知识条目（对应 Markdown 文件中的一个章节或 block）的字段按变化频率和审阅需求分为两类。

第一类为「静态知识字段」，继续保留在共享 Markdown 文件中，接受版本控制。包括：知识标题、知识正文（语义描述与规则说明）、知识之间的显式关联（如父节点引用、相关条目链接）、知识类型标签、创建者和最后修订者标识、以及人工标注的成熟度级别（如「草稿」「已审阅」「已确认」由人工修订触发）。这些字段变化频率低、变更有语义含义，适合团队审阅和 diff 对比。

第二类为「动态信号字段」，从 Markdown 中迁出，存储于各用户本地的动态信号叠加层中。包括：检索命中次数及最近命中时间、使用频率统计（如被引用次数、被召回次数）、本机排序权重系数、知识新鲜度或衰减评分、自动推断的成熟度建议值、以及本机缓存热度。这些字段变化频繁（每次检索和每次使用都可能触发更新），不具备版本对比的语义价值，写入共享文件只会制造噪声。

Markdown 文件中仅保留一个轻量的「动态信号锚点」——一个不可见或折叠的引用 ID 字段，用于在读取时将静态知识与本地动态信号精确关联。该锚点值在知识条目创建时生成，除非条目被删除或合并，否则终生不变。

### 动态信号叠加层的结构

动态信号叠加层是每个用户本地的持久化存储，不纳入共享版本控制。其数据结构以知识条目的锚点 ID 为键，值为一个信号记录对象，包含以下字段：命中计数（hit_count）及最近命中时间戳、使用计数（usage_count）及最近使用时间戳、本机排序权重（local_weight，浮点数）、自动成熟度评分（auto_maturity_score，由系统根据使用频率和时效衰减计算）、本机缓存热度（cache_heat，基于 LRU 或 LFU 策略）、以及本机自定义标签或备注（user_tags）。

叠加层存储引擎选择本地嵌入式键值数据库（如 SQLite 或 LevelDB），以文件形式存在于用户工作区中（例如 .byterover/signals.db），不纳入 Git 跟踪（通过 .gitignore 排除）。对于跨设备协同场景，叠加层数据可通过加密的端到端同步通道在用户自有设备间同步，但不进入共享仓库。每次信号更新以 upsert 方式写入，不产生历史版本；仅保留最新值，避免存储膨胀。

### 读取融合流程

当系统需要读取并展示知识库内容（如检索、浏览上下文树、生成提示词）时，执行以下融合流程：

步骤一：解析 Markdown 文件，提取所有知识条目及其锚点 ID，构建静态知识对象图。步骤二：以批量查询方式从本地动态信号叠加层中读取所有锚点 ID 对应的信号记录。对于叠加层中不存在的锚点（新条目或首次在本机访问），使用默认信号值（命中计数为 0、权重为默认中性值等）初始化，并异步回写一条空记录以建立映射。步骤三：将静态字段与动态信号按锚点 ID 合并为统一的知识条目视图对象。合并后的视图对象对外暴露所有字段，调用方无需感知数据来源。步骤四：根据合并后的动态信号执行排序、过滤、权重调整等下游逻辑。

融合过程在读路径上以读时合并（merge-on-read）模式执行，不修改 Markdown 文件。信号更新在写路径上以独立事务写入叠加层，两条路径互不阻塞。

### 迁移期兼容

方案设计了平滑迁移机制，确保从「动态信号嵌入 Markdown」的旧格式过渡到双层架构时，不影响现有团队工作流和已积累的动态数据。

迁移分为三个阶段。第一阶段（检测与标记）：系统在读取 Markdown 文件时，检测知识条目中是否存在旧格式的内嵌动态信号字段（如 YAML front matter 中的 hit_count、weight 等）。若检测到，系统在内存中将动态信号提取出来，写入本地叠加层，同时在 Markdown 的对应条目中插入锚点 ID，并保留旧字段的注释副本（以 HTML 注释或 front matter 中标记 deprecated 的方式）供人工确认。此阶段 Markdown 文件中同时存在新旧两种表示，系统以叠加层数据为准。第二阶段（清理）：经过一个可配置的宽限期（如 30 天）后，系统在下次读取时自动删除 Markdown 中已标记 deprecated 的动态字段，仅保留锚点 ID 和静态字段。此操作产生一次 Git commit，commit message 明确标注为自动迁移清理。第三阶段（完成）：所有知识条目完成迁移后，Markdown 文件不再包含任何动态信号字段，系统进入纯双层架构运行模式。

迁移期间，未迁移的旧条目与已迁移的新条目共存于同一知识库中，系统在读取时按条目粒度判断数据来源：有锚点 ID 的条目走融合路径，无锚点 ID 的旧条目直接从 Markdown 中解析动态字段并同步写入叠加层。

### 并发更新与冲突处理

本方案涉及两类并发场景：多用户对共享 Markdown 的并发编辑（通过 Git），以及同一用户本机多进程对叠加层的并发读写。

对于共享 Markdown 的并发编辑，由于动态信号已迁出，Markdown 文件的变更集中在静态知识字段的增删改，变更频率大幅降低，Git 合并冲突的概率显著减少。当确实发生静态字段的合并冲突时，冲突范围仅限于知识正文、标题和显式关联字段，不再混杂命中计数等频繁变化的数值字段。系统提供合并辅助工具：在 Git merge conflict 时，对锚点 ID 字段采用「保留双方」策略（两个锚点均保留并建立映射关系），对静态正文字段采用常规的三路合并，标记冲突交由人工解决。

对于本机叠加层的并发读写，由于叠加层引擎（SQLite 或 LevelDB）本身支持多读单写或 WAL（Write-Ahead Logging）模式，动态信号的更新采用「读取-合并-写入」原子事务：读取当前信号值、在内存中累加增量（如 hit_count += 1）、在事务中写回。若事务冲突（如另一进程已修改），系统自动重试有限次数（默认 3 次），每次重试重新读取最新值后重新计算增量。重试耗尽后，采用「最后写入者获胜」策略记录本次增量，并输出一条低级别日志告警，不影响主路径。

### 失败隔离与降级

方案将动态信号叠加层设计为「尽力而为」组件，其故障不影响系统的核心知识读写路径。具体隔离策略如下：

当叠加层存储不可用（如数据库文件损坏、磁盘满、权限不足）时，系统进入降级模式：读取操作仅返回 Markdown 中的静态字段，所有动态信号字段回退为默认中性值；信号更新操作被静默丢弃并记录到错误日志，不抛出异常阻塞主流程。降级模式对上层调用者透明，知识检索和展示功能继续正常工作，仅排序和推荐质量暂时下降。系统在每次读取操作前执行叠加层健康检查（轻量 ping 操作，如执行 SELECT 1），若连续 N 次（默认 3 次）健康检查失败，触发告警通知用户检查本地存储。一旦叠加层恢复可用，系统自动退出降级模式，后续的信号更新和融合正常执行。

对于 Markdown 文件本身的读取失败（如 Git 冲突导致文件格式损坏），系统采用逐条目的容错解析：跳过解析失败的条目并记录，正常解析其余条目，保证部分可用而非全量不可用。

### 归档/剪枝/合并时的清理一致性

当知识条目发生归档、剪枝或合并操作时，其关联的动态信号必须同步清理，否则叠加层中会积累无主信号数据，造成存储膨胀和检索干扰。

对于归档操作：Markdown 中的知识条目被移动到归档目录或标记为 archived 状态后，系统在下一次全量索引重建时，扫描叠加层中所有锚点 ID，将 Markdown 中已不存在的锚点对应的信号记录标记为 orphan（孤儿），并移入单独的 orphan_signals 表而非直接删除。orphan 表保留 90 天，期间若条目被恢复（unarchive），信号记录自动从 orphan 表迁回主表；90 天后 orphan 记录被物理删除。

对于剪枝（删除）操作：用户执行删除知识条目时，系统同步从叠加层主表中删除对应锚点的信号记录。该操作为软删除：先标记 deleted 状态保留 30 天（支持撤销恢复），30 天后由后台清理任务物理删除。

对于合并操作：两个知识条目合并为一个时，系统生成新的锚点 ID。被合并的两个旧锚点及其信号记录不是简单丢弃，而是按以下策略合并：命中计数和使用计数取和值；排序权重取加权平均值（按各自历史命中次数加权）；最近命中/使用时间取两者中的较晚值；成熟度评分取加权平均值。合并后的信号记录绑定到新锚点 ID，旧锚点标记为 merged 并保留引用到新锚点 ID，供审计追溯。清理任务在 90 天后物理删除 merged 记录。

所有清理操作均由后台定时任务驱动（默认每 24 小时执行一次），不在用户交互路径上执行，确保 UI 响应不受影响。清理任务在执行前获取叠加层的排他写锁，清理完成后释放锁并记录清理摘要日志。

### 技术效果

本方案在保持知识文件可共享、可审阅、可版本对比的前提下，继续利用运行时动态信号，带来以下技术效果：

其一，版本控制噪声显著降低。动态信号从 Markdown 中迁出后，共享文件的变更集中在有语义价值的知识内容变化上，diff 结果精简且可读，团队 code review 和 Git blame 的可用性大幅提升。其二，合并冲突减少。频繁变化的数值字段不再写入共享文件，多人并行编辑同一知识库时，Git merge conflict 的概率和冲突范围均显著缩小。其三，知识检索质量不受损。动态信号仍可通过叠加层参与排序、推荐和过滤，系统在降级模式下也能以默认信号继续运行，不丢失核心检索功能。其四，存储与维护分离。静态知识由共享仓库保证一致性和历史追溯，动态信号由本地存储保证写入性能和隔离性，各司其职。其五，迁移平滑可逆。旧格式条目可与新格式条目共存，且归档/剪枝/合并操作中的信号清理采用延迟物理删除策略，支持误操作恢复。

### 风险与待确认问题

以下为当前方案中需要结合 ByteRover 实际代码库进一步确认的风险点：

1. 锚点 ID 的生成与一致性：锚点 ID 需要在知识条目创建时生成，且需保证在团队不同成员的克隆副本中一致。若当前 ByteRover 知识条目没有唯一标识符，需要引入 ID 生成机制（如基于内容哈希或 UUID 并存入 Markdown）。需确认现有 Markdown 解析器是否支持在 front matter 或 HTML 注释中嵌入锚点 ID。2. 叠加层存储的具体选型：本方案建议 SQLite 或 LevelDB，需结合 ByteRover 的运行时依赖（Node.js / Python / Rust 等）选择合适的绑定库，并确认多进程并发访问模式下的性能。3. 跨设备同步策略：本方案将叠加层设计为本机存储，若 ByteRover 支持多设备使用场景，需设计端到端加密同步通道，但该需求是否在当前版本范围内需与产品确认。4. 旧格式迁移的触发时机：迁移清理阶段由后台任务还是用户手动触发需确认，避免自动 commit 污染 Git 历史或触发 CI/CD 流水线。5. 动态信号的隐私边界：若命中计数和使用频率被视为团队敏感信息（反映个人工作习惯），需考虑是否对叠加层数据提供加密存储。
