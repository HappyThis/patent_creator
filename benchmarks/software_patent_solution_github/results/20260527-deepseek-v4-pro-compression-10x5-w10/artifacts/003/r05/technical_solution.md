## 技术方案

本方案提出一种将 Mission Control 任务数据以机器可读任务镜像文件形式同步至 Git 托管代码仓库的技术机制。该机制在 Mission Control 现有任务看板和数据库保持为唯一写入入口的前提下，通过异步解耦的同步通道，将任务状态、属性和生命周期变化映射为仓库内结构化的任务文件及其版本历史，使外部 agent 工具无需直接访问 Mission Control 数据库即可读取、追踪和协作处理当前任务队列。同步通道的设计遵循「主路径不阻塞、失败不回退」原则：任务的创建、更新与删除操作在主数据库事务中完成即视为成功，同步操作以异步任务形式在事后执行；同步失败时仅记录失败状态和重试信息，不影响主路径的可用性和数据一致性。

### 整体架构

系统由三个核心模块构成：事件捕获模块、同步编排模块和 Git 操作模块。事件捕获模块监听 Mission Control 主数据库的任务变更事件（创建、更新、删除），将事件转化为标准化的同步消息写入同步消息队列。同步编排模块从消息队列中消费同步消息，负责确定任务镜像文件的存储路径、生成文件内容，并构造 Git 提交所需的变更集合。Git 操作模块接收变更集合，在目标 Git 仓库的工作副本中执行文件写入、暂存、提交和推送操作。三个模块之间通过消息队列解耦；事件捕获模块运行在主数据库事务提交之后、以非阻塞方式投递消息，确保主路径不受同步链路延迟或失败的影响。

### 任务镜像文件结构与标识映射

每个 Mission Control 任务在仓库中对应一个独立的机器可读任务镜像文件。文件采用 Markdown 正文与 YAML 前置元数据（front matter）的复合格式：YAML 区域包含任务的稳定标识符、标题、状态、优先级、指派人、标签、创建时间、更新时间等结构化字段；Markdown 区域承载任务描述、验收标准、子任务清单等富文本内容。这种格式同时满足机器解析（agent 工具可直接解析 YAML 字段获取结构化状态）和人类可读（开发者可直接在编辑器中查看和编辑）的双重需求。

任务标识到文件路径的映射采用确定性哈希分桶策略。系统以任务的稳定唯一标识符（UUID）为输入，计算 SHA-256 哈希值，取哈希值的前两位十六进制字符作为第一级目录名、第三至四位作为第二级目录名，在两级分桶目录下以完整任务标识符加扩展名（.md）作为文件名。例如，任务 ID 为 "task-abc123"、其哈希前缀为 "a1b2"，则文件路径为 "tasks/a1/b2/task-abc123.md"。该映射策略无需维护额外的查找表，外部系统在已知任务 ID 时可独立计算出文件路径，实现无中心索引的定向访问。分桶设计确保单个目录下文件数量可控，避免文件系统级别的性能退化。

### 同步触发与异步执行机制

同步触发采用数据库变更事件驱动模式。Mission Control 主数据库在任务表上注册数据库触发器或应用层事件钩子，当 INSERT、UPDATE 或 DELETE 操作提交成功后，事件捕获模块将变更类型、任务标识符、变更前后关键字段的差异快照封装为同步事件消息，以 at-least-once 语义投递到持久化消息队列中。消息投递与主数据库事务解耦：投递失败时仅写入本地重试日志，不阻塞也不回滚已提交的主事务。

同步编排模块以独立进程或工作线程运行，从消息队列中拉取同步事件并执行处理流水线：首先校验事件有效性（任务是否仍存在、事件是否过期）；然后按任务标识符计算目标文件路径；接着读取仓库工作副本中该路径的当前文件内容（若存在），与事件携带的最新状态进行对比；当检测到实际状态变化时，生成新的任务镜像文件内容，构造文件级变更操作（新增/修改/删除），并将该变更操作提交给 Git 操作模块。对于短时间窗口内的同一任务多次变更，编排模块通过消息去重窗口合并连续事件，减少冗余 Git 操作。

### Git 操作与版本管理

Git 操作模块维护一个与目标远程仓库关联的本地工作副本。模块收到同步编排模块提交的文件变更集合后，按以下顺序执行 Git 操作：（1）对工作副本执行 git pull --rebase，拉取远程最新提交并尝试将本地未推送变更 rebase 到远程分支之上；（2）按变更集合逐一写入文件内容，新增文件通过 git add 暂存，修改文件通过覆盖写入后暂存，删除文件通过 git rm 暂存；（3）执行 git commit，提交信息自动生成为包含操作类型、任务标识符和关键字段摘要的结构化消息；（4）执行 git push 将提交推送至远程仓库。

每次同步批次的多个文件变更聚合为单个 Git 提交，提交信息格式为 "sync: <操作类型> task <任务ID> — <标题摘要>"，方便外部系统通过 git log 快速定位任务变更历史。任务的完整生命周期变更通过 Git 提交历史形成可审计的版本轨迹，外部 agent 工具可通过 git diff 对比任意两个版本间的任务状态差异。

### 冲突与失败处理

冲突处理覆盖两种典型场景。第一种是 Git rebase 冲突：当远程仓库存在外部提交修改了同一任务文件时，git pull --rebase 可能产生合并冲突。此时 Git 操作模块放弃本次 rebase（通过 git rebase --abort），将当前同步批次标记为冲突状态，同时保留事件消息在重试队列中，等待下一轮同步周期重试。重试时若远程冲突已由外部解决，则 rebase 可顺利通过。第二种是并发写入冲突：两个同步编排实例可能同时处理同一任务的不同版本事件。系统通过对任务标识符的哈希分片分配消费实例，确保同一任务的事件始终由同一个编排实例串行处理，从设计上消除并发写入冲突。

失败处理遵循「降级不降可用」原则。Git 操作模块在执行 push 失败（如网络不可达、认证过期、远程仓库不可用）时，不阻塞后续同步批次的处理；失败消息回写到消息队列的延迟重试分区，按指数退避策略在 30 秒、2 分钟、10 分钟、30 分钟后重试，超过最大重试次数后转入死信队列并触发告警通知。在整个失败-重试链路中，Mission Control 主数据库的任务操作不受任何影响。同步状态（成功、待重试、失败告警）通过同步状态表持久化记录，可供管理面查询和手动干预。

### 删除同步与生命周期追踪

任务在主数据库中删除时，同步机制不在仓库中直接物理删除文件，而是将任务镜像文件替换为删除标记文件。该标记文件在 YAML 前置元数据中设置 status 为 "deleted"、deleted_at 为删除时间戳，保留任务标识符和历史可追溯信息；Markdown 正文替换为简短说明，指出该任务已在 Mission Control 中删除。该设计的目的是保持 Git 历史中任务的完整生命周期记录：外部 agent 工具通过 git log 可追溯任务从创建、历次更新到最终删除的全部变更；通过检查文件当前内容中的 status 字段即可判断任务是否已终止。同时，删除标记的存在避免了纯物理删除后，外部工具因文件突然消失而误判为同步异常的问题。

### 技术效果

本方案在以下方面产生区别于现有方式的技术效果。第一，基于确定性哈希分桶的标识到路径映射，使外部 agent 工具在仅知道任务 ID 的条件下即可独立定位任务文件，无需依赖中心索引服务或数据库查询，降低了跨系统协作的耦合度。第二，异步解耦的同步通道设计确保同步链路的任何延迟、失败或不可用均不会反向影响任务主数据库的写入可用性，避免了分布式事务或两阶段提交带来的可用性退化。第三，以 Git 提交历史承载任务的状态变更轨迹，赋予任务数据天然的版本化和审计能力——外部工具可通过 git log、git diff 和 git blame 等标准 Git 原语查询任务演化历史，而不需要在 Mission Control 内部额外实现版本存储。第四，删除标记文件机制替代物理删除，既保持了生命周期完整性，又消除了文件消失导致外部工具状态误判的问题。

### 风险与待确认点

以下为需要后续确认和评估的风险点：（1）任务标识符的稳定性——如果 Mission Control 任务主键在任务生命周期内可能发生变化，哈希分桶映射会导致文件路径漂移，需要确认当前系统是否使用不可变 UUID 作为任务标识。（2）仓库文件总量增长——在任务数量极大（如百万级）时，两级哈希分桶的目录数（256×256=65536）是否满足文件系统性能要求可能需要评估；必要时可扩展为三级分桶。（3）外部直接修改任务文件——如果外部用户或 agent 直接向仓库提交对任务镜像文件的修改，这些修改不会自动反向同步到 Mission Control 主数据库，需要明确是否需要实现双向同步或至少检测并告警外部修改。（4）Git 操作模块的仓库工作副本管理——长期运行中工作副本可能积累磁盘占用，需要配套定期的仓库维护策略（如浅克隆、定期清理、仓库重建）。（5）消息队列的持久化和重试语义需要与 Mission Control 现有基础设施（消息中间件选型、部署拓扑）对齐确认。
