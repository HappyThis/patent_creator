## 技术方案

### 技术问题概述

Mission Control 作为任务管理看板应用，其任务数据存储在应用自身数据库中，外部 agent 工具和开发者工作流无法在不直接访问数据库的情况下读取、同步和追踪任务队列。现有 GitHub issue 同步能力虽然可将任务映射为 GitHub issue，但 issue 作为平台特定对象与代码仓库的版本化协作载体存在本质差异：issue 不跟随代码分支流转，不在仓库本地可访问，且其字段语义与 Mission Control 任务模型不完全对应。本方案提出一种将 Mission Control 任务数据以机器可读文件格式同步至 Git 代码仓库的技术机制，使任务数据成为仓库中可版本化、可分支跟随、可被标准 Git 工具和 agent 工作流直接消费的一等公民。

### 任务文件结构设计

在 Git 仓库中建立专用的任务镜像目录（默认为 .mission-control/tasks/），每个 Mission Control 任务对应该目录下的一个独立文件。文件格式采用机器可读的结构化文本格式（YAML 或 JSON），便于 agent 工具解析和处理。每个任务文件包含以下字段：任务唯一标识（id）、标题（title）、描述（description）、状态（status）、优先级（priority）、指派人（assignee）、标签（labels）、创建时间（created_at）、更新时间（updated_at）以及自定义字段扩展区（custom_fields）。这些字段与 Mission Control 任务模型保持语义一致，使得外部 agent 无需理解 Mission Control 内部数据库 schema 即可消费任务信息。

任务文件不包含 Git issue 编号或平台特定引用，仅以仓库相对路径标识自身。这种自包含设计使得任务镜像可以在任意 Git 分支上独立存在，跟随分支切换自然反映不同开发上下文中的任务视图，且不会与 GitHub/GitLab 等平台的对象 ID 产生耦合。

### 稳定任务标识到文件路径的映射

为实现任务标识到文件路径的稳定、确定性映射，系统使用 Mission Control 数据库中的任务主键（UUID）作为文件命名基础。映射规则为：task_id → .mission-control/tasks/{task_uuid}.{format}，其中 task_uuid 是 Mission Control 为每个任务分配的不可变唯一标识符，format 为约定的文件格式扩展名（yaml 或 json）。

该映射具有以下技术特性：（1）确定性——给定任务 UUID，无需查询任何外部索引即可计算出文件路径；（2）稳定性——任务 UUID 在任务生命周期内不变，因此文件路径在任务重命名、状态变更等操作下保持稳定；（3）无冲突性——UUID 的全局唯一性保证了不同任务之间不会产生文件路径冲突。外部 agent 可通过约定好的路径规则直接定位目标任务文件，无需维护额外的 ID-路径映射表。

### 同步机制与处理流程

同步模块作为 Mission Control 应用内部的独立组件运行，不侵入现有任务 CRUD 的核心路径。它采用事件驱动与定期巡检相结合的双模同步策略，确保任务镜像与数据库状态最终一致。

事件驱动路径：Mission Control 在任务创建、更新、删除操作成功后，向内部事件总线发布对应的领域事件（TaskCreated、TaskUpdated、TaskDeleted）。同步模块订阅这些事件，将事件携带的任务数据变更写入待同步队列（sync queue），由后台工作线程异步消费。事件发布在数据库事务提交之后进行，确保只有已持久化的变更才会触发同步。

定期巡检路径：同步模块维护一个轻量级的同步状态表（sync_state），记录每个任务最近一次成功同步的数据库版本号和时间戳。后台定时任务定期扫描数据库中更新时间晚于同步时间戳的任务记录，将其纳入待同步队列。巡检路径作为事件驱动路径的兜底机制，处理事件丢失、消费者重启等异常场景。

同步工作线程从队列中取出待同步任务后，执行以下流程：（1）根据任务 UUID 计算出目标文件路径；（2）在本地 Git 工作副本中写入或更新任务文件，将任务数据序列化为约定的结构化格式；（3）执行 git add 将变更暂存；（4）执行 git commit 提交变更，提交信息包含任务 UUID 和操作类型以便追溯；（5）执行 git pull --rebase 拉取远端变更并尝试自动合并；（6）执行 git push 将提交推送至远端仓库。每一步失败时均进入对应的失败处理分支。

### 冲突检测与失败处理

系统设计遵循'主数据源优先'原则：Mission Control 数据库始终是任务状态的权威来源，Git 仓库中的任务文件为派生镜像。在此原则下，冲突和失败处理策略如下：

Git 合并冲突处理：当 git pull --rebase 或 git push 因远端冲突而失败时，同步模块采用'本地覆盖'策略——首先执行 git fetch 获取远端最新状态，然后以 Mission Control 数据库中的当前任务数据重新生成任务文件并强制写入（git checkout --theirs 等效行为），再次提交并推送。对于已被远端删除的任务文件，同步模块将其视为正常状态变更并重新创建文件。这种策略确保 Mission Control 的数据库状态始终是最终生效的版本。

同步失败隔离：同步操作与 Mission Control 的任务 CRUD 操作完全解耦。任务创建、更新或删除的 API 请求在数据库事务提交后立即返回成功，同步操作在后台异步执行。若同步过程中发生网络故障、Git 认证失败、磁盘空间不足等错误，同步模块记录失败日志并将该任务标记为'待重试'状态，通过指数退避策略安排后续重试。无论同步成功与否，均不影响用户在 Mission Control 看板中的正常操作。

重试与告警：同步模块维护每个任务的连续失败计数。当连续失败次数超过阈值时，触发告警通知并暂停该任务的自动同步，由人工介入排查。其他任务的同步不受影响。重试间隔采用指数退避（如 1min、2min、4min、8min），最长不超过 30 分钟。当同步队列因持续故障积压时，巡检路径在下一个周期会自动兜底覆盖积压的任务。

### 删除同步机制

当 Mission Control 中的任务被删除时，同步模块需要将对应的任务文件从 Git 仓库中移除，而非仅标记为已删除状态。删除同步采用以下机制：

删除事件消费：同步模块订阅 TaskDeleted 领域事件，事件中携带被删除任务的 UUID。工作线程根据 UUID 计算出文件路径后，执行 git rm 删除该文件，然后通过 git commit 和 git push 将删除操作同步至远端仓库。与创建/更新同步一致，删除同步也遵循'主数据源优先'原则：即使远端仓库中该文件已被其他协作者修改，同步模块仍执行删除操作。

硬删除与软删除的区分：Mission Control 中可能存在软删除（逻辑删除，任务标记为已删除但数据库记录保留）和硬删除（物理删除记录）两种模式。对于软删除，同步模块在任务文件中写入 status: deleted 并保留文件，使外部 agent 可感知任务的生命周期终止；对于硬删除，同步模块执行 git rm 彻底移除文件。同步状态表中的记录在硬删除对应条目后保留一段宽限期（默认 7 天），以防止巡检路径将远端残留文件错误地重新创建。

### 技术效果

本方案相比现有技术方案（如仅将任务同步为 GitHub issue）具有以下技术效果：

（1）版本化跟随：任务文件作为 Git 仓库内容的一部分，自动跟随分支切换和版本历史，使任务状态与代码版本天然关联。外部 agent 可通过 git checkout 到特定分支或提交，直接获得对应时刻的任务视图，无需额外的时间戳查询或 API 分页。

（2）离线可访问：任务文件以本地文件形式存在于开发者的 Git 工作副本中，即使无网络连接或 Mission Control 服务不可用，外部 agent 仍可通过读取本地文件获取完整的任务信息。这消除了对 Mission Control API 或数据库的运行时依赖。

（3）平台无关：任务文件采用通用的结构化文本格式（YAML/JSON），不与任何特定 Git 托管平台（GitHub、GitLab、Gitee 等）的对象模型耦合。任何支持 Git 的基础设施均可作为同步目标，agent 工具只需文件读写和标准 Git 操作即可消费任务数据。

（4）故障隔离：同步模块与任务 CRUD 核心路径解耦，同步失败不阻塞用户正常操作。双模同步策略（事件驱动 + 定期巡检）保证了在网络不稳定或远端仓库短暂不可用的情况下也能最终达到一致状态。

（5）确定性寻址：基于任务 UUID 的文件路径映射使得外部 agent 无需查询索引或遍历目录即可直接定位特定任务文件。这在 agent 工作流中尤为重要——agent 可通过简单的路径拼接操作引用任务，实现任务状态的程序化读写和流水线集成。

### 风险与待确认问题

以下是当前方案中需要后续确认的技术风险点：

1. 大仓库性能：当 Mission Control 中存在大量任务（如数万条）时，.mission-control/tasks/ 目录下可能包含大量文件，需评估 Git 操作（git status、git add）的性能影响以及文件系统的 inode 压力。可考虑按 UUID 前缀分片（如 tasks/ab/cd/abCD...）的目录结构优化。
2. 分支间任务视图差异：不同 Git 分支可能拥有不同的任务文件集合，这既是特性也是潜在困惑点。需明确文档说明：外部 agent 应始终以当前 checkout 分支下的任务文件为准，跨分支任务状态对比需通过 Git diff 实现，不存在全局统一的任务视图。
3. 并发同步与 Git 锁：多个同步工作线程同时执行 git 操作时可能产生锁冲突（如 .git/index.lock）。需要在同步模块内部实现 Git 操作串行化或基于文件锁的互斥机制。
4. 远端仓库写入权限：本方案假设 Mission Control 拥有对目标 Git 仓库的写入权限（通过 deploy key 或 personal access token），这在实际部署中需要额外的密钥管理和权限配置。
5. 任务 UUID 的不可变性要求：本方案依赖任务 UUID 的不可变性来保证文件路径的稳定性。如果 Mission Control 存在任务 ID 迁移或重新生成机制，映射关系将断裂，需设计迁移方案。
