## 技术方案

### 技术问题概述

在基于大语言模型的AI对话系统中，对话请求通常具有长执行周期、流式输出和服务端持久计算的需求。客户端与云端Agent之间通过WebSocket等长连接进行通信，但客户端侧存在多种不同语义的断开事件：浏览器刷新、标签页关闭、React组件卸载、用户点击停止按钮、网络短暂断开等。现有方案将上述事件不加区分地映射为服务端取消，导致两个核心问题：一是浏览器刷新等短暂断开会错误终止正在执行的服务端推理，造成计算资源浪费和用户体验中断；二是用户停止生成的语义（仅停止前端展示）与服务端取消的语义（终止推理计算）被混为一谈，开发者无法根据场景灵活配置。本方案通过区分本地生命周期清理与服务端取消意图、引入可配置的持久化模式和请求级联生命周期模式、以及流恢复与多标签页协同机制，系统性地解决上述问题。

### 整体架构

本方案的整体架构分为三层：客户端层、传输通道层、服务端Agent层。客户端层以useAgentChat为核心，封装AI SDK的useChat，统一管理对话生命周期、流式消费和取消意图发送。传输通道层由WebSocketChatTransport实现，基于PartySocket提供自动重连的WebSocket通道，承载请求发送、流式接收、恢复请求和取消消息传递。服务端Agent层基于Cloudflare Durable Object实现AIChatAgent基类，天然具备持久化执行能力——即使客户端断开连接，DO实例仍继续运行直至chat turn完成。三层之间通过自定义消息协议（CF_AGENT_前缀消息）进行通信，包括CF_AGENT_CHAT_REQUEST_CANCEL（取消请求）、CF_AGENT_STREAM_RESUME_REQUEST（流恢复请求）、CF_AGENT_STREAM_RESUMING（流恢复通知）等。服务端内部包含五个关键子系统：AbortRegistry管理每个请求的取消信号；ResumableStream管理流chunk缓存和回放；ContinuationState管理工具调用的自动续接；TurnQueue串行化对话轮次；以及可选的chatRecovery纤维化执行模式。

### 客户端生命周期事件分类与语义映射

客户端断开事件可分为四类，各自具有不同的语义和期望行为。第一类：短暂网络断开。WebSocket连接因网络波动断开，但用户意图未变，浏览器标签页仍然存活。期望行为：传输层自动重连，服务端继续执行，通过流恢复机制补发丢失的chunk。第二类：浏览器刷新或标签页关闭。用户主动刷新页面或关闭标签页，前端运行时被销毁，但用户可能很快就重新打开。期望行为（默认durable模式）：服务端继续执行推理，前端重新打开后通过resume恢复流消费；不发送取消消息。第三类：React组件卸载。组件因路由切换等原因从DOM树移除，reader取消，但同一标签页内的其他逻辑仍在运行。期望行为：执行本地清理（reader cancel、stream controller close），但不一定触发服务端取消；具体行为由开发者通过模式配置决定。第四类：用户主动停止生成。用户点击停止按钮，明确表达终止当前回复生成的意图。期望行为：发送取消消息到服务端，终止推理计算。

当前实现中，组件卸载通过options.abortSignal触发abort回调，执行路径为：onAbort → 发送CF_AGENT_CHAT_REQUEST_CANCEL → finish(streamController.error(abortError), true)。其中keepId=true保留了requestId在activeRequestIds中，等待服务端done广播后清理。用户点击停止按钮调用stop()，同样经过reader cancel → onAbort → 发送CF_AGENT_CHAT_REQUEST_CANCEL。两者在取消通道上未做区分。改进方向：引入cancelIntent参数区分两类事件——stopIntent表示用户主动停止（发送取消消息），lifecycleCleanup表示组件卸载（默认仅做本地清理，不发送取消消息），由开发者通过配置选择组件卸载时是否级联取消服务端执行。

### 取消意图通道

取消意图通过自定义协议消息CF_AGENT_CHAT_REQUEST_CANCEL从客户端传递到服务端。该消息由WebSocketChatTransport在onAbort回调中调用agent.send发送，携带requestId标识被取消的特定请求。消息格式为{type: 'CF_AGENT_CHAT_REQUEST_CANCEL', id: requestId}。关键设计点：第一，cancel消息仅在用户主动停止（stopIntent）场景下发送；在durable模式下，组件卸载和浏览器刷新不发送此消息。第二，cancel消息通过同一WebSocket连接发送，不需额外通道；若连接已断开且属于stopIntent，则在重连后补发cancel消息。第三，cancel消息与resume请求互斥——收到cancel的请求不会触发流恢复，避免已取消的流被意外恢复。第四，服务端收到cancel消息后通过AbortRegistry查找对应AbortController并调用abort()，SSE reader loop检测到abortSignal后退出，标记流为aborted状态并发送done信号。第五，cancel操作是幂等的——重复cancel同一requestId不会产生副作用。

### 服务端取消执行机制

服务端通过AbortRegistry管理每个请求的取消信号。AbortRegistry是per-instance的注册表，提供四个核心方法：getSignal(requestId)获取或创建指定请求的AbortController和AbortSignal；cancel(requestId)触发abort，使对应signal进入aborted状态；remove(requestId)清理已完成的请求信号；destroyAll()在DO销毁或resetTurnState时清空所有注册信号。取消执行流程如下：服务端收到CF_AGENT_CHAT_REQUEST_CANCEL消息后，在onChatRequestCancel处理函数中调用_abortRegistry.cancel(data.id)。底层AbortController.abort()使关联的AbortSignal变为aborted。SSE reader loop在每次读取chunk前检查abortSignal.aborted标志，检测到aborted后立即退出循环，将流状态标记为aborted，并通过_cleanupAfterStream发送done广播通知所有连接。TurnQueue中的pending请求若检测到关联signal已aborted，则跳过执行并标记为stale。

### Durable模式与Request-lifetime模式

本方案引入两种可配置的执行生命周期模式，由开发者在初始化useAgentChat时通过executionMode参数选择。默认durable模式：服务端AIChatAgent基于Durable Object运行，chat turn的执行生命周期独立于客户端连接。客户端断开（包括组件卸载、浏览器刷新、网络断开）时，服务端不终止正在执行的推理，DO实例继续运行直到LLM响应完成或超时。前端恢复连接后，通过resume机制回放缓存的流chunk并继续接收新输出。可选request-lifetime模式：将chat turn的执行生命周期绑定到客户端请求的生命周期。当客户端组件卸载或标签页关闭时，自动发送CF_AGENT_CHAT_REQUEST_CANCEL消息，服务端终止推理。此模式适用于对计算成本敏感的场景。两种模式的选择影响客户端在lifecycleCleanup事件中的行为：durable模式下仅执行本地清理，不发送cancel消息；request-lifetime模式下在本地清理的同时发送cancel消息。用户主动停止（stopIntent）始终发送cancel消息，不受模式影响。

### 流恢复机制

流恢复机制由ResumableStream子系统实现，确保客户端重连后不丢失已生成的内容。_startStream(requestId)在chat turn开始时创建流元数据，包含streamId、状态和chunk缓冲区。_storeStreamChunk(streamId, body)将每个SSE chunk追加到内存缓冲区。_completeStream(streamId)标记流完成。当客户端发起恢复请求时，replayChunks(connection, requestId)按顺序回放缓冲区中的所有chunk，然后切换到实时流模式继续接收新chunk。恢复流程：客户端reconnectToStream发送CF_AGENT_STREAM_RESUME_REQUEST，服务端onConnect检测_hasActiveStream为true后，通过_notifyStreamResuming通知客户端即将恢复流。为防止恢复期间的消息广播冲突，重连连接被加入_pendingResumeConnections集合，排除在live broadcast之外，直到收到客户端ACK确认。若DO因休眠被驱逐后重新唤醒，_persistOrphanedStream检测到孤立流时，从存储中重建部分assistant message，保证长时推理任务不会因DO休眠而丢失中间结果。

### 多标签页协同

多标签页协同通过广播机制和请求来源追踪实现。服务端通过onAgentMessage监听器向所有连接的客户端广播消息，包括CF_AGENT_CHAT_MESSAGES（新消息）、CF_AGENT_CHAT_CLEAR（清空对话）、CF_AGENT_STREAM_RESUMING（流恢复通知）。每个标签页维护localRequestIdsRef，记录本标签页发起的请求ID集合。收到广播消息时，标签页检查消息中的requestId是否在localRequestIdsRef中：若存在，说明是本标签页发起的请求，跳过处理以避免重复渲染；若不存在，则同步更新本地状态。关键设计：请求级别的来源追踪而非连接级别的追踪，使得同一标签页可以同时处理多个请求且正确区分来源。chat clear操作通过generation递增实现失效机制：clear时generation加1，所有排队中且generation低于当前值的turn被标记为stale并跳过执行，确保多标签页间对话状态一致性。用户在一个标签页清除对话后，其他标签页收到广播并同步清空。

### 迟到消息处理

迟到消息指服务端在客户端已认为请求结束或取消后，仍通过广播发送的消息。本方案从三个层面处理迟到消息。第一，done信号终结：服务端在chat turn完成或取消后发送done广播，客户端收到done后从activeRequestIds中移除对应requestId。此后到达的该请求相关消息因requestId不在active集合中被丢弃。第二，stale检测：TurnQueue在取出turn执行前检查generation是否匹配。若在排队期间发生了chat clear导致generation递增，旧的turn被标记为stale并跳过，其后续产生的消息不会广播。第三，工具continuation的特殊处理：ContinuationState维护pending和deferred队列。当上一个continuation尚未完成时，新的continuation请求排队等待。若在此期间收到取消或clear，deferred continuation被清理。对已发送到客户端的工具调用结果，若客户端在处理前断开，_continuation.awaitingConnections跟踪等待连接的continuation状态——等待超时后自动完成流并标记。ContinuationState在onClose时清理pending、deferred和activeConnectionId，防止僵尸状态导致迟到广播。

### 技术效果

本方案通过系统性地解耦客户端生命周期事件与服务端取消语义，取得以下技术效果。第一，语义精确控制：区分浏览器刷新、组件卸载、用户停止和网络断开四类事件，每种事件具有独立的处理路径，开发者可通过executionMode和cancelIntent参数灵活配置。第二，计算资源高效利用：默认durable模式下，短暂断开不终止服务端推理，避免因页面刷新导致的重复计算，节省LLM调用成本。第三，用户体验无缝恢复：流恢复机制确保重连后不丢失已生成内容，支持chunk级精确回放，用户感知不到连接中断。第四，多标签页状态一致性：通过请求级来源追踪和generation失效机制，保证多标签页间对话状态实时同步，避免消息重复或丢失。第五，迟到消息安全兜底：通过done信号终结、stale检测和continuation生命周期管理三层防护，杜绝已取消请求的迟到广播污染客户端状态。第六，工具调用鲁棒性：ContinuationState的pending/deferred队列和等待超时机制确保工具自动续接在断连场景下正确完成或清理。
