# 软件专利技术方案 Benchmark 测试项筛选评估

评估时间：2026-05-15

## 评估结论

当前 10 个 case 中，建议先形成三层样本池：

- 强黄金 case：`007`、`010`
- 优先补跑验证的黄金候选：`005`、`008`、`002`、`004`
- 中等难度控制样本：`006`、`009`、`003`
- 暂缓作为黄金 case：`001`

其中 `007` 和 `010` 已经在清理历史运行后完成一次端到端评估，分别得到 `92.5` 和 `86` 分，题目质量和 judge 区分度都比较好。`001` 虽然端到端跑通并得到 `75` 分，但题目依赖较多 OpenCode 外部事实假设，参考答案和评分容易把“项目内可确认机制”和“外部 runtime 未确认细节”混在一起，暂不建议作为第一批黄金 case。

## 评估方式

本次评估分为两部分：

- 动态运行：重新跑通 `001`、`007`、`010`，验证 subject agent 能生成技术方案，Codex judge 能给出结构化评分。
- 静态筛选：阅读全部 10 个 case 的 `request.md`、`reference_solution.md`、`rubric.md`、`metadata.json` 和难度复评，判断题目是否适合长期作为软件专利技术方案生成能力 benchmark。

曾尝试启动全量多次评估，但批处理在 `001` 的 subject 生成阶段被已知执行链问题拖住，未形成有效 result。这个失败不计入 case 内容质量判断，只说明当前不适合直接做 10 个 case x 多轮的大批量自动跑。

## 去留标准

一个 case 建议进入黄金池，需要同时满足：

- 需求足够粗粒度：像真实用户提出的目标，而不是把实现步骤全部说完。
- 必须是功能或架构机制：避免 bug fix、参数调整、局部重构这类不太像发明的任务。
- 项目上下文可支撑：关键事实应能从快照源码、文档或测试中读到，不能高度依赖外部未确认知识。
- 参考方案足够细：需要说明模块关系、数据流、状态机、接口边界、异常/恢复、安全约束和技术效果。
- rubric 可区分好坏：不仅看是否写到关键词，还要能处罚空泛、编造、越权、缺少项目约束的方案。
- 至少能端到端跑通：subject agent 能产出 `disclosure.technical_solution`，judge 能稳定给出 JSON 评分。

## 后续建议

第一阶段先把 `007`、`010` 作为黄金 case 固定下来，并优先补跑 `005`、`008`、`002`、`004`。如果这些 case 单次跑通且 judge 反馈稳定，再进入多次重复评估。

第二阶段再决定 `003`、`006`、`009` 是否作为“中等难度控制样本”长期保留。它们不一定是最高价值发明题，但对模型能力分层有用。

第三阶段处理 `001`。它可以保留为 runtime 接入方向的题型，但建议减少对 OpenCode 未确认外部格式的依赖，或者换成项目快照中事实更完整的 runtime 接入需求。

在执行链问题修复前，不建议直接跑全量多轮评估。当前更合理的路线是：先筛出候选黄金池，再对候选逐个补跑；等 `section_writer` 子 agent 协议和 `document_edit.operations` 字符串化等问题稳定后，再做 3-5 次重复评估。
