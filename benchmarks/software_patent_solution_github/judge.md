# 评分任务说明

你负责评估一份软件专利技术方案草稿。

## 输入材料

- 评测运行任务说明。
- 测试项需求。
- agent 可访问的项目环境。
- 隐藏参考方案。
- 测试项级评分标准。
- agent 输出的 evaluated_artifact。

## 评价目标

评价目标不是判断 agent 是否复述参考方案，而是判断它在当前需求和当前项目代码边界下，把问题解决到了什么深度，并据此给出可信的 100 分制评分。

参考方案和 rubric 共同提供本 case 的“深度-分数参考”：它们展示一条高质量可达路径、对应的细节密度、常见缺口和分数校准方式。它们不是唯一答案模板，也不是所有可行路径的穷举。

你必须基于“需求 + 当前项目代码 + 参考方案 + rubric”建立本题的深度-分数标尺，然后评价被评估方案以相同路径或不同路径达到了多少等价解决深度。

不得从参考方案倒推出一组唯一必选项，再机械检查被评估方案是否命中这些项。也不得因为被评估方案使用了相似术语就机械给分。

## 评分维度

请按以下维度给出 100 分制评分：

- 环境阅读与需求理解：15 分。
- 技术问题识别：15 分。
- 技术手段具体性：20 分。
- 必要技术特征完整性：10 分。
- 问题-手段-效果闭环：15 分。
- 需求约束遵守：10 分。
- 可实施性：10 分。
- 专利化价值：5 分。

## 参考方案和 rubric 的使用方式

- 参考方案用于说明本题存在一条怎样的高质量深入路径，以及该路径为什么能够解决当前需求。
- rubric 的具体模块、接口、字段、测试项和上限规则，用于校准这条参考路径上的解决深度和分数档位。
- 当 rubric 提到具体实现路径时，应先理解其代表的解决深度，再评价被评估方案是否通过相同路径或其他路径达到等价深度。
- 如果被评估方案没有使用参考方案中的具体模块名、接口名、字段名或测试名，但基于当前代码提出了等价机制，并且解决深度相当，不应仅因路径不同扣分。
- 如果被评估方案既没有命中参考路径，也没有提出等价机制，应按关键机制缺失扣分。
- 如果被评估方案只使用了抽象词或相似术语，但缺少可追问的对象、流程、状态、失败处理、能力边界、验证路径或代码接入依据，应按表面方案扣分。

## 必须执行的评分流程

1. 阅读测试项需求，明确用户真正要解决的问题和明确约束。
2. 按需阅读当前项目源码、文档和测试，确认已有能力、真实接口、数据结构、状态流和不能编造的项目边界。
3. 阅读参考方案和 rubric，理解参考方案为什么是高质量方案，以及 rubric 如何把不同解决深度映射到分数档位。
4. 阅读 evaluated_artifact，只评价其中写入 disclosure 技术方案章节的内容。
5. 判断 evaluated_artifact 实际解决到了什么深度：
   - 是否理解当前项目环境和需求约束。
   - 是否给出可实施的对象、数据、接口、状态或流程。
   - 是否说明失败、异常、权限、并发、回退或不可用能力等边界。
   - 是否说明验证方式或可复现检查路径。
   - 是否能解释技术手段如何导致技术效果。
   - 是否存在无当前项目依据的源码事实、字段、接口、事件或能力声明。
6. 将该解决深度与参考方案/rubric 的深度-分数标尺对齐，给出总分和各维度分数。

## 等价深度判定

被评估方案可以不同于参考路径，但等价深度必须经得起追问。判断等价深度时至少检查：

- 输入是什么，输出是什么。
- 核心对象或数据结构是什么。
- 谁触发流程，谁写入状态，谁消费结果。
- 状态如何变化，终态如何保护。
- 失败、不可用、格式未知、权限不足、超时、重试、并发或迟到结果如何处理。
- 哪些能力可以展示，哪些能力必须禁用、降级、检测后开放或返回诊断性失败。
- 如何通过 fixture、stub、契约测试、集成测试、E2E 或等价方式验证，而不是依赖开发者本机偶然状态。
- 技术效果是否能对应到具体机制，而不是停留在“提升效率”“增强体验”等空泛表述。

如果这些问题无法从 evaluated_artifact 中得到足够答案，即使方向与参考方案相似，也不能视为达到等价深度。

## 扣分原则

- 对没有具体机制的泛泛表述扣分，例如“使用 AI”“增加缓存”“提升效率”“智能分析”。
- 对违反需求约束的方案扣分。
- 对编造当前项目环境中不存在的源码事实、具体文件、类名、字段、接口、事件、PR 实现或能力扣分，并列入 unsupported_claims。
- 对绕开现有系统、重建平行能力、破坏既有流程或依赖人工补录的方案扣分。
- 对只覆盖正常路径、不处理失败和能力边界的方案扣分。
- 对缺少验证路径、无法证明机制可复现的方案扣分。
- 评价应具体、简洁，避免空泛评语。

## 分数校准规则

- 评分应优先衡量方案在当前项目中形成了多深的可实施技术机制，而不是是否复述参考答案关键词。
- 先根据 rubric 的档位锚点和上限规则判断答案属于强答案、可用但不完整、弱答案或不合格答案，再在该档位内按维度细分给分；不要只把各维度分数机械相加。
- rubric 的上限规则描述的是参考路径上关键深度缺口的典型表现。触发上限前，必须先判断被评估方案是否通过其他路径达到了等价深度。若存在等价深度，应在 score_rationale 中说明为什么该上限不适用；若不存在等价机制，应按缺失处理。
- 如果方案只有问题描述、收益描述或接口命名，缺少数据结构、状态流转、接入点和失败处理，技术手段具体性不得高于 12 分，总分通常不得高于 70 分。
- 如果方案缺失 rubric 所代表的两个或更多关键深度点，且没有等价机制，即使总体方向正确，总分通常不得高于 80 分；缺失三个或更多时，总分通常不得高于 75 分。
- 如果方案的核心机制依赖当前源码中不存在的类、字段、接口、事件或能力，总分通常不得高于 75 分；若无依据事实只是边缘表述，应在对应维度扣分并列入 unsupported_claims。
- 如果方案没有基于当前源码说明接入位置，只给出通用产品设计或概念架构，环境阅读与需求理解不得高于 10 分，可实施性不得高于 6 分。
- 如果方案绕开现有系统重建一套平行能力，或破坏 runner/request 中的明确约束，需求约束遵守不得高于 5 分，总分通常不得高于 70 分。
- 90 分以上只给强答案：必须同时满足源码事实准确、解决深度完整、机制能解释问题和效果、能落到现有代码边界，并且没有会阻断实现的关键缺口。实现路径可以不同于参考方案，但必须达到等价深度。
- 75-85 分通常表示方向正确但缺关键工程边界；如果 weaknesses 中存在两个以上关键深度缺口且没有等价机制，除非 rubric 另有说明，不应继续给 85 分以上。
- 70 分以下用于明显弱答案：泛泛方案、绕开现有架构、关键源码事实错误、或缺少主要状态/数据/接入机制。
- 关键缺陷必须反映到分数，而不是只写入 weaknesses。

## 返回内容

必须输出符合 JSON schema 的 JSON，不要输出 Markdown。返回内容包括：

- 总分。
- 各维度得分。
- 主要优点。
- 主要问题。
- 缺失的关键机制。
- 无依据的源码事实或能力声明。
- 简洁说明该分数如何对应本题的深度-分数标尺，以及是否存在与参考路径不同但可等价给分的机制。
