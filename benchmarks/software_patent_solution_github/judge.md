# 评分任务说明

你负责评估一份软件专利技术方案草稿。

输入材料：

- 评测运行任务说明。
- 测试项需求。
- agent 可访问的项目环境。
- 隐藏参考方案。
- 测试项级评分标准。
- agent 输出。

请按以下维度给出 100 分制评分：

- 环境阅读与需求理解：15 分。
- 技术问题识别：15 分。
- 技术手段具体性：20 分。
- 必要技术特征完整性：10 分。
- 问题-手段-效果闭环：15 分。
- 需求约束遵守：10 分。
- 可实施性：10 分。
- 专利化价值：5 分。

评分规则：

- 不要求 agent 输出与参考方案完全一致。
- 如果方案基于需求和项目环境且技术上合理，应允许不同于参考方案的实现路径。
- 对没有具体机制的泛泛表述扣分，例如“使用 AI”“增加缓存”“提升效率”“智能分析”。
- 对违反需求约束的方案扣分。
- 对编造当前项目环境中不存在的源码事实、具体文件、类名或 PR 实现扣分。
- 评价应具体、简洁，避免空泛评语。

分数校准规则：

- 评分应优先衡量方案是否形成可实施的技术机制，而不是是否复述参考答案关键词。
- 先根据 rubric 的“档位锚点”判断答案属于强答案、可用但不完整、弱答案或不合格答案，再在该档位内按维度细分给分；不要只把各维度分数机械相加。
- 如果方案只有问题描述、收益描述或接口命名，缺少数据结构、状态流转、接入点和失败处理，技术手段具体性不得高于 12 分，总分通常不得高于 70 分。
- 如果方案缺失测试项 rubric 中列出的两个或更多关键机制，即使总体方向正确，总分通常不得高于 80 分；缺失三个或更多关键机制时，总分通常不得高于 75 分。
- 如果方案的核心机制依赖当前源码中不存在的类、字段、接口、事件或能力，总分通常不得高于 75 分；若无依据事实只是边缘表述，应在对应维度扣分并列入 unsupported_claims。
- 如果方案没有基于当前源码说明接入位置，只给出通用产品设计或概念架构，环境阅读与需求理解不得高于 10 分，可实施性不得高于 6 分。
- 如果方案绕开现有系统重建一套平行能力，或破坏 runner/request 中的明确约束，需求约束遵守不得高于 5 分，总分通常不得高于 70 分。
- 90 分以上只给强答案：必须同时满足源码事实准确、关键机制完整、能解释机制如何解决问题、能落到现有代码边界，并且没有会阻断实现的关键缺口。
- 75-85 分通常表示方向正确但缺关键工程边界；如果 weaknesses 中存在两个以上关键机制缺失，除非 rubric 另有说明，不应继续给 85 分以上。
- 70 分以下用于明显弱答案：泛泛方案、绕开现有架构、关键源码事实错误、或缺少主要状态/数据/接入机制。
- 关键缺陷必须反映到分数，而不是只写入 weaknesses。

返回内容：

- 总分。
- 各维度得分。
- 主要优点。
- 主要问题。
- 缺失的关键机制或无依据假设。
