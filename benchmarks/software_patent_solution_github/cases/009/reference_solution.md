# 参考技术方案

## 方案概述

该方案面向 agent workspace 读取多模态文件的场景，提出一种基于文件操作抽象、媒体类型识别和模型输出转换的 workspace read 工具增强机制。系统在读取文件前先获取文件状态与字节内容，根据元数据和内容特征判断文件类型；对文本文件执行行号化分页读取，对图片和 PDF 生成可被多模态模型消费的内容块，对不支持的二进制文件返回结构化描述；同时通过大小限制和后端抽象兼容不同 workspace 实现。

## 核心组件

1. WorkspaceLike 后端抽象

系统定义最小文件操作接口，包含读取文本、读取字节、获取文件状态、写入、列目录、搜索和删除等能力。read 工具依赖该抽象而非具体 workspace 类，从而支持 Durable Object workspace、共享 workspace 代理和自定义文件后端。

2. 文件状态与字节读取层

read 工具接收路径后，先调用 stat 获取文件类型、名称、大小、可能的 MIME 信息。若目标不存在或是目录，则返回错误。对于需要进一步判断的文件，再读取字节内容供类型探测和模型内容生成使用。

3. 媒体类型识别器

系统优先使用文件状态中的 MIME 信息；当 MIME 信息缺失或过于泛化时，读取文件头字节进行嗅探。识别规则包括 PNG、JPEG、GIF、WebP、PDF、SVG 等常见格式；若未命中特征，则通过文本解码质量和空字节判断是否为文本，否则归为普通二进制。

4. 文本读取处理器

对于文本文件，系统按用户提供的 offset 和 limit 读取指定行区间，给每行附加行号，并对超长行和超多行进行截断，返回总行数、起止行号和内容。该路径保证传统代码文件、日志、配置文件仍以低 token 成本进入模型。

5. 多模态输出转换器

对于图片和 PDF，read 工具的普通执行结果先返回文件元信息；随后通过模型输出转换流程读取文件字节，检查大小限制，编码为模型可接受的数据块，并附加文本说明。图片输出为 image-data 内容，PDF 或其他支持文件输出为 file-data 内容。

6. 限制与降级策略

系统设置可进入模型上下文的最大文件字节数。超过限制时返回错误文本，说明文件路径、媒体类型、实际大小和限制大小。对于不支持的二进制文件，返回结构化 JSON，包括路径、文件名、媒体类型、大小和 unsupported 标记。

## 执行流程

1. 模型调用 workspace read 工具并传入文件路径及可选行范围。
2. 系统调用文件状态接口确认文件存在且不是目录。
3. 系统根据 MIME 元数据和文件字节探测媒体类型。
4. 若为文本类型，执行行号化分页读取并返回文本内容。
5. 若为图片类型，返回图片元信息，并在模型输出转换阶段读取字节生成图片内容块。
6. 若为 PDF 或可作为文件传递的类型，返回文件元信息，并在模型输出转换阶段生成文件内容块。
7. 若为不支持的二进制类型，返回结构化文件描述，不把原始字节传入模型。
8. 若文件过大或字节读取失败，返回可解释错误。

## 技术效果

该方案使 agent 可以在统一 workspace read 工具下处理文本、图片、PDF 和二进制文件，避免把所有文件都当作文本或不可读对象。模型在可行时获得真实多模态内容，在不可行时获得结构化文件信息和失败原因，从而提升代码仓库、文档工作区和文件型任务中的理解能力。

## 目标能力边界

必须解决的是 workspace read 工具从纯文本读取升级为“按文件类型选择模型输出形态”。方案不要求所有二进制都可被模型理解，也不要求实现 OCR 或 PDF 解析；对于模型可消费的图片/PDF，应传递文件内容块；对于不支持或过大的文件，应返回结构化说明和限制原因。

该能力应保持原有文本读取体验，包括行号、offset/limit、长行截断和大文本控制。不能为了支持多模态而破坏代码文件读取。

## 核心数据结构与输出模型

read tool 普通结果可分为：

- text：`path`、`content`、`totalLines`、`fromLine/toLine`。
- image：`kind=image`、`path`、`name`、`mediaType`、`sizeBytes`。
- file：`kind=file`、`path`、`name`、`mediaType`、`sizeBytes`。
- binary：`kind=binary`、`unsupported=true`、`path`、`name`、`mediaType`、`sizeBytes`。
- error：错误文本或结构化错误。

模型输出转换层应将普通结果进一步转换：

- text -> model text。
- image -> text note + image-data。
- PDF/file -> text note + file-data。
- binary -> JSON/结构化描述。
- 超限或字节读取失败 -> error-text。

媒体类型判断应优先使用 stat MIME；如果是缺失或泛化类型，再读取头部字节识别 PNG/JPEG/GIF/WebP/PDF/SVG，最后用 UTF-8 replacement ratio 和空字节判断是否文本。

## 限制与异常细节

- 最大模型文件字节数应独立于普通文件大小，用于阻止大型图片/PDF base64 填爆上下文。
- 目录路径、文件不存在、字节读取失败、未知二进制都要返回可解释结果。
- 对文本文件，offset 从 1 开始，limit 控制读取行数；超长行和超多行应截断并说明。
- 对 SVG 等文本/图片交界格式，应通过内容嗅探给出稳定判断。
- 自定义 workspace 后端必须提供 readFile/readFileBytes/stat 等最小接口，否则无法支持多模态路径。

## 项目集成点

方案应落在 Think workspace tools、WorkspaceLike 或等价后端抽象、shell workspace 文件状态、AI SDK tool 的 `toModelOutput` 或等价转换层，以及 README/docs。只在 UI 上显示文件类型不是完整方案，关键是让模型实际获得可消费内容。

## 必须命中的评分锚点

- 区分文本、图片、PDF/文件、普通二进制和错误。
- 使用元数据 + 字节嗅探，而不是只靠扩展名。
- 文本读取保留分页、行号和截断。
- 图片/PDF 通过模型内容块传递，不只是返回路径。
- 有最大字节限制和超限错误。
- 通过后端抽象兼容不同 workspace。

## 常见错误方案

- 只返回文件路径，让模型自己“读取”图片/PDF。
- 把所有非文本都 base64 塞进文本输出。
- 只按扩展名判断媒体类型。
- 多模态支持破坏文本文件的行号分页读取。
- 没有大小限制，导致上下文膨胀或请求失败。

`readFileBytes` 是当前源码中已有的字节读取能力名，不限定接口命名。若方案通过等价的 byte read/inspect 接口获得字节、MIME、大小和 stat 信息，并能完成模型内容块转换和结构化降级，应视为等价有效机制。
