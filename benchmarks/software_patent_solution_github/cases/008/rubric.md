# 评分 Rubric

总分 100 分。

## 评分关系说明

- 本 rubric 的具体模块、接口、字段、测试项和档位锚点来自参考方案路径，用于校准本 case 的解决深度和分数，不代表唯一答案。
- 评分时应结合需求、当前项目代码、参考方案和本 rubric 判断被评估方案达到的等价解决深度；若方案采用不同路径但解决深度相当，应按等价机制给分。
- 路径不同不应机械扣分；但只有术语相似、缺少对象/流程/状态/失败处理/能力边界/验证路径或代码依据的方案，应按表面方案扣分。

## 1. 环境阅读与场景理解（15 分）

- 结合当前项目环境识别需求不是普通工具调用，而是 LLM 生成代码编排浏览器侧动态工具：5 分
- 结合现有 client tool 和 agent chat 上下文，识别浏览器工具不适合全部搬到服务端：3 分
- 结合前端执行边界，识别生成代码不能直接运行在主页面环境：4 分
- 能说明该能力与 codemode / agent chat / client tool 的关系：3 分

## 2. 隔离执行机制（20 分）

- 设计浏览器侧隔离容器，例如 iframe、Web Worker 或等价沙箱：5 分
- 说明执行代码如何被注入、启动和终止：4 分
- 说明主页面对象隔离和资源加载限制：4 分
- 设计执行超时与资源清理：4 分
- 说明每次执行独立、避免状态泄漏：3 分

## 3. 工具调度协议（20 分）

- 设计隔离环境到主页面的工具调用消息：5 分
- 设计主页面到隔离环境的工具结果消息：4 分
- 使用调用 id 或等价机制关联请求和响应：4 分
- 说明工具提供者、工具名、参数的校验：4 分
- 能处理多个工具和动态工具集合：3 分

## 4. 工具描述与名称映射（10 分）

- 根据当前工具生成 LLM 可用的代码编排工具描述：3 分
- 处理输入输出 schema 或结构描述：3 分
- 处理非法工具名、冲突名和保留名：2 分
- 维护规范化名称与真实工具之间的映射：2 分

## 5. 安全与异常处理（15 分）

- 说明消息来源校验：3 分
- 说明非法工具调用返回错误而非执行：3 分
- 说明生成代码异常、工具异常、加载失败的回传方式：4 分
- 说明日志收集与错误隔离：2 分
- 说明默认安全边界及可配置安全策略：3 分

## 6. 工程可落地性（10 分）

- 与现有 codemode 执行器接口兼容：3 分
- 与浏览器 client tool / agent chat 工具调用流程兼容：3 分
- 避免引入过重依赖：2 分
- 接口和数据结构具备可实现性：2 分

## 7. 专利技术方案表达质量（10 分）

- 技术问题、技术手段、技术效果闭环清晰：4 分
- 方案具有浏览器隔离执行与工具协议结合的机制创新：3 分
- 表达为技术方案而非产品说明或使用教程：3 分

## 扣分项

- 建议直接在主页面 eval 生成代码且无隔离措施：最多扣 25 分
- 只描述“调用浏览器工具”，没有消息协议或调度流程：最多扣 18 分
- 未考虑超时和资源清理：最多扣 10 分
- 未考虑非法工具名、工具不存在或工具异常：最多扣 10 分
- 把方案写成纯 UI 交互，无底层执行机制：最多扣 15 分

## 源码级评分补充

- 高分方案必须说明 provider/namespace 随工具调用消息传递或等价路由机制，避免多个 ToolProvider 或工具名规范化后发生歧义。
- 必须覆盖工具名规范化映射、重复名/保留名拒绝、input/output schema 的描述传递或外层校验接入、iframe ready/load/error/timeout/cleanup、postMessage 来源窗口校验（可叠加 origin 校验）和限制性 CSP 或等价资源控制。
- 只写“iframe sandbox + postMessage 调工具”但没有生命周期、错误状态、schema 和命名空间边界的方案应显著扣分。

## 档位锚点

- 90-100 分强答案：必须同时具备隔离执行容器、代码注入/启动/终止、主页面代理真实工具、provider/namespace 路由、规范化名称映射与冲突拒绝、input/output schema 描述、ready/execute/tool-call/tool-result/execution-result/error/logs/cleanup 生命周期、call id 关联、执行结束或超时后的 iframe/listener/timer/pending 资源释放、来源窗口校验（或等价来源校验）、限制性 CSP/资源控制、codemode Executor/createCodeTool/ToolProvider/useAgentChat 源码接入。
- 75-85 分可用但不完整：具备 iframe/worker 隔离和结构化工具调用协议，能处理命名空间、schema、超时和错误，但源码执行器接入、生命周期字段、CSP/资源控制或 pending cleanup 中缺一到两个关键边界。
- 60-74 分弱答案：主要是 iframe + postMessage，缺完整生命周期、schema、命名空间或安全资源控制，可能可演示但难以安全接入现有工具体系。
- 0-59 分不合格：直接在主页面 eval、无隔离、无工具调度协议、无错误/超时/清理，或允许生成代码直接操作主页面私有对象。

## 分数上限规则

以下上限规则描述参考路径上关键深度缺口的典型表现。触发上限前，应先判断方案是否通过其他路径达到等价解决深度；若存在等价机制，上限可不适用，并应在评分理由中说明。若没有等价机制，则按缺失处理。

- 如果方案没有明确对接当前 codemode Executor 抽象、createCodeTool 类型生成、ToolProvider/ResolvedProvider 命名空间和 useAgentChat/onToolCall 工具回传链路，总分通常不得高于 82 分。
- 如果方案只细化工具调用消息，而没有 ready、execute、tool-call、tool-result、execution-result、错误/日志回传、cleanup 等生命周期协议，总分通常不得高于 84 分。
- 如果方案没有限制性 CSP、资源加载白名单或等价外部资源控制机制，总分通常不得高于 82 分。
- 如果方案声称隔离代码不能访问 window/document 等全局对象，但没有可落地执行技术或沙箱限制依据，总分通常不得高于 80 分。
- 如果方案没有处理 pending tool calls 在超时、清理或 iframe 销毁时随执行上下文一起释放，或没有说明调用方如何收到终态错误，总分通常不得高于 84 分。
- 如果同时缺失源码执行器接入、完整生命周期协议、CSP/资源控制、pending 清理中任意两个关键机制，总分不得高于 80 分；缺失三个或更多时，总分不得高于 74 分。
