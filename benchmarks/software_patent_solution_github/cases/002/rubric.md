# 评分标准

总分 100 分。

## 评分关系说明

- 本 rubric 的具体模块、接口、字段、测试项和档位锚点来自参考方案路径，用于校准本 case 的解决深度和分数，不代表唯一答案。
- 评分时应结合需求、当前项目代码、参考方案和本 rubric 判断被评估方案达到的等价解决深度；若方案采用不同路径但解决深度相当，应按等价机制给分。
- 路径不同不应机械扣分；但只有术语相似、缺少对象/流程/状态/失败处理/能力边界/验证路径或代码依据的方案，应按表面方案扣分。

## 环境阅读与需求理解：15 分

- 13-15 分：能结合需求并在当前项目环境中识别 task、agent、session、spawn history、eval、event bus、MCP server 和既有 API 之间的上下文关系。
- 8-12 分：能识别需要记录 agent 执行过程，也能阅读部分项目路径，但缺少对评估附着、外部查询或长期质量分析的关联。
- 0-7 分：未有效阅读当前项目环境，只泛泛描述“增加日志”或“记录任务结果”。

## 技术问题识别：15 分

- 13-15 分：准确指出问题本质是 agent 执行过程缺少统一结构化 run 抽象，导致溯源、评估、成本、查询和工具集成割裂。
- 8-12 分：能指出需要记录执行过程，但没有充分分析运行来源、评估附着或外部工具复用问题。
- 0-7 分：把问题理解为普通日志、审计表或前端展示。

## 技术手段具体性：20 分

- 17-20 分：提出统一运行记录对象（可称 AgentRun 或采用等价命名）、provenance、spawn history 自动桥接、eval 附着、leaderboard 聚合、事件流和工具化访问等具体机制。
- 10-16 分：提出 run 记录模型和查询接口，但缺少自动桥接、评估附着、事件流或工具访问中的多个关键部分。
- 0-9 分：只说“保存日志”“增加统计接口”“用数据库记录”，缺少可实施方案。

## 必要技术特征完整性：10 分

- 8-10 分：覆盖运行对象、关联关系、生命周期更新、溯源、评估、事件、查询和兼容现有系统。
- 4-7 分：覆盖主要数据模型和接口，但缺少评估、事件或兼容路径。
- 0-3 分：只覆盖单点记录或单个展示页面。

## 问题-手段-效果闭环：15 分

- 13-15 分：能说明每个技术手段如何解决执行过程割裂、不可追踪、不可评估、不可工具化复用的问题。
- 8-12 分：能说明一部分效果，但闭环主要停留在“方便查看历史”。
- 0-7 分：缺少因果关系或技术效果空泛。

## 需求约束遵守：10 分

- 8-10 分：复用现有 task、agent、session 和 spawn history，不重写调度系统；能兼容已有 MCP server 和评估接口。
- 4-7 分：大体兼容现有系统，但存在与现有历史记录或工具链割裂的风险。
- 0-3 分：要求推翻现有任务系统、独立维护一套无法关联的日志系统，或依赖人工手动补录。

## 可实施性：10 分

- 8-10 分：给出清晰的数据结构、生命周期流程、API/工具边界、错误处理和聚合方式。
- 4-7 分：总体方向可行，但缺少关键字段、状态更新流程或接口边界。
- 0-3 分：方案过于抽象，无法指导工程实现。

## 专利化价值：5 分

- 4-5 分：能抽象为“agent 执行过程的结构化运行记录、溯源和评估附着机制”。
- 2-3 分：有一定机制抽象，但偏普通日志平台或任务统计。
- 0-1 分：只是业务报表或日志保存说明。

## 明确扣分项

- 只提出保存文本日志，不建立结构化 run 对象。
- 只做前端历史页面，不说明数据来源、生命周期和关联关系。
- 要求用户手动填写执行结果或评估结果，缺少自动桥接。
- 把 run 记录做成与 task、agent、session 完全割裂的独立表。
- 没有说明如何关联成本、状态、错误、输出或评估。
- 没有考虑外部工具或 agent 如何查询、附着或复用运行记录。

## 源码级评分补充

- `AgentRun` 只是参考方案中的命名。使用 `RunRecord`、`ExecutionRun`、`AgentExecution` 或其他名称，只要形成统一运行记录契约并覆盖关联、状态、评估和查询能力，应按等价机制给分。
- 不应要求方案凭空声称当前源码已有统一 run 模型；高分方案应指出现有 spawn history、eval、token/cost、pipeline run、MCP task/cost 工具等信息是分散的，需要桥接。
- 泛泛新增日志表、只记录最终输出、或无法把 run 与 task/session/spawn/eval/cost/provenance 关联的方案应显著扣分。

## 档位锚点

- 90-100 分强答案：必须同时具备统一 run 契约、task/session/agent/spawn/eval/cost 关联、结构化 provenance/lineage、spawn 创建/完成/失败/取消自动桥接、run 级 eval attach/update、事件流、MCP 工具层查询/附着、leaderboard 聚合和源码级 schema/API/event 接入说明。多评估历史、评估版本链或终态保护属于增强项，不是本 case 的硬性前提。
- 75-85 分可用但不完整：有统一 run 对象和主要关联，能复用现有任务/agent/session/spawn 信息，但 provenance、spawn 自动桥接、eval attach、MCP 工具或 leaderboard 中缺一到两个关键机制。
- 60-74 分弱答案：主要是日志表或运行历史页面，只有部分关联或最终输出记录，不能支撑溯源、评估附着和外部工具复用。
- 0-59 分不合格：只保存文本日志、要求人工补录、与 task/session/spawn/eval/cost 割裂，或编造当前源码已有完整 run 模型。

## 分数上限规则

以下上限规则描述参考路径上关键深度缺口的典型表现。触发上限前，应先判断方案是否通过其他路径达到等价解决深度；若存在等价机制，上限可不适用，并应在评分理由中说明。若没有等价机制，则按缺失处理。

- 如果方案没有结构化 provenance/lineage 字段和生成流程，总分通常不得高于 82 分。
- 如果方案没有说明 spawn 创建、完成、失败、取消等路径如何自动桥接 run 生命周期，总分通常不得高于 82 分。
- 如果方案只把 eval 写成单个分数字段，没有 run 级 eval attach/update 契约、pass/fail、说明、指标或 benchmark 元数据，总分通常不得高于 85 分。不强制要求多评估历史或固定 evaluator 字段命名。
- 如果方案没有 MCP 工具层的 run 查询、溯源查询、评估附着或 leaderboard 聚合能力，总分通常不得高于 85 分。
- 如果同时缺失 provenance/lineage、spawn 自动桥接、eval attach、MCP/leaderboard 中任意两个关键机制，总分不得高于 78 分；缺失三个或更多时，总分不得高于 72 分。
- 如果核心论证依赖当前源码中不存在的表字段、事件、API 或调用路径，总分不得高于 75 分。
