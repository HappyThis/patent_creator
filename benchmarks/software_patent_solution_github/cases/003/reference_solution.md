# 隐藏参考方案

## 技术问题

Mission Control 的任务数据主要保存在应用数据库中，适合应用内部查询、看板展示和 agent 调度，但不利于 Git-native agent 工作流、代码仓库协作和外部 agent 工具直接读取。团队希望任务能够跟随代码仓库或外部 agent 协议流转，但又不能把 Mission Control 的主存储替换掉，否则会破坏现有任务看板、权限、调度、评论和状态流转。

如果只做一次性导出，外部系统无法持续追踪任务变化；如果把外部仓库作为主存储，则会引入一致性和故障风险；如果同步失败阻断任务创建或更新，又会影响日常使用。因此需要一种以 Mission Control 为主、外部 Git-native 仓库为可选同步目标的任务持久化机制。

## 核心技术构思

在 Mission Control 中建立“主存储优先 + Git-native 可选镜像 + 状态语义映射 + 非阻塞同步 + 管理入口”的任务同步机制。

系统继续以 Mission Control 数据库作为任务主存储，在任务创建、更新和删除等生命周期节点上，将任务转换为外部 agent 协作格式并写入一个 Git-native 仓库。该仓库保存任务 JSON 文件，并通过 Git 提交记录任务变化。系统在同步过程中执行状态、优先级、标签、负责人和项目关联等字段映射，使外部格式能够理解 Mission Control 的任务语义。同步过程作为可选能力执行，失败时记录告警但不阻断主任务流程；同时提供初始化、状态查询和手动同步入口，便于用户控制外部镜像状态。

## 必要技术特征

1. 主存储保持：Mission Control 数据库仍作为任务事实来源，外部仓库仅作为可选同步目标。
2. 外部格式转换：将任务 id、标题、描述、状态、优先级、负责人、标签、创建/更新时间和项目关联转换为外部 agent 协作格式。
3. 语义映射：建立 Mission Control 状态与外部协议状态、Mission Control 优先级与外部优先级之间的映射关系。
4. 生命周期挂接：在任务创建、更新和删除路径中触发外部同步，保持外部镜像随任务生命周期变化。
5. Git-native 持久化：按任务维度写入外部仓库中的结构化文件，并通过 Git add/commit/push 记录变更历史。
6. 非阻塞失败处理：同步失败只写入日志或告警，不影响主数据库事务和任务 API 响应。
7. 可配置启用：通过配置项控制是否启用同步、同步仓库位置、是否自动同步以及远端设置。
8. 管理 API：提供外部仓库初始化、同步状态查询和手动同步入口。
9. UI 状态提示：在任务看板中展示外部同步状态和手动同步入口，避免用户不知道外部镜像是否可用。

## 关键流程

### 初始化流程

1. 用户启用外部 agent 协作同步能力并配置仓库路径。
2. 系统检查目标目录是否已初始化。
3. 若未初始化，则创建协议所需目录、版本文件、agent 描述文件和任务目录。
4. 系统初始化 Git 仓库并提交初始结构。
5. 管理 API 返回仓库初始化状态、任务数量和远端信息。

### 任务创建/更新同步流程

1. 用户或 agent 在 Mission Control 中创建或更新任务。
2. 主任务 API 按原有逻辑写入数据库。
3. 若同步能力开启，则系统把任务对象转换为外部格式。
4. 系统将转换后的任务写入外部仓库的任务文件。
5. 系统提交 Git 变更；若存在远端，则尝试推送。
6. 若外部同步失败，系统记录告警，但任务创建或更新仍然成功。

### 任务删除同步流程

1. 用户或 agent 删除 Mission Control 任务。
2. 主任务 API 按原有逻辑删除数据库记录。
3. 若同步能力开启，则系统删除外部仓库中对应任务文件。
4. 系统提交删除变更并尝试推送远端。
5. 删除同步失败不影响主任务删除结果。

### 手动同步流程

1. 用户在看板或管理接口触发同步。
2. 系统读取外部仓库状态并在有远端时尝试拉取。
3. 系统检查任务文件数量、未提交变更和远端信息。
4. 系统提交并推送需要同步的变更。
5. 系统向 UI 返回同步时间、任务数量和错误信息。

## 技术效果

- Mission Control 任务可以被 Git-native agent 工作流和外部工具读取，提升跨工具协作能力。
- 数据库主存储不被替换，现有任务看板、权限和调度流程保持稳定。
- 状态和优先级映射减少不同系统之间的语义偏差。
- Git 提交记录为任务变化提供可追踪历史，便于审计、回滚和团队协作。
- 非阻塞同步避免外部仓库故障影响日常任务操作。
- 管理 API 和 UI 状态提示让用户能够观察和控制同步目标。

## 目标能力边界

必须解决的是“Mission Control 任务到 Git-native agent 协作格式的持续镜像同步”，而不是把外部仓库变成新的主数据库。数据库仍是事实来源；Git 仓库是可选镜像和协作出口。同步失败不应阻塞任务创建、更新或删除。

方案可以不要求双向实时同步，也不必解决所有 Git 冲突自动合并，但必须定义初始化、增量写入、删除、状态查询和手动同步路径。

## 核心数据结构与状态模型

- 同步配置：`enabled`、`repoPath`、`autoSync`、`remoteUrl`、`branch`、`lastSyncAt`、`lastError`。
- 任务映射对象：Mission Control task id 到外部 task 文件路径的稳定映射。
- 外部任务文件：保存 title、description、status、priority、assignee、labels、project、timestamps、source id 等字段。
- 状态映射表：Mission Control 状态到外部协议状态，Mission Control priority 到外部 priority。
- 同步状态：`uninitialized/ready/syncing/error/disabled` 或等价状态，用于 UI 和管理 API。

任务生命周期应采用主事务优先：主数据库写入成功后触发 fire-and-forget 或后台同步。同步失败只记录错误和待同步状态，不回滚主任务。

## 项目集成点

方案应落在任务创建、更新、删除 API，配置读取模块，任务看板 UI 状态提示，以及 Git 同步引擎。高分方案会说明已有 `github-sync-engine` 可作为工程参考，但 Git-native agent protocol 需要独立格式转换和仓库管理，而不是复用 GitHub issue 同步语义。

## 等价机制说明

Git-native 协作镜像不限定必须使用某个具体目录名或文件扩展名。只要方案使用仓库内机器可读文件、稳定任务标识映射、Git 版本化提交和非阻塞同步管理，并且不把 GitHub issue API 同步当成完整答案，应视为等价有效机制。

## 必须命中的评分锚点

- 明确主存储与镜像仓库的事实来源关系。
- 任务字段到外部格式的语义映射完整。
- Git 写入、commit、push 与失败记录流程清楚。
- 同步是非阻塞的，不影响主任务 API。
- 有初始化、状态查询、手动同步入口。
- 删除任务时同步删除或标记外部任务文件。

## 常见错误方案

- 把 Git 仓库设为主存储，导致现有任务看板和 API 语义被破坏。
- 只做一次性 export，没有生命周期挂接。
- 同步失败直接让任务创建失败。
- 不做状态/优先级映射，导致两个系统语义漂移。
- 只保存 Markdown 文本，缺少机器可读 JSON 和稳定 task id。

## 对应真实实现

真实 PR #396 采用了如下实现方向：

- 新增 `src/lib/gnap-sync.ts`，实现 Mission Control 任务到 GNAP JSON 的转换、写入、删除、拉取、状态查询和 Git 操作。
- 新增 `GET/POST /api/gnap`，提供启用状态、初始化和手动同步能力。
- 在任务创建、更新和删除 API 中以 fire-and-forget 方式触发 GNAP 同步。
- 在配置中增加 `GNAP_ENABLED`、`GNAP_REPO_PATH`、`GNAP_AUTO_SYNC`、`GNAP_REMOTE_URL` 等选项。
- 在任务看板中展示 GNAP 状态和手动同步入口。
- 增加覆盖状态映射、优先级映射、仓库初始化、任务推送、任务删除、拉取和状态查询的单元测试。
