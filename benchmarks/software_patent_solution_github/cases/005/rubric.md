# 评分标准

总分 100 分。

## 环境阅读与需求理解：15 分

- 13-15 分：能结合需求并在当前项目环境中识别 Think Session、server-driven messages、chat recovery、cancellation、workflow/webhook、observability 和 durable execution 相关上下文。
- 8-12 分：能识别快速返回和后台执行，也能阅读部分项目路径，但对重复提交、消息应用边界或恢复风险分析不足。
- 0-7 分：未有效阅读当前项目环境，只泛泛描述“加一个异步接口”。

## 技术问题识别：15 分

- 13-15 分：准确指出问题本质是外部调用方需要持久接收边界、幂等重试、后台执行和可恢复状态，而不是简单等待模型完成。
- 8-12 分：能指出需要快速返回和后续查询，但缺少重复提交、消息应用边界或恢复风险分析。
- 0-7 分：把问题理解为普通队列、普通日志或前端 loading 状态。

## 技术手段具体性：20 分

- 17-20 分：提出持久提交记录、幂等身份、状态模型、后台领取执行、会话应用边界、恢复判定、取消/重置、条件终态更新和可观察性等具体机制。
- 10-16 分：提出 submission/queue 概念，但缺少消息应用边界、恢复规则、幂等冲突处理或取消语义。
- 0-9 分：只说“异步处理”“使用队列”“保存请求”，缺少可实施机制。

## 必要技术特征完整性：10 分

- 8-10 分：覆盖提交、查询、列表、取消、删除、重试、执行、恢复、错误和清理。
- 4-7 分：覆盖主要提交流程，但缺少恢复、取消或清理。
- 0-3 分：只覆盖一个提交接口。

## 问题-手段-效果闭环：15 分

- 13-15 分：能说明各技术手段如何解决超时不确定、重复提交、会话重复写入、恢复不安全和外部系统不可观测问题。
- 8-12 分：有基本闭环，但效果主要停留在“后台执行更方便”。
- 0-7 分：缺少因果关系或技术效果空泛。

## 需求约束遵守：10 分

- 8-10 分：复用 Think 现有 Session、streaming、chat recovery、cancellation 和 workflows 边界；不替代 saveMessages 或 workflows。
- 4-7 分：大体兼容现有系统，但存在与普通聊天或 workflow 职责重叠不清的问题。
- 0-3 分：要求重写 Think 执行体系，或把所有 chat turn 都强制改成外部提交。

## 可实施性：10 分

- 8-10 分：给出清晰的数据字段、状态转换、领取执行、恢复规则、取消规则和接口边界。
- 4-7 分：总体可行，但缺少关键状态字段或故障处理。
- 0-3 分：方案过于抽象，无法指导工程实现。

## 专利化价值：5 分

- 4-5 分：能抽象为“面向外部调用方的 agent 对话任务持久接收、幂等执行与恢复控制机制”。
- 2-3 分：有一定机制抽象，但偏普通任务队列。
- 0-1 分：只是异步 API 或数据库记录说明。

## 明确扣分项

- 只用内存队列，不能跨 hibernation 或重启恢复。
- 没有幂等键或重复请求处理。
- 接收提交时就直接把消息写入 Session，缺少安全应用边界。
- 重试可能重复追加用户消息。
- 取消或 reset 后迟到的完成状态可以覆盖终态。
- 把该能力设计成替代 workflows 或替代所有普通 chat turn。
