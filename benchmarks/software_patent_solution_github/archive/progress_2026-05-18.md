### 4. 中间状态不可见问题已处理

低并发小批量运行时发现 `run_all.py` 原先使用 `subprocess.run(..., capture_output=True)` 调用单 case，导致子进程输出被缓存在内存中，只有 case 结束后才一次性打印。长时间 subject 写作或 judge 阶段会表现为终端无输出，难以判断是否卡住。

已改为：

- `run_all.py` 实时转发 `run_case.py` 的 stdout/stderr。
- `run_case.py` 在 `prepare`、`subject`、`subject_round`、`artifact`、`judge`、`result` 阶段打印 `[benchmark]` 状态行。
- 每个 case 写入 `progress.json` 和 `progress.jsonl`，可直接查看当前阶段和完整状态流。
- Codex-as-judge 改为使用 `codex exec --json`，并将 Codex 的 thread、turn、item、usage 事件映射为 `judge_codex` 状态；原始事件保存到 `judge/codex_judge_events.jsonl`。

可用以下方式查看运行状态：

```bash

tail -f benchmarks/software_patent_solution_github/runs/<run_id>/cases/<case_id>/progress.jsonl
tail -f benchmarks/software_patent_solution_github/runs/<run_id>/cases/<case_id>/judge/codex_judge_events.jsonl
```

## 多 worker 日志区分

发现并发运行时虽然已经能实时输出，但多个 worker 的 stdout/stderr 会交错，裸日志不利于判断是哪一个 case 或 repeat 产生的问题。

已调整 `run_all.py`：

- `ThreadPoolExecutor` 使用 `bench-worker` 前缀命名 worker 线程。
- 批量运行实时转发 stdout/stderr 时，每条终端日志都加来源前缀，例如 `worker=bench-worker_0 run=r01-001 case=001 repeat=1/2`。
- stderr 会标为 `stderr`，stdout 会标为 `stdout`。
- 落盘的 `run_case_stdout.txt` 和 `run_case_stderr.txt` 保持原始内容，不混入终端前缀，方便后续机器解析。

README 已同步说明多 worker 日志前缀约定。

## LLM 流式断流重试与 001 复跑

针对 `001` 在 subject 第一轮约 98 秒处出现的 provider streaming `httpx.ReadError`，补充在 agent runtime 层处理 transient stream failure，而不是在 benchmark runner 中按失败类型特殊标记。

实现边界：

- `generate_with_tools_stream()` 对 `httpx/httpcore` 读写、连接、远端协议类异常，以及 OpenAI SDK 的连接/超时异常做当前 LLM step 级重试。
- 仅在尚未向上游发出任何 text delta 时重试，避免 UI/调用方看到重复文本。
- 如果已经输出过文本 delta，则抛出 `ApiError(502, "llm_stream_error", ...)`，由上层按普通失败处理。
- tool call 只会在完整流读取成功后执行，因此 retry 不会重复执行工具。
- benchmark 仍只关心最终 `scored` / `round_failed` / `judge_failed` 等结果，不关心底层失败原因。

验证：

```bash
cd backend && .venv/bin/python -m pytest tests/test_openai_compat.py
cd backend && .venv/bin/python -m pytest
benchmarks/software_patent_solution_github/bench.py run 001 --run-id 20260518-llmretry-001
```

结果：

- `tests/test_openai_compat.py`：`8 passed`
- backend 全量测试：`70 passed`
- `001` 复跑：`status=scored`，`subject_status=completed`，`artifact_extracted=true`，judge 分数 `72`

复跑观察：

- 本次 001 没有再次触发 `transient_error retrying` 日志，因此实盘未命中断流重试路径。
- 运行越过了此前约 98 秒的断点，subject 在约 590 秒完成，随后 Codex judge 完成评分。
- `section_writer` 仍触发 `subagent_plain_response` 已知问题，但主 agent 改用分段 `document_edit` 自恢复并完成 artifact 写入。
- 该结果说明：agent 层重试逻辑已有单元测试覆盖；benchmark 复跑已确认 001 当前能跑通闭环，但本次实盘不能作为“重试命中后成功”的证据。

- 抽取当前已写入的技术方案并写入 `technical_solution_after_round_N.md` 和 `evaluated_artifact.md`。
