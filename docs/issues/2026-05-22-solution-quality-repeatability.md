# 技术方案质量重复运行稳定性不足

> 状态：进行中
> 最后更新：2026-05-22
> 关闭条件：同一 case 多次运行的分数波动下降，低分尾部减少，agent 不再依赖偶发深度探索才能写出高质量技术方案。

## 背景

一次高分不能证明 agent 能力稳定。`20260522-deepseek-v4-pro-reasoning-5x` 每个 case 重复 5 次，暴露出部分 case 的得分波动仍然较大。

## 观测数据

整体：

- 总运行：50
- 平均分：80.2
- 最低分：68
- 最高分：95
- 标准差：6.36

波动较明显的 case：

| Case | 分数 | 标准差 | 观察 |
| --- | --- | ---: | --- |
| 004 | 82, 95, 89, 82, 89 | 4.92 | 偶尔能进入 95，但低分仍缺接口与字段边界。 |
| 006 | 88, 88, 91, 76, 82 | 5.37 | 最低 76，取消/恢复链路有时明显不完整。 |
| 008 | 82, 80, 88, 89, 88 | 3.67 | 浏览器沙箱方案质量逐次差异较大。 |

低分 case：

| Case | 均分 | 主要短板 |
| --- | ---: | --- |
| 005 | 70.6 | submission ledger、reset/clear、终态条件更新不足。 |
| 001 | 72.4 | runtime/API/UI 集成边界不足。 |
| 002 | 75.6 | AgentRun/provenance/MCP 外部访问抽象不足。 |

## 影响

- 评测结果受采样影响较大，单次运行不一定代表真实能力。
- 线上用户可能随机遇到浅层方案，体验不稳定。
- 后续改进难以判断是能力提升还是随机波动。

## 处理方向

- 对每个 case 保持多次重复评估，不只看单次得分。
- 分析低分 run 与高分 run 的差异：源码阅读深度、是否调用子 agent、写入时机、是否覆盖关键 rubric 机制。
- 将“必须覆盖的工程边界清单”前置到主 agent 策略中，减少随机探索带来的质量差异。

## 验证方式

- 使用同一模型对正式 case 每个重复 5 次。
- 观察平均分、最低分、标准差同时变化。
- 目标优先级：先提高最低分，再提高平均分。
